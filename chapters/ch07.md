# Memory Management

Every object needs bytes, and every byte has to come from somewhere: the stack frame of the current function, a region reserved when the program was loaded, or a general-purpose allocator that asks the operating system for pages. Where the bytes come from decides three things a low-latency engineer cares about: how long it takes to get them, whether getting them can occasionally take a thousand times longer than usual, and where they end up relative to the other data you are touching (which decides cache behaviour).

The rule most trading systems follow is short: **acquire memory at startup, touch it before trading begins, and never allocate on the hot path.** This chapter explains why, from the stack pointer up through glibc's `malloc`, the C++ `new` machinery and the kernel's page-fault handler, and then shows the tools that make the rule practical: arenas, pools, `std::pmr`, and a way to prove in tests that the hot path does not allocate. Object layout and padding are in Section 6.1; this chapter is about where objects live and how they get there. The operating-system side of virtual memory is in Sections 13.2 and 13.3.

## Stack vs Heap

### The intuition

Think of the **stack** as a stack of plates in a canteen. Each function call puts a plate (its *frame*) on top; the plate holds that call's local variables. When the function returns, its plate is removed. You can only add or remove at the top, so "allocating" is just moving the top, and nothing ever needs searching.

The **heap** is a warehouse with shelves of many sizes. You ask for space of a given size and get a shelf address; you return it whenever you like, in any order. Someone has to keep track of which shelves are free, find one of the right size, and tidy up fragmented space. That bookkeeping is the allocator, and its cost is not constant.

### What the stack really is

On x86-64, the stack is an ordinary region of memory and the register `rsp` points to its current top. The stack grows *downwards*, toward lower addresses. A function's prologue reserves its whole frame with one instruction, typically `sub rsp, N`, where *N* is computed by the compiler from all the locals it needs (rounded so that `rsp` stays 16-byte aligned at calls, as the System V ABI requires). The epilogue gives the frame back with `add rsp, N` or `leave`. So the cost of a local array, however large, is zero extra instructions: it is folded into an adjustment that happens anyway. Leaf functions often do not even move `rsp`: the System V ABI guarantees a 128-byte *red zone* below `rsp` that signal handlers will not overwrite, and a leaf may keep its locals there.

The stack is also almost always hot in the L1 cache, because the same few kilobytes are reused by every call. That is a second, often larger, advantage over heap memory.

The limits are just as concrete:

- **Size is fixed and small.** The main thread's stack may grow up to the `RLIMIT_STACK` soft limit, commonly 8 MiB on Linux. New threads created by glibc get, by default, a stack of the same size (when that limit is finite), allocated with `mmap` when the thread is created; `pthread_attr_setstacksize` (or a thread library that exposes it) changes it. Below each stack is a guard region; running into it is a segmentation fault, not an exception you can catch.
- **Lifetime is the scope.** A local cannot outlive its function. Returning a pointer or reference to one is a dangling-pointer bug (Section 11.4).
- **Stack pages are demand-faulted too.** The 8 MiB is *reserved* address space; physical pages are supplied by page faults the first time each 4 KiB page is touched (Section 7.4). A thread that suddenly uses 200 KiB more stack than ever before takes about 50 page faults.
- **Variable-length arrays and `alloca`** put a runtime-sized block on the stack. VLAs are not standard C++ (GCC accepts them as an extension), and neither offers any protection against overflowing the stack. Use a fixed-capacity buffer with an explicit size check instead.

### Choosing between them

| Use | When | Watch out for |
|---|---|---|
| Stack (automatic storage) | Size known at compile time and modest (up to a few KiB), lifetime ends with the scope | Deep recursion; large arrays in threads with small stacks |
| Static storage | One instance for the whole program, size known at compile time | Initialization order across translation units (Section 5.3); shared mutable state between threads |
| Heap, at startup | Size known only at run time, or large, or must outlive the creating scope | Nothing on the hot path, provided the memory is pre-faulted (Section 7.4) |
| Heap, on the hot path | Avoid | Variable latency, lock contention, page faults, fragmentation (the rest of this chapter) |

## How glibc malloc Works

On Linux, `operator new` in libstdc++ calls `malloc`, and `malloc` is usually glibc's implementation (called *ptmalloc2*, derived from Doug Lea's dlmalloc). Interviewers at low-latency firms often ask "what happens when you call `malloc(32)`?" The answer below describes glibc 2.39, the version in the build environment. The broad structure has been stable for many years, but details (especially tcache limits) change between releases, so treat specific numbers as version-dependent and check `man mallopt` and the glibc manual's tunables section for the version you run.

### Chunks and size classes

glibc manages memory in **chunks**. On 64-bit systems, each chunk begins with an 8-byte size field (and, logically, an 8-byte "previous size" field that belongs to the preceding chunk's space when that chunk is in use). The pointer `malloc` returns points just past the header, so the header sits immediately below your data. Chunk sizes are multiples of 16 bytes and at least 32 bytes, which keeps every user pointer 16-byte aligned. A request for *n* bytes therefore needs a chunk of

chunk(n) = max(32, round up (n + 8) to a multiple of 16),

and the *usable* size is chunk(n) − 8 (the 8 bytes of the next chunk's "previous size" field are usable while this chunk is allocated). So `malloc(1)` and `malloc(24)` both get 24 usable bytes in a 32-byte chunk, `malloc(25)` gets a 48-byte chunk, and a 64-byte object costs an 80-byte chunk. The low three bits of the size field are flags, because sizes are multiples of 16: *previous chunk in use*, *chunk was obtained with mmap*, and *chunk belongs to a non-main arena*.

Two consequences matter for latency work. First, small objects carry 8–15 bytes of overhead and are not cache-line aligned: an 80-byte chunk holding a 64-byte object starts 16 bytes into some 64-byte line, so the object spans two cache lines (Section 12.2) unless you ask for 64-byte alignment. Second, writing even one byte past the end of a heap block corrupts the next chunk's header, which is why heap overflows crash later, somewhere else, in `free`.

### The free lists, in the order malloc checks them

Freed chunks are kept on lists (*bins*) so they can be reused. On a `malloc`, glibc looks in roughly this order:

1. **tcache** (per-thread cache, since glibc 2.26). Each thread has 64 singly linked lists, one per chunk size from 32 to 1040 bytes in 16-byte steps (usable sizes up to 1032 bytes). Each list holds at most 7 chunks by default (tunable `glibc.malloc.tcache_count`). A tcache hit pops the head of a list belonging to the calling thread: no lock, no atomic instruction, a handful of loads and stores. This is why a `malloc`/`free` pair of the same small size in a tight loop is fast.
2. **fastbins**, per arena: singly linked LIFO lists for small chunks (requests up to 128 bytes by default on 64-bit, setting `M_MXFAST`). Chunks in fastbins are not merged with their neighbours, which keeps them cheap but fragments memory.
3. **smallbins** (62 lists, one per exact chunk size below 1024 bytes) and **largebins** (63 lists covering size ranges, kept sorted), per arena, doubly linked.
4. The **unsorted bin**: recently freed chunks are first placed here. A `malloc` that misses the faster paths walks the unsorted bin, returning an exact fit if it finds one and sorting the others into their small or large bins. A large request may also trigger *consolidation* of fastbin chunks into larger free chunks. This walk is where an ordinary `malloc` call occasionally does much more work than usual.
5. The **top chunk**: the free space at the end of the arena. A request that nothing else satisfies is carved from it.
6. **The operating system.** If the top chunk is too small, glibc grows the arena (Section 7.2.3) or, for a large request, maps a dedicated region.

`free` runs the path in reverse: put the chunk in the thread's tcache if that list has fewer than 7 entries; otherwise take the arena's lock and place it in a fastbin, or merge it with free neighbours and put it in the unsorted bin. If the merged free space at the top of the main arena exceeds the *trim threshold* (`M_TRIM_THRESHOLD`, 128 KiB by default), glibc returns it to the kernel by shrinking the heap, which means a later allocation will need fresh pages and fresh page faults.

### Where memory comes from: brk, mmap and the thresholds

The main arena lives in the `[heap]` region and grows by moving the *program break* with `brk`/`sbrk`. Requests at or above the **mmap threshold** (`M_MMAP_THRESHOLD`, 128 KiB by default) bypass the bins: glibc calls `mmap` for that one chunk and `munmap` when it is freed. Each of those is a system call, and the pages of a new mapping are not yet backed by physical memory, so the first touch of each page faults.

The threshold is **dynamic** unless you set it. When an mmapped chunk is freed, glibc raises the threshold to that chunk's size (up to 32 MiB on 64-bit) and raises the trim threshold to twice that, on the theory that a program which frees large blocks will allocate them again. Listing 7.2, step 3, shows this: the first 200 KiB request is mmapped, and after it is freed the identical request is served from `[heap]` instead. Setting `M_MMAP_THRESHOLD` or `M_TRIM_THRESHOLD` with `mallopt` (or the corresponding `GLIBC_TUNABLES` environment settings) disables the adjustment.

### Arenas and threads

One lock around one heap would serialize every allocating thread. glibc therefore keeps several **arenas**, each with its own bins and its own mutex. The main arena uses `[heap]`; additional arenas live in mmapped *heaps* (each reserved as a 64 MiB region on 64-bit systems and committed gradually). A thread is attached to an arena the first time it allocates: glibc reuses an arena left behind by a thread that has exited, or creates a new one, up to a limit of 8 arenas per CPU core on 64-bit systems by default (`M_ARENA_MAX` changes it); past the limit, threads share existing arenas. Listing 7.2, step 4, shows a second thread's allocation landing in an anonymous mapping, not in `[heap]`.

Several latency-relevant facts follow:

- **tcache hits never take a lock.** Anything that misses the tcache does: the arena mutex is an atomic read-modify-write even when uncontended (Section 14.1), and a real wait if another thread is using the same arena.
- **Cross-thread frees.** In a producer–consumer design, the producer allocates messages and the consumer frees them. `free` first tries the *consumer's* tcache, so the first few chunks land there, where only the consumer will reuse them. Once that list is full, each further `free` locks the *producer's* arena to return the chunk, contending with the producer's own allocations, and the producer's tcache is never refilled by the consumer's frees. The cache lines holding each chunk header also move between cores (Section 12.3).
- **Memory growth.** Free memory in one arena cannot satisfy requests from a thread attached to another, so many-threaded programs can use far more memory than they hold live. Reducing `M_ARENA_MAX` trades this against more lock contention.

These are the reasons latency-critical threads either avoid the general allocator entirely or pass ownership through pre-allocated rings of fixed slots (Section 14.5) instead of passing heap pointers.

### Other allocators

jemalloc, tcmalloc and mimalloc are common replacements, linked in or loaded with `LD_PRELOAD`. They differ in detail but share ideas that glibc only partly has: per-thread (or per-CPU) caches for most size classes, size-segregated slabs (all objects in a page have the same size, so no per-object header is needed), and more aggressive handling of cross-thread frees. Switching allocators can reduce average cost and fragmentation; it does not make allocation deterministic, and it does not remove page faults or system calls. For the hot path the rule is unchanged: do not allocate there. Which allocator is best for a whole process is an empirical question, answered by measuring your workload (Section 16.4), not by reputation.

## new, delete, Placement New and Aligned New

### The new-expression and operator new

`new T(args)` is an expression that does two separate things:

1. Calls an **allocation function**, `operator new(sizeof(T))`, to obtain raw bytes. The default version loops: call `malloc`; if it returns null, call the installed *new-handler* (`std::set_new_handler`) and retry; if there is no handler, throw `std::bad_alloc`.
2. **Constructs** a `T` in those bytes. If the constructor throws, the expression calls the matching `operator delete` to free the bytes before the exception propagates, so a throwing constructor does not leak.

`delete p` runs the destructor, then calls `operator delete`. The allocation functions are *replaceable*: defining `operator new(std::size_t)` in your program replaces the library's version everywhere, including inside the standard library. Listings 7.3, 7.7 and 7.8 use that to watch and count allocations. A class can also define its own `operator new`/`operator delete` members, which apply only to that class (and its derived classes) and are a simple way to route one type to a pool.

`new (std::nothrow) T` returns a null pointer instead of throwing. On Linux this is less useful than it looks: by default the kernel overcommits memory, so allocation rarely fails even when memory is short; the failure appears later as the out-of-memory killer terminating the process when pages are touched.

### Arrays and the cookie

`delete[] p` must call a destructor for every element, so it needs the element count, which the pointer alone does not carry. Under the Itanium C++ ABI (used by GCC and Clang on Linux), `new T[n]` for a type with a non-trivial destructor allocates extra space before the array, the *array cookie*, and stores *n* there. The cookie is `max(sizeof(std::size_t), alignof(T))` bytes. For trivially destructible types no destructors run, so no cookie is stored. Mismatching `new[]` with `delete` (or `new` with `delete[]`) is undefined behaviour precisely because the two forms disagree about where the allocation starts and how many destructors to run.

### Sized and aligned allocation

Since C++14, `delete` passes the object's size to `operator delete(void*, std::size_t)` when it knows it, so an allocator can skip looking the size up. Since C++17, a type whose alignment exceeds `__STDCPP_DEFAULT_NEW_ALIGNMENT__` (16 on x86-64 with GCC) is allocated through `operator new(std::size_t, std::align_val_t)`. Before C++17, `new` of an `alignas(64)` type silently returned 16-byte-aligned memory, a classic source of false sharing and misaligned SIMD loads. The libstdc++ build used here implements the aligned overload with `posix_memalign`, and glibc serves that through a more general code path than plain `malloc`, one that must find or carve out a suitably aligned chunk; compare the two rows in Listing 7.10.

### Placement new, construct_at and destroy_at

**Placement new**, `new (ptr) T(args)`, skips step 1: it constructs a `T` in storage you already have. It is the building block of every pool, arena, ring buffer and container. Its contract is that you are responsible for everything the new-expression normally does for you:

- the storage must be large enough and suitably aligned for `T` (`alignas(T) std::byte buf[sizeof(T)]`);
- you must eventually run the destructor yourself (`p->~T()` or `std::destroy_at(p)`), exactly once, and never `delete` a placement-new pointer;
- if you reuse storage that held an object of a type with `const` or reference members, use the pointer returned by placement new (or `std::launder`) rather than an old pointer (Section 11.4).

C++20's `std::construct_at(p, args...)` is a placement new that is usable in constant expressions and generic code; `std::destroy_at` is its counterpart.

### Allocation elision

Since C++14, the compiler may omit calls to replaceable allocation functions when it can satisfy the new-expression another way, for example when the object never escapes and can live in registers or on the stack. GCC does this at `-O2`. It is helpful in production and confusing in experiments: a microbenchmark of `new`/`delete` may measure nothing at all. The listings in this chapter use an `escape` helper (an empty `asm` statement that claims to read the pointer and clobber memory) to keep allocations observable.

## Page Faults, Pre-faulting and mlock

### Demand paging in one paragraph

When a program maps memory, whether through `mmap`, `brk`, a new thread stack or the loader, the kernel only records that the address range is valid. No physical page is assigned. The first access to each page traps into the kernel (a **page fault**); the kernel allocates a physical page, fills it with zeros (for anonymous memory) or with file contents, installs the page-table entry and returns. A fault that needs no disk I/O is a **minor** fault; one that must read from disk is a **major** fault and costs milliseconds. Freeing memory back to the kernel (`munmap`, heap trimming, `madvise(MADV_DONTNEED)`) means the next use faults again. Section 13.2 covers the kernel side, including copy-on-write after `fork`; here we measure the cost and remove it from the hot path.

### Techniques

- **Touch everything at startup.** After allocating pools, rings, order books and buffers, write to every page (writing matters: reading a never-written anonymous page may map the shared zero page and fault again on the first write). Pools whose construction writes a free list through every slot (Listing 7.9, line 80) pre-fault as a side effect.
- **Pre-fault stacks.** Each latency-critical thread can touch its expected maximum stack depth at startup, for example by calling a function that writes to a large local array (which must not be optimized away).
- **`MAP_POPULATE`** for mappings you create yourself, and **`mlockall(MCL_CURRENT | MCL_FUTURE)`** to fault in and lock everything the process has and will map. `MCL_FUTURE` makes later mappings fault in at creation, which moves the cost of any later allocation into the allocation call; it does not make later allocation free.
- **Stop the allocator returning memory.** Setting `M_TRIM_THRESHOLD` high and `M_MMAP_THRESHOLD` to a large fixed value with `mallopt` keeps freed memory in the process. Most production systems also simply avoid freeing and reallocating large buffers.
- **Huge pages** for large, randomly accessed structures (Section 13.3), and **first-touch NUMA placement**: a page is placed on the NUMA node of the CPU that first touches it, so the thread that will use a structure should be the one that pre-faults it (Section 13.7).
- **Swap.** A locked or frequently used page is not swapped; on trading hosts swap is usually disabled anyway (Section 13.8).

## Custom Allocators: Arenas, Pools, std::pmr

A general-purpose allocator must handle any size, any order of frees and any thread. A custom allocator wins by giving up generality you do not need. The two shapes that cover most hot-path needs are the **arena** (free everything at once) and the **pool** (one size, free in any order).

### Monotonic arenas

An arena owns a block of memory and a cursor. Allocation rounds the cursor up to the requested alignment, checks the capacity and advances the cursor: an add, a mask and a compare. There is no per-object free; `reset()` moves the cursor back to the start. This fits work with a natural phase boundary, such as everything allocated while processing one market-data packet, one request, or one simulation step.

### Fixed-size pools

A pool serves objects of one size from a pre-allocated slab. Free slots are linked into a **free list** that is stored *inside* the free slots themselves (an *intrusive* list), so the pool needs no memory beyond the slab. Allocation pops the head; deallocation pushes the slot back. Both are O(1) with no search and no size computation. The complete pool is Listing 7.9 in Section 7.8; its key properties are:

- **No per-object header.** A 64-byte object costs 64 bytes, and the slab can be laid out so each object occupies exactly one cache line.
- **LIFO reuse.** The most recently freed slot is handed out next, and it is the one most likely to still be in cache.
- **Fixed capacity or chunked growth.** A pool can refuse when full, or grow by allocating another chunk (never moving existing objects, since pointers to them are live). Problem P7.10 builds the growing version.
- **Single-threaded by design.** A pool owned by one thread needs no synchronization. A pool shared by threads needs a lock or a lock-free free list, and lock-free free lists bring the ABA problem (Section 14.8). The usual design keeps one pool per thread and passes objects between threads only through queues of indices.
- **Debuggability.** Pools hide use-after-free bugs from AddressSanitizer, because freed slots stay valid memory. Mitigations: poison freed slots in debug builds (fill with a pattern, or use ASan's manual poisoning interface), keep a liveness flag per slot (Problem P7.10), and run tests with a build option that routes the pool to plain `new`/`delete` so the sanitizers can see every object.

### std::pmr

The standard allocator model (`std::allocator<T>` as a template parameter) makes the allocator part of the container's type: a `std::vector<int, ArenaAllocator<int>>` is a different type from `std::vector<int>`, so functions that take one do not accept the other. C++17's **polymorphic memory resources** (`<memory_resource>`) solve this with run-time polymorphism. A `std::pmr::vector<int>` is `std::vector<int, std::pmr::polymorphic_allocator<int>>`, and the allocator holds a pointer to a `std::pmr::memory_resource`, an abstract class with virtual `do_allocate`, `do_deallocate` and `do_is_equal`. All `pmr` containers have the same type regardless of where their memory comes from.

The standard library supplies:

- `std::pmr::new_delete_resource()`: forwards to `operator new`/`delete` (the default).
- `std::pmr::null_memory_resource()`: throws `std::bad_alloc` on every allocation. Use it as the *upstream* of a buffer resource to make "never fall back to the heap" a checked property.
- `std::pmr::monotonic_buffer_resource`: an arena. It can start from a buffer you supply (on the stack, static, or pre-faulted) and asks its upstream for more only when that runs out; `deallocate` does nothing; memory is released when the resource is destroyed or `release()` is called.
- `std::pmr::unsynchronized_pool_resource` and `synchronized_pool_resource`: pools of several block sizes, carved from chunks obtained from the upstream. The synchronized version takes a lock.

For the hot path, `pmr` is most useful as a way to make standard containers allocate from a pre-faulted arena during a bounded piece of work. Hand-written pools remain faster for a single object type. Writing a classic stateful allocator that rebinds correctly is Problem P7.9; how containers use allocators internally is in Section 10.6.

## Smart Pointers and Their Real Costs

### unique_ptr

`std::unique_ptr<T>` is a pointer that deletes its object when it is destroyed and can be moved but not copied. With the default deleter, or any empty deleter type, it is exactly the size of a raw pointer: the deleter is stored with the empty-base optimization (Section 6.2). Dereferencing compiles to the same instruction as a raw pointer. Its costs are small and specific:

- **A stateful deleter costs space.** A function-pointer deleter adds 8 bytes; a `std::function` deleter adds 32 (Listing 7.7). Prefer an empty function-object type.
- **Moving writes null to the source**, and the destructor tests for null before deleting. Both are a few instructions.
- **Passing by value is not free in the ABI.** Under the System V x86-64 ABI, a class type with a non-trivial destructor or copy/move constructor cannot be passed in a register; the caller creates a temporary in memory and passes its address, and the caller destroys it after the call. A `unique_ptr<T>` argument therefore costs a store, a load and a null check where a `T*` would be one register. This is usually negligible, but it is the honest answer to "is `unique_ptr` zero-cost?": zero-cost in space and dereference, not entirely zero-cost at function boundaries.

The guideline that follows: pass `T&` or `T*` to functions that only use an object, and pass `unique_ptr<T>` by value only to functions that take ownership.

### shared_ptr

`std::shared_ptr<T>` is two pointers (16 bytes): one to the object and one to a **control block**. The control block holds the *use count* (number of `shared_ptr`s), the *weak count* (number of `weak_ptr`s, plus one while any `shared_ptr` exists), and, depending on how it was created, a vtable pointer, the deleter and the allocator. When the use count reaches zero, the object is destroyed; when the weak count reaches zero, the control block is freed.

- **Allocations.** `std::shared_ptr<T>(new T)` makes two allocations: the object, then the control block. `std::make_shared<T>()` makes one, placing the object inside the control block: fewer allocations and better locality.
- **The `make_shared` trade-off.** Because the object lives inside the control block, its *memory* cannot be freed until the last `weak_ptr` is gone, even though its destructor ran when the last `shared_ptr` went away. Listing 7.7 shows the destructor and the deallocation happening at different times. For large objects observed by long-lived `weak_ptr`s, this is a memory leak in practice (Problem P7.6).
- **Atomic reference counts.** Copying a `shared_ptr` increments the use count; destroying one decrements it. These must be atomic so that copies in different threads stay consistent: a `lock`-prefixed read-modify-write on x86-64, which costs a few nanoseconds when the cache line is local and far more when threads on different cores are copying the same `shared_ptr` and the control block's line bounces between them (Section 12.3).
- **Thread safety, precisely.** The *counts* are thread-safe. The pointed-to object is not protected at all. A single `shared_ptr` *instance* is not safe to read and write from two threads at once; C++20's `std::atomic<std::shared_ptr<T>>` is, but in libstdc++ it is implemented with an internal lock (`is_lock_free()` returns false).
- **Other tools:** `std::enable_shared_from_this` lets an object hand out `shared_ptr`s to itself (the control block must already exist); the *aliasing constructor* creates a `shared_ptr` that shares ownership of one object while pointing at a member of it.

### The single-threaded shortcut in libstdc++

libstdc++ checks, before each reference-count update, whether the process is still single-threaded, using glibc's `__libc_single_threaded` variable (glibc 2.32 and later). If it is, the update is a plain increment; otherwise it is an atomic one. glibc sets the variable to false when the first additional thread is created and does not set it back. ## No Allocation on the Hot Path: Enforcing It

The previous sections give the reasons: an allocation costs tens of nanoseconds at best, can take a lock, can trigger page faults and system calls, and scatters objects across memory. "We don't allocate on the hot path" is easy to say and hard to keep true, because many standard facilities allocate without saying so. The only reliable approach is to **test it**.

### Where hidden allocations come from

Listing 7.8 runs common operations inside a guarded region and counts calls to `operator new`. The results, for GCC 13 and libstdc++ on x86-64, are in its output; the general patterns are:

- **Strings longer than the small-string buffer.** libstdc++ stores up to 15 characters inline; 16 or more allocate. `std::to_string` of a large number, string concatenation and `substr` produce new strings.
- **Containers that grow.** `push_back` beyond capacity, node-based containers (`std::map`, `std::list`, `std::unordered_map`) on every insert. Lookups and updates of existing elements do not allocate (but `operator[]` on a *missing* key inserts).
- **`std::function`** whose callable is larger than its internal buffer (16 bytes in libstdc++) or is not trivially copyable. Section 8.7 covers the alternatives.
- **Algorithms** that use temporary buffers: `std::stable_sort`, `std::stable_partition`, `std::inplace_merge`.
- **Shared ownership:** `make_shared`, `std::thread`, `std::promise`/`std::future` shared state.
- **Exceptions.** Throwing allocates the exception object with `__cxa_allocate_exception`, which calls `malloc` directly (with an emergency pool as a fallback), so an `operator new` hook cannot see it. Standard exception types such as `std::runtime_error` also allocate their message string. Section 8.6 covers exception costs.
- **Formatting and I/O.** `std::ostringstream`, `std::format` returning a `std::string`, locale machinery. `std::format_to_n` into a fixed buffer allocated nothing in Listing 7.8.
- **Type erasure and lambdas captured into it,** `std::any`, coroutines (whose frames are heap-allocated unless the compiler elides it).

- **Count in production** cheaply by sampling allocator statistics (`mallinfo2()` totals, or the allocator's own counters) before and after a trading session; a hot path that allocates shows up as growth proportional to message count.

### Design rules that make the test pass

- Size everything at startup from configuration: `reserve` vectors, size hash tables (Section 10.5), create pools and arenas, and pre-fault them (Section 7.4).
- Prefer fixed-capacity containers (`std::array`, a ring buffer, a "static vector" with an inline array and a size) and indices into pools over pointers to heap objects.
- Pass `std::string_view` and `std::span` instead of owning strings and vectors (Section 8.8); keep identifiers as integers or fixed-size character arrays.
- Store callbacks as templates, function pointers or fixed-capacity callable wrappers, not `std::function` (Section 8.7).
- Report errors on the hot path with error codes or status values, not exceptions (Section 8.6).
- Move formatting off the hot path: log binary records into a pre-allocated ring and format them on another thread (Section 18.5).
- Run a warm-up phase before trading starts that exercises every hot-path branch once, so that lazy initializations (function-local statics, the first use of a locale, first-touch faults) happen before they matter.

### Reading the results

On this machine the pooled handler is roughly twice as fast at the median and has a correspondingly lower 99th and 99.9th percentile, in every run. Three effects contribute, and only one of them is the cost of `malloc` itself:

1. **Allocator work.** Two allocate/free pairs per message at roughly 10–20 ns each in the best case (Section 7.9), replaced by a few instructions.
2. **Cache-line layout.** Pool objects never share or straddle lines; heap orders often straddle two, so a random order update can miss twice.
3. **Locality and reuse.** The arena's scratch memory is the same warm 1 KiB every message; the naive version's scratch buffers come from wherever the bins have free chunks.

## Interview Questions

**Q1. Why is stack allocation faster than heap allocation, and when can't you use the stack?**
Stack space is reserved by adjusting `rsp` once per function call, a cost that exists anyway, and the memory is almost always in L1. Heap allocation runs allocator code, may take a lock, and returns memory that may be cold or not yet faulted in. You cannot use the stack when the size is unknown at compile time and potentially large, when the object must outlive the function, or when it is too large for the thread's stack (8 MiB by default on Linux, less for some threads).

**Q2. Walk me through `malloc(32)` in glibc.**
The request needs a 48-byte chunk (32 + 8, rounded up to 16). First, the thread's tcache list for 48-byte chunks: if non-empty, pop and return, with no lock. Otherwise lock the thread's arena and check the fastbin for that size, then the smallbin, then process the unsorted bin, possibly consolidating, and finally split the top chunk. If the top chunk is too small, grow the heap with `brk` (main arena) or extend the mmapped heap (other arenas). The returned pointer is 16 bytes past the chunk start and 16-byte aligned.

**Q3. A process frees 2 GB but RSS does not drop. Why?**
glibc returns memory to the kernel only in specific cases: mmapped chunks are unmapped on `free`, and free space at the top of the main heap is trimmed past `M_TRIM_THRESHOLD`. Free chunks in the middle of the heap, or in other arenas, stay mapped (fragmentation), and the dynamic threshold may have moved large blocks into the heap. `malloc_trim(0)` releases what it can; tuning thresholds, using fewer arenas, or a different allocator may help. For a trading process, keeping memory is usually what you want.

**Q4. What is the difference between `new` and `malloc`?**
`malloc` returns raw bytes or null. A new-expression calls `operator new` to get bytes (which throws `std::bad_alloc` on failure after trying the new-handler), then runs the constructor, and frees the bytes if the constructor throws. `delete` runs the destructor before freeing. `operator new` can be replaced globally or per class. Memory from one family must be released by the same family.

**Q5. What is placement new and what are its pitfalls?**
It constructs an object in storage you supply, without allocating. You must ensure size and alignment, call the destructor yourself exactly once, never `delete` the pointer, and use the pointer it returns (or `std::launder`) when reusing storage for a new object in some cases. It is how pools, arenas, `std::vector` and `std::optional` construct elements.

**Q6. Why does `delete[]` need to know the element count, and what happens if you call `delete` on memory from `new[]`?**
It must run every element's destructor. For types with non-trivial destructors, the Itanium ABI stores the count in a cookie before the array, so the allocation starts before the pointer you hold. `delete` would pass the wrong address to `operator delete` and run one destructor: undefined behaviour, typically heap corruption.

**Q7. `make_shared` or `shared_ptr<T>(new T)`?**
`make_shared` does one allocation instead of two, keeps the count next to the object, and is exception-safe in all argument-evaluation orders. Its drawbacks: the object's memory lives until the last `weak_ptr` is gone, and it cannot use a custom deleter. Use `shared_ptr(new T, deleter)` or `allocate_shared` when you need those.

**Q8. Is `shared_ptr` thread-safe?**
The reference counts are updated atomically, so different threads can copy and destroy *different* `shared_ptr` objects that share ownership. The pointed-to object gets no protection. Concurrent reads and writes to the *same* `shared_ptr` object are a data race; use `std::atomic<std::shared_ptr<T>>` (C++20), which in libstdc++ uses a lock internally.

**Q9. How would you guarantee that the hot path never allocates?**
Design: pre-size and pre-fault all structures, pools and arenas, fixed-capacity containers, views instead of owning strings, no exceptions or formatting on the hot path. Verify: replace global `operator new` with a thread-local guard that aborts inside the hot region in test builds; interpose `malloc` for C-level allocations; replay production data in staging under a malloc uprobe or heap profiler; watch allocator statistics in production.

**Q10. What is a page fault, and how do you keep them off the hot path?**
The first access to a virtual page with no physical page behind it traps into the kernel, which allocates and zeroes a page and maps it: around a microsecond for a minor fault, milliseconds for a major one. Avoid them by touching or `MAP_POPULATE`-ing all memory at startup, locking it with `mlock`/`mlockall`, not returning memory to the kernel, pre-faulting thread stacks, using huge pages for large structures, and disabling swap.

**Q11. Design an allocator for 64-byte order objects on one thread.**
A slab of N 64-byte-aligned slots allocated and touched at startup, with an intrusive LIFO free list through the free slots. `create` pops and placement-constructs; `destroy` runs the destructor and pushes. O(1), no header, one cache line per object, warm reuse. Decide what happens when full (refuse and alarm, or grow by chunks without moving objects); add debug-build poisoning and a liveness check; if other threads must free objects, send the slot index back to the owner through an SPSC queue (Section 14.5) instead of sharing the free list.

**Q12. Does `unique_ptr` cost anything compared with a raw pointer?**
With an empty deleter it is the same size and dereferences identically. Moving it writes null to the source, and its destructor checks for null. Because it has a non-trivial destructor, the x86-64 System V ABI passes it by value through memory rather than in a register, so a function taking `unique_ptr<T>` by value costs slightly more at the call boundary than one taking `T*`.

## Key Takeaways

- **Rule:** allocate and pre-fault at startup; never allocate, free or fault on the hot path. Verify it with tests, not by inspection.
- **Stack:** one `rsp` adjustment per frame, hot in L1, limited size (8 MiB typical), scope lifetime; stack pages are demand-faulted too.
- **glibc malloc:** 16-byte-aligned chunks with an 8-byte header, minimum 32 bytes; usable = max(32, round16(n + 8)) − 8. Lookup order: per-thread tcache (64 sizes up to 1032 usable bytes, 7 entries each, no lock) → per-arena fastbins, small/large bins, unsorted bin (locked) → top chunk → `brk`/`mmap`. Requests ≥ 128 KiB are mmapped by default, with a dynamic threshold. Arenas: up to 8 per core; cross-thread frees are slow.
- **new/delete:** a new-expression is allocate + construct, with automatic cleanup if construction throws. Arrays of non-trivially-destructible types carry a cookie. Over-aligned types use `align_val_t` overloads (C++17). Placement new constructs without allocating; you destroy explicitly. Compilers may elide allocations.
- **Page faults:** ~1 µs per minor fault, ms per major. Pre-fault by writing, `MAP_POPULATE`, `mlock`/`mlockall`; avoid trimming and unmapping; huge pages cut fault and TLB-miss counts.
- **Custom allocation:** arenas (bump + reset) for phase-scoped data; fixed-size pools with intrusive LIFO free lists for objects; per-thread ownership; `std::pmr` to put standard containers on your memory, with `null_memory_resource` upstream to forbid fallback.
- **Smart pointers:** `unique_ptr` is free in size and dereference, slightly costly to pass by value. `shared_ptr` is 16 bytes plus a control block; `make_shared` saves an allocation but ties the memory to `weak_ptr`s; counts are atomic once any second thread has existed. Pass by reference; don't copy `shared_ptr` per message.
- **Hidden allocations:** strings over 15 characters, container growth, node containers, large or non-trivially-copyable `std::function` targets, `stable_sort`, exceptions, streams and formatting to `std::string`.
