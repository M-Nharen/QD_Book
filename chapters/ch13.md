# Operating Systems and Linux

Chapter 12 described the machine as if your program owned it. It does not. The Linux kernel decides which thread runs on which core and for how long, when each virtual page gets a physical page, which core handles each interrupt, and how long asking for the time takes. For a trading system those decisions are the main source of *jitter*: the gap between the median and the 99.9th percentile is usually made of page faults, context switches, interrupts and system calls, not of slow code.

This chapter explains what the kernel does on your behalf, what each kind of kernel involvement costs, and how trading hosts keep the kernel off the hot path: processes and threads (13.1), page faults (13.2), huge pages (13.3), scheduling (13.4), system calls and the vDSO (13.5), pinning and isolation (13.6), NUMA (13.7) and a host tuning checklist (13.8). The showdown (13.9) takes one hot loop from a naive process setup to a tuned one and cuts its 99th-percentile latency by about an order of magnitude without touching the loop body. Section 7.4 (first-touch faults, pre-faulting, `mlock`) and Section 12.4 (page tables and the TLB) are prerequisites and are not repeated.

**About the measurements.** Listings were compiled with g++ 13.3 at `-O2` against glibc 2.39 and run in the build container: a KVM guest running Linux 6.18 on 2 vCPUs of an Intel Xeon at 2.1 GHz nominal, one NUMA node, no swap, transparent huge pages in `madvise` mode, a 250 Hz timer tick. A virtual machine is a poor place to study OS jitter, because the hypervisor adds interruptions the guest cannot see (Listing 13.6 shows this), so the text gives approximate bare-metal ranges next to the container measurements. Both depend on CPU, kernel version and configuration; treat them as orders of magnitude.

## Processes and Threads

### What the kernel schedules

A **process** is a running program plus the resources the kernel tracks for it: an address space, open file descriptors, signal handlers, credentials and limits. A **thread** is a flow of execution: registers, a stack and a scheduling identity. Linux implements both with one object, the *task* (`struct task_struct`). Every thread is a task with its own **thread ID** (TID); the tasks of a process form a *thread group* whose ID, the TID of the first thread, is what `getpid()` returns. The scheduler (13.4) schedules tasks, not processes. Both are created by `clone`, and its flags decide what is shared: `fork()` shares nothing (it gets a copy-on-write copy of the address space, 13.2), while `pthread_create`, which `std::thread` calls, shares the address space, file table and signal handlers and gets a new stack and thread-local storage block.

- **Creation cost (lines 76–82):** tens of microseconds per create-and-join here (stack `mmap`, `clone`, scheduling, exit, a futex wake for `join`). **Threads are created at startup and kept.**

### Signals and fork

**Signals are delivered to the process** and then to any one thread that does not block them. A handler running on the latency-critical thread steals its time at an arbitrary point. The standard design blocks asynchronous signals with `pthread_sigmask` in `main` before creating threads (they inherit the mask) and handles them in one dedicated thread with `sigwait` or a `signalfd`.

**`fork()` in a multithreaded process copies only the calling thread**, but all the memory, including mutexes held by other threads, which stay locked forever in the child. glibc protects its own internal locks (the `malloc` arenas) across `fork`, not yours, so the child may call only async-signal-safe functions until it `exec`s. Start helper processes before creating threads, or use `posix_spawn`.

Work can also be split across *processes* sharing memory (`shm_open` and `mmap` with `MAP_SHARED`). That buys fault isolation, independent restarts, and separate address spaces, so one process's `munmap` causes no TLB shootdowns in another (13.2). A lock-free ring (14.5) costs the same between processes as between threads, provided it stores offsets rather than pointers.

## Virtual Memory and Page Faults

### The kernel's view: VMAs and lazy page tables

Besides the page tables of 12.4, the kernel keeps a list of **virtual memory areas** (VMAs): address ranges with one set of permissions and one backing (anonymous memory, a file, a device), printed by `/proc/<pid>/maps`, with per-area statistics in `/proc/<pid>/smaps`. `mmap`, `brk` and thread creation only create VMAs; page-table entries are filled in lazily, one fault at a time.

### What happens on a page fault

When an access finds its page-table entry missing or too restrictive, the CPU raises a page fault, with the address in `CR2` and an error code (read or write, user or kernel, page present or not). The kernel then finds the VMA (none, or wrong permissions: `SIGSEGV`), allocates any missing page-table levels, and resolves the fault by backing:

- **anonymous, read, never written:** map the system-wide **zero page** read-only; no memory is used;
- **anonymous, write:** allocate a page, zero it (the kernel never leaks another process's data), map it writable;
- **file-backed:** take the page from the **page cache** (a **minor fault**) or read it from storage (a **major fault**: the thread sleeps for tens of microseconds on NVMe to milliseconds on disk);
- **copy-on-write:** below.

It installs the entry and returns, and the instruction is retried. All of this runs on the faulting thread, in its time.

### Copy-on-write and fork

`fork` does not copy memory. It copies the page tables and marks every private writable page read-only in *both* processes. The first write to a page in either process faults, and the kernel copies that page for the writer.

### Overcommit, reclaim and TLB shootdowns

Because pages are allocated at first touch, Linux by default **overcommits**: `malloc(1 << 30)` usually succeeds even without free memory, and the bill comes at touch time. A fault that finds no free page enters *direct reclaim*, freeing page cache or swapping on the faulting thread's time (milliseconds), and failing that the OOM killer ends a process. Size memory with a margin, disable swap or lock the process's memory (7.4), and touch everything at startup.

When the kernel removes or downgrades a mapping (`munmap`, `madvise(MADV_DONTNEED)`, `mprotect`, a copy-on-write break, page migration), every core that may cache the old translation must flush it: the kernel sends an inter-processor interrupt to each core running a thread of that address space (the `TLB` row of `/proc/interrupts`). The cost lands on the *other* cores, so a housekeeping thread returning memory interrupts the hot thread of the same process: one more reason never to free memory after startup (7.7).

## Huge Pages

### Two mechanisms

Huge pages (2 MiB or 1 GiB on x86-64) multiply TLB reach by 512 or more and shorten page walks (12.4). Linux offers them in two ways.

**hugetlbfs** (explicit huge pages): an administrator reserves a pool at boot (`hugepagesz=1G hugepages=16`; 1 GiB pages are reliably available only this way) or at run time (`sysctl vm.nr_hugepages=1024`, which may partly fail on fragmented memory). Programs map them with `MAP_HUGETLB` (plus `MAP_HUGE_1GB` for 1 GiB) or through a mounted `hugetlbfs` file. Pool pages are never swapped or split, and the `mmap` either succeeds or fails at once. DPDK and other kernel-bypass stacks (15.4) use them.

**Transparent huge pages** (THP): the kernel backs a 2 MiB-aligned block of anonymous memory with a huge page when it is first faulted, if a free 2 MiB block exists. `/sys/kernel/mm/transparent_hugepage/enabled` chooses `always`, `madvise` (only ranges marked `MADV_HUGEPAGE`) or `never`; `khugepaged` also collapses 4 KiB pages into huge pages in the background; `defrag` decides whether a fault may stall to compact memory when no free block exists.

### The trade-offs

Huge pages trade many small first-touch stalls for a few large ones, so they belong only on memory **faulted in at startup**. THP adds *memory bloat* (a whole 2 MiB page for a few bytes, severe with `enabled = always`), *compaction stalls* of milliseconds when `defrag = always`, and background collapsing and splitting with their TLB shootdowns. Trading hosts therefore typically run THP in `madvise` mode (or off), reserve hugetlbfs pages at boot for the big structures (order books, instrument tables, rings, packet buffers), and pre-fault everything.

## Scheduling and Context Switches

### What the scheduler does

Each CPU has a **run queue** of runnable tasks. A task that blocks leaves it; when its event happens it is *woken* onto some CPU's queue. Scheduling classes are tried in priority order: an internal *stop* class (migration work), `SCHED_DEADLINE` (tasks declare runtime, deadline and period), the real-time `SCHED_FIFO` and `SCHED_RR` (fixed priorities 1–99; a higher priority always preempts; FIFO runs until it blocks, RR adds time slices), the *fair* class (`SCHED_OTHER`, `SCHED_BATCH`; CPU time shared by nice-value weights), and `SCHED_IDLE`.

Normal threads use the fair class, which since Linux 6.6 uses EEVDF (earliest eligible virtual deadline first) in place of the older CFS. Three consequences matter: a normal thread sharing a CPU is preempted for milliseconds at a time; a newly woken task may preempt the running one (*wakeup preemption*); and the scheduler **migrates** tasks between CPUs to balance load, away from their warm caches. Preemption is driven by the **timer tick**, an interrupt on every busy CPU `CONFIG_HZ` times a second (commonly 250 or 1000; 250 here), which also runs timers and statistics. Idle CPUs stop their tick; a CPU with one runnable task can too, if configured (`nohz_full`, 13.6).

**Real-time priority is not free speed.** A `SCHED_FIFO` thread that never blocks starves everything else on its CPU, including per-CPU kernel threads, so the kernel limits it: classic *RT throttling* gives real-time tasks 950 ms of every second (`kernel.sched_rt_runtime_us`), and since Linux 6.12 a deadline "fair server" reserves time (50 ms per second by default) for starved normal tasks. A spinning real-time thread can thus be stopped for tens of milliseconds (P13.10); isolate the CPU (13.6) instead.

### What a context switch costs

The *direct* cost of a switch is kernel work: entry, choosing the next task, saving and restoring registers (including SIMD state when used), switching stacks, and loading the next address space's page-table root if it is another process (PCID, 12.4, avoids a full TLB flush). The *indirect* cost, the incoming task refilling caches, TLB and predictors, is often larger. Switches are **voluntary** (the task blocked) or **involuntary** (it was preempted), counted per thread in `/proc/<pid>/task/<tid>/status`, by `getrusage`, and by `perf stat -e context-switches,cpu-migrations`. A busy-polling thread on an isolated core should show neither.

## System Calls and the vDSO

### The path into the kernel

User code puts the system-call number in `rax` and up to six arguments in `rdi`, `rsi`, `rdx`, `r10`, `r8`, `r9`, and executes `syscall`. The CPU enters kernel mode at the entry point the kernel registered at boot; the kernel switches to its stack, saves registers, applies speculative-execution mitigations (12.1), dispatches, and returns with `sysret`. A result in −4095…−1 is an error, which glibc turns into `-1` and `errno`. The mitigations dominate the cost: on CPUs affected by Meltdown, *kernel page-table isolation* (KPTI) switches page tables on every entry and exit; other mitigations flush or fence predictor state. `/sys/devices/system/cpu/vulnerabilities/` lists what applies; the container's CPU needs no KPTI. A trivial system call typically costs roughly 100–300 ns on current servers and up to about a microsecond on older CPUs with KPTI: one to two orders of magnitude more than a function call, before doing any work.

### The vDSO

At every `exec` the kernel maps a small shared library, the **vDSO**, and a read-only data page it keeps updated into the process; glibc finds it through the auxiliary vector (`AT_SYSINFO_EHDR`) and routes `clock_gettime`, `gettimeofday`, `time` and `getcpu` through it. For clocks, the data page holds the parameters to convert a TSC reading into time, guarded by a sequence counter (like the seqlock of 14.7), so the time is computed entirely in user space. This requires a TSC clocksource (`/sys/devices/system/clocksource/clocksource0/current_clocksource`); with another clocksource the vDSO falls back to a real system call.

## CPU Pinning and Isolation

### Affinity is not isolation

Every task has a **CPU affinity mask**. `sched_setaffinity`, `pthread_setaffinity_np` or `taskset -c` restrict it, so a pinned thread never migrates and keeps its L1, L2 and TLB contents. The convention is one critical thread per physical core, its SMT sibling idle (12.1), and CPU 0 left for housekeeping, where the kernel and devices often put work by default. But a pinned thread still shares its CPU with everything else allowed there: other threads, per-CPU kernel threads, interrupts, softirqs, timer ticks and RCU callbacks. The first step is to measure how much of the CPU those take.

### Isolation, layer by layer

Isolation removes the other users of a CPU in layers:

- **Other tasks:** `isolcpus=` removes CPUs from scheduler load balancing (its flag form, such as `isolcpus=nohz,domain,managed_irq,2-7`, adds more); cgroup **cpusets** (or systemd's `AllowedCPUs=`/`CPUAffinity=`) do the same at run time. Check with `ps -eLo tid,psr,comm`.
- **Interrupts:** set `/proc/irq/<n>/smp_affinity_list`, default new ones with `irqaffinity=0-1`, and stop or reconfigure `irqbalance`, which rewrites the masks. NIC queues for market data are placed deliberately on the NIC's NUMA node (13.7).
- **The tick and RCU:** `nohz_full=2-7` stops the tick while exactly one task is runnable (a residual tick about once a second remains, and any system call or fault brings kernel work back); `rcu_nocbs=2-7` moves RCU callback processing to housekeeping CPUs.
- **Other kernel work:** unbound workqueues via `/sys/devices/virtual/workqueue/cpumask`; a longer `vm.stat_interval`; `skew_tick=1` to stagger ticks between CPUs.

## NUMA

### Nodes, distances and devices

A multi-socket server has **non-uniform memory access**: each socket and its DRAM form a NUMA **node**, and a core reaches another node's memory over the inter-socket link (Intel UPI, AMD Infinity Fabric), typically at about 1.3–2 times local latency and with limited bandwidth. Large processors can also be split into several nodes (Intel sub-NUMA clustering, AMD NPS modes). Devices are local too: a NIC hangs off one socket's PCIe lanes (`/sys/class/net/<if>/device/numa_node`), so a feed handler on the other socket pays a cross-socket trip per packet. `numactl --hardware` prints the nodes, their CPUs and the distance matrix (10 means local).

### Where pages go

The default policy is **first touch**: a page lands on the node of the CPU that first faults it in, not the one that called `malloc`. `set_mempolicy` (per thread) and `mbind` (per range) can *bind*, *prefer* or *interleave* instead; `numactl --cpunodebind=0 --membind=0 ./app` binds a whole process. `move_pages` with a null target list reports each page's node (or `-ENOENT` for an untouched page); `move_pages` and `migrate_pages` move pages. The rules that follow:

- **Pin each thread first, then let it allocate and touch its own data.** The classic bug initializes everything in the main thread and then starts workers on another socket.
- **Run the hot path on the NIC's node:** the receiving and sending threads, their memory and the NIC's interrupts or polling.
- **Disable automatic NUMA balancing** (`kernel.numa_balancing = 0`). It works by periodically unmapping pages to sample accesses through faults, and then migrating them: unpredictable stalls by design.
- **Replicate shared read-mostly data** (reference data) per node rather than reading it remotely from half the threads.

## A Low-Latency Host Tuning Checklist

These settings recur in low-latency host configurations. None is universal: check each against the hardware and kernel, and measure before and after with a tool like Listing 13.6. Several trade power, security margin or throughput for latency, deliberately, on dedicated machines.

### Firmware (BIOS/UEFI)

Choose the maximum-performance or vendor low-latency power profile; disable deep C-states and C1E (waking from deep idle costs tens of microseconds or more on every wake-up, 13.4, at the price of power and heat); disable SMT or leave the siblings of critical cores idle (12.1); decide on turbo deliberately (faster, but the frequency varies with load and temperature); keep NUMA enabled without node interleaving and populate all memory channels (13.7).

### Kernel command line

| Parameter | Purpose (section) |
|---|---|
| `isolcpus=…` or cgroup cpusets | keep other tasks off application cores (13.6) |
| `nohz_full=…`, `rcu_nocbs=…` | stop the tick and RCU callbacks on application cores (13.6) |
| `irqaffinity=…` | default interrupt affinity: housekeeping cores (13.6) |
| `intel_idle.max_cstate=0` or `1`, `processor.max_cstate=1` | limit idle depth from the OS side; `idle=poll` goes further and spins, at a large power cost |
| `transparent_hugepage=madvise` or `never` | avoid surprise compaction and bloat (13.3) |
| `hugepagesz=`, `hugepages=`, `default_hugepagesz=` | reserve explicit huge pages at boot, before memory fragments (13.3) |
| `skew_tick=1`, `nosoftlockup`, `nmi_watchdog=0` | stagger ticks; remove periodic watchdog work |
| `mitigations=…` | a *security* decision about speculative-execution mitigations (13.5), not an engineer's unilateral call |

### Run time

- **Interrupts:** stop `irqbalance` (or exclude application cores) and set `/proc/irq/*/smp_affinity_list` explicitly; NIC queue interrupts go to the NIC's node.
- **CPU frequency governor** `performance`; **clocksource** `tsc`, so that the vDSO works (13.5).
- **Memory:** swap off or `vm.swappiness` near 0; `kernel.numa_balancing = 0`; `vm.stat_interval` raised (say to 10 s); THP `defrag` not `always`; KSM off.
- **Kernel work:** unbound workqueues on housekeeping CPUs; RT throttling or fair-server defaults left alone unless the CPU is isolated (13.4).
- **Profiles:** RHEL's `tuned` profiles (`latency-performance`, `network-latency`, `cpu-partitioning`) apply many of these together; read what a profile does before relying on it.

### In the application

- Create every thread at startup, pin it, and block asynchronous signals in it (13.1, 13.6).
- At startup, map memory, request huge pages, touch every page from the thread that will use it, then `mlockall(MCL_CURRENT | MCL_FUTURE)`, in that order (7.4, 13.3, 13.7, 13.9); raise `RLIMIT_MEMLOCK` or grant `CAP_IPC_LOCK`.
- On the hot path: no system calls, no locks that can sleep, no `fork`, no memory returned to the kernel (13.2, 13.5, 14.9).
- Warm up every path, including the first clock read, then verify with counters: zero faults, zero context switches, zero migrations (13.9).

## The Nanosecond Penalty

"Typical bare metal" gives rough ranges for current x86-64 servers with default kernel settings; "measured here" is from this chapter's listings in the virtualized container and is shown for its ratios.

| Event | Typical bare metal | Measured here | Why it costs that |
|---|---|---|---|
| `clock_gettime(MONOTONIC)`, vDSO | ≈ 15–40 ns | ≈ 31 ns (13.5) | `rdtsc` + scaling + sequence check |
| trivial system call | ≈ 100–300 ns; up to ≈ 1 µs with KPTI | ≈ 140–250 ns (13.5) | mode switch, mitigations |
| minor fault, 4 KiB anonymous write | ≈ 0.5–2 µs | ≈ 1.5–2.5 µs (13.2, 13.3) | exception, VMA lookup, allocate, zero 4 KiB |
| copy-on-write fault | similar to a zero-fill fault | ≈ 2.4 µs (13.2) | copy 4 KiB instead of zeroing |
| first-touch fault, 2 MiB page | ≈ 50–500 µs | hundreds of µs (13.3) | zero 2 MiB; possibly compaction |
| context switch, same CPU | ≈ 1–3 µs plus cache refill | ≈ 1.1–1.6 µs per handoff (13.4) | entry, scheduler, register and stack switch |
| wake-up on another CPU | ≈ 2–10 µs, more from deep C-states | ≈ 5–13 µs (13.4) | IPI, idle exit, switch (hypervisor here) |
| timer tick on a busy CPU | ≈ 1–5 µs every 1–4 ms | ≈ 250 per s (13.6) | interrupt + scheduler bookkeeping |
| thread create + join | roughly 10–50 µs | ≈ 40 µs (13.1) | `mmap`, `clone`, scheduling, futex |
| `fork` + exit + wait | ms, growing with memory | ≈ 2–13 ms (13.2) | page-table copy; COW faults afterwards |
| remote NUMA DRAM access | ≈ 1.3–2× local | — (one node) | inter-socket link |

Kernel events cost microseconds while the hot path's own work costs nanoseconds, and they are *bimodal*: most events pay nothing and a few pay a lot. That is why they show up in the 99th and 99.9th percentiles rather than the median.

## Interview Questions

**Q1. What is the difference between a process and a thread on Linux?**
Both are tasks created by `clone`; the flags decide what is shared. Threads of a process share the address space, file descriptors and signal handlers, and each has its own TID, registers, stack and TLS; `getpid()` returns the thread-group ID. The scheduler schedules threads independently. Processes share nothing by default, which gives isolation at the cost of explicit communication.

**Q2. What happens when a program touches a page it has never touched?**
A page fault with the address in `CR2`. The kernel finds the VMA (none: `SIGSEGV`), allocates missing page-table levels, and for anonymous memory maps the zero page (read) or allocates and zeroes a page (write); for files it uses the page cache (minor) or reads storage (major). It installs the entry and the instruction is retried. About a microsecond for a minor fault.

**Q3. What does a context switch cost?**
Directly about a microsecond or two (entry, scheduler, registers, stack, maybe page tables). Indirectly often more: the incoming thread refills caches, TLB and predictors. A wake-up on another CPU adds an IPI and the idle core's C-state exit.

**Q4. Why is `clock_gettime` fast when `getpid` is not?**
The common clocks are computed in user space by the vDSO from `rdtsc` and kernel-published parameters; `getpid` is a real system call (glibc stopped caching it in 2.25). The vDSO needs a TSC clocksource, otherwise `clock_gettime` falls back to a system call.

**Q5. You pinned your thread with `taskset`, yet it sees 10 µs stalls every few milliseconds. Why?**
Pinning keeps the thread on the CPU, not other things off it: the tick (every 1–4 ms), interrupts routed there, other tasks allowed there, kernel threads and RCU callbacks, a busy SMT sibling. Use `isolcpus` or cpusets, `nohz_full`, `rcu_nocbs` and interrupt affinity, and find the culprit with a jitter tool or the `osnoise` tracer.

**Q6. What does `mlockall(MCL_CURRENT | MCL_FUTURE)` do, and not do?**
It populates and locks current mappings and makes later mappings populate and lock at creation, so nothing is reclaimed or swapped. It does not make later allocations free (their faults move into `mmap`), it needs `RLIMIT_MEMLOCK` or `CAP_IPC_LOCK`, it does not populate the vDSO's data page, and set before `madvise(MADV_HUGEPAGE)` it populates with 4 KiB pages.

**Q7. A latency-critical thread shows thousands of voluntary context switches per second. What does that tell you?**
It is blocking: a contended mutex, a condition variable, a blocking read, a sleep or a major fault. A busy-polling thread shows none; involuntary switches would instead mean preemption by something else runnable on its CPU. Investigate with `perf trace` or `perf sched` (and `strace -f -T` only in a test environment, since it slows the process heavily).

## Key Takeaways

- **Tasks:** threads are tasks sharing one address space, each with its own TID, stack and `fs`-relative TLS. Create them at startup, block signals in hot threads, never `fork` a running latency-critical process.
- **Memory:** mapping is lazy; first writes fault (≈ 1–2 µs per 4 KiB page, hundreds of µs per 2 MiB page), and after `fork` every write faults. Request huge pages, touch everything, then `mlockall`, at startup; never return memory (TLB shootdowns).
- **Scheduler and kernel entry:** a context switch costs ≈ 1–2 µs plus cache refill, a cross-CPU wake-up more; a system call ≈ 100–300 ns; vDSO clocks tens of ns. The hot path neither blocks nor calls the kernel.
- **Isolation and NUMA:** pinning is not isolation; add `isolcpus`/cpusets, `nohz_full`, `rcu_nocbs`, interrupt affinity and shallow C-states, and measure the remaining noise. Place data by first touch from the using thread, on the NIC's node. VMs cannot be made quiet from inside.
- **Showdown:** the same loop's p90 and p99 fell about 10× from process setup alone; verify with counters: zero faults, switches and migrations.
