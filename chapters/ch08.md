# Modern C++

"Modern C++" usually means the language since C++11: move semantics, lambdas, `auto`, smart pointers, and the vocabulary types added in C++17 and C++20. For a low-latency engineer the point of these features is not style. They let you write code that says exactly what happens to every object (who owns it, when it is copied, when it is destroyed) and then let the compiler generate the same machine code you would have written by hand, or better. Used carelessly, the same features hide copies, allocations, indirect calls and exception paths behind innocent syntax.

This chapter explains each feature at the level an interviewer probes: the rule, the mechanism the compiler uses, what it costs, and where it goes wrong. It builds on Chapter 5 (references, argument passing and the rule of zero/three/five in Sections 5.2 and 5.5; the exception overview in Section 5.8) and on Chapter 7 for allocation costs. Templates themselves are Chapter 9; lifetime bugs involving views and captures are catalogued in Section 11.4.

## Value Categories

### The intuition

Every C++ expression has two independent properties: a **type** (`int`, `std::string`) and a **value category**, which answers two questions:

1. **Does it have identity?** Can you take its address and refer to the same object again later? A named variable does; the result of `x + 1` does not.
2. **Can its resources be stolen?** Is anyone else going to look at it after this expression? A temporary will be destroyed at the end of the full expression, so nobody will; a named variable will still be there.

The three primary categories are the three useful combinations:

| Category | Identity? | Resources may be stolen? | Examples |
|---|---|---|---|
| **lvalue** | yes | no | `x`, `*p`, `a[i]`, `++x`, a function returning `T&`, a string literal |
| **xvalue** ("expiring") | yes | yes | `std::move(x)`, a function returning `T&&`, a member of an xvalue |
| **prvalue** ("pure") | no | (it is not an object yet) | `42`, `x + 1`, `x++`, a function returning `T` by value, `T{}` |

Two grouping terms appear in the standard and in error messages: a **glvalue** is an lvalue or xvalue (has identity), and an **rvalue** is an xvalue or prvalue (may be moved from).

### What C++17 changed: prvalues are not objects

Since C++17, a prvalue is not a temporary object. It is a *recipe for initializing an object*: `T{args}` describes how to construct a `T`, and the object is created only when the prvalue is used to initialize something. If that something is a variable, the variable itself is constructed from the recipe; if a prvalue must be treated as an object (you call a member function on it, or bind a reference to it), the compiler **materializes** a temporary, which is an xvalue. This is the rule behind guaranteed copy elision (Section 8.4), and it is why `make_quote().px` below is an xvalue: the prvalue `make_quote()` was materialized so that its member could be named.

### Why a QD interviewer cares

Value categories decide which constructor runs, which decides whether an `std::string` or `std::vector` argument costs an allocation and a `memcpy` (tens to hundreds of nanoseconds, Section 8.10) or a three-pointer swap (about a nanosecond). They also decide whether a function overload taking `T&&` is selected, and whether a `return` statement copies, moves or does neither.

## Move Semantics

### The idea

A type that owns a resource through a pointer, such as `std::string`, `std::vector` or `std::unique_ptr`, can be *copied* by duplicating the resource (allocate, copy bytes) or *moved* by transferring the pointer and leaving the source empty. Moving is legitimate only when nobody will use the source's value again, which is exactly what an rvalue says. C++11 added **rvalue references** (`T&&`), which bind only to rvalues, so a class can provide a second constructor and assignment operator, `T(T&&)` and `T& operator=(T&&)`, that are selected for rvalue arguments and steal instead of copying.

### std::move is a cast (diagnostic D7)

`std::move(x)` does nothing at run time. It is defined, in essence, as

```cpp
template <class T>
constexpr std::remove_reference_t<T>&& move(T&& t) noexcept {
    return static_cast<std::remove_reference_t<T>&&>(t);
}
```

It converts its argument to an xvalue, which changes which overload is chosen. It generates no instructions. If the result is never used to initialize or assign an object, nothing moves. If the chosen overload is a copy (because the type has no move constructor, or because the argument is `const`), a copy happens. A better name would have been `rvalue_cast`.

### What a move costs, and when it is not cheap

A move constructor of `std::string` (libstdc++, 32 bytes) copies the pointer, size and capacity and resets the source to an empty inline buffer: a handful of loads and stores. A `std::vector` move copies three pointers and nulls the source. Neither touches the heap. But "move" means "the cheapest correct transfer the type knows", and for some types that is a full copy:

- **Trivially copyable types** (`int`, `double`, a struct of them, `std::array<int, 1000>`) have no resource to steal. Moving a 4 KB `std::array` copies 4 KB.
- **Short strings** live in the small-string buffer (up to 15 characters in libstdc++), so moving one copies the characters.
- **Types with a user-declared destructor or copy operation** and no declared move have no move constructor at all; "moving" them copies (Section 5.5).
- **Node-based containers with a sentinel inside the object** (libstdc++'s `std::list`, `std::map`) must fix up pointers when moved, which is still O(1) but not free.

### Rules that keep moves correct

- **Do not use an object after moving from it** except to assign or destroy it. Clang-tidy's `bugprone-use-after-move` check finds many cases.
- **Make move operations `noexcept`** whenever they cannot fail (Section 8.6), and leave the source in a state that the destructor and assignment can handle.
- **Do not `std::move` a `const` object, a return value, or a function argument you will use again.** The first silently copies, the second can disable elision (Section 8.4), the third is a use-after-move bug.
- **`std::exchange(member, new_value)`** is the idiomatic way to write move constructors that steal and reset in one expression (Listing 8.5, line 17).
- **Ref-qualified member functions** (`std::string name() &&`) let a class offer a stealing version of an accessor when called on an rvalue, as `std::optional::value() &&` and `std::move(q).venue` do.

## Forwarding References and Perfect Forwarding

### The special rule for T&& in a deduced context

When a function template parameter has the form `T&&` and `T` is deduced from the argument, the parameter is a **forwarding reference** (the term older material uses is *universal reference*), not an rvalue reference. Deduction follows a special rule: if the argument is an lvalue of type `int`, `T` is deduced as `int&`; if it is an rvalue, `T` is deduced as plain `int`. The parameter type `T&&` is then computed with **reference collapsing**:

| T | T&& becomes | because |
|---|---|---|
| `int` | `int&&` | no reference to collapse |
| `int&` | `int&` | `& &&` collapses to `&` |
| `int&&` | `int&&` | `&& &&` collapses to `&&` |

Any lvalue reference in the mix wins. The result is that one template accepts every argument, and `T` remembers whether the argument was an lvalue or an rvalue. `auto&&` in a variable declaration or a generic lambda parameter is a forwarding reference by the same rule.

Only the exact form `T&&` with `T` a template parameter of *this* function being deduced qualifies. `const T&&` is an rvalue reference to const. In `template <class T> struct Box { void set(T&& v); };`, `set` takes an rvalue reference, because `T` was fixed when `Box<T>` was instantiated; only a member *template* (`template <class U> void set(U&& v)`) forwards.

### std::forward

Inside the template the parameter has a name, so it is an lvalue (Section 8.1). `std::forward<T>(p)` restores the original category: it casts `p` to `T&&`, which by reference collapsing is an lvalue reference when `T` is `X&` and an rvalue reference when `T` is `X`. Like `std::move`, it is a cast and generates no code.

### When perfect forwarding is not perfect

Forwarding fails, or changes meaning, for arguments whose meaning depends on the target type: braced initializer lists (`f({1, 2})` cannot deduce `T`), `0` or `NULL` used as a null pointer (deduced as `int`), overloaded function names and function templates (no single type to deduce), bit-fields (cannot bind a reference), and `static constexpr` data members that are declared but not defined (pre-C++17 code; they are implicitly `inline` since C++17). The fixes are to spell the type (`f(std::initializer_list<int>{1, 2})`, `nullptr`, `static_cast` to the right function-pointer type, a copy of the bit-field).

## Copy Elision and RVO

### What return does in the ABI

On x86-64 Linux, a function returning a class that is not trivially copyable, or is larger than 16 bytes, does not return it in registers. The *caller* reserves space for the result and passes its address as a hidden first argument (in `rdi`); the callee constructs the result there and returns the same address in `rax`. Copy elision is the language permission, and since C++17 in part the requirement, to construct the returned object directly in that caller-provided slot.

### The rules

1. **Returning a prvalue, or initializing from one: guaranteed elision (C++17).** `return T{args};` and `T t = make();` never copy or move; there is no temporary to copy (Section 8.1). The type does not even need a copy or move constructor.
2. **Named return value optimization (NRVO): permitted, not guaranteed.** `T t; ...; return t;` may construct `t` directly in the return slot. GCC and Clang do this whenever every `return` in the function returns the same local variable, at all optimization levels.
3. **Implicit move.** When NRVO does not happen and the returned expression is the *name* of a local variable or a by-value parameter, the compiler treats it as an rvalue first, so it moves rather than copies. C++20 extended this to rvalue-reference parameters (and C++23 simplified the rules further).
4. **Everything else copies.** Returning a global, a member, a `*this`, a reference parameter, an element (`v[0]`), a structured binding, or any expression that is not a plain name (`cond ? a : b`) copies.

## RAII

### The idea

**Resource Acquisition Is Initialization** ties a resource to an object's lifetime: the constructor acquires (or receives) the resource and the destructor releases it. Because C++ runs destructors of automatic objects deterministically, in reverse order of construction, when a scope is left by *any* route (falling off the end, `return`, `break`, an exception), the release cannot be forgotten. Memory is only one kind of resource; in trading systems RAII equally manages file descriptors and sockets, memory mappings, locks, thread pinning, timers, subscriptions to a feed, kernel-bypass handles and "this order is in flight, roll it back unless we finish" obligations.

### Writing an owner

An RAII owner usually follows a fixed shape: owns exactly one resource, is move-only (copying would create two owners), has a `noexcept` move that leaves the source empty, and offers `get`, `release` and `reset`. `std::unique_ptr` with a custom deleter covers pointer-like handles; Listing 8.5 writes the shape out for a file descriptor, and Problem P8.8 generalizes it with a traits class.

### Rules and edge cases

- **Destructors are implicitly `noexcept`.** If a destructor throws during unwinding, or at all unless declared `noexcept(false)`, the program calls `std::terminate`. A destructor that can fail (closing a file that may report an I/O error) should either ignore the error, log it, or offer an explicit `close()` that reports it and leave the destructor as a fallback.
- **Members are destroyed in reverse order of declaration,** after the destructor body runs; bases after members. Declare a member that others depend on (for example a memory pool) *before* the members that use it.
- **A constructor that throws destroys the members and bases already constructed,** but not the object itself, whose destructor never runs. Acquire each resource in its own member (rule of zero) so that partial construction cleans up automatically.
- **Unwinding is not guaranteed when no handler exists.** If an exception escapes `main` or a thread function, `std::terminate` is called, and whether destructors ran first is implementation-defined. Long-running processes catch at the top of each thread and shut down deliberately.
- **Lock guards are RAII:** `std::lock_guard`, `std::scoped_lock` (several mutexes, deadlock-free) and `std::unique_lock` (movable, can unlock early); Section 14.1 covers them. Listing 7.8's hot-path marker is another RAII object.
- **Cost:** a destructor that is inlined costs exactly the release code you would have written. What RAII adds is in the *exception* path: each scope with a non-trivial destructor needs a landing pad that runs the destructor during unwinding, which lives in cold code (Section 8.6). And, as Section 5.2 explains, a non-trivial destructor stops a small type from being passed in registers.

## noexcept and the Cost of Exceptions

Section 5.8 explained how table-based exceptions work and when to prefer error codes. This section adds what `noexcept` means precisely, how it changes generated code and library behaviour, and what throwing actually costs.

### What noexcept means

`noexcept` (equivalently `noexcept(true)`) on a function is a promise that no exception will leave it. It is not checked at compile time. If an exception does try to leave, the runtime calls `std::terminate`, and the standard does not even require the stack to be unwound first. Related forms:

- `noexcept(expr)` with a constant boolean makes the promise conditional: `void swap(T& a, T& b) noexcept(std::is_nothrow_move_constructible_v<T> && ...)`.
- The **`noexcept` operator**, `noexcept(expression)`, is a compile-time query that is true if the expression is declared not to throw. Libraries use it to choose algorithms.
- Destructors, and implicitly declared or defaulted special members whose subobjects' operations are all `noexcept`, are `noexcept` automatically. This is one more reason for the rule of zero.
- Since C++17, `noexcept` is part of the function type: a `void (*)() noexcept` pointer cannot point to a potentially-throwing function.

### What it changes in the generated code

When a function with a local object that has a destructor calls another function that might throw, the compiler must emit a **landing pad**: code that runs the destructor and resumes unwinding, plus an entry in the exception table. If the callee is `noexcept`, none of that is needed. Here is GCC 13's output (`-O2`, stack protector off for clarity) for two functions that differ only in whether `send_order` is `noexcept`:

```asm
; void a() { Guard g; send_order(); }         send_order() may throw
_Z1av:
    push  rbx
    sub   rsp, 16
    call  _Z10send_orderv@PLT
    lea   rdi, 15[rsp]
    call  _ZN5GuardD1Ev@PLT                    ; normal path: destroy g
    add   rsp, 16
    pop   rbx
    ret
_Z1av.cold:                                    ; landing pad, in a separate section
    lea   rdi, 15[rsp]
    call  _ZN5GuardD1Ev@PLT                    ; destroy g while unwinding
    mov   rdi, rbx
    call  _Unwind_Resume@PLT                   ; ...and keep unwinding
; void b() { Guard g; send_order_nx(); }      send_order_nx() is noexcept
_Z1bv:
    sub   rsp, 24
    call  _Z13send_order_nxv@PLT
    lea   rdi, 15[rsp]
    call  _ZN5GuardD1Ev@PLT
    add   rsp, 24
    ret
```

The normal paths are nearly identical: table-based exceptions add no instructions to it, only a saved register here. The landing pad is placed in a `.cold` section so it does not pollute the instruction cache. So `noexcept` rarely speeds up the code it is written on; its main effects are smaller binaries and occasionally more freedom for the optimizer around calls. Do not sprinkle it everywhere for speed.

### Where noexcept really matters: library algorithms

`std::vector` growth must provide the **strong exception guarantee**: if `push_back` throws, the vector is unchanged. When it reallocates, it must relocate existing elements into the new buffer. If it *moved* them and a move threw halfway, the old buffer would already be partly gutted and could not be restored. So `std::vector` moves elements only if the move constructor is `noexcept` (or the type is not copyable); otherwise it copies them. The library uses `std::move_if_noexcept` for this. `std::deque`, `std::optional`, `std::variant` and `std::swap` make similar choices.

### Error handling without exceptions

- **Enumerated status codes** with `[[nodiscard]]` (Section 5.8) for operations that only succeed or fail.
- **`std::optional<T>`** (Section 8.8) when the only failure is "no result".
- **`std::expected<T, E>`** (C++23; GCC 13 provides it with `-std=c++23`), or a small equivalent in C++20: either a value or an error, with the error type chosen by you. It returns in registers when both are small and trivially copyable.
- **Fatal conditions** (failed startup, corrupted internal state) may still throw or terminate, off the hot path.

## Lambdas and std::function

### A lambda is a class

A lambda expression creates an object of a unique, unnamed **closure type** that the compiler generates: captured variables become data members, and the body becomes a `const` member function `operator()`. `[x, &y](int q) { return q + x + y; }` is equivalent to

```cpp
class __closure {
    int x;                                     // captured by value: a copy, made once
    int& y;                                    // captured by reference: an alias
public:
    __closure(int x_, int& y_) : x(x_), y(y_) {}
    int operator()(int q) const { return q + x + y; }
};
```

Everything about lambdas follows from that translation:

- **Size** is the size of the captures, laid out like struct members (Section 6.1). A captureless lambda is an empty class of size 1.
- **Every lambda expression has its own type**, even two identical ones. Code that takes a lambda as a template parameter is instantiated per lambda, which is what makes it inlinable (and what makes binary size grow, Section 9.7).
- **Capture by value happens when the closure is created,** not when it is called. `mutable` removes the `const` from `operator()` so the closure can change *its own* copies.
- **Capture by reference stores a reference.** If the closure outlives the variable, calling it is a use of a dangling reference. The same applies to `[this]`, which captures only the pointer: the object must outlive every copy of the closure (Section 11.4). C++17's `[*this]` captures a copy of the object; C++20 deprecates implicit capture of `this` through `[=]`.
- **Init-captures** (`[s = std::move(str)]`, C++14) create a member initialized by any expression, which is how you move a move-only object such as a `unique_ptr` into a closure.
- **Generic lambdas** (`[](auto a, auto b)`) have a template `operator()`. C++20 also allows an explicit template parameter list, `[]<class T>(const std::vector<T>& v) { ... }`, and lambdas in unevaluated contexts (Listing 8.7, line 33).
- **A captureless lambda converts to a function pointer**, which is how you pass one to a C API. A unary `+` forces the conversion.

It achieves this by **type erasure**: the object stores the callable somewhere and keeps pointers to functions, instantiated for the stored type, that know how to call, copy and destroy it. In libstdc++:

- `sizeof(std::function<...>)` is 32 bytes: 16 bytes of local storage plus two function pointers (a manager for copy/destroy and an invoker).
- A callable is stored **inline** only if it fits in 16 bytes, is suitably aligned, *and is trivially copyable*; anything else is **allocated on the heap** (Listing 7.8 and Problem P7.2). Copying a `std::function` copies the callable, which may allocate again.
- **Calling** goes through the invoker pointer: an indirect call that the compiler can almost never inline, plus a check for emptiness (calling an empty `std::function` throws `std::bad_function_call`).
- The callable must be **copyable**, so a lambda that owns a `unique_ptr` cannot be stored. C++23 adds `std::move_only_function`, and C++26 adds `std::function_ref`, a non-owning reference (Problem P8.9 builds one).

### Choosing a callback mechanism

| Mechanism | Call cost | Stores | Allocates | When |
|---|---|---|---|---|
| Template parameter (`template <class F> void f(F&& cb)`) | inlinable: often zero | the callable itself | never | The callee is a template or header code; the hot path |
| Function pointer | indirect call, no inlining | 8 bytes | never | C APIs; a fixed set of free functions |
| Non-owning function reference (two pointers) | indirect call | nothing (the caller keeps the callable) | never | Callbacks that are used during the call only |
| Fixed-capacity inline function (stores up to N bytes) | indirect call | the callable, inline | never; fails to compile if too big | Stored callbacks on the hot path |
| `std::function` | indirect call plus checks | the callable, maybe on the heap | if large or non-trivially-copyable | Configuration-time wiring, off the hot path |
| Virtual interface (Section 6.4) | indirect call | an object pointer | depends on the object | Open set of implementations |

Section 8.10 measures the call costs; Section 6.6 compares these with CRTP and `std::variant` as alternatives to virtual dispatch.

## Vocabulary Types (optional, variant, span, string_view)

C++17 and C++20 added small types that let interfaces say precisely what they mean without allocating. All four are cheap value types: copy them, pass them by value.

### std::optional<T>

An `optional<T>` holds either a `T` or nothing, **inline**: the storage for a `T` plus a `bool`, padded to `T`'s alignment (`optional<int>` is 8 bytes, `optional<double>` 16). It never allocates. It replaces sentinel values (−1, `nullptr`, `NaN`) and "bool return plus out-parameter" pairs.

- `has_value()`, `operator bool`, `value_or(default)`.
- `value()` throws `std::bad_optional_access` if empty; `operator*` and `operator->` do not check, and using them on an empty optional is undefined behaviour. In hot code, check once and then use `*`.
- `optional<T&>` is not allowed (until C++26); use `T*` for "maybe a reference".
- Returning `optional<T>` uses the return slot like any other class (Section 8.4); for small trivially copyable `T` it comes back in registers.

### std::variant<Ts...>

A `variant` holds exactly one of a fixed set of types: storage large enough for the largest alternative plus a small index (in the output of Listing 8.8, the 32-byte `Msg` holds a 24-byte `AddOrder` plus the index, padded). It never allocates. It is a type-safe tagged union and the natural representation of "one of these message kinds".

- `index()`, `std::holds_alternative<T>(v)`, `std::get<T>(v)` (throws `std::bad_variant_access` on a mismatch), `std::get_if<T>(&v)` (returns null instead).
- **`std::visit(f, v)`** calls the overload of `f` for the active alternative. Implementations dispatch through a jump table or an equivalent switch; with the *overloaded lambdas* idiom (Listing 8.8, line 18, plus C++20's aggregate deduction) a missing case is a compile error, which an `enum` switch only warns about.
- A variant can become *valueless by exception* if assigning a new alternative throws after the old one was destroyed; with nothrow-movable alternatives this does not happen in practice.
- Compared with virtual dispatch (Section 6.6), a variant is a closed set known at compile time, stored by value contiguously, with no heap allocation and no vtable pointer per object.

### std::span<T>

A `span` is a non-owning view of a contiguous sequence: a pointer and a length (16 bytes), or just a pointer when the extent is fixed at compile time (`span<int, 4>`, 8 bytes). One function taking `std::span<const T>` accepts a C array, a `std::array`, a `std::vector` or a sub-range of any of them, with no template and no copy, replacing the error-prone `(const T* p, size_t n)` pair. `first(n)`, `last(n)` and `subspan(offset, n)` create sub-views in O(1). Its `operator[]` is not bounds-checked in C++20.

### std::string_view

A `string_view` is a span of `const char` with string operations: a pointer and a length, 16 bytes, passed by value. `substr`, `remove_prefix` and `remove_suffix` are O(1) and never allocate, which makes it the natural type for parsing (Listing 8.8, lines 53–62, and the showdown below). Three properties need care:

- **It does not own its characters.** A view into a `std::string` that is destroyed or modified (any operation that may reallocate) dangles. Returning a `string_view` to a local or temporary string is the classic bug; Section 11.4 lists the shapes it takes. Use `string_view` for parameters and short-lived locals; store `std::string` (or fixed-size character arrays) in objects that outlive the call.
- **It is not null-terminated.** `sv.data()` passed to a C function expecting a C string reads past the end of the view. Print with `%.*s` (Listing 8.8, line 59) or convert explicitly.
- **Comparing and hashing** a view compares the characters, not the pointer.

## Interview Questions

**Q1. What does `std::move` do?**
Nothing at run time. It is a `static_cast` to an rvalue reference, which turns its argument into an xvalue so that overload resolution can choose a move constructor or move assignment. If no such overload is viable (no move constructor, or the argument is const), the copy is chosen; if the result is not used to initialize or assign anything, nothing happens at all.

**Q2. What is the difference between an lvalue, an xvalue and a prvalue? Give an example of each.**
An lvalue has identity and may not be stolen from (`x`, `v[i]`, `*p`); an xvalue has identity and may be stolen from (`std::move(x)`, a call to a function returning `T&&`); a prvalue has no identity and is a recipe for initializing an object (`42`, `x + 1`, `make()` returning by value). A named rvalue reference is an lvalue.

**Q3. Why should move constructors be `noexcept`?**
Containers that offer the strong exception guarantee, notably `std::vector` during reallocation, move elements only if the move cannot throw; otherwise they copy, which can turn an O(1)-per-element relocation into an allocation per element. The implicitly generated move constructor is `noexcept` when the members' moves are, which is one reason to follow the rule of zero.

**Q4. What is a forwarding reference, and what does `std::forward` do?**
A parameter of the form `T&&` where `T` is deduced by that function template. For an lvalue argument `T` deduces to `X&` and the parameter collapses to `X&`; for an rvalue, `T` is `X` and the parameter is `X&&`. Inside the function the parameter is an lvalue because it has a name; `std::forward<T>(p)` casts it back to the original category so that it can be passed on without unnecessary copies.

**Q5. When is copy elision guaranteed? When does `return x;` copy?**
Guaranteed since C++17 when initializing from a prvalue, including `return T{...};`. Returning a single named local is NRVO, permitted and done by GCC and Clang but not required; if not elided it is implicitly moved. Returning a global, member, reference, element, structured binding or a non-name expression such as `c ? a : b` copies. `return std::move(local)` prevents NRVO and costs a move.

**Q6. Should you write `return std::move(result);`?**
No, for a local or a by-value parameter: it disables NRVO and adds a move (GCC warns with `-Wpessimizing-move`). It is appropriate only for something that would otherwise be copied and that you are entitled to steal from, such as a data member in an rvalue-qualified member function.

**Q7. What does `noexcept` do if the function throws anyway? Does it make code faster?**
`std::terminate` is called, possibly without unwinding. It rarely speeds up the function itself, because table-based exceptions add no instructions to the normal path; it removes landing pads (smaller code) and, more importantly, lets library code choose faster algorithms through `noexcept` queries.

**Q8. How much does throwing an exception cost, and why?**
Microseconds rather than nanoseconds: allocating the exception object, a first unwinding pass that walks every frame's unwind information to find a handler, a second pass that runs destructors, and RTTI-based type matching, all in code and data that are cold in the caches. The normal path costs nothing. So exceptions are for rare, usually fatal conditions, not for expected outcomes on the hot path.

**Q9. What is a lambda, really? What is its size?**
An object of a unique compiler-generated class whose data members are the captures and whose `operator()` is the body. Its size is the size of its captures, laid out like a struct; a captureless lambda has size 1 and converts to a function pointer.

**Q10. What does `std::function` cost compared with a template parameter?**
32 bytes in libstdc++; possibly a heap allocation when constructed or copied (if the callable exceeds 16 bytes or is not trivially copyable); an indirect call that blocks inlining on every invocation. A template parameter costs nothing and is usually inlined. Use `std::function` to store callbacks configured at startup, not on the per-message path.

**Q11. When would you use `std::string_view`, and what is the danger?**
For read-only string parameters and for parsing: no allocation, O(1) substrings, and it accepts `std::string`, literals and buffers alike. It does not own the characters, so it dangles if the underlying string is destroyed or reallocated, and it is not null-terminated, so `data()` must not be passed to functions expecting a C string.

**Q12. `std::variant` versus a virtual base class: when do you choose which?**
Variant for a closed set of types known at compile time: values stored inline and contiguously, no allocation, no vptr, exhaustive handling checked by `visit`. Virtual functions for an open set (plugins, types added without recompiling the dispatcher) or very differently sized types. Section 6.6 compares the costs.

**Q13. What is RAII, and what happens to RAII objects when an exception is thrown?**
A resource is owned by an object whose destructor releases it. During unwinding, destructors of all fully constructed automatic objects between the `throw` and the matching `catch` run in reverse order of construction, so resources are released on every path. If no handler exists, `std::terminate` is called and unwinding may not happen. Destructors must not throw.

## Key Takeaways

- **Value categories:** lvalue (identity, not stealable), xvalue (identity, stealable), prvalue (no identity; since C++17 a recipe, not an object). A named rvalue reference is an lvalue. `decltype((e))` reveals the category.
- **Moves:** `std::move` is a cast and emits no code. A move steals resources and leaves a valid but unspecified source. Moving const objects copies; moving trivially copyable types and short strings copies bytes. Make moves `noexcept`. Use the by-value sink parameter for stored arguments.
- **Forwarding:** `T&&` with deduced `T` collapses to `X&` or `X&&`; `std::forward<T>` restores the category. Forward each argument once. `emplace_back` builds in place but does not turn lvalues into moves.
- **Elision:** returning or initializing from a prvalue never copies (C++17). NRVO of a single named local is near-universal but not guaranteed; otherwise locals and by-value parameters are implicitly moved. Globals, members, `c ? a : b`, structured bindings copy. Never `return std::move(local)`.
- **RAII:** every resource has one owning object, move-only, released in the destructor; destruction is in reverse order on every exit path. Destructors are `noexcept`. Scope guards express rollback.
- **Exceptions and noexcept:** the normal path costs nothing; a throw costs microseconds and grows with depth. `noexcept` violations call `std::terminate`. `noexcept` mostly matters because libraries check it (`vector` copies instead of moving otherwise). Use status codes, `optional` or an `expected`-like type on the hot path.
- **Lambdas:** a closure is a class; size = captures; capture by value happens at creation; references and `[this]` can dangle. Template parameters inline; function pointers and `std::function` make indirect calls; `std::function` may allocate (inline only ≤ 16 bytes and trivially copyable in libstdc++).
- **Vocabulary types:** `optional` (inline, no allocation, `*` unchecked), `variant` (closed set, inline, `visit` checks exhaustiveness), `span` and `string_view` (pointer + length, non-owning, pass by value, can dangle, `string_view` not null-terminated). Parse with `std::from_chars`.
