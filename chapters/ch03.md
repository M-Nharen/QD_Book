# DSA I: Foundations for Online Tests

The online assessment (OA) is the first filter in almost every QD process (Section 1.4): typically two to four problems in 60–120 minutes, an automated judge with hidden tests, a time limit per test and a memory limit. The problems are rarely exotic. They are drawn from a small set of patterns, and the candidates who fail usually fail for one of four reasons: they picked an algorithm that is too slow for the limits, they overflowed an integer, they read input too slowly, or they had an off-by-one error they could not find under time pressure. This chapter fixes all four.

Sections 3.1–3.2 are about the mechanics of the test: reading the constraints and writing C++ that is fast and safe by default. Sections 3.3–3.9 cover the patterns that solve most first-round problems: prefix sums and hashing, two pointers, binary search, stacks and monotonic structures, heaps, bits and greedy algorithms. Chapter 4 continues with trees, graphs, dynamic programming, range-query structures and strings. Because this is an HFT book, each section also says what the structure costs on real hardware; Section 3.10 is a worked example where the "obvious" complexity argument and the hardware disagree, and Section 3.11 measures the costs.

## Complexity and Reading the Constraints

### Big-O, precisely enough for an interview

f(n) = O(g(n)) means that for large enough n, f(n) ≤ c·g(n) for some constant c. It is an upper bound that hides constants and lower-order terms. Two consequences matter in practice. First, two O(n) algorithms can differ in speed by a factor of 50, as Section 3.10 shows. Second, Big-O describes growth, so it only predicts which algorithm wins once n is large enough; for small n the constant decides.

Say which case you mean. *Worst case* bounds the slowest input. *Average case* assumes a distribution of inputs (hash tables are O(1) on average and O(n) per operation in the worst case, which Section 3.3 exploits). *Amortized* bounds the total cost of a sequence of operations, which is different from both, and is covered below.

### From the input limits to the algorithm

The limits in the problem statement tell you which complexity the setter intended. Use a conservative planning figure of about 10^{8} "basic steps" per second of time limit. A tight loop of simple arithmetic on data in cache can run several times faster than that; a loop that misses the cache on every step, allocates memory or makes a function call through a pointer can be ten times slower. The figure is a rule of thumb for planning, not a property of any machine.

| Largest n | Target complexity | Typical technique |
|---|---|---|
| ≤ 10–11 | O(n!) or O(n!·n) | try all permutations (`std::next_permutation`) |
| ≤ 20–25 | O(2^{n}·n) | all subsets as bitmasks (3.8), bitmask DP (4.5) |
| ≤ 40 | O(2^{n/2}·n) | meet in the middle (Problem P3.13) |
| ≤ 100–500 | O(n^{3}) | interval DP, Floyd–Warshall (4.3) |
| ≤ 2000–5000 | O(n^{2}) | quadratic DP, all pairs |
| ≤ 10^{5}–10^{6} | O(n log n) or O(n log^{2} n) | sorting, binary search, heaps, segment trees (4.6) |
| ≤ 10^{7}–10^{8} | O(n), small constant | one pass, prefix sums, two pointers |
| ≥ 10^{9} | O(log n), O(√n) or O(1) | binary search on the answer, mathematics |

Use the table in both directions. If n ≤ 2×10^{5}, an O(n^{2}) solution performs about 4×10^{10} steps and will time out; the intended solution is O(n log n) or better. If n ≤ 18, the setter is telling you to enumerate subsets. Limits that look strangely small are hints.

Three details that cost marks:

- **"The sum of n over all test cases does not exceed 2×10^{5}."** This means each test is cheap, but you may have 10^{4} tests. Never clear a global array of size 10^{6} at the start of every test (10^{10} writes in total); clear only the first n entries.
- **Memory limits.** 256 MB holds 64×10^{6} `int`s or 32×10^{6} `long long`s, minus overhead. A 5000 × 5000 table of `long long` is 200 MB: probably too much. A node-based container uses far more memory per element than an array (Section 10.3).
- **Recursion depth.** The main thread's stack on Linux is typically 8 MiB. A recursive DFS on a path of 10^{6} vertices uses 10^{6} stack frames of perhaps 50–100 bytes each and will crash. Section 4.2 shows the iterative version.

### Amortized analysis

Some operations are occasionally expensive but cheap on average over any sequence. The standard example is `std::vector::push_back`. When the vector is full, it allocates a buffer larger by a constant factor (libstdc++ doubles it), moves every element, and frees the old buffer. Appending n elements copies at most 1 + 2 + 4 + … + n/2 + n < 2n elements in total during growth, so the *amortized* cost per `push_back` is O(1), even though a single call can cost O(n). The geometric growth is essential: growing by a fixed 1000 elements each time would cost O(n^{2}/1000) in total. (Section 10.1 covers the details, including iterator invalidation; in latency-sensitive code the occasional O(n) call is itself the problem, which is why `reserve` exists.)

The second amortized argument you need is the **pointer argument**: if each element can enter and leave a structure at most once, the total work is O(n) no matter how many times an inner `while` loop runs for a single element. It is how two pointers (3.4), monotonic stacks (3.6) and Section 3.10's sliding window are analysed. Say it out loud in interviews: "each index is pushed once and popped at most once, so the nested loop is O(n) in total."

### Overflow discipline

Integer overflow is the most common cause of a "wrong answer" on hidden tests that you cannot reproduce on the samples, because samples are small. The rules:

- **`int` holds about ±2.147×10^{9}.** The product of two values up to 10^{5} is 10^{10}: overflow. A sum of 2×10^{5} values up to 10^{9} is 2×10^{14}: overflow. When in doubt use `long long`, which holds about ±9.22×10^{18}.
- **The type of an expression is decided by its operands, not by where the result goes.** `long long x = a * b;` with `int a, b` multiplies in `int` and overflows *before* the conversion. Write `1LL * a * b`. Likewise `1 << 40` is an `int` shift by more than the width, which is undefined; write `1LL << 40`.
- **Signed overflow is undefined behaviour, not wrap-around.** The optimizer assumes it never happens, so an overflow can produce results that look impossible (Section 11.2). Unsigned arithmetic wraps modulo 2^{n} by definition.
- **`size()` is unsigned.** `for (int i = 0; i < v.size() - 1; ++i)` with an empty `v` computes `0 - 1` in `size_t`, which is 18,446,744,073,709,551,615. Cast first (`int(v.size()) - 1`) or rewrite as `i + 1 < v.size()`. Comparing a negative `int` with an unsigned value converts the `int` to a huge unsigned number; `-Wall -Wextra` warns about this (`-Wsign-compare`). Section 5.6 explains the promotion rules.
- **Midpoints.** `(lo + hi) / 2` overflows when both are large; write `lo + (hi - lo) / 2` (C++20 also offers `std::midpoint`).
- **Modular arithmetic.** With the usual modulus 10^{9} + 7, reduce after every multiplication: `(a * b) % MOD` needs `a` and `b` below 2^{31.5} ≈ 3×10^{9}, which holds if both are already reduced. In C++ the remainder takes the sign of the dividend (`-7 % 3 == -1`), so normalize subtraction results with `((x % MOD) + MOD) % MOD`.
- **Floating point for integer questions.** `(long long)sqrt(x)` can be off by one for x near 10^{18}, because a `double` has 53 bits of mantissa: Listing 3.4 shows `sqrt` of 10^{18} − 1 rounding up to exactly 10^{9}. Use integer binary search or correct the result with a check. Section 5.7 covers floating point in depth.

## Arrays, Prefix Sums, Difference Arrays and Hashing

### Prefix sums

For an array a_{0..n−1}, define P_{0} = 0 and P_{i+1} = P_{i} + a_{i}. Then the sum of a_{l..r} (inclusive) is P_{r+1} − P_{l}: O(n) preprocessing, O(1) per query. The off-by-one is avoided by giving P one more element than a, so that P_{i} is "the sum of the first i elements".

In two dimensions, with P_{i,j} the sum of the rectangle of rows < i and columns < j:

P_{i+1,j+1} = a_{i,j} + P_{i,j+1} + P_{i+1,j} − P_{i,j}, and the sum over rows r_{1}..r_{2}, columns c_{1}..c_{2} is P_{r2+1,c2+1} − P_{r1,c2+1} − P_{r2+1,c1} + P_{r1,c1}.

The same idea works for any operation with an inverse: prefix XOR (XOR is its own inverse), prefix products modulo a prime (using modular inverses), or prefix counts of each letter for "how many 'a's in s[l..r]". It does not work for minimum or maximum, which have no inverse; those need a sparse table, a monotonic structure (3.6, 3.10) or a segment tree (4.6).

**Subarray sums with a hash map.** The number of subarrays with sum exactly k equals the number of pairs i < j with P_{j} − P_{i} = k. Sweep j, keep a count of every prefix sum seen so far, and add the count of P_{j} − k. Initialize the count of P = 0 to 1 (the empty prefix). This works with negative numbers, unlike the two-pointer method of Section 3.4, and is Problem P3.3. Replacing "= k" by "divisible by m" means counting equal prefix sums modulo m.

**Kadane's algorithm**, from Listing 3.1, is the maximum-sum version: the best subarray ending at j is max(a_{j}, best ending at j − 1 + a_{j}); equivalently P_{j+1} − (minimum earlier prefix).

### Difference arrays

The inverse of a prefix sum. To add v to every element in a_{l..r} for many updates and read the array only at the end, set d_{l} += v and d_{r+1} −= v; the final array is the prefix sum of d. Each update is O(1) instead of O(r − l + 1). The same trick in two dimensions adds to a rectangle with four corner updates. It is the standard solution to "flights booked on a range of days" or "how many intervals cover each point" (sweep line), and Problem P3.2 practises it. If reads and updates interleave, you need a Fenwick tree (Section 4.6).

### Hashing: what `std::unordered_map` really does

`std::unordered_map<K, V>` in libstdc++ is a **separately chained** hash table: an array of buckets, each pointing into a singly linked list of heap-allocated nodes holding (key, value) pairs. A lookup computes `hash(key)`, reduces it to a bucket index with `hash % bucket_count`, then follows pointers through that bucket's nodes comparing keys. When the number of elements exceeds `max_load_factor() × bucket_count()` (default 1.0) the table rehashes into a larger prime number of buckets.

The low-level consequences:

- **Every insert allocates a node** (Section 7.2 explains what `malloc` costs) and every lookup chases at least one pointer to a node that can be anywhere in memory. For a table larger than the caches, expect one to two cache misses per lookup.
- **The bucket index is a remainder by a run-time prime**, which needs an integer division instruction. Section 3.11 measures what that costs on this machine.
- **`std::hash` for integers is the identity function** in libstdc++. That is fast and fine for random keys, and terrible for keys with structure.

### Anti-hash tests

Because the hash is the identity and the bucket count follows a fixed, public sequence of primes, an adversary who knows the implementation can choose keys that are all multiples of the final bucket count B. Every key then lands in bucket 0, every insert walks the whole chain to check for a duplicate, and n inserts cost O(n^{2}). Contest problem setters and "hackers" on Codeforces do exactly this; an OA's hidden tests can include it. Listing 3.3 performs the attack.

Mixing the key is cheap insurance.

### Coordinate compression

When values are large (up to 10^{9}) but there are only n of them, and only their *order* matters, replace each value by its rank: copy, `sort`, `unique`, `erase`, then `lower_bound` each value. The ranks 0..n−1 can index plain arrays, Fenwick trees (4.6) and so on. It costs O(n log n) once and turns hash-map lookups into array indexing, which is 10–20 times cheaper (Section 3.11).

## Two Pointers and Sliding Window

### When it applies

Two pointers is a way of enumerating pairs (l, r) in O(n) instead of O(n^{2}), and it is valid when there is **monotonicity**: moving one pointer in its direction never requires moving the other one back. Two common forms:

- **Opposite ends of a sorted array.** For "find a pair with sum s": if a_{l} + a_{r} < s, then a_{l} pairs with nothing at or left of r that reaches s, so discard l; if it is greater, discard r. Each step discards one element: O(n). 3Sum is a loop over the first element plus this inner two-pointer search: O(n^{2}).
- **A window [l, r] that slides right.** If a window is "valid" whenever a larger window containing it is valid (or vice versa), then for each r the best l only moves right.

### The window templates

**Longest valid window**, for properties that survive shrinking (at most k distinct values, sum at most S with non-negative numbers, no repeated character):

```cpp
for (int l = 0, r = 0; r < n; ++r) {
    add(a[r]);                         // extend to the right
    while (!valid()) remove(a[l++]);   // shrink until valid again
    best = max(best, r - l + 1);       // [l, r] is the longest valid window ending at r
}
```

**Shortest valid window**, for properties that survive growing (sum at least S with non-negative numbers, contains all required characters): extend r; *while* the window is valid, record its length and shrink from the left.

**Counting windows.** The number of subarrays with at most k distinct values is Σ_{r} (r − l + 1) using the first template. "Exactly k" is then atMost(k) − atMost(k − 1): a transformation worth remembering because "exactly" windows are not monotone, but "at most" windows are.

**Why both loops together are O(n):** l and r each move right at most n times in total, so `add` and `remove` are called at most n times each. This is the pointer argument of Section 3.1.

### When it fails

With negative numbers, "sum at least S" is no longer monotone: shrinking a window can increase its sum. Use prefix sums instead: for "sum exactly k", the hash map of Section 3.3; for "shortest subarray with sum at least k", a monotonic deque over prefix sums (Problem P3.12). Recognizing that the window property is not monotone, and saying so, is what the interviewer is checking when they add negative numbers to a familiar problem.

Two-pointer loops also have excellent hardware behaviour: both pointers stream forward through memory, which the hardware prefetcher detects, so they rarely wait for memory (Section 12.2).

## Binary Search and Binary Search on the Answer

### One invariant instead of many templates

Most binary search bugs come from mixing conventions: `lo <= hi` versus `lo < hi`, `hi = mid` versus `hi = mid - 1`, and which one to return. Avoid them all with a single formulation: **find the first x for which a monotone predicate is true.** Keep two variables with an invariant that holds from start to finish:

- `pred(lo)` is false (or lo is a virtual position before the range),
- `pred(hi)` is true (or hi is a virtual position after the range),

and shrink the gap until hi = lo + 1. Then hi is the first true position. Because lo and hi are never both moved past the boundary, there is no case analysis.

### Recognizing "binary search on the answer"

The pattern appears whenever a question asks for the minimum (or maximum) value such that something is possible, and checking possibility for a fixed value is easier than optimizing directly: minimize the largest part when splitting an array (Problem P3.7), minimum eating speed (P3.4), maximize the minimum distance when placing k items on positions, the k-th smallest value in a sorted matrix (count how many are ≤ x). The total cost is O(check × log(range)). For a range of 10^{18}, that is 60 iterations.

### What a binary search costs on hardware

Binary search does O(log n) comparisons, but two hardware effects decide its speed:

- **Each comparison is an unpredictable branch.** Whether the target lies left or right of the midpoint is a coin flip, so the branch predictor is wrong about half the time, and each misprediction discards 15–20 cycles of speculative work on a modern x86-64 core (Section 12.5). A branch-free version computes the next position arithmetically from the comparison result, which the compiler can turn into a conditional move (`cmov`).
- **The probes jump through memory.** The first few probes touch the same few cache lines on every search and stay in cache; for an array larger than the cache, each of the last log_{2}(n) − log_{2}(cache-resident elements) probes is a cache miss.

Section 3.11 measures both: on this machine the branch-free search is about five times faster for small arrays, and slightly *slower* for arrays much larger than the cache, for a reason explained there.

## Stacks, Queues, Monotonic Stack and Deque

### The containers

`std::stack` and `std::queue` are *adaptors*: thin interfaces over another container, `std::deque` by default. For a stack, a `std::vector` with `push_back`/`pop_back`/`back` is simpler and faster: one contiguous buffer. libstdc++'s `std::deque` is a map (an array of pointers) to fixed-size blocks of 512 bytes, so it can grow at both ends without moving elements; the price is an extra indirection on every access and an allocation every 512 bytes (Section 10.2). In latency-critical code a fixed-capacity ring buffer replaces both, as Section 3.10 shows and Section 14.5 builds on.

Classic uses that interviewers still ask: matching brackets (push openers, pop on closers), evaluating expressions (two stacks, or convert to postfix), undo histories, a queue from two stacks (push onto `in`; pop from `out`, refilling `out` from `in` only when `out` is empty: each element moves at most twice, so O(1) amortized), and a min-stack (store the running minimum alongside each element).

### The monotonic stack

A monotonic stack keeps indices whose values are sorted. It answers "for every element, what is the nearest element to the left (or right) that is greater (or smaller)?" in O(n) total. The key insight: when a new element a_{i} arrives, every element on the stack that is smaller than a_{i} has found its next greater element (it is a_{i}), and none of them can ever be the answer for anything to the right of i, because a_{i} is both closer and larger. ### The monotonic deque

When the window has a left edge that moves, elements must also leave from the front once they are out of range: a **monotonic deque**. It gives the maximum (or minimum) of every window of size k in O(n) total and is the subject of Section 3.10. It also optimizes DP recurrences of the form f(i) = max_{i−k ≤ j < i} (f(j)) + cost(i), and combined with prefix sums it solves Problem P3.12.

## Heaps and Priority Queues

### The array representation

A binary heap is a complete binary tree stored in an array with no pointers: the children of index i are 2i + 1 and 2i + 2, and its parent is (i − 1)/2. In a **min-heap** every parent is at most its children, so the minimum is at index 0. Two primitive operations restore the order after a change:

- **sift-up:** while an element is smaller than its parent, swap them. Used by `push` (append, then sift up). O(log n).
- **sift-down:** while an element is larger than its smaller child, swap with that child. Used by `pop` (move the last element to the root, then sift down). O(log n).

### Bottom-up heapify is O(n)

There are two ways to turn an array of n elements into a heap. Pushing the elements one at a time costs O(n log n): in the worst case (line 49's descending input, for a min-heap) every new element is the smallest so far and sifts up to the root. Floyd's **bottom-up** method (lines 41–44) instead calls sift-down on every non-leaf node, from the last parent back to the root.

Why is this O(n)? A sift-down from a node moves at most its *height* (the distance to the deepest leaf below it). In a heap, half the nodes are leaves (height 0), a quarter have height 1, an eighth height 2, and so on: at most ⌈n/2^{h+1}⌉ nodes have height h. The total work is at most

Σ_{h≥0} (n/2^{h+1})·h = (n/2)·Σ_{h} h/2^{h} = (n/2)·2 = n.

So most of the work is done by the many nodes near the bottom, each of which moves very little; the few nodes near the top move far, but there are few of them. In fact the sum of the heights of all nodes in an n-node heap is exactly n − popcount(n), where popcount counts the 1 bits in n (Problem P3.14). The output confirms it: descending input needs exactly n − popcount(n) swaps for n = 2^{20} − 1, against 18.9 million swaps for repeated insertion, and the time ratio follows. This is why `std::make_heap` is specified to use at most 3n comparisons, and why `std::priority_queue`'s constructor from a range is faster than n pushes.

Note the asymmetry: building is O(n), but *extracting* all elements in order is still Θ(n log n) (that is heapsort), because comparison sorting needs n log n comparisons.

### `std::priority_queue` in practice

- It is a **max-heap** by default (`std::less`). For a min-heap: `std::priority_queue<T, std::vector<T>, std::greater<T>>`. For pairs, the comparison is lexicographic, so `{distance, vertex}` pairs order by distance.
- `top()` is O(1), `push` and `pop` O(log n). There is no `decrease-key` and no way to delete an arbitrary element. The standard workaround is **lazy deletion**: push a new entry with the new priority and, when popping, skip entries that are out of date. Dijkstra's algorithm in Section 4.3 is written this way. A "stale" check needs some way to know an entry is old: compare with the current best distance, or keep a version number.
- The heap functions `std::make_heap`, `std::push_heap`, `std::pop_heap` work on any random-access range when you need access to the underlying array.

### Patterns

- **Top k of a stream.** Keep a *min*-heap of size k holding the k largest seen so far; a new element replaces the root if it is larger. O(n log k) time and O(k) memory, and it works on a stream that does not fit in memory. If all data is in memory and you only need the k-th element, `std::nth_element` (introselect: quickselect with a fallback) is O(n) on average.
- **Running median.** A max-heap holds the lower half and a min-heap the upper half, rebalanced so their sizes differ by at most one. Each insert is O(log n) and the median is read from the tops (Problem P3.9).
- **k-way merge.** Merge k sorted lists by keeping one candidate per list in a min-heap: O(N log k) for N elements in total.
- **Greedy with a heap.** "Repeatedly take the best available option" is a heap: merging ropes or Huffman coding (Problem P3.10), scheduling with deadlines, meeting rooms (a min-heap of end times).

### Heaps and the cache

The top levels of a heap stay in cache because every operation touches them. Further down, sift-down jumps from i to 2i + 1: the children of a node are adjacent, but each level is a new cache line, so on a heap much larger than the cache each `pop` costs about one cache miss per level below the cached part. Section 3.11 measures about 180 ns for a push plus a pop on a heap of 10^{6} `int`s. A **4-ary heap** (children 4i + 1 to 4i + 4) halves the depth, and its four children usually share one 64-byte cache line (Section 12.2); it does more comparisons per level but fewer cache misses, and is often faster for large heaps. (Section 18.1 discusses why a heap is usually *not* the right structure for an order book's price levels.)

### Subsets as integers

A subset of {0, …, n − 1} is an n-bit mask. Lines 26–33 show the two loops you need. Iterating `mask` from 0 to 2^{n} − 1 visits every subset (O(2^{n})). The inner loop `s = (s - 1) & mask` visits every *submask* of `mask`, in decreasing order: subtracting 1 clears the lowest set bit and sets all bits below it, and `& mask` keeps only bits that belong to the mask. Over all masks, the total number of (mask, submask) pairs is 3^{n}, because each element is independently in neither, in the mask only, or in both. The output confirms 3^{10} = 59,049. That is the cost of a subset-over-subsets DP, and it is why such DPs stop at about n = 15–16 (3^{16} ≈ 4.3×10^{7}).

`std::bitset<N>` packs N bits into 64-bit words and performs `&`, `|`, `^`, shifts and `count()` a word at a time. It speeds up some O(n^{2}) or O(n^{3}) algorithms by a factor of about 64 (reachability, subset-sum feasibility with `dp |= dp << w`).

### XOR tricks

XOR is associative, commutative, has identity 0 and is its own inverse (x ^ x = 0). Hence: the element that appears an odd number of times among pairs is the XOR of everything (line 40); the XOR of a subarray is a difference of prefix XORs; swapping two values with XOR works but is slower and less clear than `std::swap`, so do not use it. When elements appear three times except one, count each bit position modulo 3 (Problem P3.5).

### Shifts and undefined behaviour

- Shifting by a negative amount or by at least the width of the (promoted) type is **undefined** in C++, even in C++20: `1u << 32` is undefined, and on x86 the hardware masks the count to 5 or 6 bits, so it typically produces 1, not 0.
- Since C++20, left-shifting a *signed* value is defined as the corresponding two's complement result (`1 << 31 == INT_MIN`), and right-shifting a negative value is an arithmetic shift. Before C++20 both were undefined or implementation-defined, and much existing code and many interviewers still treat them as unsafe. Use unsigned types for bit manipulation and you never need to think about it.
- `1 << k` is an `int`. For k ≥ 31 write `1ULL << k`.

### What the hardware does

Bit operations are among the cheapest instructions: AND, OR, XOR, shifts and additions take about one cycle each, and a modern core can execute three or four of them per cycle. `popcnt` takes about three cycles of latency with a throughput of one per cycle on recent Intel cores. **But only if the compiler is allowed to use it.** The default x86-64 target dates from 2003 and predates `popcnt`. Without `-mpopcnt` (or `-march=x86-64-v2` or higher, or `-march=native`), GCC 13 compiles `std::popcount` on a 64-bit value to a call to the library function `__popcountdi2`, a sequence of shifts and masks. In a contest, `#pragma GCC target("popcnt")` at the top of the file is the common workaround. In production you choose the target architecture deliberately, at build time, for the machines you deploy on (Section 16.1).

Bit-level packing also appears in low-latency systems: several boolean flags in one byte, side and order-type in a few bits of a message field, or bitmaps of which price levels in a range are non-empty (a `countr_zero` then finds the next non-empty level in one instruction; Section 18.1 uses this idea).

## Greedy Algorithms and Exchange Arguments

A greedy algorithm builds a solution by repeatedly making the choice that looks best right now and never revisiting it. Greedy algorithms are short and fast, and often wrong. In an interview, a greedy answer without a proof is a guess, and interviewers know it. The standard proof technique is the **exchange argument**.

### The exchange argument

1. Let G be the greedy solution and O an optimal solution. If they are equal, done.
2. Find the first place where they differ: greedy chose g, the optimum chose o.
3. Show that you can *exchange* o for g in O without making it worse, producing an optimal solution O′ that agrees with G for one more step.
4. Repeat: some optimal solution agrees with G everywhere, so G is optimal.

**Worked example: interval scheduling.** Choose the maximum number of pairwise non-overlapping intervals. Greedy: sort by *end time*; repeatedly take the interval that ends first among those compatible with what you have taken. Proof: let g be the greedy first choice (earliest end) and o the first interval of an optimal solution O. Since g ends no later than o, replacing o by g in O cannot create an overlap with O's later intervals (they start after o ends, hence after g ends). O′ is still feasible and has the same size. Apply the same argument to the remaining subproblem. Sorting by start time or by length both fail; find the counterexamples (one long interval that starts first; a short interval that overlaps two otherwise compatible ones). Problem P3.11 is the "dual" version: the minimum number of points that stab all intervals equals the maximum number of disjoint intervals, and the same sort finds both.

### Classic greedy results

| Problem | Greedy rule | Why it works |
|---|---|---|
| Interval scheduling | earliest end time | exchange argument above |
| Minimum meeting rooms | sort by start; reuse the room that frees earliest (min-heap of ends) | rooms needed = maximum overlap at a point |
| Fractional knapsack | highest value per weight first | exchange a unit of a worse item for a better one |
| Merging ropes / Huffman coding | merge the two smallest | the two smallest can be the deepest siblings in an optimal tree |
| Minimize maximum lateness | earliest deadline first | swapping an adjacent inverted pair never increases lateness |
| Jump game ("can you reach the end?") | track the farthest reachable index | any index before the frontier is reachable |
| Coin change with 1, 2, 5, 10, … | largest coin first | true for canonical coin systems only |

### When greedy fails, and how to find out

Greedy coin change fails for coins {1, 3, 4} and amount 6: greedy takes 4 + 1 + 1 (three coins), the optimum is 3 + 3. The 0/1 knapsack (items cannot be split) is not greedy-solvable at all; it needs dynamic programming (Section 4.5). The practical test in an OA is the stress test of Listing 3.2: implement the greedy and an exhaustive search for n ≤ 8, compare on random inputs, and you will usually find a counterexample within seconds if one exists. This is exactly how the greedy answers in this chapter's solutions were checked.

A useful signal: if the problem's constraints are small (n ≤ 100) and the greedy is O(n log n), the setter may be inviting a greedy that does not work; if n is 10^{5} or more and you cannot see a DP that fits, the intended solution is probably greedy or a data structure.

### What the measurements say

Three lessons, each of which interviewers probe:

1. **Asymptotics win eventually, and decisively.** At k = 1024 the O(n) algorithm is about 70 times faster than the O(nk) one.
2. **For small inputs, the constant factor and the hardware decide.** At k = 8 the "slow" scan, a loop of conditional moves over 8 adjacent integers, is faster than both the tree and the deque. Before reaching for a sophisticated structure, ask how large the input actually is.
3. **The deque's remaining cost is mostly branch mispredictions.** Whether the new price pops zero, one or several elements is random for a random walk, so the `while` on line 48 is unpredictable. The last output line runs the identical ring-buffer code on a steadily rising series, where line 48 always pops exactly one element and line 47 never fires: the branches become predictable and the cost falls from about 10 ns to about 3.5 ns per price. The difference, roughly 7 ns or 15 cycles at this clock speed, is the size of one misprediction (Section 12.5). The algorithm is unchanged; only the predictability of its branches differs.

**Binary search (part 1).** For a 4 KiB array (n = 2^{10}), everything is in L1 cache, yet `std::lower_bound` costs about 65 ns per search: ten levels, about half of them mispredicted at roughly 15 cycles each. libstdc++'s implementation compiles to a conditional jump. As n grows past the L2 cache (about 2 MiB here), both versions slow down because the last levels miss in cache. For arrays far larger than the cache, the branchy version catches up and even wins. The reason is speculation: the branchy search *guesses* the direction and starts loading the next probe before the current comparison resolves, and half the time the guess is right, so two cache misses overlap. In the branch-free version each probe's address depends on the previous load's value, so the misses are strictly serialized. Production searches over large sorted data fix this with software prefetching of both possible next probes, or with a cache-friendlier layout such as the Eytzinger (BFS-order) array. Khuong and Morin's paper "Array Layouts for Comparison-Based Searching" studies these trade-offs in detail.

**Lookups among 10^{6} keys (part 2).** A well-sized `unordered_map` costs about 35–40 ns per hit here, roughly one or two cache misses into its bucket array and node. A binary search over a sorted `vector` of the same keys costs about 210 ns: 20 levels, mispredictions near the top, cache misses near the bottom. A plain array indexed directly costs about 2 ns. If the keys can be made dense (coordinate compression, Section 3.3; order IDs assigned by your own system), an array is an order of magnitude better than any map.

**A heap of 10^{6} elements (part 3).** One push plus one pop costs about 180 ns: two traversals of a 20-level path, with unpredictable comparisons and cache misses in the lower levels. That is cheap compared with network latency but expensive compared with an L1 hit, which is why heaps are used sparingly on hot paths.

**Division (part 4).** Each step of the loop on lines 79–85 depends on the previous result, so it measures latency. With a constant divisor the compiler replaces division by a multiplication with a precomputed reciprocal and shifts; with a run-time divisor it emits a `div` instruction. On this CPU the two cost the same, about 14 cycles: recent Intel and AMD cores divide 64-bit integers in roughly 10–20 cycles. On older cores, such as Intel's Skylake generation, 64-bit division took several tens of cycles, and the constant-divisor trick (and hash tables with power-of-two sizes, which use a mask instead of a remainder) mattered much more. Always check on the hardware you deploy on.

## Interview Questions

**Q1. The constraints say n ≤ 2×10^{5} and the time limit is 1 second. Which complexities are acceptable?**
O(n log n) is about 3.6×10^{6} basic steps: comfortable. O(n log^{2} n) is about 6×10^{7}: fine. O(n√n) is about 9×10^{7}: risky with a large constant. O(n^{2}) is 4×10^{10}: too slow. I would aim for O(n log n) and check that I am using `long long` wherever sums or products can exceed 2×10^{9}.

**Q2. Your solution uses `unordered_map` and passes locally but times out on one hidden test. What happened?**
Probably an anti-hash test: libstdc++ hashes integers with the identity function and reduces with a fixed sequence of prime bucket counts, so keys that are multiples of the final bucket count all land in one bucket and inserts become O(n). Fix it with a randomized mixing hash such as SplitMix64 seeded from the clock, or avoid hashing with sorting plus binary search, or with coordinate compression and an array. (A second possibility: rehashing; calling `reserve(n)` first removes it.)

**Q3. Explain why `vector::push_back` is O(1) amortized. Why can't the vector grow by a fixed amount?**
When full, the vector allocates a buffer a constant factor larger and moves the elements. Over n pushes, the moves total at most n + n/2 + n/4 + … < 2n, so the cost per push is O(1) amortized. Growing by a fixed c elements makes the total n^{2}/(2c): quadratic. The amortized bound says nothing about a single push, which can be O(n); latency-sensitive code calls `reserve` up front.

**Q4. This binary search sometimes loops forever. Why, and how do you write it so it can't?**
The usual cause: `while (lo < hi) { mid = (lo + hi) / 2; if (ok(mid)) hi = mid; else lo = mid; }`. When hi = lo + 1, mid = lo, and `lo = mid` makes no progress. I keep an invariant instead: `pred(lo)` is false and `pred(hi)` is true; loop while `hi - lo > 1`; `mid = lo + (hi - lo) / 2` is strictly between them; assign `mid` to whichever side matches `pred(mid)`. The loop always shrinks and ends with hi the first true position.

**Q5. Find the k-th largest element of an unsorted array of n numbers. Compare the options.**
Sorting: O(n log n). A min-heap of size k: O(n log k) time, O(k) memory, works on a stream. Quickselect (`std::nth_element`): O(n) on average, O(n^{2}) worst case for plain quickselect (libstdc++'s introselect falls back to a guaranteed method), and it reorders the input. Median-of-medians gives O(n) worst case with a large constant. For a stream or large n with small k, the heap; for an in-memory array, `nth_element`.

**Q6. Describe an O(n) algorithm for the maximum of every window of size k. Why is it O(n) when there is a loop inside a loop?**
A deque of indices with decreasing values. For each new element, pop from the back every index whose value is ≤ the new one (they can never be a maximum again), push the new index, pop the front if it has left the window, and report the front. Each index is pushed once and popped at most once, so the inner loop's total work over the whole run is at most n.

**Q7. Is building a heap from n elements O(n log n)?**
Not with the bottom-up method. Sift-down from a node costs at most its height; half the nodes have height 0, a quarter height 1, and so on, so the total is at most Σ h·n/2^{h+1} = n. Inserting elements one by one is O(n log n) in the worst case. Extracting all elements in sorted order is Θ(n log n) either way.

**Q8. How do you check whether x is a power of two? Count its set bits? Find its lowest set bit?**
`x != 0 && (x & (x - 1)) == 0`, or `std::has_single_bit(x)` in C++20. Count bits with `std::popcount`, which compiles to one `popcnt` instruction if the target allows it (otherwise a library call); or loop `x &= x - 1` once per set bit. The lowest set bit is `x & -x` (as a value) or `std::countr_zero(x)` (as an index). I would use unsigned types to avoid sign issues.

**Q9. Prove that sorting intervals by end time gives the maximum number of non-overlapping intervals.**
Exchange argument. Let g be the interval with the earliest end and O any optimal solution with first interval o. g ends no later than o, so replacing o by g keeps O feasible (every later interval in O starts after o ends) and the same size. Now some optimal solution starts with g; recurse on the intervals that start after g ends.

**Q10. When can an O(n log n) or O(n) algorithm be slower than an O(n^{2}) one?**
When n is small enough that constants dominate: allocation, pointer chasing, cache misses and branch mispredictions cost far more than simple arithmetic on contiguous data. In my rolling-maximum measurements, a naive O(nk) scan beat both a `multiset` and a monotonic deque at k = 8, because the scan is a branch-free loop over adjacent integers while the deque has an unpredictable branch per element. So I would check the real size of the input before optimizing, and measure.

**Q11. A hot path needs to look up a few thousand instrument IDs per message. Hash map, sorted vector or something else?**
First ask whether the IDs can be mapped to small dense integers once, at start-up or subscription time; then the lookup is an array index, a couple of nanoseconds. If not, a few thousand keys fit in L1 or L2, so a branch-free binary search over a sorted array of keys is a few tens of nanoseconds and has no allocation, while a node-based `unordered_map` costs a pointer chase per lookup. An open-addressing table with a good hash (Section 10.5) is the general answer for larger key sets. Whatever is chosen, measure it on the real distribution of keys.

**Q12. Your greedy passes all samples. How do you gain confidence before submitting?**
Try to prove it with an exchange argument. In parallel, write an exhaustive search for tiny inputs and stress-test the greedy against it on thousands of random cases. If the stress test finds a counterexample, the problem needs DP or a different greedy criterion.

## Key Takeaways

- **Read the limits first.** About 10^{8} simple steps per second is a planning figure. n ≤ 20 → subsets; n ≤ 5000 → O(n^{2}); n ≤ 2×10^{5} → O(n log n); n ≤ 10^{18} → logarithmic or math. "Sum of n over tests" means: clear only what you used.
- **Amortized arguments:** geometric growth makes `push_back` O(1) amortized; "each element enters and leaves once" makes nested two-pointer and monotonic-stack loops O(n).
- **OA C++:** fast I/O (`sync_with_stdio(false)`, `cin.tie(nullptr)`, `'\n'`, or an `fread` parser); `long long` and `1LL *` wherever values can exceed 2×10^{9}; sentinels outside the answer range; no `size() - 1` on unsigned; reduce modulo after every multiply; `-fsanitize=address,undefined` and `-D_GLIBCXX_DEBUG` locally; a brute-force stress test when stuck.
- **Prefix sums** give O(1) range sums; a hash map of prefix sums counts subarrays with a given sum (negatives allowed); **difference arrays** give O(1) range updates read at the end.
- **`unordered_map`** is chained, node-based and identity-hashed for integers in libstdc++: one allocation per insert, pointer chases per lookup, and vulnerable to anti-hash tests. Use a randomized SplitMix64 hash, sorting, coordinate compression, or an array.
- **Two pointers / windows** need monotonicity. "Exactly k" = atMost(k) − atMost(k − 1). With negative numbers, switch to prefix sums.
- **Binary search** as "first true" with the invariant `!pred(lo) && pred(hi)` and loop `while (hi - lo > 1)`. Binary search on the answer when feasibility is monotone. Branch mispredictions dominate small searches; a branch-free version can be 5× faster; for huge arrays, cache misses dominate.
- **Monotonic stack:** nearest greater/smaller element, histogram rectangle, contribution counting (strict on one side, non-strict on the other). **Monotonic deque:** window maxima in O(n).
- **Heaps:** array layout, sift-up/sift-down, bottom-up build in O(n) (sum of heights = n − popcount(n)), `priority_queue` is a max-heap, no decrease-key (lazy deletion), top-k with a size-k min-heap, two heaps for the median.
- **Bits:** `x & (x - 1)`, `x & -x`, submask enumeration totals 3^{n}, XOR cancels pairs; use unsigned types and `<bit>`; `popcount` is one instruction only if the target architecture allows it; shifting by ≥ the width is UB.
- **Greedy** needs a proof (exchange argument) or at least a stress test against brute force. Earliest end time for interval scheduling; two smallest for Huffman; it fails for 0/1 knapsack and non-canonical coins.
- **Hardware:** in the rolling-maximum showdown, O(n) beat O(nk) by 70× at k = 1024, but the naive scan won at k = 8, and branch mispredictions accounted for about two thirds of the O(n) version's cost.
