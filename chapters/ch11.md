# Undefined Behaviour and the Optimizer

Undefined behaviour (UB) is the single C++ topic most likely to separate a candidate who has *used* C++ from one who *understands* it. Interviewers at trading firms ask about it constantly, for a practical reason: low-latency code is full of the patterns that produce it (casting network buffers to structs, hand-rolled integer arithmetic on prices and quantities, lock-free flags, aggressive reuse of memory), and it is compiled with optimization levels at which UB stops being a theoretical concern. A bug of this kind can pass every test at `-O0`, pass most tests at `-O2`, and then change behaviour when an unrelated edit changes what the compiler inlines.

This chapter builds the right mental model first (11.1), then walks through the classic forms of UB (11.2), strict aliasing and type punning (11.3) and lifetime bugs (11.4). Section 11.5 reads the assembly that g++ 13 actually produces for UB-adjacent code, so you can see the optimizer use each rule. Section 11.6 is about detection: which tool catches which kind of UB, and which kinds no tool catches. The code showdown (11.7) rewrites a buffer-casting message decoder into a correct one and shows that correctness is free; Section 11.8 measures what the safe idioms and the detection tools cost.

Throughout, "UB" means behaviour for which the C++ standard imposes no requirements. All assembly in this chapter was produced by g++ 13.3 with `-O2 -std=c++20` for x86-64 Linux, printed in Intel syntax (destination operand first), with assembler directives removed. Section 16.3 teaches assembly reading in general; here we only need a handful of instructions.

## What UB Is

### Four kinds of "the standard doesn't say exactly"

The C++ standard defines the behaviour of an *abstract machine*. For most constructs it says exactly what happens. Where it does not, it uses one of four categories, and confusing them is a common interview mistake:

| Category | Meaning | Examples |
|---|---|---|
| Implementation-defined | Each implementation must choose a behaviour **and document it** | `sizeof(long)`, whether plain `char` is signed, `alignof(std::max_align_t)` |
| Unspecified | The implementation chooses among allowed behaviours; it need not document or be consistent | order in which function arguments are evaluated; whether two string literals with the same text share storage |
| Undefined | **No requirements at all** on a program execution that contains it | signed overflow, out-of-bounds access, data races, reading through a dangling pointer |
| Ill-formed, no diagnostic required (IFNDR) | The program is invalid but the compiler need not say so | two different definitions of the same inline function in different translation units (an ODR violation, 5.1) |

C++20 moved several things out of the undefined and implementation-defined columns: integers are now required to use two's complement, conversions from an out-of-range integer value to a signed integer type are defined to wrap modulo 2^{N}, `1 << 31` on a 32-bit `int` is defined (it gives `INT_MIN`), and right-shifting a negative number is defined to be an arithmetic shift. Signed *arithmetic* overflow, however, remains undefined (11.2). C++26 adds a fifth category, *erroneous behaviour*, initially used for reads of uninitialized automatic variables: the program is wrong, but the result is no longer unbounded. Interviews in the near future will still expect the C++20 rules.

### "No requirements" means the whole execution

The key sentence in the standard is that if an execution contains UB, the standard places no requirement on *that execution*, **not even on the operations before the UB**. Compilers exploit this in a way that feels like time travel: if a path is certain to reach UB, the compiler may assume the path is never taken, and it may use that assumption to transform code that runs *earlier*. Section 11.5 shows a loop whose final iteration would read out of bounds being compiled into `return true;`, so the reads of the in-bounds elements disappear too.

### Why UB exists, and why it is not going away

UB was originally a portability device. C ran on machines where signed overflow trapped, where integers were ones' complement, and where dereferencing an invalid pointer could do anything from returning garbage to halting the machine. Declaring these cases undefined let the language map directly onto each machine's native instructions.

Today the main reason is **optimization**. Each UB rule is a promise the programmer makes, and each promise is a fact the optimizer may assume:

| The programmer promises… | …so the compiler may assume |
|---|---|
| signed arithmetic never overflows | `x + 1 > x`; `x * 10 / 10 == x`; a signed loop counter can be widened to 64 bits |
| every array access is in bounds | a loop that indexes `a[i]` exits before `i` leaves the array |
| a dereferenced pointer was not null | a later `p == nullptr` check is false |
| an `int` and a `float` are never the same object | a store through `float*` cannot change a value already loaded through `int*` |
| no other thread writes a non-atomic variable concurrently | a value read in a loop can be kept in a register |
| a loop without side effects terminates | such a loop can be deleted |

These assumptions are worth real performance in loops, which is why compilers will not give them up by default and why flags such as `-fwrapv` (11.5) exist only as opt-outs.

### The correct mental model

Do not think "UB means the program crashes" or "UB means I get some arbitrary value". Think: **the compiler is entitled to produce code that is correct only for executions without UB.** Whatever the generated code happens to do on an execution with UB is an accident of which transformations ran. Consequences:

- "It works on my machine" is not evidence. It works with this compiler version, these flags, this inlining decision.
- The bug may appear far from the UB, because the compiler propagates assumptions across inlined function boundaries.
- Adding a `printf` to debug it often makes it disappear, because the extra call changes what the optimizer can prove.
- Reasoning about what "the hardware does" (x86 `add` wraps, x86 loads tolerate misalignment) is irrelevant: the compiler, not the hardware, decides what instructions you get.

## Classic UB

### Signed integer overflow (diagnostic D6)

Overflow of `+`, `-` and `*` on signed integers is UB. Unsigned arithmetic is the opposite: it is *defined* to wrap modulo 2^{N}. The full list of arithmetic UB in C++20:

- signed `+`, `-`, `*` whose mathematical result is not representable (including `-x` for `x == INT_MIN`);
- integer division or remainder by zero;
- `INT_MIN / -1` and `INT_MIN % -1` (the quotient 2^{31} is not representable; on x86-64 the `idiv` instruction raises a divide error for it, so this one usually crashes);
- a shift by a negative amount or by at least the width of the (promoted) left operand: `1 << 32` and `x >> -1`;
- converting a floating-point value to an integer type when the truncated value does not fit (`int(1e10)`).

The trap that catches experienced programmers is **integer promotion** (5.6). Arithmetic on types narrower than `int` is performed in `int`. So with `unsigned short a = 65535;`, the expression `a * a` multiplies two `int`s, the result 4,294,836,225 does not fit, and the behaviour is undefined, even though every variable involved is unsigned. UBSan reports it as `signed integer overflow: 65535 * 65535 cannot be represented in type 'int'`. Casting one operand to `unsigned` first (`1u * a * a`) makes it defined.

In trading code, signed overflow appears in quantity × price products (Section 11.7 has one), in timestamp arithmetic (nanoseconds since 1970 fit comfortably in `int64_t` but not in 32 bits, and multiplying seconds by 10^{9} in `int` overflows instantly), and in hash functions written with `int`.

How to write overflow-safe code:

- Use a wider type for products: `int64_t(price) * qty` (both factors 32-bit) cannot overflow.
- Test *before* the operation, using only operations that cannot overflow: `b > 0 && a > INT_MAX - b` (Listing 11.3, line 19).
- Use the GCC/Clang builtins `__builtin_add_overflow`, `__builtin_sub_overflow` and `__builtin_mul_overflow`, which compute the wrapped result and return whether overflow happened. They compile to the arithmetic instruction plus a check of the overflow flag (11.5).
- Use unsigned arithmetic when wrapping is the intended semantics (hashes, sequence numbers, ring-buffer indices).
- Use `std::midpoint` (C++20) instead of `(a + b) / 2`, and `std::cmp_less` and friends (C++20) to compare signed with unsigned values correctly.

### Out-of-bounds access and invalid pointer arithmetic

Reading or writing outside an object is UB. Two less obvious parts of the rule:

- **Forming** an out-of-range pointer is already UB, even without dereferencing it. For an array of *n* elements, pointers to elements 0 … n and the one-past-the-end pointer are valid; `a + n + 1` and `a - 1` are not.
- `std::vector::operator[]`, `std::array::operator[]`, `std::span::operator[]` and `std::string_view::operator[]` do not check bounds. `at()` does and throws `std::out_of_range`. Section 11.8 measures what the check costs.

An out-of-bounds read in a loop gives the optimizer an assumption about the trip count, with dramatic results:

```cpp
int table[4] = {1, 2, 3, 4};
bool contains(int v) {
    for (int i = 0; i <= 4; ++i)        // off by one: reads table[4]
        if (table[i] == v) return true;
    return false;
}
```

g++ 13.3 at `-O2` compiles `contains` to:

```asm
contains(int):
    mov     eax, 1
    ret
```

The reasoning is legitimate. If the loop reaches `i == 4`, the program has UB, so the compiler may assume it does not. The only way for the loop to stop before `i == 4` is `return true`. Therefore the function returns `true`. All four in-bounds comparisons vanish with the out-of-bounds one, and no warning is printed with `-Wall -Wextra`. Problem P11.8 shows a variant that returns a wrong *index*.

### Null pointer dereference

Dereferencing a null pointer is UB, so after `*p` the compiler may assume `p != nullptr` and delete later null checks (Listing 11.2, lines 19–23, compiled in 11.5). This has caused real security bugs: a widely discussed 2009 Linux kernel vulnerability involved a null check that GCC removed because the pointer had been dereferenced one line earlier, and the kernel has been built with `-fno-delete-null-pointer-checks` since. The rule extends to calling a non-static member function through a null pointer, even one that does not touch any member: `p->f()` with `p == nullptr` is UB.

### Uninitialized reads

Reading an automatic variable that was never initialized is UB in C++20 (with narrow exceptions for `unsigned char` and `std::byte`). The compiler does not "read whatever was in the register": it may pick any value that simplifies code, and different uses of the same variable may see different values. For example:

```cpp
int classify(int x) {
    int r;                    // not set when x == 0
    if (x > 0) r = 1;
    else if (x < 0) r = -1;
    return r;
}
```

g++ warns (`'r' may be used uninitialized [-Wmaybe-uninitialized]`) and then emits code that returns 1 for `x == 0`: it merged the `x == 0` path into whichever branch was cheapest. Initialize every variable at its declaration; where that is wasteful (a large buffer about to be overwritten), make it obvious and local. GCC 12+ and Clang offer `-ftrivial-auto-var-init=zero` to zero-initialize automatic variables as a hardening measure, and C++26 makes such reads erroneous behaviour rather than UB.

### Data races

A data race is two accesses to the same memory location from different threads, at least one a write, not ordered by synchronization (Section 14.2 defines "ordered" precisely). Any data race is UB, not just one that "loses an update". The classic consequence is a spin-wait on a plain `bool`:

```cpp
bool ready = false;          // written by another thread
int payload = 0;
int wait_for_payload() {
    while (!ready) { }       // data race
    return payload;
}
```

g++ 13.3 at `-O2` compiles this to:

```asm
wait_for_payload():
    mov     eax, DWORD PTR payload[rip]
    ret
```

Two UB rules combine here. Because no other thread may write `ready` without synchronization, its value cannot change inside the loop, so the compiler may read it once. A loop that cannot change anything and never ends would violate the C++ *forward progress* rule (a thread is assumed to eventually terminate, perform I/O, access a volatile or atomic object, or synchronize), so the compiler may also assume the loop terminates. With `-fno-finite-loops` the second assumption is disabled and the code becomes "if `ready` was false at the first read, spin forever", which is equally wrong. The fix is `std::atomic<bool>` with release/acquire ordering (14.2). `volatile` is *not* a fix: it forces the reads but provides no ordering between `ready` and `payload` in the C++ memory model.

### Other UB worth knowing by name

- Flowing off the end of a non-`void` function (other than `main`) without returning a value.
- Modifying a `const` object (for example through `const_cast`), or a string literal.
- Two unsequenced modifications of the same scalar: `i++ + i++` is still UB in C++20 (C++17 sequenced `i = i++ + 1` and the operands of `<<`, but not this).
- Calling `std::sort` with a comparator that is not a strict weak ordering (for example `<=`, or a comparison of floating-point values that may be NaN). libstdc++'s unguarded insertion sort can then walk off the end of the range: a crash in `std::sort` is usually a comparator bug.
- `std::memcpy` with overlapping source and destination (use `std::memmove`).
- Violating a library precondition: `front()` on an empty vector, dereferencing `end()`, `std::optional::operator*` on an empty optional, `std::string_view` constructed from `nullptr`.
- An infinite loop with no observable side effects (above).
- Breaking the ODR or `[[noreturn]]` and `[[assume]]` promises (C++23's `[[assume(expr)]]` turns an expression into a UB-backed assumption on purpose).

## Strict Aliasing and Type Punning

### The rule

C++ allows you to access an object only through an lvalue (roughly, a named variable or a dereferenced pointer) of one of these types:

1. the object's own type (ignoring `const`/`volatile`);
2. the signed or unsigned counterpart of that type (`int` and `unsigned int`);
3. `char`, `unsigned char` or `std::byte`.

Everything else is UB. In particular, a `float` object cannot be read through `int*`, a `double` cannot be read through `uint64_t*`, and, the case that matters most in trading systems, **an array of `unsigned char` cannot be read through `uint64_t*` or `SomeHeader*`**. The `char` exception works in one direction only: you may look at any object's bytes through `unsigned char*`, but a byte buffer does not contain `uint64_t` objects just because you cast its address.

### Why compilers enforce it

The rule enables *type-based alias analysis*: the compiler may assume that pointers to unrelated types never refer to the same memory. That lets it keep values in registers across stores. Listing 11.2 (lines 26–27) has two functions that differ only in the pointer types:

```asm
store_int_float(int*, float*):
    mov     DWORD PTR [rdi], 1
    mov     eax, 1                        ; return value is the constant 1
    mov     DWORD PTR [rsi], 0x40000000   ; the store of 2.0f comes after
    ret
store_int_int(int*, int*):
    mov     DWORD PTR [rdi], 1
    mov     DWORD PTR [rsi], 2
    mov     eax, DWORD PTR [rdi]          ; must reload: j may equal i
    ret
```

For `int*` and `float*` the compiler returns the constant 1 without reloading, because the `float` store cannot have changed an `int`. Calling the first function with both pointers referring to the same `int` (via `reinterpret_cast<float*>`) is UB, and the observed result depends on flags. Running exactly that experiment in the build container:

```text
-O0:                        returned 1073741824, x now holds 1073741824
-O2:                        returned 1, x now holds 1073741824
-O2 -fno-strict-aliasing:   returned 1073741824, x now holds 1073741824
```

At `-O2` the function returns a value that disagrees with memory. This is how aliasing bugs look in practice: a value "lags behind" a store made through a differently typed pointer.

### Type punning: the wrong ways and the right ways

*Type punning* means reinterpreting the bytes of one type as another, for example to get the bit pattern of a `double`, or to read a `uint64_t` field from a received packet.

| Method | Status in C++20 | Notes |
|---|---|---|
| `*reinterpret_cast<uint64_t*>(&d)` | UB (aliasing) | g++ warns: `dereferencing type-punned pointer will break strict-aliasing rules` |
| `union { double d; uint64_t u; }`, write `d`, read `u` | UB in C++ (reading an inactive member) | Defined in C. GCC documents it as a supported extension, so it works with GCC, but the code is not portable C++ |
| `std::memcpy(&u, &d, 8)` | Defined | The traditional portable idiom; compilers recognize it |
| `std::bit_cast<uint64_t>(d)` | Defined (C++20) | Requires equal sizes and trivially copyable types; also usable in `constexpr` |

### Alignment

Separately from aliasing, every type has an alignment requirement (`alignof(uint64_t)` is 8 on x86-64; Section 6.1 explains why). Accessing an object through a misaligned pointer is UB, even on x86-64, where the hardware tolerates misaligned loads. The compiler may, for example, use an aligned SIMD instruction that faults on misaligned addresses. UBSan checks it:

```text
runtime error: load of misaligned address 0x55ac756d92c6 for type 'const long unsigned int',
which requires 8 byte alignment
```

`memcpy` and `bit_cast` have no alignment requirement on the source bytes, which is a second reason to decode packets with them. (Whether misaligned access is *slow* is a hardware question, answered in 12.2.)

### Related tools

- `-fno-strict-aliasing` turns the aliasing rule off for a translation unit. Some large C codebases, including the Linux kernel, build with it. It costs some optimization (every store may invalidate every cached load of a different type) and it does not fix alignment or lifetime problems.
- `__restrict` (a GCC/Clang extension in C++, standard `restrict` in C) is the opposite promise: two pointers *of the same type* do not alias. It can enable vectorization; breaking the promise is UB.
- C++23 adds `std::start_lifetime_as<T>(p)`, which explicitly creates a `T` object from existing bytes without copying, so a received buffer can be viewed as a header struct legally. It was not yet implemented in g++ 13; until your toolchain has it, use `memcpy`.

## Lifetime Bugs

An object's *lifetime* (5.3) begins when its initialization completes and ends when its destructor starts (or, for trivial types, when its storage is released or reused). Using an object outside its lifetime is UB, and in modern C++ the commonest way to do it is through a non-owning handle that outlives what it refers to. These bugs are the C++ equivalent of use-after-free and are the main source of crashes in otherwise clean code.

### Views and references to temporaries

```cpp
std::string make_symbol(int id) { return "INSTRUMENT_" + std::to_string(id); }
std::string_view sv = make_symbol(1);   // the std::string dies at the semicolon
std::printf("%c\n", sv[0]);             // reads destroyed storage
```

`std::string_view`, `std::span`, raw pointers, references and iterators never extend the life of what they point to. (The rule that binding a temporary to a `const&` extends its lifetime applies only to a reference bound *directly* to the temporary, not to a view constructed from it.) g++ prints no warning for this snippet with `-Wall -Wextra`. AddressSanitizer reports it in the build container as:

```text
ERROR: AddressSanitizer: stack-use-after-scope on address 0x7f828c700070 ...
READ of size 1 at 0x7f828c700070 thread T0
    #0 0x55c6b2096480 in main t3.cpp:7
```

Why *stack*-use-after-scope, when strings use the heap? Because "INSTRUMENT_1" has 12 characters, which fits in libstdc++'s small-string buffer (up to 15 characters) inside the `std::string` object itself, which was a temporary on the stack. With a longer name the same bug becomes a heap-use-after-free. The bug is identical; how it shows up depends on the data, which is why such bugs survive testing.

### Invalidation

Containers move their elements when they grow or rehash (10.1, 10.4; diagnostic D5):

```cpp
std::vector<Order>& book = ...;
Order& best = book.front();
book.push_back(incoming);     // may reallocate: best now dangles
best.qty -= fill;             // UB if a reallocation happened
```

The same applies to iterators and pointers into `std::vector`, `std::string` and `std::deque` (on insertion at the ends, references survive but iterators do not), and to iterators into `std::unordered_map` across a rehash. Node-based containers (`std::map`, `std::list`) keep references valid until the element is erased.

### Escaping references and captures

- Returning a reference or `string_view` to a local variable or to a by-value parameter.
- A lambda that captures locals by reference (`[&]`) and is stored for later: a callback registered with a timer or an event loop and invoked after the registering function has returned. Capture by value, or capture an owning `std::shared_ptr` if the lifetime really is shared (7.6).
- `std::thread` or `std::jthread` started with a reference to a local that goes out of scope before the thread finishes.

### Range-for over a temporary's member

```cpp
for (const Level& l : load_book().levels()) { ... }   // levels() returns const&
```

The range-for statement binds `auto&& __range = load_book().levels();`. The reference returned by `levels()` refers into the temporary book, which in C++20 is destroyed at the end of that hidden declaration, before the first iteration. C++23 (proposal P2718) extends the lifetime of all temporaries in the range expression to the end of the loop, but code that must compile as C++20 has to name the object first: `auto book = load_book(); for (auto& l : book.levels())`.

### Reusing storage

When you construct a new object in the storage of an old one with placement new (7.3), use the pointer that placement new returns. Reaching the new object through an old pointer is only valid in limited cases, and `std::launder` exists for the rest (for example when the old type had `const` or reference members). In practice, pools and arenas (7.5) should hand out the pointer returned by placement new and never reinterpret old ones.

### What is *not* a lifetime bug

Using a moved-from standard-library object is not UB: it is in a *valid but unspecified* state, so you may assign to it, destroy it, or call functions without preconditions (`size()`, `clear()`), but not functions with preconditions (`front()`) unless you check first. Moving does not end the lifetime (8.2). For your own types, the moved-from state is whatever your move constructor leaves.

### (1) An overflow check that tests for overflow by overflowing (line 8)

```asm
add_overflows_naive(int, int):
    shr     esi, 31            ; esi = (b < 0) ? 1 : 0
    mov     eax, esi
    ret
add_overflows_ok(int, int):
    add     edi, esi
    seto    al                 ; al = CPU overflow flag
    ret
```

Because `a + b` cannot overflow, `a + b < a` is algebraically equivalent to `b < 0`, and that is all the naive function computes (the sign bit of `b`). It therefore reports "overflow" for `add_overflows_naive(5, -1)` and misses the real overflow of `INT_MAX + 1`. The builtin (lines 9–12) compiles to the hardware add followed by `seto`, which reads the processor's signed-overflow flag: correct and essentially free.

### (2) Algebraic simplification (lines 15–16)

```asm
times10_div10(int):
    mov     eax, edi                   ; return x
    ret
times10_div10_u(unsigned int):
    lea     eax, [rdi+rdi*4]           ; x * 5
    mov     edx, 3435973837
    add     eax, eax                   ; x * 10, wraps mod 2^32
    mov     eax, eax
    imul    rax, rdx                   ; divide by 10 via multiply-by-reciprocal
    shr     rax, 35
    ret
```

For `int`, `x * 10 / 10` is `x`. For `unsigned` the multiplication may wrap, which is defined, so the compiler must compute it: for 500,000,000 the output shows 70,503,270, which is (5 × 10^{9} mod 2^{32}) / 10. The signed version is not "wrong"; it is correct for every input on which it is defined. The division is implemented as a multiplication by a fixed-point reciprocal and a shift, because a 32-bit `div` instruction costs tens of cycles (12.1).

### (3) The deleted null check (lines 19–23)

```asm
deref_then_check(int const*):
    mov     eax, DWORD PTR [rdi]
    ret
```

The load happens first, so if `p` were null the program would already have UB; the compiler deletes the check. Reordering the source (check first, then load) is the fix.

### (4) Strict aliasing (lines 26–27)

Shown in 11.3: with `int*` and `float*` the returned value is a constant; with two `int*` it is reloaded.

### (5) Trip counts and induction variables (lines 30–39)

```asm
count_up(int):
    movsx   rax, edi           ; n, sign-extended to 64 bits
    xor     edx, edx
    add     rax, 1             ; n + 1
    test    edi, edi
    cmovs   rax, rdx           ; if n < 0 then 0
    ret
```

With a signed counter, `i <= n` must become false after exactly n + 1 iterations (the loop cannot run past `INT_MAX`, as that would overflow `i`), so the whole loop is replaced by a formula. The unsigned version (lines 35–39) keeps a real loop, because for `n == UINT_MAX` it never terminates and the compiler must preserve that.

The same reasoning has a performance benefit in ordinary code. When a 32-bit `int` index is used to address memory, the compiler may widen it to a 64-bit register once, before the loop, and fold arithmetic on it into the addressing mode. With a 32-bit `unsigned` index it must reproduce wrap-around at 2^{32} on every iteration. For `out[i] = a[2 * i] * 0.5f`:

```asm
; int i                                   ; unsigned i
.L3:                                      .L8:
    movss   xmm0, DWORD PTR [rsi+rax*8]       lea     ecx, [rax+rax]   ; 2*i mod 2^32
    mulss   xmm0, xmm1                        movss   xmm0, DWORD PTR [rsi+rcx*4]
    movss   DWORD PTR [rdi+rax*4], xmm0       mulss   xmm0, xmm1
    add     rax, 1                            movss   DWORD PTR [rdi+rax*4], xmm0
    cmp     rax, rdx                          add     rax, 1
    jne     .L3                               cmp     rdx, rax
                                              jne     .L8
```

One extra instruction per iteration is small, but in other loops the same uncertainty blocks vectorization entirely. The practical rule: index with `std::size_t` (64-bit, no wrap concern within an address space) or `int`/`std::ptrdiff_t`; avoid 32-bit `unsigned` for loop indices in hot code.

### How the reasoning works inside the compiler

The examples above come from a few general analyses, all of which take UB-freedom as an axiom:

- **Value-range propagation**: after `int v = *p`, the range of `p` excludes null; after `if (i + 1 > i)`, nothing is learned because the condition is always true.
- **Induction-variable analysis and scalar evolution**: computes trip counts in closed form, assuming signed counters do not wrap.
- **Alias analysis**: type-based (strict aliasing) plus points-to analysis decides which loads may be reused after a store.
- **Unreachable-path elimination**: a path that must execute UB is treated like `__builtin_unreachable()` (or C++23 `std::unreachable()`), and the conditions leading to it are assumed false. GCC's `-fisolate-erroneous-paths-dereference` (on at `-O2`) instead replaces a provable null dereference with a trap instruction.

### Flags that define the undefined

| Flag (GCC/Clang) | Effect | Typical use |
|---|---|---|
| `-fwrapv` | signed overflow wraps (two's complement) | legacy code; costs some loop optimizations |
| `-ftrapv` | signed overflow aborts | debugging; slow and not maintained as well as UBSan |
| `-fno-strict-aliasing` | disables type-based alias analysis | code that casts buffers to structs |
| `-fno-delete-null-pointer-checks` | keeps null checks after dereference | kernels, embedded |
| `-fno-finite-loops` (GCC) | side-effect-free loops may be infinite | code relying on spin loops of the 11.2 kind (still a data race) |
| `-ftrivial-auto-var-init=zero` | zero-initializes automatic variables | hardening |

These flags change what the code means, so code that "needs" one of them is not portable C++. Fix the code; use the flags as a temporary mitigation or for defence in depth.

## Detecting UB

No tool finds all UB, and the most dangerous kinds (aliasing violations, many lifetime bugs, data races that happen rarely) are the hardest to detect. The table shows which tool covers what. Section 16.6 covers how to use the sanitizers and gdb day to day; here the question is coverage.

| UB category | Compiler warnings | ASan | UBSan | TSan | Constant evaluation |
|---|---|---|---|---|---|
| signed overflow, shifts, division | some cases | — | yes | — | yes |
| out-of-bounds (heap, stack, global) | some constant cases | yes | arrays of known bound | — | yes |
| use-after-free, use-after-scope, double free | rarely | yes | — | — | yes |
| null dereference | some | crashes are reported | yes | — | yes |
| misaligned access | `-Wcast-align` (limited) | — | yes | — | n/a |
| uninitialized read | `-Wmaybe-uninitialized` | — | — | — | yes |
| strict aliasing | `-Wstrict-aliasing` (simple casts only) | — | — | — | partly (`reinterpret_cast` not allowed) |
| data races | — | — | — | yes (on executions that race) | n/a |
| float → int out of range | — | — | `-fsanitize=float-cast-overflow` | — | yes |

Notes on the columns:

- **AddressSanitizer** (`-fsanitize=address`) surrounds objects with poisoned "redzones" and keeps freed memory in quarantine; every load and store checks a shadow byte that records whether the address is addressable. It finds out-of-bounds and use-after-free reliably *when the bad access happens in a test*, but it cannot detect an out-of-bounds access that lands inside another valid object.
- **UndefinedBehaviorSanitizer** (`-fsanitize=undefined`) inserts a check before each operation that can have UB (every signed add, every shift, every pointer dereference for null and alignment). With `-fno-sanitize-recover=all` (as `build.py --sanitize` uses) the first report aborts the program. In GCC, `float-cast-overflow` must be requested separately; `-fsanitize=undefined` does not include it.
- **ThreadSanitizer** (`-fsanitize=thread`, cannot be combined with ASan) tracks happens-before relations between threads and reports conflicting accesses. It only sees races in executions that actually interleave the accesses, so stress tests matter. Chapter 14's listings are run under it.
- **MemorySanitizer** (Clang only, `-fsanitize=memory`) detects reads of uninitialized memory, which nothing in GCC detects at run time. Valgrind's memcheck also detects uninitialized reads, without recompiling, at a much larger slowdown.
- **libstdc++ assertions**: `-D_GLIBCXX_ASSERTIONS` turns library preconditions into checks (bounds in `operator[]`, `front()` on empty, and so on) without changing the ABI; `-D_GLIBCXX_DEBUG` adds iterator-invalidation checking but changes container layouts, so every object file must be compiled with it.

### A process, not a tool

Teams that take UB seriously combine these: warnings as errors (`-Wall -Wextra -Werror`, which this book's build uses), a CI configuration that runs the test suite under ASan+UBSan and another under TSan, fuzzing of every parser of external input (feed handlers, configuration parsers) with sanitizers enabled, `constexpr` tests for arithmetic helpers, and periodic runs of the optimized production build against recorded data, because some UB only changes behaviour at the production optimization level.

### What the safe idioms cost

### Costs at a glance

| Idiom or tool | Approximate cost on a modern x86-64 core | Why |
|---|---|---|
| `memcpy`/`bit_cast` instead of `reinterpret_cast` | 0 cycles | compiles to the same single load or register move |
| unaligned scalar load within one 64-byte line | usually 0 extra cycles | modern cores handle it in the load unit; crossing a line boundary costs extra, crossing a page much more (measured in 12.9) |
| bounds check with predictable outcome | 0–1 cycle per access; often 0 after hoisting | one compare + one predicted branch; may block vectorization |
| `__builtin_*_overflow` | 0–1 cycle | the flag is produced by the arithmetic instruction anyway |
| 64-bit instead of 32-bit multiply | 0 cycles on current cores | `imul r64` and `imul r32` have similar latency (about 3 cycles) |
| 32-bit `unsigned` loop index | 0–1 extra instruction per iteration, sometimes loss of vectorization | wrap-around must be preserved (11.5) |
| `-fwrapv` | usually small; occasionally large in loops that needed widening or vectorization | removes the no-overflow assumption |
| UBSan | measured 1.3–1.5× on Listing 11.5 | a check before every arithmetic operation and dereference |
| ASan | measured about 2.3× on Listing 11.5 | a shadow-memory check on every load and store, plus redzones that increase memory footprint |
| ASan + UBSan | measured about 2.6× on Listing 11.5 | both of the above |
| ASan + UBSan on tight loops | measured 8–11× on the loops of Listing 11.6 | checks dominate when the loop body is a few instructions |

The sanitizer figures were measured in the build container by recompiling the listings with `-O2` plus the sanitizer flag (range over three runs each: Listing 11.5 ran at 6.0–6.4 ns/message plain, 8.3–8.7 with UBSan, 13.8–15.1 with ASan, 15.4–17.2 with both). Clang's documentation describes a typical ASan slowdown of about 2× and ThreadSanitizer as typically 5–15×; the slowdown depends strongly on how memory-intensive the code is.

The asymmetry to remember is that the UB-free idioms cost close to nothing in production, while the cost of the bug is unbounded. Sanitizers cost a few times the run time, so they belong in test and CI builds, never in production binaries.

## Interview Questions

**Q1. Is signed integer overflow defined in C++? Unsigned? What changed in C++20?**
Signed overflow is undefined; unsigned arithmetic wraps modulo 2^{N}. C++20 mandated two's complement representation and made conversions to signed types and left shifts of negative or large values (within the shift-width limit) well-defined, but deliberately kept signed arithmetic overflow undefined so that compilers can keep assuming `x + 1 > x`.

**Q2. What is the difference between undefined, unspecified and implementation-defined behaviour?**
Implementation-defined: the implementation chooses and documents (size of `long`). Unspecified: one of several allowed outcomes, not documented, not necessarily consistent (argument evaluation order). Undefined: no requirements on the whole execution, including what happened before the UB point; the compiler may assume it never happens.

**Q3. Why might a compiler remove `if (p == nullptr) return;`?**
If `p` was dereferenced earlier on every path to the check, a null `p` would already have caused UB, so the compiler may infer `p != nullptr` and delete the branch. Fix by checking before dereferencing.

**Q4. You need the bit pattern of a `double`. How?**
`std::bit_cast<std::uint64_t>(d)` in C++20, or `std::memcpy` into a `uint64_t` before that. Not `reinterpret_cast` (strict-aliasing UB) and, in portable C++, not a union (reading an inactive member is UB, though GCC supports it as an extension). Both correct forms compile to a single register move.

**Q5. What is the strict aliasing rule, and why does it exist?**
An object may only be accessed through its own type, its signed/unsigned counterpart, or `char`/`unsigned char`/`std::byte`. It lets the compiler assume that stores through one type do not modify objects of an unrelated type, so values can stay in registers and loops can be vectorized. Violations show up as stale values at `-O2`.

**Q6. Is `reinterpret_cast<const Header*>(buffer)` on a received packet legal?**
Not reliably. There is no `Header` object in the byte buffer (aliasing and lifetime), the address may be misaligned, and any non-standard packing is an extension. Use `memcpy` (or `bit_cast`) per field or into a local `Header`; it compiles to the same loads. C++23 adds `std::start_lifetime_as` for the cases where you need an in-place view.

**Q7. A teammate's spin-wait `while (!flag) {}` on a plain `bool` hangs at `-O2` but works at `-O0`. Explain.**
The concurrent write makes it a data race, which is UB, so the compiler may load `flag` once and never again; it may even delete the loop under the forward-progress rule. Use `std::atomic<bool>` with a release store and an acquire load (14.2), which also orders the data the flag protects. `volatile` forces the reloads but provides no inter-thread ordering.

**Q8. Which sanitizer would you use for (a) a use-after-free, (b) `INT_MAX + 1`, (c) a race on a counter, (d) reading an uninitialized `int`?**
(a) ASan. (b) UBSan. (c) TSan, in an execution where the threads actually overlap. (d) MemorySanitizer (Clang) or valgrind; GCC's sanitizers do not detect it, though `-Wmaybe-uninitialized` may warn at compile time.

**Q9. Why is `for (unsigned i = 0; i < n; ++i) out[i] = a[2*i];` potentially slower than the same loop with `int i`?**
For `int`, overflow is UB, so the compiler may widen `i` to 64 bits and fold `2*i` into the address. For 32-bit `unsigned`, `2*i` must wrap at 2^{32}, so it is recomputed in 32 bits every iteration, which adds instructions and can prevent vectorization. `std::size_t` avoids both problems.

**Q10. Your program crashes inside `std::sort`. What do you check first?**
The comparator. If it is not a strict weak ordering (it uses `<=`, it is inconsistent, or it compares floating-point values that can be NaN), the behaviour is undefined and libstdc++'s unguarded partition can run past the end of the range.

**Q11. How can `constexpr` help you find UB?**
In a constant expression the compiler must diagnose UB, so a `static_assert` over a `consteval` test function that runs edge cases (`INT_MIN`, `INT_MAX`, −1, 0) proves those cases are UB-free at every build, with no run-time cost and no false positives.

## Key Takeaways

- **UB means no requirements on the whole execution.** The compiler generates code that is correct for UB-free executions only and uses every UB rule as an assumption. "It works" is not evidence.
- **Arithmetic:** signed overflow, `INT_MIN / -1`, division by zero, out-of-range shifts and float-to-int conversions are UB; unsigned wraps. Watch integer promotion (`unsigned short * unsigned short` is `int` arithmetic). Use wider types, pre-checks, `__builtin_*_overflow`, `std::midpoint`.
- **Memory:** out-of-bounds access and even out-of-range pointer arithmetic are UB, and they let the compiler rewrite loops (`contains` → `return true`). Null checks after a dereference are deleted.
- **Aliasing:** access objects only through their own type, its signed/unsigned twin, or `char`/`unsigned char`/`std::byte`. Pun with `std::bit_cast` or `memcpy`, which compile to the same single instruction. Decode network buffers field by field with `memcpy`.
- **Lifetime:** views (`string_view`, `span`, iterators, references, `[&]` captures) never extend lifetimes. Watch temporaries, container growth, escaping lambdas, and range-for over a temporary's member in C++20.
- **Concurrency:** any data race is UB; spin-waits on plain variables get hoisted or deleted. Use atomics (14.2), not `volatile`.
- **Detection:** warnings as errors; ASan for memory errors, UBSan for arithmetic, alignment and null, TSan for races, MSan or valgrind for uninitialized reads; `constexpr` tests for edge cases; fuzz every parser. No tool catches aliasing or all lifetime bugs, so prefer idioms that cannot have them.
- **Cost:** the correct idioms are essentially free in optimized code; sanitizers cost roughly 1.3–11× and belong in CI. Avoid 32-bit `unsigned` loop indices in hot loops.
