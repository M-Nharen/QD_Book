# C++ Foundations Bridge

You can already write C++ that compiles and gives the right answer for a test case. A QD interviewer wants to know whether you understand *what the compiler and the machine do with it*: where an object lives, when it is created and destroyed, how it is passed to a function, what bits represent an integer or a price, and what goes wrong at each boundary. This chapter is the bridge from "C++ syntax" to that level. It covers the material that the rest of Part B assumes, and it is deliberately concrete: every claim about code generation is backed by assembly that GCC 13 actually produced, and every claim about cost is either an approximate hardware range with its reason or a measurement labelled as such.

Several topics are introduced here and finished elsewhere. Move semantics and value categories are Chapter 8; templates are Chapter 9; undefined behaviour is Chapter 11; the price and time types of a real trading system are Section 18.6. When you meet a cross-reference, the later section assumes you have read this one.

## The Compilation Model

### Intuition: a book written by many authors

Think of a large program as a book written by many authors in parallel. Each author writes one chapter (a source file) and may *mention* things defined in other chapters ("see the definition of `Order` in Chapter 3") without seeing them. An editor (the linker) later binds the chapters together and checks that every mention points at exactly one real definition. C++ compiles each source file *in isolation*; almost every confusing rule about headers, `inline`, `static` and "multiple definition" errors follows from that single fact.

### The four stages

`g++ main.cpp -o app` hides four separate steps, each of which you can stop after:

| Stage | Stop with | Output | What happens |
|---|---|---|---|
| Preprocess | `g++ -E` | translation unit (text) | `#include` pastes files; macros expand |
| Compile | `g++ -S` | assembly (`.s`) | parse, instantiate templates, optimize |
| Assemble | `g++ -c` | object file (`.o`) | machine code, symbol table, relocations |
| Link | `g++ a.o b.o` | executable | resolve symbols, lay out sections |

The output of the preprocessor for one `.cpp` file is a **translation unit** (TU): the source file with every header pasted in. TUs are big. In the build container, a file containing only `#include <vector>` and an empty `main` preprocesses to about 26,000 lines, `<iostream>` to about 43,000, and `<bits/stdc++.h>` to about 165,000; compiling those trivial files at -O2 took roughly 0.2 s, 0.4 s and 2 s respectively (measured in the build container; your machine will differ). That is why large codebases care about what they include (Section 9.7), and why `bits/stdc++.h` is fine for an online test (Section 3.2) but not in production code.

### Declarations, definitions and the symbol table

A **declaration** introduces a name and its type: `void log_order(std::int64_t id);`. A **definition** also creates the entity: the function body, or the storage for a variable. A TU may *use* something it has only declared; the compiler then emits a reference to an *undefined symbol* and leaves it to the linker. The object file's symbol table shows exactly what each TU provides and needs. For this file:

```cpp
// symbols.cc -- one translation unit, compiled with: g++ -O0 -std=c++20 -c symbols.cc
#include <cstdint>
std::int64_t order_count = 0;                 // external linkage, zero-initialized
std::int64_t tick_size = 5;                   // external linkage, constant-initialized
static int retries = 3;                       // internal linkage
namespace { int helper(int x) { return x * retries; } }   // internal linkage
void log_order(std::int64_t id);              // declared only: defined elsewhere
inline int twice(int x) { return 2 * x; }     // inline: may be defined in many TUs
int submit(std::int64_t id) {                 // external linkage, defined here
    ++order_count;
    log_order(id);
    return helper(twice(1));
}
```

`nm -C symbols.o` printed (captured in the build container; the files are in `code/ch05/odr/`):

```text
0000000000000000 W twice(int)
0000000000000017 T submit(long)
                 U log_order(long)
0000000000000008 d retries
0000000000000000 t (anonymous namespace)::helper(int)
0000000000000000 B order_count
0000000000000000 D tick_size
```

The letters are the whole story of linkage. **T** is a function defined here and visible to other TUs; **U** is undefined, to be found by the linker; **D** and **B** are global variables in the initialized-data and zero-initialized (`.bss`) sections; lower-case **t** and **d** are *local* symbols, invisible outside this TU; **W** is a *weak* definition that the linker may see many times and is allowed to keep just one of. Without `-C`, `nm` shows the *mangled* names (`_Z6submitl` for `submit(long)`): C++ encodes parameter types into the symbol name, which is how overloading survives a linker that only compares strings.

Two kinds of linkage follow:

- **External linkage**: the name refers to the same entity in every TU. Non-`static` functions and non-`const` global variables have it by default.
- **Internal linkage**: each TU has its own private entity. You get it with `static` at namespace scope, by putting the entity in an unnamed namespace, and, by default, for namespace-scope `const` and `constexpr` variables that are not declared `inline` or `extern`.

### The One Definition Rule

The **One Definition Rule** (ODR) says: every function or variable with external linkage that is used must be defined *exactly once in the whole program*, with two important exceptions. Classes, inline functions, inline variables (C++17) and templates may be defined in every TU that uses them, *provided every definition is token-for-token the same* (and means the same). That exception is what makes headers work: a class definition in a header is pasted into fifty TUs, and that is legal because all fifty copies are identical.

Break the first part of the rule and you get a linker error ("multiple definition of `foo`" or "undefined reference to `foo`"), which is annoying but safe. Break the second part, two *different* definitions of the same inline function or class, and the standard says the program is ill-formed with **no diagnostic required**. Nothing warns you. The demonstration below is the classic way it happens: a header was changed, but one object file was built from the old version.

```cpp
// fees_a.cc -- compiled with an old copy of the header: fee is 3 bp
inline long fee_bp() { return 3; }
long fee_from_a(long notional) { return notional * fee_bp() / 10000; }

// fees_b.cc -- compiled with the new header: fee is 2 bp
inline long fee_bp() { return 2; }
long fee_from_b(long notional) { return notional * fee_bp() / 10000; }
```

Linked with a `main` that prints both results for a notional of 1,000,000 (script `code/ch05/odr/run.sh`, output captured in the build container):

```text
-O0: a: 300  b: 300
-O2: a: 300  b: 200
```

At -O0 each TU emits an out-of-line weak `fee_bp`, the linker keeps one of them, and both callers use it. At -O2 each TU inlines its own copy before the linker ever runs. The same source produces different results depending on the optimization level, which is the signature of an ODR violation. Linking with `-flto` gave the -O2 answer and no warning. The defence is process, not language: one header per definition, a build system that tracks header dependencies, and never defining something in two places.

### What `inline` means in modern C++

`inline` is primarily a *linkage* keyword: "this definition may appear in several TUs; they are all the same; keep one." It is *not* a reliable request to inline. GCC decides inlining with its own heuristics (Section 16.2) and inlines non-`inline` functions freely when it can see their bodies. The practical rules:

- A function **defined in a header** must be `inline` (or a template, or a member function defined inside its class, which is implicitly inline), or every TU that includes the header defines it and the link fails.
- A global **variable defined in a header** must be `inline` (C++17), or be declared `extern` in the header and defined in exactly one `.cpp`. Marking it `static` instead gives each TU its own copy, which compiles and links but is a different program: fifty independent counters instead of one.
- **Templates** are defined in headers because the compiler needs the full definition to instantiate them (Section 9.1). Each TU instantiates what it uses; the copies are emitted as weak symbols and merged by the linker, exactly like `twice(int)` above.
- Guard every header with `#pragma once` (not in the standard, but supported by GCC, Clang and MSVC) or an `#ifndef` include guard, so that a TU that includes it twice does not define a class twice.

### What the model costs at run time

Because each TU is compiled alone, **the optimizer cannot inline a function whose body is in another `.cpp` file**. A call across TUs is a real `call` instruction, and worse, the compiler must assume the callee may read or write any memory reachable from globals or from pointers it was given, which blocks optimizations around the call. This is why hot-path code in low-latency systems lives in headers, and why link-time optimization (`-flto`, Section 16.1), which lets the optimizer see across TUs, matters. Calls into a *shared library* add an indirect jump through the procedure linkage table (PLT) as well; small in cycles when predicted, but it is one reason latency-sensitive binaries are sometimes linked statically or built with `-fno-plt`.

## Values, References, Pointers and const

### Objects, values and addresses

An **object** is a region of storage with a type, a size and (usually) an address. A variable is a name for an object. `int x = 10;` creates a 4-byte object holding the bits of 10. Assignment and pass-by-value *copy bits into another object*; they never create aliases. Everything in this section is about the two ways to refer to an object without copying it.

A **pointer** is itself an object (8 bytes on x86-64) whose value is an address. It can be null, can be reseated to point elsewhere, and supports arithmetic within an array. A **reference** is an alias: another name for an existing object. It must be bound when created, cannot be reseated, and has no null state (forming a reference from a null pointer is undefined behaviour). Whether a reference occupies storage is unspecified by the language; in practice, a reference *parameter* or *member* is implemented exactly like a pointer. The function `long f(const Px& p)` and the function `long f(const Px* p)` compile to identical machine code: the address arrives in a register (`rdi`) and the members are loaded from memory.

### Reading const declarations

Read declarations right to left, starting from the name:

| Declaration | Read as | What may change |
|---|---|---|
| `const int* p` (or `int const* p`) | p is a pointer to const int | p may be reseated; `*p` may not be written through p |
| `int* const p` | p is a const pointer to int | `*p` may be written; p may not be reseated |
| `const int* const p` | const pointer to const int | neither |
| `const int& r` | reference to const int | nothing through r |

`const` on a member function (`int size() const`) means `this` points to a const object, so the function may not modify non-`mutable` members and may be called on const objects. Use `const` everywhere it is true: it documents intent and catches mistakes. But understand exactly what it promises, because interviewers probe the gap.

### const does not mean "will not change": aliasing

`const T&` promises that *this code* will not modify the object *through this reference*. It does not promise that the object will not change. Another reference, a pointer or another thread may modify it. Two names for the same storage are called **aliases**, and the compiler must assume aliasing is possible whenever it cannot prove otherwise.

```asm
.L3: movsd  xmm0, QWORD PTR [rdi]
     add    rdi, 8
     divsd  xmm0, QWORD PTR [rdx]     ; reload f from memory every iteration
     movsd  QWORD PTR -8[rdi], xmm0
; scale_val(double* v, int n, double f)         -- loop body
.L8: movsd  xmm1, QWORD PTR [rdi]
     add    rdi, 8
     divsd  xmm1, xmm0                ; f stays in register xmm0
     movsd  QWORD PTR -8[rdi], xmm1
```

The reference version re-reads `f` from memory (`[rdx]`) on every iteration because the store on the previous line might have changed it. In this loop the extra load is cheap (it hits the L1 cache), but the same uncertainty also blocks vectorization, hoisting and constant propagation in larger loops. The same thing happens with an accumulator passed by reference: `void total(long& t, const long* q, int n)` stores `t` to memory on every iteration because `q[i]` might be `t`. The cure is the same: copy into a local, work on the local, write back once. GCC also accepts the non-standard `__restrict` qualifier, a promise that a pointer is the only way to reach its object; break the promise and the behaviour is undefined (Section 11.3 covers the related strict-aliasing rule).

### How arguments are passed

How a parameter reaches a function is fixed by the platform ABI, which on Linux x86-64 is the System V ABI plus the Itanium C++ ABI. The rules that matter:

- The first six integer or pointer arguments go in `rdi, rsi, rdx, rcx, r8, r9`; the first eight floating-point arguments go in `xmm0`–`xmm7`; the return value comes back in `rax` (and `rdx`) or `xmm0`.
- A small **trivially copyable** struct (up to 16 bytes) is split into its eightbytes and passed *in registers*.
- A larger struct is copied to the stack.
- A type with a **non-trivial copy constructor, move constructor or destructor** is never passed in registers. The caller materializes a temporary in memory and passes its address, however small the type.

The last rule surprises people. With `struct Px { std::int64_t ticks, qty; };`, GCC 13 compiled `return p.ticks * p.qty;` for a by-value `Px` to two instructions on registers:

```asm
_Z8notional2Px:          ; notional(Px p): p arrives in rdi, rsi
    mov   rax, rdi
    imul  rax, rsi
    ret
_Z9notionalD3PxD:        ; notionalD(PxD p), PxD = Px plus  ~PxD() {}
    mov   rax, QWORD PTR [rdi]       ; p arrives as a hidden pointer
    imul  rax, QWORD PTR 8[rdi]
    ret
```

Adding an empty user-provided destructor turned the 16-byte value into a hidden pointer, with the caller storing both fields to memory first. The resulting rule of thumb for parameters:

- **Pass by value** anything trivially copyable and at most about 16 bytes: integers, doubles, pointers, `std::string_view`, `std::span`, small structs of these. You avoid aliasing and the indirection.
- **Pass by `const&`** anything larger or with non-trivial copying: `std::string`, `std::vector`, large structs.
- **Pass by value and move** when the function stores its own copy (a "sink" parameter); Section 8.2 explains why.

## Object Lifetime and Storage Duration

### Storage versus lifetime

Two separate questions describe every object. Its **storage duration** says how long the *memory* exists. Its **lifetime** says when the *object* exists in that memory: it begins when initialization completes and ends when the destructor starts (or, for types without a destructor, when the storage is released or reused). The distinction matters because storage can exist without a live object, before construction or after destruction, and touching an object outside its lifetime is undefined behaviour even though the bytes are still there. Most of the bugs in this section are exactly that.

### The four storage durations

| Storage duration | Declared as | Memory exists | Object created | Object destroyed |
|---|---|---|---|---|
| Automatic | local variable | while the block runs | at the declaration | at block end, in reverse order |
| Static | global, or `static` local or member | for the whole run | before `main`; locals at first pass | after `main`, in reverse order |
| Thread | `thread_local` | for each thread's life | at thread start or first use | at thread exit |
| Dynamic | `new`, or via an allocator | allocation to deallocation | by `new` | by `delete` |

### What static locals and thread_local cost

Since C++11, initialization of a function-local static is thread-safe: if two threads call `registry()` at once, one constructs and the other waits. GCC implements this with a hidden *guard byte* per static. The fast path, once initialized, is a byte load and a branch (GCC 13, -O2, for a `static const std::string` local):

```asm
    movzx  eax, BYTE PTR _ZGVZ10venue_nameB5cxx11vE4name[rip]   ; guard byte
    test   al, al
    je     .L15        ; not yet initialized: cold path calls __cxa_guard_acquire
```

On x86 a plain load already has acquire semantics (Section 14.3), so the fast path costs about one cycle when the guard is in cache and the branch is predicted. The slow path takes a lock inside `__cxa_guard_acquire` and runs once. If a static local has a constant initializer (`static int depth = 10;` or anything `constexpr`), there is no guard at all; the value is baked into the data section.

`thread_local` variables live in per-thread storage addressed through the `fs` segment register. For a variable defined in the executable itself, access is one instruction, as cheap as a global:

```asm
    mov    rax, QWORD PTR fs:tl_seq@tpoff     ; ++tl_seq
    add    rax, 1
    mov    QWORD PTR fs:tl_seq@tpoff, rax
```

Two cases are slower. A `thread_local` with a *dynamic* initializer (a `std::string`, say) used from another TU is reached through a call to a compiler-generated TLS init function on every access, so that it can be constructed lazily. And code in a *shared library* typically uses the general-dynamic TLS model, which calls `__tls_get_addr`. If you use `thread_local` on a hot path, give it a constant initializer and keep it in the executable. Operating-system detail on threads is in Section 13.1.

### Dangling: the shapes you will meet

A **dangling** reference, pointer, iterator or view refers to an object whose lifetime has ended. The common shapes:

1. **Returning a reference or view to a local.** `std::string_view name() { std::string s = build(); return s; }` returns a view into a buffer that `s`'s destructor frees on return. GCC 13 warns when a function returns a plain reference or pointer to a local (`-Wreturn-local-addr`), but compiled this `string_view` version without a word.
2. **Binding to a temporary through a function.** A temporary bound *directly* to a `const T&` or `T&&` local has its lifetime extended to that of the reference: `const std::string& r = std::string("x");` is safe. The extension does *not* pass through a function call. `const std::string& r = std::max(a, std::string("zzz"));` binds `r` to whichever argument `max` returned; if it was the temporary, it dies at the end of the full expression and `r` dangles.
3. **Range-for over a member of a temporary, via a function.** `for (char c : make_order().symbol)` is safe: the temporary `Order` is extended because `.symbol` names a member of it directly. `for (char c : make_order().get_symbol())`, where `get_symbol()` returns a `const std::string&`, dangles in C++20: the `Order` dies before the loop body runs. AddressSanitizer reported `stack-use-after-scope` for the second form in the build container. C++23 extends the lifetimes of all temporaries in the range expression, but you are writing C++20.
4. **Container reallocation.** A pointer, reference or iterator into a `std::vector` dangles after a `push_back` that reallocates. That is diagnostic question D5; Section 10.1 covers the rules.
5. **Lambdas that capture by reference** and outlive the scope they captured from (a callback stored for later). Capture by value, or make sure the lambda dies first.

The common thread is that C++ does not track lifetimes for you. Every reference, pointer, `string_view`, `span` and iterator is a non-owning view, and you must be able to say what owns the object and why it outlives the view. Section 11.4 covers lifetime bugs as undefined behaviour, and Section 16.6 covers the tools that catch them.

### The static initialization order fiasco

Within one TU, namespace-scope variables are initialized in the order they are defined. *Across* TUs, the order of dynamic initialization is unspecified. If `b.cpp` has `bool ok = g_registry.add("X");` and `g_registry` is a `Registry` with a constructor defined in `a.cpp`, then `add` may run on an object that has not been constructed yet, and whether it does depends on link order. The standard fixes are:

- **Construct on first use**: replace the global with a function returning a reference to a function-local static (the `registry()` pattern on lines 15–18 of Listing 5.2). Initialization order now follows call order, at the price of the guard check above. The mirror-image problem, a destructor using another static that has already been destroyed at exit, remains; the usual answer is to never destroy the object (allocate it with `new` and leak it on purpose).
- **Constant initialization**: if the object can be initialized at compile time, declare it `constinit` (C++20). The compiler then refuses to compile unless the initialization is constant, and constant initialization happens before any dynamic initialization, so the ordering problem cannot arise. Section 9.2 covers `constexpr`, `consteval` and `constinit`.

## Initialization

### The forms

C++ has many initialization syntaxes, and they do not all mean the same thing. The ones that matter:

| Kind of init | Example | Scalar | Class type |
|---|---|---|---|
| Default | `int x;` `T t;` | indeterminate (automatic or dynamic storage) | default constructor runs |
| Value | `int x{};` `T t{};` `T()` | zero | zeroed, then default-constructed (see below) |
| Zero | every static or thread-local variable, first | zero | all bytes zero, before its own initialization |
| Direct | `T t(a, b);` | converts; narrowing allowed | constructor overload resolution |
| List | `T t{a, b};` `T t = {a, b};` | narrowing is an error | `initializer_list` constructor wins if viable |
| Aggregate | `Order o{1, 2};` `Order o{.id = 1};` | — | members in declaration order |

Two details the table compresses. Value-initialization zeroes a class object first only if its default constructor is not user-provided; with a user-provided one, it simply calls it. In aggregate initialization, members you omit take their default member initializer if they have one and are value-initialized otherwise. Reading an indeterminate value is undefined behaviour (Section 11.2). The rule for writing code is therefore simple: **never leave a scalar default-initialized**. Give every member a default member initializer, and write `{}` for locals you fill in later.

### The most vexing parse

If something can be parsed as a declaration, C++ parses it as a declaration:

```cpp
Timer t();                 // declares a FUNCTION t returning Timer, not an object
Session s(Clock());        // declares a function s taking a (pointer to a) function
                           // returning Clock, and returning Session
Timer t2{};                // fix: braces cannot be a parameter list
Session s2{Clock{}};       // fix
```

GCC 13 warns about both forms (`-Wvexing-parse`, on by default), but the error you usually see is a confusing one later, when you try to call a member function on `t`. Brace initialization removes the ambiguity.

### Initialization you pay for

Value-initialization is not free when the object is large. `std::make_unique<char[]>(n)` and `std::vector<char>(n)` both zero all n bytes, which is a `memset`: cheap for a few kilobytes, measurable for a few megabytes, and it also *touches every page*, which forces the operating system to back the memory with physical pages (Section 7.4). When the buffer will be completely overwritten anyway (a receive buffer, say), C++20's `std::make_unique_for_overwrite<char[]>(n)` (line 69) default-initializes instead and skips the `memset`. For vectors, `reserve(n)` allocates without constructing anything; elements are constructed as you `push_back` or `emplace_back` them.

## Classes: Constructors, Destructors, Rule of 0/3/5

### The special member functions

The compiler can generate six **special member functions** for a class: the default constructor, the destructor, the copy constructor, the copy assignment operator, the move constructor and the move assignment operator. Whether it does depends on what you declare yourself:

| You declare | Default ctor | Copy ctor and copy assign | Move ctor and move assign |
|---|---|---|---|
| nothing | implicit | implicit | implicit |
| any constructor | none | implicit | implicit |
| a destructor | implicit | implicit (deprecated) | **not declared** |
| copy ctor or copy assign | implicit (none if copy ctor) | yours; the other implicit (deprecated) | **not declared** |
| move ctor or move assign | implicit (none if move ctor) | **deleted** | yours; the other not declared |

The destructor is implicitly declared unless you declare one. "Declare" includes `= default`: writing `~T() = default;` is a user-*declared* destructor and suppresses the implicit moves just as much as `~T() {}` does. The "not declared" entries are the dangerous ones. When the move constructor is not declared, an expression like `T(std::move(x))` does not fail to compile; overload resolution quietly picks the copy constructor, because a `const T&` parameter accepts an rvalue.

### The rule of three and the rule of five

If a class *owns a resource* by hand (memory from `new`, a file descriptor, a socket, a mapped region), the generated members do the wrong thing: they copy the handle, not the resource, so two objects end up owning the same thing and both release it. The **rule of three** (pre-C++11) says that if you need a custom destructor, copy constructor or copy assignment, you need all three. The **rule of five** adds the two move operations, without which the class is copyable but every "move" is a copy.

### The rule of zero, and the destructor that turns moves into copies

### Trivially copyable types

A type is **trivially copyable** if copying it is the same as copying its bytes: no user-provided copy, move or destructor, and every member and base trivially copyable. The property matters out of proportion to its definition:

- `std::memcpy` of such an object is a valid copy, so it can be sent over the network or shared memory as raw bytes, written to a binary log, or placed in a lock-free queue slot.
- It is passed in registers when small (the ABI rule above).
- Containers and algorithms copy it with `memmove` rather than an element-by-element loop.

Message structs on a hot path should be trivially copyable, and it costs one line to guarantee it: `static_assert(std::is_trivially_copyable_v<OrderMsg>);`. Adding a `std::string` member or an innocent-looking destructor then fails the build instead of silently changing performance. The byte layout of such structs is the subject of Section 6.1.

### Conversions: explicit

A constructor callable with one argument is also an implicit conversion. With `struct Price { Price(std::int64_t ticks); };`, a call `send(42)` to `void send(Price)` compiles and constructs a `Price` from 42, which is rarely what anyone meant when there is also a `Quantity` type constructible from an integer. Mark single-argument constructors `explicit` unless the implicit conversion is genuinely the intent (as it is for `std::string` from a string literal). Strong types for prices, quantities and order IDs that do not convert into each other prevent a whole class of bug at zero runtime cost; Section 18.6 builds them.

## Integer Representation

### Two's complement

Since C++20, signed integers are guaranteed to use **two's complement**: an n-bit signed value with bits b_{n−1} … b_{0} means −b_{n−1}·2^{n−1} + Σ_{i<n−1} b_{i}·2^{i}. So −1 is all ones (`0xffffffff`), the minimum value is `0x80000000` (−2,147,483,648 for 32 bits), and the range is asymmetric: there is one more negative value than positive, so `-INT_MIN` and `std::abs(INT_MIN)` overflow. Addition, subtraction and multiplication are the *same machine instructions* for signed and unsigned values; only comparison, division, right shift and widening differ.

### Widths on Linux x86-64

Linux on x86-64 uses the **LP64** data model: `int` is 32 bits, `long` and `long long` are 64 bits, pointers and `std::size_t` are 64 bits. Windows uses **LLP64**, where `long` is 32 bits. Code that must have a particular width says so with `<cstdint>` types: `std::int32_t`, `std::uint64_t`, and so on. Use them for anything stored, sent over a wire, or used in arithmetic that might be large: prices in ticks, quantities, notionals, sequence numbers, nanosecond timestamps (2^{63} ns is about 292 years, while 2^{31} ns is about 2.1 seconds).

### Promotions and the usual arithmetic conversions

Before arithmetic, C++ applies two sets of rules, and almost every integer bug in an interview question comes from them:

1. **Integral promotion.** Operands narrower than `int` (`char`, `short`, `std::uint8_t`, `bool`) are converted to `int` first. So `std::uint8_t` + `std::uint8_t` is an `int`, and 200 + 100 is 300, not 44.
2. **Usual arithmetic conversions.** If the operands then differ, they are converted to a common type. The rule that bites: if one operand is unsigned and the other is signed of the same rank (`int` and `unsigned`, `long` and `unsigned long`), **the signed operand is converted to unsigned**. So `-1 < 1u` compares 4294967295 with 1 and is false.

### Division, remainder and shifts

Integer division truncates toward zero, and the remainder takes the sign of the dividend, so that `(a / b) * b + a % b == a` always holds: −7 / 2 = −3 and −7 % 2 = −1. An arithmetic right shift rounds toward negative infinity instead: −7 >> 1 = −4 (right-shifting a negative value has been defined as arithmetic since C++20). So `x / 2` and `x >> 1` differ for negative `x`, and the compiler cannot turn one into the other for signed types. GCC's code shows the fix-up it adds for signed division:

```asm
_Z5sdiv2i:              ; int sdiv2(int x) { return x / 2; }
    mov   eax, edi
    shr   eax, 31       ; 1 if x is negative, else 0
    add   eax, edi      ; bias negative values toward zero
    sar   eax           ; arithmetic shift
    ret
_Z5udiv2j:              ; unsigned udiv2(unsigned x) { return x / 2; }
    mov   eax, edi
    shr   eax
    ret
_Z6sdiv10l:             ; long sdiv10(long x) { return x / 10; }
    movabs rax, 7378697629483820647   ; about 2^66 / 10
    imul  rdi           ; high half of the 128-bit product in rdx
    sar   rdi, 63
    sar   rdx, 2
    mov   rax, rdx
    sub   rax, rdi      ; correct the rounding for negative x
    ret
_Z5sdivvll:             ; long sdivv(long x, long d) { return x / d; }
    mov   rax, rdi
    cqo                 ; sign-extend rax into rdx:rax
    idiv  rsi           ; the slow instruction
    ret
```

Division by a *compile-time constant* becomes a multiplication by a precomputed reciprocal plus shifts, a few cycles. Division by a *runtime* value is the `idiv` instruction, which is the slowest common integer instruction (Section 5.10 measures it). That is a reason to keep tick sizes and lot sizes as compile-time constants where possible, to divide once and multiply many times, or to precompute a reciprocal for a divisor that changes rarely. Other shift rules: shifting by a negative amount or by at least the width of the type is undefined behaviour, and `1 << 31` in `int` is now well defined (it produces `INT_MIN`), but `1u << 31` says what you mean.

## Floating Point and Fixed-Point Prices

### IEEE 754 binary64 in one paragraph

A `double` is 64 bits: 1 sign bit, an 11-bit exponent and a 52-bit fraction. A normal value is (−1)^{s} × 1.f × 2^{e−1023}, so there are 53 significant bits, about 15–17 significant decimal digits. Consequences you must know: every integer up to 2^{53} = 9,007,199,254,740,992 is exact, but beyond it consecutive doubles are at least 2 apart. The gap between 1.0 and the next double is `DBL_EPSILON` = 2^{−52} ≈ 2.2 × 10^{−16}. Each arithmetic result is the exact result *rounded* to the nearest representable value (ties to even). Below 2^{−1022} come **subnormals**, which trade precision for gradual underflow down to about 4.9 × 10^{−324}. There are infinities, signed zeros (−0.0 == 0.0, but they are different bit patterns), and NaNs, which compare unequal to everything, including themselves. `float` is the same idea with 32 bits: 24 significant bits, so integers are exact only up to 2^{24} = 16,777,216.

The decisive fact for trading: **most decimal fractions are not representable.** 0.1, 0.05, 1.15 and 100.10 all become the nearest binary fraction, which is slightly above or slightly below the decimal value.

### Fixed-point: prices as integers

The robust representation for a price is an **integer count of a fixed unit**. Two common choices:

- **Ticks of the instrument.** A price of 1.15 with a tick size of 0.05 is the integer 23. Every valid price is representable, every invalid price is detectable, and you can index arrays by price (Section 18.1 does this for an order book). The drawback is that the unit differs per instrument, and tick sizes can change.
- **A fixed decimal scale for everything,** such as units of 10^{−4} or 10^{−8} of the currency. One type for all instruments, and conversion to ticks is an exact integer division. The range is still ample: with a scale of 10^{−8}, `std::int64_t` holds values up to about 9.2 × 10^{10} currency units.

Lines 11–28 of Listing 5.7 parse decimal text straight into units of 10^{−4} without ever creating a double. They reject more decimals than the scale can hold (line 21) instead of rounding silently, reject values that would overflow (line 16), and reject trailing garbage (line 25). Then lines 61–71 check whether a price is on the tick grid with an exact remainder test, something that cannot be done reliably with doubles.

With integers, equality is exact, hashing is exact, sums never drift, and comparisons are single-cycle integer instructions. The costs are explicit scaling when multiplying (price × quantity has the units of both, and a product of two scaled numbers needs rescaling) and overflow budgeting, since a notional of 10^{10} currency units in 10^{−8} units is 10^{18}, close to the `int64` limit of 9.2 × 10^{18}. Use `__int128` for intermediate products when the budget is tight.

Doubles remain the right tool for quantities that are inherently approximate: model outputs, volatilities, statistics, signals. The rule is to **convert at the boundary, once, with rounding**: a model may produce a theoretical price as a double, and the code that turns it into an order rounds it to an integer price on the tick grid (choosing the rounding direction deliberately, since rounding a bid up could cross the spread). Everything from that point on is integers. Section 18.6 builds full price and time types on this foundation.

### Hazards that cost time

- **Subnormals.** On many Intel cores, an operation that consumes or produces a subnormal can take a microcode *assist* costing on the order of 100 cycles (Section 5.10 measured one). Values can drift into the subnormal range in decaying filters and exponential moving averages. Setting the FTZ (flush-to-zero) and DAZ (denormals-are-zero) bits of the MXCSR register makes the hardware treat them as zero, at the cost of strict IEEE semantics.
- **`-ffast-math`.** It lets GCC reassociate and vectorize floating-point code, which can be a large speedup, but it also assumes NaNs and infinities never occur (`-ffinite-math-only`), so explicit `std::isnan` checks may be optimized away. When used to link an executable on x86, it also adds start-up code that sets FTZ and DAZ for the whole process. Use it deliberately and per file, never as a blanket flag on code that validates inputs.

## Exceptions vs Error Codes

This section is an overview; Section 8.6 measures the costs and covers `noexcept` in depth.

### How exceptions work in GCC

GCC on Linux uses **table-based** ("zero-cost") exceptions, as specified by the Itanium C++ ABI. The compiler emits no extra instructions on the normal path for `try` blocks. Instead it writes *unwind tables* (`.eh_frame` and `.gcc_except_table`) that describe, for each range of instruction addresses, how to restore the stack and which destructors and handlers to run. A `throw` allocates the exception object on the heap (`__cxa_allocate_exception`), then the unwinder walks the stack *twice*: once to find a matching handler, and once to run destructors while unwinding to it. Each frame requires a table lookup, and matching a handler involves run-time type information. So:

- **Not throwing is nearly free** in executed instructions. Costs remain: larger binaries, and the optimizer must keep state consistent at every call that might throw, which can block some optimizations. Marking functions `noexcept` helps (Section 8.6).
- **Throwing is expensive**: a heap allocation, table searches and type matching, orders of magnitude more than a return. It also takes code paths that are cold in every cache.

### Which to use

The guideline used in most low-latency codebases follows from those costs:

- **Expected outcomes are return values.** A risk check rejecting an order, a parse failure on malformed input, a full queue, an unknown instrument ID: these happen in normal operation, so they are values. Return an `enum class` code, a small struct, or `std::optional` when there is nothing more to say. C++23 adds `std::expected<T, E>`, which carries either a value or an error; in C++20 you write a small equivalent yourself or use `std::error_code`.
- **Truly exceptional, unrecoverable conditions may throw**, typically outside the hot path: an invalid configuration at start-up, failure to allocate the memory pools, a corrupted state that means the process must stop trading. An exception carries rich context up to a place that can log it and shut down cleanly.
- **Some codebases compile with `-fno-exceptions`** and treat any such condition as fatal. `try` and `throw` then no longer compile, and an exception thrown from inside the standard library (by `new`, `std::vector::at` and so on) finds no handler and terminates the process. That is a legitimate choice, as long as it is a conscious one.

## Interview Questions

**Q1. Walk me through what happens between `g++ main.cpp` and a running program.**
Preprocessing pastes headers and expands macros, producing a translation unit. Compilation parses it, instantiates templates, optimizes and emits assembly. The assembler produces an object file with machine code, a symbol table of defined and undefined symbols, and relocations. The linker combines object files and libraries, resolves every undefined symbol to exactly one definition, and writes the executable. At run time the loader maps it into memory, the dynamic linker resolves shared-library symbols, static initializers run, and then `main` is called. A strong answer mentions that each TU is compiled in isolation, which explains headers, the ODR and the need for LTO to inline across files.

**Q2. What does `inline` mean today?**
It means the definition may appear in multiple TUs, which must all be identical; the linker keeps one. That is what allows functions and (since C++17) variables to be defined in headers. It is only a weak hint for the inliner, which inlines based on its own heuristics whenever it can see the body.

**Q3. You get "multiple definition of `foo`" at link time. What happened, and how do you fix it?**
A function or variable with external linkage was defined in a header included by several `.cpp` files, so several object files define it. Fix a function by making it `inline` or moving its body to one `.cpp` file. Fix a variable with `inline` (C++17) or with an `extern` declaration in the header and one definition in a `.cpp`. Do not reach for `static` unless you really want a separate copy per TU.

**Q4. How is a reference different from a pointer, and how is it implemented?**
A reference is an alias that must be initialized, cannot be reseated, and has no null state; a pointer is an object holding an address that can be null and reassigned, and supports arithmetic. At the ABI level a reference parameter or member is passed and stored exactly like a pointer. The difference is in what the language allows and what the compiler may assume, not in the machine code.

**Q5. When do you pass by value and when by const reference?**
By value for cheap, trivially copyable types up to about 16 bytes (scalars, `string_view`, `span`, small structs): they travel in registers and cannot alias. By `const&` for large or expensive-to-copy types. By value plus `std::move` for sink parameters the function will store. A small type with a non-trivial destructor goes through memory even when passed by value.

**Q6. Can a value change while you hold a `const&` to it?**
Yes. `const` restricts writes through that name only. The object can be changed through another alias or by another thread, and the compiler has to assume that might happen, which is why it reloads values through references after any store it cannot prove unrelated.

**Q7. What is the static initialization order fiasco, and how do you avoid it?**
Dynamic initialization order of namespace-scope objects across TUs is unspecified, so an initializer in one file may use an object from another file before it is constructed. Avoid it with a function-local static (constructed on first use, thread-safe since C++11, with a guard check on each call), or with `constinit` and constant initialization, which happens before any dynamic initialization. Mention the mirror problem at exit, and that a deliberately leaked singleton avoids it.

**Q8. State the rule of three, five and zero. What happens if I add an empty destructor to a class with a `std::vector` member?**
If a class manages a resource by hand, it needs a custom destructor, copy constructor and copy assignment (three), plus move constructor and move assignment for efficiency (five). Better, use members that manage themselves and declare none of them (zero). Declaring any destructor, even `= default`, suppresses the implicit move operations, so moves of the class silently fall back to copies: an allocation and a byte copy for every "move", and `std::vector` reallocation copies instead of moving. Restore them with `= default` for all five, or remove the destructor.

**Q9. Why does `-1 < 1u` evaluate to false?**
The usual arithmetic conversions convert the `int` to `unsigned` because both have the same rank, so −1 becomes 4294967295. Compile with `-Wall -Wextra` (`-Wsign-compare` catches it), use `std::cmp_less` for mixed comparisons, and keep sizes and indices in one signedness, for example with `std::ssize`.

**Q10. Why shouldn't prices be stored as `double`?**
Most decimal prices are not representable in binary, so the same price computed in two ways can give two different doubles. That breaks equality, map and hash keys, and tick conversion by truncation, and sums drift away from the exchange's decimal records. Store prices as integers (ticks or a fixed decimal scale), parse text directly into integers, and if a double comes from a model, convert it once with deliberate rounding. Integers are also faster to compare and allow price-indexed arrays.

**Q11. What is a subnormal, and why would a latency engineer care?**
A subnormal is a nonzero double smaller in magnitude than the smallest normal value, about 2.2 × 10^{−308}, stored without the implicit leading 1. On many Intel cores an operation that consumes or produces one triggers a microcode assist costing on the order of 100 cycles. They appear in decaying filters and moving averages. The fixes are to clamp tiny values to zero or to set FTZ/DAZ.

**Q12. Exceptions or error codes in a trading system?**
Error codes (or `std::optional`, a result type, or `std::expected` in C++23) for anything that happens in normal operation: rejects, parse failures, full queues. The happy path of table-based exceptions is nearly free, but a throw costs a heap allocation, table lookups and stack unwinding, orders of magnitude more than a return, so it must never be the way normal events are reported. Exceptions are acceptable for fatal conditions such as start-up configuration errors, where a rich message and clean shutdown matter more than speed. Some firms compile with `-fno-exceptions` altogether.

**Q13. Explain the most vexing parse.**
If a statement can be parsed as a declaration, it is. `Timer t();` declares a function returning `Timer`, and `Session s(Clock());` declares a function taking a function. Use braces, `Timer t{};` and `Session s{Clock{}};`, which cannot be parsed as parameter lists.

## Key Takeaways

- **Compilation model:** each `.cpp` is compiled alone into an object file with defined (T, D, B) and undefined (U) symbols; the linker joins them. Headers are pasted text. The ODR allows identical inline, template and class definitions in many TUs; *different* definitions are undiagnosed undefined behaviour that can change with the optimization level. `inline` means "many identical definitions allowed", not "inline this". No inlining across TUs without LTO.
- **References and const:** a reference is an alias implemented as a pointer; `const&` restricts *you*, not the object, and the compiler must assume aliasing, which costs reloads and blocks optimization. Pass small trivially copyable types by value; types with non-trivial copy or destruction are always passed through memory.
- **Lifetime:** four storage durations (automatic, static, thread, dynamic). Static locals cost a guard check; `thread_local` in the executable is as cheap as a global. Lifetime extension applies only to a temporary bound directly to a local reference. Every view (reference, pointer, `string_view`, `span`, iterator) needs an owner that outlives it. Avoid cross-TU static initialization dependencies with function-local statics or `constinit`.
- **Initialization:** never leave scalars default-initialized; prefer braces (no narrowing, no vexing parse) but remember that they prefer `initializer_list`; members initialize in declaration order; value-initializing big buffers is a `memset` you may not need (`make_unique_for_overwrite`).
- **Special members:** rule of zero by default; rule of five for a class that wraps one resource, with `noexcept` moves. Declaring any destructor, even `= default`, silently turns moves into copies. Keep hot-path message types trivially copyable and `static_assert` it.
- **Integers:** two's complement, LP64 widths, promotion of small types to `int`, signed-to-unsigned conversion in mixed comparisons (`std::cmp_less`, `std::ssize`). Widen before multiplying; detect overflow with `__builtin_*_overflow`. Division truncates toward zero, `>>` floors; division by a runtime value is the slowest common integer operation, and division by a constant is cheap.
- **Floating point:** 53-bit significands, exact integers to 2^{53}, decimal fractions are approximations, results depend on operation order, NaN ≠ NaN, subnormals can cost ~100 cycles. Prices are integers (ticks or a fixed decimal scale), parsed directly from text; convert model doubles once with deliberate rounding.
- **Errors:** return values for expected outcomes, exceptions only for rare fatal conditions off the hot path; `[[nodiscard]]` on results that must be checked.
