# The C++ Object Model

Chapter 5 treated objects as values with lifetimes. This chapter opens them up: which bytes an object occupies, where each member and base class sits, what the hidden pointer in a polymorphic object points to, and what each of those decisions costs when a loop touches millions of objects. These are the questions behind "what does `sizeof` print?", "how does a virtual call work?" and "why is your order struct 40 bytes?", and they come up in almost every C++ round at a low-latency firm, because the answers decide how many cache lines a hot path touches and how many unpredictable branches it executes.

Everything here describes GCC on x86-64 Linux, which follows the System V ABI and the **Itanium C++ ABI** (named after the platform it was first written for, but used by GCC and Clang on essentially every non-Windows platform). The C++ standard leaves most layout decisions to the implementation; where a rule below is an ABI rule rather than a language rule, the text says so. MSVC on Windows uses a different ABI, and a few details differ there.

## Object Layout, Alignment and Padding

### Intuition: boxes on aligned shelves

Picture memory as a long shelf marked every byte, and every type as a box that may only be placed at a mark divisible by its **alignment**: a 4-byte `int` at multiples of 4, an 8-byte `double` at multiples of 8. A struct is a row of boxes placed left to right in declaration order. When the next box cannot start at the current position, the gap is left empty: that gap is **padding**. The struct as a whole must also end at a multiple of its own alignment, so that a second copy placed immediately after it (as in an array) is aligned too. That end gap is **tail padding**.

Why does the hardware care? A load of an aligned 8-byte value touches exactly one 64-byte cache line and one page, so the CPU can read it in a single access. A misaligned value can straddle two lines or even two pages. x86-64 handles that correctly but more slowly (Section 6.9 measures it); some other architectures fault. A locked (atomic) instruction on a value that straddles two cache lines, a *split lock*, is far slower still and recent Linux kernels can be configured to warn about or penalize it. Compilers therefore align every object by default, and `std::atomic` objects are always naturally aligned.

### The rules

On x86-64 Linux the alignment of each fundamental type equals its size, up to 16:

| Type | Size | Alignment |
|---|---|---|
| `char`, `bool`, `std::int8_t` | 1 | 1 |
| `short`, `std::int16_t` | 2 | 2 |
| `int`, `float`, `std::int32_t` | 4 | 4 |
| `long`, `long long`, `double`, pointers, `std::size_t` | 8 | 8 |
| `long double` (x87 80-bit, padded) | 16 | 16 |
| `__int128`, `std::max_align_t` | 16 | 16 |

For a class type:

1. Non-static data members are laid out **in declaration order** (the standard guarantees this for members with the same access level; the Itanium ABI uses declaration order throughout), each at the next offset that is a multiple of its alignment.
2. The class's **alignment** is the largest alignment of any member or base (or larger, if you ask for it with `alignas`).
3. Its **size** is rounded up to a multiple of its alignment. Hence `sizeof(T)` is always a multiple of `alignof(T)`, and the array stride is exactly `sizeof(T)`.

Diagnostic question D4 is the canonical example. In `struct S { char a; int b; char c; };`, `a` sits at offset 0, `b` needs a multiple of 4 so three padding bytes follow `a` and `b` occupies offsets 4–7, `c` sits at offset 8, and three bytes of tail padding round the size up to 12. Half of the object is padding. Reordering as `int b; char a; char c;` gives 4 + 1 + 1 = 6 bytes of data plus 2 of tail padding: 8.

- **Lines 62–70.** An array of 24-byte elements that starts on a line boundary has one element in four straddling two cache lines (the output reports 16 of 64), and 40- or 48-byte elements straddle half the time. Reading a straddling element can cost two cache misses instead of one. Sizes that divide 64 (16, 32) or are multiples of it never straddle, which is one reason to pad a hot record from 24 to 32 bytes or to split it, a decision Section 6.7 and Section 18.1 return to.

Reordering for size is not the only consideration. Fields read together should sit together (ideally in one cache line), and the fields used on the hot path can be grouped at the front with rarely used fields at the back or in a separate "cold" struct. Minimal size and good locality usually agree, and when they disagree, measure.

### Packed structs and wire formats

Binary market-data and order-entry protocols define messages with fields at exact byte offsets and no padding. The usual way to describe such a message in C++ is a **packed** struct, as on lines 33–42: `#pragma pack(push, 1)` sets the maximum alignment to 1, so members are placed back to back, and `static_assert` pins the size and offsets to the specification so that any mistake is a compile error. Three cautions:

- **Members of a packed struct are misaligned.** The compiler knows this when you access `msg.price` directly and emits instructions that tolerate it (on x86-64 an ordinary `mov`). But a pointer or reference to a packed member *loses* that knowledge: `std::uint32_t* p = &msg.qty;` produces a pointer the compiler assumes is 4-byte aligned, and dereferencing it is undefined behaviour (Section 11.3) that can break when the compiler uses instructions that require alignment. GCC 13 diagnoses this for `__attribute__((packed))` structs (binding a non-const reference is an error, taking the address is a `-Waddress-of-packed-member` warning) but printed nothing for the same struct declared under `#pragma pack` in the build container.
- **Reading a message out of a network buffer by casting the buffer pointer to `WireAddOrder*` is undefined behaviour** under the strict-aliasing and lifetime rules, however common it is. The defined way is `std::memcpy` of the bytes into a local object (or of each field into a local variable). For fixed small sizes, GCC compiles that memcpy to a plain load, so it costs nothing (Section 11.3; Section 18.2 builds a parser this way).
- **Byte order is part of the format.** x86-64 is little-endian; a protocol that specifies big-endian fields needs an explicit byte swap (`std::byteswap` is C++23; in C++20 use `__builtin_bswap32` and friends). Read each protocol's specification rather than assuming.

To inspect layouts in practice, `offsetof` plus `static_assert` documents and enforces them in code; `-Wpadded` makes GCC report every padding gap; `g++ -fdump-lang-class` dumps class and vtable layouts; and the `pahole` tool (from the dwarves package) prints the layout of every struct in a compiled binary, with holes marked.

## Empty Base Optimization and [[no_unique_address]]

### Why an empty class has size 1

A class with no data members, such as a stateless comparator, an allocator, a deleter or a locking policy that does nothing, still has `sizeof` equal to 1. The language requires distinct objects of the same type to have distinct addresses, and `sizeof(T) == 0` would put every element of a `T[10]` at the same address. As an ordinary member, that one byte also brings padding up to the alignment of the next member, so an empty policy can cost a whole 8 bytes.

## Inheritance Layout and this-Pointer Adjustment

### Single inheritance

A derived object contains its base class as a **subobject**, normally at offset 0, followed by the derived class's own members. Converting `Derived*` to `Base*` is then free: the address does not change. Two Itanium ABI details are worth knowing for interviews:

- **Tail-padding reuse.** If the base is not a POD type in the ABI's sense (roughly: it has virtual functions, base classes, a user-provided constructor or destructor, or non-public members), the derived class may place its first members *inside the base's tail padding*. A `struct P { virtual ~P(); int x; };` is 16 bytes (vptr plus `x` plus 4 bytes of tail padding), and `struct Q : P { int y; };` is also 16, with `y` at offset 12. For a plain aggregate base, the padding is never reused (Problem P6.5).
- **The primary base.** If the first base class is not polymorphic but a later one is, the ABI places the polymorphic base first, so that its vptr can be shared with the derived class. Declaration order of bases is then not memory order.

### Virtual inheritance and the diamond

If two bases share a common base (`EquityA` and `ListedA` both derive from `Instrument`), a class deriving from both contains *two* `Instrument` subobjects (lines 19–22), and `stock.id` is ambiguous. Declaring the inheritance `virtual` (lines 23–25) makes the derived class contain one shared `Instrument`, placed at the end of the most-derived object (lines 53–59: both paths reach offset 32). Because its position depends on the most-derived type, code that only knows it has an `EquityV&` cannot compute the offset at compile time; it loads the offset from the vtable at run time. Virtual inheritance therefore adds vptrs (`StockV` is 40 bytes holding three `long`s of data) and an extra dependent load per access to a virtual base member. It is used in some library hierarchies (the iostreams classes, for example) and is rare on hot paths.

## vptr and vtable Mechanics

### The pieces

A class with at least one virtual function is **polymorphic**. Under the Itanium ABI each polymorphic object begins with a hidden pointer, the **vptr**, which points into a **vtable**, a read-only table that exists once per class (not per object). Here is the vtable GCC 13 emitted for the `Strategy` class of Listing 6.3 (assembler output, names mangled):

```asm
_ZTV8Strategy:                          ; vtable for Strategy
    .quad  0                            ; offset to top (0: this is the primary table)
    .quad  _ZTI8Strategy                ; pointer to the type_info for RTTI
    .quad  _ZN8StrategyD1Ev             ; <- vptr points here: ~Strategy() (complete)
    .quad  _ZN8StrategyD0Ev             ;    ~Strategy() then operator delete
    .quad  _ZN8Strategy7on_fillEl       ;    Strategy::on_fill(long)
    .quad  _ZN8Strategy3logEl           ;    Strategy::log(long)
    .quad  -8                           ; secondary table, for the Logger subobject
    .quad  _ZTI8Strategy
    .quad  _ZThn8_N8StrategyD1Ev        ; thunks that subtract 8 from this
    .quad  _ZThn8_N8StrategyD0Ev
    .quad  _ZThn8_N8Strategy3logEl
```

The vptr points at the first function slot (the *address point*), with the offset-to-top and the `type_info` pointer just before it. A virtual destructor occupies two slots: one that destroys the object, and a "deleting" one used by `delete p` that also frees the memory with the right size. The secondary table serves `Logger*` pointers: its offset-to-top of −8 lets `dynamic_cast<void*>` find the start of the whole object, and its slots are the thunks from Section 6.3.

A virtual call is two dependent loads and an indirect jump. For `long call_virtual(Handler& h, long x) { return h.on_msg(x); }`, GCC 13 produced:

```asm
_Z12call_virtualR7Handlerl:
    mov    rax, QWORD PTR [rdi]          ; load the vptr from the object
    jmp    [QWORD PTR 16[rax]]           ; load slot 2 (after the two destructors), jump
```

(It is a `jmp` rather than a `call` because the virtual call is the function's last action: a tail call.) The slot index is fixed at compile time from the declaration order of the virtual functions in the class definition, which is why adding a virtual function to a base class in a shared header changes the ABI, and every user must be recompiled.

### Where the vtable lives: the key function

The vtable must be emitted in exactly one object file. The Itanium ABI picks the TU that defines the class's **key function**: the first virtual function that is neither inline nor pure. If the class has no key function (every virtual function is defined inline in the class), every TU that needs the vtable emits a weak copy and the linker keeps one, like an inline function (Section 5.1). The classic error message **"undefined reference to `vtable for Foo`"** means the key function was declared but never defined, or its `.cpp` file was not linked: the linker cannot find the vtable, so it complains about the vtable rather than about the missing function.

## The Cost of Virtual Dispatch and Devirtualization

A virtual call costs in three distinct ways, and interviewers want to hear all three:

1. **Instructions and loads.** Load the vptr, load the function pointer, make an indirect call. Both loads are usually L1 hits (4–5 cycles each on recent cores), but they are dependent, and if the object or its vtable is cold the cost is a cache miss.
2. **Prediction.** The CPU predicts the target of an indirect call (Section 12.5) and speculatively executes it. A correct prediction makes the call nearly free. A misprediction is discovered only after both loads complete, and then the pipeline restarts down the right path.
3. **Lost optimization.** The compiler cannot inline a call whose target it does not know, so it cannot propagate constants into it, hoist work out of the loop, vectorize the loop, or keep values in caller-saved registers across it. This is often the largest cost, and it never shows up in a micro-benchmark of "one virtual call".

Reading the results:

- **Same target every time:** about 1.5 ns per call (roughly 4–5 cycles at the container's clock), including the loop and the arithmetic. The predictor always guesses right, and the two loads overlap with earlier iterations' work in the out-of-order core.
- **Targets cycling A, B, C:** almost as fast. Modern indirect-branch predictors use the history of recent branches, so a regular pattern is learned. Real message streams are rarely this regular.
- **Random targets:** about 6 times slower. With three equally likely types, the predictor can do little better than a guess, so roughly two calls in three are mispredicted. The implied cost per misprediction (about 12 ns, or 30-plus cycles here) is larger than the textbook 15–20-cycle branch-misprediction penalty because the mistake can only be detected after the two dependent loads have completed.
- **Direct call to a `final` class:** the virtual call disappears entirely and the body is inlined, so GCC unrolled the loop and combined two iterations' additions into one instruction, about 0.25 ns per element. No virtual-call implementation can come close to that, because the body is invisible to the optimizer.

### Devirtualization

The compiler can replace a virtual call with a direct one whenever it can prove the dynamic type:

- **The class or the function is `final`.** A call through a `Fast&` where `struct Fast final : Handler` cannot reach any other override. GCC compiled `long call_final(Fast& f, long x) { return f.on_msg(x); }` to a single `lea rax, 1[rsi]`: devirtualized and inlined. Marking leaf classes `final` is free and helps.
- **The object's type is known locally:** a local variable, or an object the compiler just watched being constructed.
- **Speculative devirtualization** (`-fdevirtualize-speculatively`, enabled at -O2): when analysis suggests one target is likely, GCC emits "if the vptr equals this class's vtable, run the inlined body; otherwise make the virtual call". It helps when one implementation dominates.
- **Link-time optimization** (`-flto`, Section 16.1) lets GCC see the whole program's class hierarchy and devirtualize calls whose possible targets only become clear across translation units.

The practical rule: a virtual call at *coarse* granularity (once per message or per strategy callback, with predictable targets) costs a few nanoseconds and buys a great deal of design flexibility. A virtual call *per element in an inner loop*, with unpredictable targets, can dominate the loop. The next section shows the alternatives.

## Alternatives: CRTP, std::variant, Function Pointers, Type Erasure

### The options

- **CRTP (static polymorphism).** A base class template takes the derived class as a parameter and calls it through `static_cast<Derived*>(this)`, so every call is resolved and inlinable at compile time (Section 9.5 covers the mechanics). Its limit is that each derived class is a *different type*: you cannot keep a `Handler<A>` and a `Handler<B>` in one container or choose between them at run time without another mechanism.
- **`std::variant<A, B, C>`** (Section 8.8). A closed set of alternatives stored *by value*: the storage is as large as the largest alternative plus an index. `std::variant<Equity, Future, Option>` from Listing 6.6 is 16 bytes, with the index byte at offset 8, after the storage. `std::visit` dispatches on the index; for three alternatives GCC 13 generated a short compare-and-branch chain:

```asm
_Z3valRKSt7variantIJ6Equity6Future6OptionEEl:   ; std::visit over the variant
    movzx  eax, BYTE PTR 8[rdi]          ; the index
    cmp    al, 1
    je     .L2                           ; Future
    cmp    al, 2
    mov    rax, rsi
    jne    .L6                           ; Equity: return mid
    imul   rax, QWORD PTR [rdi]          ; Option: (mid * delta) >> 10, inlined
    sar    rax, 10
    ret
```

  Every alternative's body is inlined. No heap allocation, no vptr, contiguous storage. Adding a new alternative is a code change to every `visit`, which is a feature when the set really is closed, such as the message types of one exchange protocol.
- **A tag and a `switch`.** The hand-written version of a variant, with the same code generation. It is what most feed parsers do anyway, since the message type byte arrives first on the wire.
- **A table of function pointers** indexed by a tag. Calls are indirect (not inlinable), but the table is a single cache line and the mechanism is easy to extend.
- **Type erasure**: `std::function`, or a hand-written equivalent. Any callable with the right signature is stored behind a uniform interface, usually a pointer to a small table of operations (a hand-made vtable; Problem P6.12 builds one). In libstdc++, `std::function` is 32 bytes and stores small callables inline but larger ones on the heap; every call is indirect. Section 8.7 covers its costs in detail.

## Array of Structs vs Struct of Arrays

### Intuition: rows or columns

A list of orders can be stored like a spreadsheet saved row by row (an **array of structs**, AoS: each order's fields together) or column by column (a **struct of arrays**, SoA: all prices together, all quantities together). Memory always moves in 64-byte cache lines, so the right layout depends on the *access pattern*. A query that reads every field of one order wants the order's fields in one line (AoS). A query that reads two fields of every order wants those two fields packed densely, with no unused fields sharing their lines (SoA). Between them is the **hot/cold split**: an array of small structs holding only the frequently used fields, with everything else in a parallel array.

AoS is not wrong. Looking up one order by ID and reading or updating most of its fields touches one cache line in AoS and one line *per field* in SoA. Order books therefore typically use AoS records for the orders themselves, often hot/cold split, and SoA-like arrays where whole-book scans happen; Section 18.1 makes those choices for a real book. A hybrid, **AoSoA** (arrays of small fixed-size blocks, each block stored column-wise), gets SIMD-friendly columns while keeping one record's fields within a few nearby lines.

| Operation | Approx. cost on recent x86-64 | Measured here | Why |
|---|---|---|---|
| Aligned load hitting L1 | 4–5 cycles latency | about 1.5 ns per dependent load (Listing 6.10) | address generation plus L1 tag and data access |

| Inlined call to a `final` class | 0 (the call disappears) | about 0.25 ns per element | the optimizer sees the body: unrolling, folding, possibly vectorization |
| `std::visit` or `switch` on random types | the same misprediction cost as above, minus the loads | about 7 ns per item (Listing 6.6) | a data-dependent branch, but contiguous data and inlined bodies |
| Grouping by type instead of dispatching | removes the decision | about 0.3 ns per item | no branch to mispredict; simple loops |
| `static_cast` down a hierarchy | 0–1 cycles | about 0.35 ns (with the loop's loads) | compile-time offset, no check |
| `typeid(*p) == typeid(T)` | a few cycles | about 0.7 ns | load the `type_info` pointer from the vtable and compare |
| `dynamic_cast`, success | tens of cycles | about 4 ns | a library call that walks the class hierarchy's type information |
| `dynamic_cast`, failure | more, grows with hierarchy size | about 18 ns | the search must exhaust the hierarchy before returning null |
| Heap-allocating each small object | tens of ns per allocate-and-free pair | about 4× slower event processing (Listing 6.8 vs 6.9) | allocator fast path, scattered objects, extra pointer chases (Section 7.2) |

What to take from the table: the object model's *direct* costs (a vptr, a thunk, a pointer adjustment) are single cycles. Its *indirect* costs are what matter: bytes moved through the memory hierarchy because of layout, branch mispredictions because of how dispatch is organized, and optimizations that cannot happen because the compiler cannot see through a call. Those are design decisions, and they are made when the types are designed, not when the code is tuned.

## Interview Questions

**Q1. What does `sizeof` give for `struct S { char a; int b; char c; };` on x86-64, and how would you shrink it?**
12. `a` at 0, three bytes of padding, `b` at 4–7, `c` at 8, three bytes of tail padding so the size is a multiple of the struct's alignment (4) and arrays stay aligned. Ordering the members by decreasing alignment (`int b; char a; char c;`) gives 8. Mention that padding contents are unspecified, which matters for `memcmp`, hashing and sending structs over a wire.

**Q2. Why does an empty class have size 1, and how do you avoid paying for it?**
Distinct objects of the same type must have distinct addresses, so the size cannot be zero. As a base class, an empty type can occupy zero bytes (the empty base optimization); as a member, C++20's `[[no_unique_address]]` allows the same. That is why `std::unique_ptr` with a stateless deleter is the size of a raw pointer.

**Q3. How is a virtual function call implemented?**
Each polymorphic object has a vptr, usually at offset 0, pointing into a per-class vtable of function pointers. A call loads the vptr, loads the slot for that function (its index is fixed at compile time), and calls indirectly with the object as `this`. The vtable also holds the offset-to-top and a `type_info` pointer used by `dynamic_cast` and `typeid`. Show the two-load, indirect-jump assembly if you can.

**Q4. What does a virtual call cost?**
Two dependent loads and an indirect call: a few cycles when the target is predicted and the data is cached. A mispredicted target costs a pipeline restart, which for indirect calls can be 20–30+ cycles because it is discovered late. The biggest cost is often that the call cannot be inlined, which blocks constant propagation, vectorization and other optimizations around it. Plus 8 bytes per object for the vptr.

**Q5. What happens if you call a virtual function from a constructor?**
It dispatches to the version in the class whose constructor is running, because each constructor sets the vptr to its own class's vtable before its body runs; the derived part does not exist yet. The same applies in destructors, in reverse. Calling a pure virtual function this way terminates the program with "pure virtual method called".

**Q6. How do multiple inheritance and casts interact?**
The second and later base subobjects sit at non-zero offsets, so converting a derived pointer to such a base adds an offset, and converting a null pointer must keep it null, which costs a test. Virtual functions overridden from a non-primary base are reached through thunks that adjust `this`. `reinterpret_cast` does no adjustment and produces a pointer to the wrong subobject.

**Q7. What is devirtualization, and how do you help the compiler do it?**
Replacing a virtual call with a direct (and then inlinable) call when the dynamic type is provable. Help it by marking classes or functions `final`, keeping objects whose type is locally known, and using LTO so the whole hierarchy is visible. GCC also speculatively devirtualizes likely targets behind a vptr check.

**Q8. Compare virtual functions, `std::variant`, CRTP and `std::function`.**
Virtual functions handle an open set of types, usually with heap objects, and are not inlinable. `std::variant` handles a closed set by value, contiguously, with inlinable visitors. CRTP resolves everything at compile time but gives each type its own instantiation, so it cannot form a heterogeneous container. `std::function` erases any callable behind an indirect call, with possible heap allocation for large callables. Choose by whether the set is open or closed, whether objects must live in one container, and whether the call is on a hot path.

**Q9. When is a struct of arrays better than an array of structs?**
When the hot operation reads a few fields of many records (scans, aggregations, risk sums), because SoA moves only those fields through the caches and enables SIMD. AoS is better when an operation uses most fields of one record (a lookup by ID), since they share a cache line. Hot/cold splitting is the common compromise.

**Q10. You see "undefined reference to `vtable for OrderHandler`". What happened?**
The class's key function, its first non-inline, non-pure virtual function, is declared but not defined anywhere in the link, or the file defining it was not linked. The vtable is emitted only in the TU that defines the key function, so the linker reports the missing vtable. Define the function (often a forgotten destructor body) or link the right object file.

**Q11. What is false sharing, and what does it have to do with layout?**
Two threads writing different variables that happen to share a 64-byte cache line force the line to bounce between their cores' caches, even though they never touch the same data. The fix is layout: put independently written variables on separate lines, for example with `alignas(64)` on each. Section 14.4 covers the coherence mechanics.

**Q12. How do you represent a binary wire message in C++?**
A packed struct with `static_assert`s on `sizeof` and every `offsetof`, matching the specification, used only as a description of the layout. Read and write it with `std::memcpy` between the network buffer and local values, never by casting the buffer pointer or by taking pointers to packed members, and handle byte order explicitly.

## Key Takeaways

- **Layout:** members in declaration order, each at a multiple of its alignment; the struct's alignment is its largest member's; the size is rounded up for arrays. `S {char; int; char}` is 12, reordered 8. Sort by decreasing alignment, keep hot fields together, and `static_assert` sizes and offsets of anything stored, hashed or sent.
- **Padding** has unspecified contents: never `memcmp`, byte-hash or transmit a padded struct (`has_unique_object_representations` checks it). Elements whose size does not divide 64 straddle cache lines; `alignas(64)` gives an object its own line.
- **Packed structs** describe wire formats; access them by member or by `memcpy`, never through pointers to members or a cast buffer pointer; handle byte order explicitly.
- **Empty types** cost one byte plus padding as members, nothing as bases (EBO) or with `[[no_unique_address]]`; stateless deleters keep `unique_ptr` at 8 bytes.
- **Inheritance:** the first base is at offset 0; later bases at offsets that pointer conversions add (with a null check); thunks adjust `this` for overrides reached through a secondary base. Virtual bases cost a vptr and a run-time offset lookup. `reinterpret_cast` between class pointers is almost always a bug.
- **vtables:** one per class; the vptr (8 bytes) points to the first function slot, preceded by offset-to-top and `type_info`. A virtual call is two loads and an indirect jump. Constructors and destructors set the vptr to their own class, so virtual calls inside them do not reach derived overrides. The vtable lives with the key function.
- **Dispatch cost** is mostly prediction and lost inlining: predictable virtual calls cost a few cycles, random ones tens of cycles, and `final`, local types or LTO let the compiler devirtualize. Variants and switches inline the bodies but still mispredict on random types; grouping work by type removes the decision and is often an order of magnitude faster.
- **AoS vs SoA:** time for scans follows bytes moved; split hot from cold fields, use columns for scans and records for lookups, and remove data-dependent branches or they will hide the memory effect.
- **Showdown lesson:** heap-allocated polymorphic events cost an allocation, a pointer chase and an unpredictable indirect call each; a reused, contiguous variant buffer allocated nothing in steady state and was about four times faster.
