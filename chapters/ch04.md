# DSA II: Trees, Graphs, Dynamic Programming, Advanced Structures

Chapter 3 covered the patterns that decide most first questions in an online assessment. This chapter covers the ones that decide the hard question and the "go deeper" follow-ups in interviews: trees, graphs, shortest paths, union–find, dynamic programming, range-query structures and string algorithms. Every listing is written iteratively where recursion could overflow the stack, uses indices into arrays rather than pointers where that is practical, and is checked against a brute force in the same file.

Two threads run through the chapter. The first is correctness under pressure: each structure comes with the invariant that makes it work, because an invariant is what lets you write the code without off-by-one errors and explain it to an interviewer. The second is the hardware. Graph and tree algorithms are dominated by memory access patterns rather than arithmetic, so the same O(m log n) algorithm can differ in speed by an order of magnitude depending on how the data is laid out (Section 4.8) and how vertices are numbered (Section 4.9).

## Trees

### Vocabulary and representation

A tree is a connected graph with n vertices and n − 1 edges, equivalently a connected graph with no cycle; there is exactly one simple path between any two vertices. Choosing a *root* gives every other vertex a *parent*; the *depth* of a vertex is its distance from the root, the *height* of a vertex is the length of the longest downward path from it, and the *subtree* of v is v with all its descendants.

Interview problems give trees in three forms: as a binary-tree node structure with `left` and `right` pointers (typical on LeetCode), as an edge list (typical in OAs and on Codeforces), or as a parent array. For an edge list, build an adjacency list and root the tree yourself.

**Traversals.** For binary trees, *preorder* (node, left, right), *inorder* (left, node, right) and *postorder* (left, right, node) are the depth-first orders, and *level order* is breadth-first. An inorder traversal of a binary search tree visits the keys in sorted order, which is the basis of "validate a BST" and "k-th smallest in a BST". (The balanced BSTs behind `std::map` are covered in Section 10.3.) Postorder is the natural order for anything computed from children: subtree sizes, heights, subtree sums, tree DP.

### Diameter

The diameter is the longest path between two vertices. **Two sweeps:** BFS from any vertex s to the farthest vertex a; then BFS from a; the largest distance found is the diameter (lines 49–61). Why it works: the vertex farthest from *any* start vertex is an endpoint of some longest path. The proof is a short case analysis on where the path from s to a meets a longest path u–v: if a were not such an endpoint, splicing the branch towards a onto u–v would give a path longer than the longest one. It needs non-negative edge lengths, and it fails on general graphs, where the longest-path problem is NP-hard. For weighted trees use DFS distances instead of BFS levels. The DP alternative, needed when you want more than the length, computes for each vertex the two longest downward paths into different children; the diameter is the best sum over all vertices.

### Lowest common ancestor by binary lifting

The LCA of a and b is the deepest vertex that is an ancestor of both. It gives distances in O(1) after LCA (dist(a, b) = depth(a) + depth(b) − 2·depth(lca), line 46) and is the basis of many path queries.

**Binary lifting** stores, for every vertex v and every k, the 2^{k}-th ancestor `up[k][v]`, computed from `up[k][v] = up[k−1][up[k−1][v]]` (lines 32–35): O(n log n) time and memory. A query (lines 37–45) has two phases:

1. Lift the deeper vertex until both are at the same depth, using the binary digits of the depth difference (line 40). If they are now equal, that vertex is the LCA.
2. For k from large to small, lift *both* by 2^{k} if their ancestors differ (line 43). The invariant is that a and b are distinct vertices at the same depth, both below the LCA. At the end they are the two children of the LCA on the paths, so the answer is their parent.

Each query is O(log n). The table is log n times larger than the tree (20 arrays of n `int`s for n = 10^{6}, about 80 MB), so it is not free; alternatives are an Euler tour with a sparse table (O(1) queries) or offline methods. For interviews, binary lifting is the version to know, because it also answers "k-th ancestor of v" directly.

## Graph Representations and Traversal

### Choosing a representation

| Representation | Memory | Iterate neighbours of v | Test edge (u, v) | Best for |
|---|---|---|---|---|
| Adjacency matrix | O(n^{2}) | O(n) | O(1) | dense graphs, n ≤ a few thousand, Floyd–Warshall |
| Edge list | O(m) | O(m) | O(m) | Kruskal, Bellman–Ford |
| `vector<vector<int>>` | O(n + m), n separate heap blocks | O(deg v) | O(deg v) | general use, graphs that change |
| CSR (compressed sparse row) | O(n + m), two flat arrays | O(deg v), contiguous | O(log deg v) if sorted | static graphs, performance |

A `vector<vector<int>>` stores each vertex's neighbours in its own heap allocation: n allocations, 24 bytes of `vector` header per vertex, and the neighbour lists of consecutive vertices may be far apart in memory. **CSR** stores all edges in a single array, grouped by source, plus an array of n + 1 offsets: the neighbours of v are `to[off[v]] … to[off[v+1] − 1]`. It is built in O(n + m) by counting sort, and it is how graph libraries and high-performance code store static graphs.

### BFS and its variants

BFS from s visits vertices in non-decreasing distance order, so the first time a vertex is reached is along a shortest path (in number of edges). O(n + m). Variants you should recognize:

- **Multi-source BFS.** Push every source with distance 0 at the start: "distance from each cell to the nearest gate", "time for rot to spread" (LeetCode 994).
- **Grids as implicit graphs.** Do not build adjacency lists for a grid; generate the four (or eight) neighbours on the fly, as `main` does on lines 83–94 to build the example. Encode a cell as r × C + c.
- **State-space BFS.** The vertices can be states such as (position, keys collected) or (cell, remaining wall breaks). The number of states, not the size of the grid, is what must fit the limits.
- **0-1 BFS (lines 36–52).** If every edge weight is 0 or 1, use a deque: relax a 0-edge to the *front* and a 1-edge to the *back*. The deque then always holds at most two consecutive distance values, in order, so it behaves like Dijkstra's priority queue at O(n + m) cost. The example asks for the fewest walls to break between two corners: plain BFS finds a 5-move path through a wall, 0-1 BFS finds that one broken wall is the minimum.

### DFS, cycles and components

DFS explores as deep as possible before backtracking. In a **directed** graph, classify vertices with three colours: 0 = not visited, 1 = on the current DFS path, 2 = finished. An edge to a colour-1 vertex is a *back edge* and closes a cycle; an edge to a colour-2 vertex does not. (Two colours are not enough: in a directed graph, reaching an already-finished vertex is normal.) Lines 56–80 do this iteratively: the stack holds vertices, and `it[v]` remembers which edge of v to try next (line 67), which is exactly the state a recursive call would keep in its stack frame. When a back edge v → u is found, the parent pointers from v back to u give the cycle (lines 71–75).

In an **undirected** graph, a cycle exists exactly when DFS meets an already-visited vertex other than the parent, or equivalently when union–find sees an edge whose ends are already connected (Section 4.4). Other DFS staples: connected components (repeat DFS or BFS from every unvisited vertex), bipartiteness (2-colour with BFS; an edge between equal colours means an odd cycle), and bridges and articulation points via low-link values (Tarjan), which appear in harder problems such as LeetCode 1192.

### Dijkstra's algorithm

For non-negative weights, Dijkstra repeatedly *settles* the unsettled vertex with the smallest tentative distance and relaxes its outgoing edges. The invariant: when a vertex is taken from the heap with its current distance, that distance is final. Proof sketch: any other path to it must leave the settled set through some unsettled vertex whose distance is already at least as large, and non-negative edges cannot make the rest of that path shorter. That last step is exactly where **negative edges break Dijkstra**: with edges A→B of weight 2, A→C of weight 3 and C→B of weight −2, Dijkstra settles B at 2, but the true distance is 1.

`std::priority_queue` has no decrease-key (Section 3.7), so Listing 4.4 uses **lazy deletion**: when a distance improves, push a new entry (line 26) and leave the old one in the heap. When an entry is popped, compare it with the current distance (line 22); if they differ, a better entry was pushed later and this one is stale. Each edge relaxation pushes at most one entry, so the heap never holds more than m + 1 entries and the total cost is O((n + m) log m) = O(m log n). In practice this beats `std::set` with erase-and-reinsert, which emulates decrease-key at the cost of tree-node allocations (Section 4.9 measures a factor of about 2.8).

Details that cost marks: use `long long` distances and an INF that cannot overflow when an edge weight is added to it (line 10); make the heap a min-heap with `std::greater` (line 16); put the distance first in the pair so the heap orders by it (line 15); and if you need the path itself, record the predecessor whenever a distance improves.

### Bellman–Ford

Relax every edge, n − 1 times (lines 34–49). After round k, every shortest path that uses at most k edges is correct, and a shortest path without cycles has at most n − 1 edges. If anything still improves in round n, some reachable cycle has negative total weight (line 46). O(nm) time; stop early when a round changes nothing. Skip vertices still at INF (line 41), or "INF + negative weight" will masquerade as a real distance.

**The classic quant application: currency arbitrage.** Given exchange rates r_{ij}, a cycle of conversions makes money exactly when r_{12} r_{23} … r_{k1} > 1. Taking −log of each rate turns the product into a sum: the condition becomes Σ −log r_{ij} < 0, a **negative cycle**. Run Bellman–Ford from a virtual source with a zero-weight edge to every currency, and report a cycle if round n still relaxes; follow predecessor pointers back n steps to land inside the cycle, then walk it. Because the weights are floating-point logarithms, compare with a small tolerance, and mention that in practice transaction costs, bid/ask spreads and the time taken to execute erase most theoretical cycles.

### Floyd–Warshall

All-pairs shortest paths in O(n^{3}) (lines 51–66). After the outer iteration for k, `d[i][j]` is the shortest path from i to j that uses only vertices 0..k as intermediates; going from k − 1 to k only adds the option "via k". That is why **k must be the outermost loop**: putting it inside computes something else, and it is a favourite "spot the bug" question. Negative edges are allowed; a negative `d[i][i]` at the end reveals a negative cycle through i. With n ≤ 400–500 it is the simplest correct all-pairs method, and its inner loop scans row k and row i sequentially, which suits the cache well.

### Which algorithm

| Situation | Algorithm | Cost |
|---|---|---|
| unweighted | BFS | O(n + m) |
| weights 0 or 1 | 0-1 BFS | O(n + m) |
| non-negative weights | Dijkstra with a binary heap | O(m log n) |
| negative weights, or negative-cycle detection | Bellman–Ford | O(nm) |
| all pairs, n ≤ ~500 | Floyd–Warshall | O(n^{3}) |
| DAG, any weights | DP in topological order (4.4) | O(n + m) |
| at most k edges | Bellman–Ford limited to k rounds (copy the array each round) | O(km) |

### Topological sort

A topological order of a directed graph lists every vertex before all vertices it points to; it exists exactly when the graph has no cycle. **Kahn's algorithm** (lines 14–29) keeps the vertices whose remaining in-degree is zero ("all prerequisites done"), repeatedly outputs one, and decrements the in-degrees of its successors (line 26). If fewer than n vertices are output, the rest lie on or behind a cycle; the output shows this for a 3-cycle. With a FIFO queue it is O(n + m); with a min-heap (line 18) it produces the lexicographically smallest order at O(n log n + m). The DFS alternative outputs vertices in reverse order of finishing time.

Topological order is what makes **DP on a DAG** possible: longest path, number of paths, earliest start times in a project schedule. Process vertices in topological order and every predecessor's value is final when you need it. The same reasoning applies to engineering systems: a trading application that starts dozens of components (logging, configuration, market-data handlers, risk checks, order gateways) must initialize them in dependency order and should detect a dependency cycle at start-up, not in production.

### Disjoint-set union (union–find)

DSU maintains a partition of {0, …, n − 1} into sets under two operations: `find(x)` returns a representative of x's set, and `unite(a, b)` merges two sets. Each set is a tree of parent pointers whose root is the representative.

Two heuristics make it fast:

- **Union by size (line 46):** hang the smaller tree under the root of the larger. A vertex's depth then increases only when its set at least doubles in size, so trees have depth at most log_{2} n.
- **Path compression (line 38):** while walking to the root, point vertices closer to it. Listing 4.5 uses *path halving*, which points each visited vertex to its grandparent: one loop, no recursion, and the same asymptotic guarantee as full compression.

With both, a sequence of operations costs O(α(n)) amortized per operation, where α is the inverse Ackermann function, below 5 for any input that fits in a computer: effectively constant. Without either heuristic, a chain of unions can make `find` O(n); Section 4.9 measures a factor of about 60,000 on a chain of 10^{5}.

DSU answers "are a and b connected?" as edges are added, counts components, detects cycles in undirected graphs (an edge whose ends already share a root closes a cycle), and groups equivalent items ("accounts merge"). It cannot *delete* edges; for that, process the operations in reverse or use other techniques.

### Minimum spanning tree

A minimum spanning tree connects all vertices with the least total edge weight. **Kruskal** (lines 53–61): sort edges by weight and add each one that joins two different components. Correctness is the *cut property*: the lightest edge crossing any cut belongs to some MST, and Kruskal's chosen edge is the lightest edge crossing the cut between its endpoint's component and everything else (an exchange argument, Section 3.9). O(m log m) for the sort. **Prim** grows one tree from a vertex, like Dijkstra with edge weights instead of path lengths; the O(n^{2}) array version (lines 63–80, used here as the reference) is best for dense graphs.

## Dynamic Programming Patterns

### The method

Dynamic programming solves a problem by combining solutions of overlapping subproblems, each solved once. Every DP answer has the same five parts, and stating them explicitly is the fastest way to a correct solution and the clearest way to explain it:

1. **State:** what f(…) means, in words. ("f[i][c] = best value using the first i items with capacity c.")
2. **Transition:** how a state is computed from smaller ones.
3. **Base cases.**
4. **Order:** an evaluation order in which every dependency is computed first.
5. **Answer:** which state(s) hold it.

**Top-down** (recursion with memoization) writes the transition directly and computes only reachable states, but pays for function calls and risks deep recursion. **Bottom-up** (loops over a table) needs an explicit order but is faster, uses no stack, and makes memory reduction possible. In an OA, write whichever you get right first; in an interview, be able to convert one into the other.

To find the state, ask what you would need to know about the past to make the remaining decisions optimally. If the answer is "the last element chosen", "the remaining capacity" or "which items are used", that is the state. The complexity is (number of states) × (cost of a transition), and it must fit the limits of Section 3.1.

### Linear DP

The state is a prefix: f[i] depends on a few earlier entries. Climbing stairs (f[i] = f[i − 1] + f[i − 2]), house robber (f[i] = max(f[i − 1], f[i − 2] + a_{i})), decode ways, maximum subarray (Kadane, Section 3.3). When f[i] needs only the last one or two values, keep them in variables: O(1) memory.

### Knapsack

**0/1 knapsack** (lines 10–17): each item is taken at most once. The two-dimensional recurrence is f[i][c] = max(f[i − 1][c], f[i − 1][c − w_{i}] + v_{i}). Keeping one row works if capacity is iterated **downwards** (line 14): when `best[c]` is updated, `best[c − w]` still holds the value from the previous item, so the item cannot be counted twice. Iterating **upwards** (line 21) lets an item be reused within its own row, which is exactly the **unbounded** knapsack. The example shows the difference: 9 for 0/1, 10 when items repeat. Both are O(n·W), *pseudo-polynomial*: polynomial in the numeric value of the capacity, not in the number of bits needed to write it. (The general problem is NP-hard; the DP works when W is up to about 10^{7}.)

The same loops answer counting questions with + instead of max. Loop order then decides *what* you count: items in the outer loop, amounts in the inner loop, counts **combinations** (coin change II: {1, 2} and {2, 1} are the same); amounts outer and items inner counts **ordered sequences**. Problem P4.4 and Problem P4.9 practise both.

### Longest increasing subsequence in O(n log n)

The O(n^{2}) DP f[i] = 1 + max{f[j] : j < i, a_{j} < a_{i}} (lines 43–52) is the reference. The fast version (lines 27–42) keeps, for each length k, the *smallest possible last value* of an increasing subsequence of length k + 1. That array is strictly increasing (a longer run must end higher), so each new element finds its place by binary search (line 32): it either extends the longest run or lowers the tail of a run. The length of the array is the answer. To recover a subsequence, store the index of each tail and a predecessor link for every element (lines 34–36), then follow the links back from the last tail. For non-decreasing subsequences use `upper_bound` instead of `lower_bound`. The tail array is *not* itself a valid subsequence, a common misconception.

### LCS and edit distance

Two strings, state (i, j) = "first i characters of s, first j of t". For edit distance (lines 54–67): either delete s_{i}, insert t_{j}, or replace/keep (cost 0 if the characters match). LCS is the same table with "match: +1, otherwise max of dropping one character". Both are O(nm) time. The table needs O(nm) memory only if you want to reconstruct the alignment; for the value, row i depends only on row i − 1, so two rows suffice (lines 56 and 64). Hirschberg's algorithm recovers the alignment in linear memory as well, by divide and conquer.

### Grid DP

f[r][c] from f[r − 1][c] and f[r][c − 1]: number of paths with obstacles, minimum path sum, largest square of 1s (f = 1 + min of three neighbours). Iterate rows in the outer loop and columns in the inner loop so that memory is accessed sequentially (row-major order, which is how C++ lays out a 2-D array); swapping the loops for a large table turns sequential access into strided access and can cost several times in speed (Section 12.2).

### Interval DP

State (l, r) = a contiguous range; the transition chooses a split point k inside it; the order is by increasing length. Matrix-chain multiplication, optimal BST, palindrome partitioning, merging stones and "burst balloons" (lines 78–93) are all O(n^{3}). The insight in burst balloons is to choose the balloon burst **last** in (l, r): its neighbours at that moment are then exactly l and r, which makes the two sides independent. Choosing the balloon burst *first* does not split the problem, because the neighbours keep changing.

### Bitmask DP

When n ≤ ~20 and the state must remember *which* items have been used, encode the set as a bitmask (Section 3.8). The travelling salesman problem (lines 11–28, the Held–Karp algorithm): f[mask][v] = cheapest path that starts at city 0, visits exactly the cities in `mask` and ends at v. There are 2^{n}·n states and n transitions each: O(2^{n} n^{2}) time and O(2^{n} n) memory, against O(n!) for trying every tour. For n = 16 that is about 1.7×10^{7} operations; for n = 20, about 4×10^{8} operations and 2^{20}·20 `long long`s ≈ 170 MB, at the edge of typical limits. Assignment problems (n workers, n jobs), "shortest path visiting all nodes", and partitioning into groups follow the same pattern.

### Digit DP

To count integers in [0, N] with a property of their digits (digit sum, no two adjacent equal digits, divisible by k), build the number digit by digit from the most significant, tracking whether the prefix is still **tight** (equal to N's prefix, which limits the next digit) or already smaller (all remaining digits free). Lines 41–62 count numbers with a given digit sum: precompute the number of ways to fill the remaining positions freely (lines 46–52), then walk N's digits and, at each position, add the counts for every digit below N's digit (line 57). The cost is O(digits × states × 10), so numbers up to 10^{18} take microseconds. A count over [L, R] is count(R) − count(L − 1).

### Tree DP and rerooting

Tree DP computes a value for each subtree from its children, in postorder (Section 4.1): maximum independent set, subtree sums, the diameter DP. **Rerooting** extends this to "compute the answer for every vertex as the root" in O(n) rather than O(n^{2}). For the sum of distances from each vertex (lines 64–89): the first pass computes subtree sizes and the sum of distances from each vertex down into its subtree; the second pass moves the root from a parent p to a child v, which brings the sub[v] vertices in v's subtree one step closer and the other n − sub[v] vertices one step further away (line 86). The output matches LeetCode 834's example.

### DAG DP and memory reduction

Any DP is a DAG of states; the evaluation order is a topological order. When the dependency structure is an explicit DAG (longest path, counting paths, "longest increasing path in a matrix"), compute it in topological order or with memoized DFS. To reduce memory, keep only the layers a transition reads: one row for knapsack, two rows for LCS, O(1) variables for linear recurrences. `std::bitset` (Section 3.8) compresses boolean DPs such as subset-sum feasibility by a factor of 64 in both memory and time.

### Fenwick tree (binary indexed tree)

Index i (1-based) stores the sum of the range (i − lowbit(i), i], where lowbit(i) = i & −i (Section 3.8). A prefix query (lines 15–19) strips the lowest set bit repeatedly, visiting at most log_{2} n entries; an update (lines 12–14) adds the lowest set bit repeatedly, visiting every entry whose range contains i. Ten lines, n + 1 numbers of memory, and a very small constant. It requires an invertible operation for range queries (sums, XOR, counts; range = prefix(r) − prefix(l)). Variants: range update with point query (Fenwick over the difference array), range update with range query (two Fenwick trees), and finding the smallest index whose prefix sum reaches a value by descending the implicit tree in O(log n).

**Counting inversions** (lines 74–82) is the canonical application: scan from right to left and, for each value, count how many smaller values have already been seen. The same pattern counts "smaller elements after self" (LeetCode 315) or computes the rank of each element in a stream. Values must be small integers, so compress coordinates first (Section 3.3).

In a trading context, a Fenwick tree indexed by price level answers "how much quantity is resting at prices up to p" in O(log n) with O(log n) updates; whether that beats simpler structures for a real order book depends on the access pattern (Section 18.1).

### Segment tree

A segment tree stores an aggregate (sum, min, max, gcd, or any associative operation) for a hierarchy of ranges: the root covers [0, n), each node's children cover its two halves. Any range [l, r) is the disjoint union of O(log n) nodes.

- **Iterative, bottom-up (lines 23–41).** Leaves are at positions n … 2n − 1 and node i has children 2i and 2i + 1, the array layout of a heap (Section 3.7). An update rewrites a leaf and recomputes its ancestors (line 31). A query moves l and r up the tree together: when l is a right child, its node is included and l moves past it; when r is a right boundary, the node to its left is included (lines 36–37). It uses 2n memory, works for any n (not only powers of two), and has no recursion. It does not support range updates.
- **Recursive with lazy propagation (lines 43–72).** For range *updates* (add x to every element in [l, r)) with range queries, a node that is fully covered by the update records the pending addition in `lazy` and stops (line 56); the addition is pushed to its children only when a later operation needs to go below that node (`push`, lines 48–53). Both operations stay O(log n). Use 4n memory for the recursive layout. The two rules to remember: apply the pending update to a node's *own* aggregate immediately (line 47 multiplies by the segment length for sums), and push before descending.

### Choosing

| Need | Structure | Query / update |
|---|---|---|
| static array, range sum | prefix sums | O(1) / rebuild O(n) |
| static array, range min/max | sparse table | O(1) / rebuild O(n log n) |
| point update, prefix or range sum | Fenwick tree | O(log n) / O(log n) |
| point update, range min/max or any associative op | iterative segment tree | O(log n) / O(log n) |
| range update + range query | lazy segment tree (or two Fenwick trees for sums) | O(log n) / O(log n) |

## String Algorithms

### The prefix function and KMP

A *border* of a string is a proper prefix that is also a suffix. The prefix function π[i] is the length of the longest border of s[0..i] (lines 11–21 of Listing 4.9). It is computed incrementally: the best border of s[0..i] is either one character longer than *some* border of s[0..i − 1], or zero. The borders of s[0..i − 1] are exactly π[i − 1], π[π[i − 1] − 1], and so on, so line 16 falls back along this chain until the next character matches.

**Why it is O(n), not O(n^{2}).** k increases by at most 1 per character (line 17) and every iteration of the `while` loop decreases it by at least 1; k never goes below zero. So the total number of fall-backs over the whole string is at most n: the pointer argument of Section 3.1 again.

**KMP search** (lines 23–36) runs the same automaton over the text: k is the number of pattern characters currently matched. On a full match, record it and fall back to π[k − 1] (line 32) so that overlapping occurrences are found ("aba" occurs at 0, 2 and 4 in "abababa"). O(n + m) in total, against O(nm) for naive comparison in the worst case. (Alternatively, compute the prefix function of `pattern + '#' + text`; every position where it equals |pattern| ends a match.)

**The link to Chapter 2.** Section 2.7 modelled waiting for a pattern of coin flips with states "longest suffix of the flips so far that is a prefix of the pattern", and Listing 2.3 built the transitions by stripping characters from the front until a valid state remained: a quadratic version of exactly this fall-back. With the prefix function, the transition from state k on symbol c is: while k > 0 and pattern[k] ≠ c, set k = π[k − 1]; then advance if pattern[k] = c. Precomputing it for every state and symbol gives the full KMP automaton in O(m × alphabet). The prefix function also gives the overlap rule of Section 2.7 directly: the expected number of i.i.d. uniform symbols until the pattern first appears is the sum of m^{b} over all border lengths b of the pattern, including the whole pattern. Lines 71–80 walk the border chain to compute it, and the output reproduces the values from Chapter 2: 6 for HH, 10 for HTH, 62 for five heads in a row.

### The Z-function

z[i] is the length of the longest common prefix of s and s[i..] (lines 38–49). The algorithm keeps the rightmost segment [l, r) known to match a prefix of s; for i inside it, z[i] is at least min(r − i, z[i − l]) by copying, and only characters beyond r are compared afresh. r only moves right, so it is O(n). It solves the same problems as the prefix function (pattern search via `pattern + '#' + text`, periods, borders) and many people find it easier to reason about. Use whichever you can write correctly from memory.

### Rolling hashes

A polynomial hash h(s) = Σ s_{i}·B^{n−1−i} mod p lets you compare any two substrings in O(1) after O(n) preprocessing, because the hash of s[l..r) is h[r] − h[l]·B^{r−l} (lines 51–69). It solves "longest duplicate substring" (binary search on the length plus hashing), counting distinct substrings and palindrome checks, and is the basis of Rabin–Karp search.

Choices that matter:

- **Collisions are certain to exist; make them improbable.** For a prime p and a base B chosen uniformly at random, two different strings of length L collide with probability at most (L − 1)/p, because their difference is a non-zero polynomial of degree below L, with at most L − 1 roots. Listing 4.9 uses p = 2^{61} − 1, so even 10^{6} comparisons of strings of length 10^{5} have a total collision probability below 10^{−7}.
- **Choose the base at run time** (line 95). A fixed, published base can be attacked exactly like the identity hash of Section 3.3. Hashing modulo 2^{64} (letting `unsigned long long` overflow) is particularly weak: Thue–Morse strings, a well-known anti-hash construction, collide for every odd base, and an even base is weak for a simpler reason (high powers of B vanish modulo 2^{64}).
- **Multiplication modulo 2^{61} − 1 without division.** Line 55 forms the 122-bit product with `unsigned __int128` (a GCC and Clang extension), and lines 56–57 reduce it using 2^{61} ≡ 1: add the low 61 bits to the high bits, then subtract p once if needed. This is the same "avoid the division instruction" idea as Section 3.11.
- **Equal hashes mean "probably equal".** When a false positive would be costly, verify the candidate match character by character.

### Aho–Corasick (overview)

To find all occurrences of *many* patterns in a text at once, build a trie of the patterns (Section 4.1) and add *failure links*: the failure link of a node is the node for its longest proper suffix that is also in the trie, which is the multi-pattern generalization of the prefix function, computed by BFS over the trie. Scanning the text then follows trie edges and failure links, and *output links* report every pattern that ends at the current position. The total cost is O(total pattern length + text length + number of matches). Interviews rarely ask for the code but do ask for the idea, for example "scan a stream of messages for any of 10,000 symbols or keywords". For heavier string work (all distinct substrings, longest common substring of many strings), suffix arrays and suffix automata are the next step; they are beyond what QD interviews usually require.

### What the difference is made of

The optimized version is about 14 times faster here. Section 4.9 isolates one part of the difference: on the same CSR graph, `std::set` with erase/insert takes about 2.8 times as long as the heap with stale entries. Copying the graph is a one-off O(n + m) cost. Most of the rest comes from replacing the two `std::map`s with arrays: every operation on a node-based tree is a chain of dependent loads to scattered addresses, while `dist[v]` is a single load at a computed address. None of this is visible in the Big-O. The lesson is the one in Section 3.10, with a larger factor: **choose flat, index-based data structures by default, and measure.**

What remains in the fast version is mostly the heap and the random access to `dist[a.to]` for each edge, both cache-unfriendly for 200,000 vertices. Further improvements, which are beyond an interview but worth knowing: renumbering vertices so that neighbours have nearby numbers (Section 4.9 shows the effect on BFS), a 4-ary heap (Section 3.7), radix or bucket queues when weights are small integers, and, for repeated queries on road networks, precomputation methods such as contraction hierarchies.

## The Nanosecond Penalty

@code ch04/graph_bench.cpp

@output ch04/graph_bench.cpp measured in the build container (virtualized Xeon, 2.1 GHz nominal, 2 MiB L2 per core); expect different absolute numbers elsewhere

**1) BFS layouts.** A BFS over 2^{20} vertices and 2^{23} random edges costs about 16–22 ns per edge with either `vector<vector<int>>` or CSR, and the two are within measurement noise of each other here. That is a useful surprise. The adjacency layout is not the bottleneck: for every edge, BFS reads `d[u]` for a *random* target u in a 4 MiB array that does not fit in the 2 MiB L2 cache, and each such access is likely a cache miss. **Renumbering the vertices in BFS order** (lines 64–71) makes vertices discovered together have nearby numbers, so both the queue's adjacency reads and many of the `d[u]` accesses become local; the identical CSR code then runs about 2–3.5 times faster (the ratio varies between runs). Locality of the *numbering* mattered more than the container. Real graphs (road networks, social graphs, dependency graphs) have much more natural locality than random ones, and reordering them (by BFS order, by space-filling curve, or by graph partitioning) is a standard optimization.

**2) Dijkstra's frontier.** On the same CSR graph, a `std::set` with erase-and-insert takes about 2.8 times as long as a binary heap with stale entries: every insert allocates a tree node, every erase frees one, both follow O(log n) pointers and may rebalance, while the heap moves elements within one array.

**3) Union–find.** On a chain of 10^{5} vertices built without either heuristic, one `find` from the far end walks the whole chain: about 250 µs. With union by size and path halving, the same unions produce shallow trees and a random `find` costs a few nanoseconds: a factor of tens of thousands.

**4) Fenwick versus segment tree for prefix sums.** A Fenwick prefix query over 2^{20} values costs about 25 ns, an iterative segment-tree query about 130 ns. The Fenwick loop visits only popcount(r) entries (about 10 on average here) with one predictable loop condition; the segment-tree loop always climbs all 20 levels, executes two data-dependent branches per level that the predictor cannot learn, and touches a 16 MiB array. When the operation is invertible and you only need sums, use the Fenwick tree.

### Rules of thumb

| Operation | Typical cost on a modern x86-64 core | Why |
|---|---|---|
| visit an edge in BFS, data in L1/L2 | ~1–3 ns | sequential arc reads, one random `d[u]` access that hits |
| visit an edge in BFS, n much larger than cache | ~10–30 ns | one or more cache misses per edge |
| heap push or pop, 10^{5}–10^{6} entries | ~50–200 ns | log n levels, mispredicted comparisons, misses in the lower levels |
| `std::set`/`std::map` insert or erase | ~100 ns to several hundred ns | node allocation plus O(log n) dependent pointer loads |
| DSU `find` with both heuristics | a few ns | trees of depth 1–2 after compression |
| Fenwick query, n = 10^{6} | ~20–50 ns | ~log n / 2 loads, predictable loop |
| DP cell, row-major, simple transition | ~1 ns or less | sequential, often vectorizable (Section 12.6) |

These ranges are approximate and depend heavily on the CPU, the size of the data relative to the caches, and the access pattern; Section 12.7 gives the latency hierarchy that explains them, and Section 16.4 how to measure them properly.

## Interview Questions

**Q1. BFS or DFS: when do you use each?**
BFS finds shortest paths in unweighted graphs, because it visits vertices in order of distance, and it is the basis of multi-source and 0-1 BFS. DFS is natural for structure: cycle detection with colours, topological order by finishing time, connected components, bridges and articulation points, and tree DP. Both are O(n + m). On large inputs I write DFS iteratively, because recursion depth can reach n and overflow the stack.

**Q2. Why does Dijkstra fail with negative edges, and what do you use instead?**
Dijkstra's invariant is that the vertex popped with the smallest tentative distance is final, which relies on extending a path never making it shorter. A negative edge breaks that: with A→B = 2, A→C = 3, C→B = −2, it settles B at 2 although the true distance is 1. Use Bellman–Ford, O(nm), which also detects negative cycles; if the graph is a DAG, a DP in topological order handles any weights in O(n + m).

**Q3. How do you implement Dijkstra with `std::priority_queue`, which has no decrease-key?**
Push a new (distance, vertex) pair whenever a distance improves and leave the old one in the heap. When popping, skip the entry if its distance differs from the current best for that vertex. There are at most m + 1 pushes, so the cost is O(m log m) = O(m log n), and in practice it is faster than a `std::set` with erase and insert.

**Q4. Detect an arbitrage opportunity among n currencies.**
Weight each conversion i→j by −log(rate), so that a cycle's total weight is −log of the product of its rates. An arbitrage cycle (product > 1) is a negative cycle. Run Bellman–Ford from a virtual source connected to every currency with weight 0; if any edge still relaxes in round n, there is a negative cycle, which I can recover by following predecessor links n times and then walking the cycle. I would use a small tolerance because of floating-point error, and note that spreads, fees and latency remove most cycles in practice. O(n^{3}) on a complete graph.

**Q5. Why must k be the outer loop in Floyd–Warshall?**
The invariant after processing k is that `d[i][j]` is the shortest path using only intermediate vertices from {0, …, k}. Adding vertex k to the allowed set needs `d[i][k]` and `d[k][j]` to be final for the set {0, …, k − 1}, which is true only if every pair has been updated for k − 1 before any pair is updated for k. With k inside, some paths are never considered.

**Q6. What is the complexity of union–find, and what makes it fast?**
With union by size (or rank) and path compression, any sequence of m operations on n elements costs O(m α(n)), where α is the inverse Ackermann function, below 5 for all practical n. Union by size alone guarantees O(log n) depth; path compression alone gives O(log n) amortized per operation; together they give near-constant time. Without either, a chain makes `find` O(n).

**Q7. Explain the O(n log n) LIS algorithm.**
Maintain `tail[k]`: the smallest last element of any strictly increasing subsequence of length k + 1 seen so far. `tail` is strictly increasing, so for each new element I binary-search the first tail ≥ it and replace it, or append if none exists. The final length of `tail` is the answer. It is not itself a subsequence; to reconstruct one I keep the index of each tail and a predecessor pointer per element.

**Q8. Fenwick tree or segment tree?**
Fenwick for sums or other invertible operations with point updates: ten lines, n + 1 memory, small constant. A segment tree for non-invertible operations like min, max or gcd, for range updates with lazy propagation, or when each node needs richer state (for example the maximum subarray sum within a range). A sparse table if the array is static and the operation is idempotent, for O(1) range-minimum queries.

**Q9. Why is KMP linear even though it has a loop inside a loop?**
The matched length k goes up by at most one per text character and every fall-back iteration decreases it by at least one, without going below zero. So the total number of fall-backs is bounded by the total number of increments, which is at most the text length. The same argument applies to computing the prefix function.

**Q10. When would you use a rolling hash, and what can go wrong?**
To compare substrings in O(1), for example to binary-search the length of the longest repeated substring. The risk is collisions: I use a large prime modulus such as 2^{61} − 1 and a base chosen at random at run time, which bounds the probability of a collision between two given strings of length L by about L/p. I avoid modulus 2^{64} with natural overflow, because Thue–Morse strings make it collide for every odd base, and an even base is weak anyway. Where a false match would be costly, I confirm candidates by direct comparison.

**Q11. How do you recognize that a problem needs DP, and how do you find the state?**
Signals: "count the ways", "minimum or maximum over all choices", decisions that interact only through a small summary of the past, and constraints where exponential search is too slow but n × (something small) fits. To find the state I ask what I need to know about the decisions so far to continue optimally: an index, a remaining budget, the last element chosen, or a set of used items. Then the transition, base case, evaluation order and where the answer is. Complexity is states × transition cost.

**Q12. Your graph algorithm has the right complexity but is ten times slower than expected. What do you look at?**
Memory layout and access patterns first: node-based containers (`std::map`, `std::set`, `std::list`) for the graph or the distances, copies of large structures passed by value, allocation inside the loop, and vertex numbering with poor locality. I would switch to CSR and flat arrays indexed by vertex, reserve the heap's storage, pass by reference, and consider renumbering vertices. Then I would profile with `perf` to confirm where the cache misses are (Section 16.5) rather than guess.

## Key Takeaways

- **Trees:** root the tree yourself and traverse iteratively (explicit stack, preorder, then reverse for postorder) to avoid stack overflow on paths of 10^{5}–10^{6}. Diameter by two BFS sweeps; LCA by binary lifting in O(log n) per query; tries in a node pool with integer child indices.
- **Graphs:** CSR (offsets + one edge array) for static graphs; mark on push in BFS; 0-1 BFS with a deque; three colours for directed cycles; components, bipartiteness and DSU for undirected structure.
- **Shortest paths:** BFS (unweighted), 0-1 BFS, Dijkstra with a min-heap and stale-entry skipping (non-negative weights, O(m log n)), Bellman–Ford (negative weights, cycle detection, O(nm)), Floyd–Warshall (all pairs, k outermost, O(n^{3})), DAG DP. Arbitrage = negative cycle under −log rates.
- **Topological sort** by Kahn's algorithm (min-heap for lexicographic order; fewer than n outputs means a cycle). **DSU** with union by size and path compression is effectively O(1); Kruskal = sort + DSU.
- **DP:** state, transition, base, order, answer. Knapsack direction (down for 0/1, up for unbounded); loop order decides combinations versus sequences; LIS with tails and binary search; two-row edit distance and LCS; interval DP by length with the "last" choice; bitmask DP for n ≤ ~20; digit DP with a tight flag; tree DP and rerooting.
- **Range queries:** Fenwick for invertible operations; iterative segment tree for any associative operation; lazy propagation for range updates; sparse table for static range minimum.
- **Strings:** prefix function and KMP in O(n + m) by the pointer argument; it is also the linear-time fall-back for Chapter 2's pattern chains, and the border chain gives expected waiting times. Z-function as an alternative. Rolling hash modulo 2^{61} − 1 with a random base; never mod 2^{64}. Aho–Corasick for many patterns.
- **Hardware:** the same Dijkstra ran about 14× faster with flat arrays than with `std::map`/`std::set`; vertex numbering changed BFS speed by 2–3.5× while the adjacency container made no measurable difference; Fenwick beat the segment tree by about 5× for prefix sums. Measure before and after.
