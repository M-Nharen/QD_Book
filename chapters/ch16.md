# Compilers and Profiling

Every earlier chapter made claims of the form "this is faster because…". This chapter is about how such claims are made honestly: what the compiler did to your code (16.1–16.3), how to measure the result without fooling yourself (16.4), how to find out where time goes in a real program (16.5), and how to find bugs the compiler cannot (16.6). Interviewers probe this area with questions like "how would you benchmark a function that takes ten nanoseconds?", "what does `-O3` do that `-O2` does not?" or "read this assembly", and the honest answers are short only if you have actually done these things. The showdown (16.7) is a benchmark that "proves" a ten-million-fold speed-up, and the corrected version that measures the real factor of three to five.

**About the measurements and tools.** Listings were compiled with Ubuntu's g++ 13.3 and run in the build container (a KVM guest on a 2.1 GHz Xeon, 2 vCPUs). The flag experiments of 16.1 and 16.6 are run *by a program in the build* (`code/ch16/lab.cpp`), which compiles the small programs in `code/ch16/lab/` with each set of flags and reports medians of three runs, so their numbers are regenerated with every build. `perf` is not part of the container's standard tools; for 16.5 it was installed from Ubuntu's `linux-tools-generic` package (perf 6.8), and the build does not run it. The virtual machine exposes **no hardware performance counters** to the guest, so events such as `cycles` and `instructions` report `<not supported>`: software events and timer-based sampling work, and their outputs below are real captures, labelled as such. For hardware events, the text shows the commands and explains what their output means, without numbers.

## Optimization Levels, LTO, PGO

### What the levels do

GCC's optimization levels are bundles of passes, and knowing roughly what is in each explains most surprises:

- **`-O0`** compiles each statement separately and keeps every variable in memory, so the debugger can see it. Nothing is inlined. Never benchmark or ship it.
- **`-O1`** adds register allocation across statements, constant propagation, dead-code elimination, simple loop optimizations.
- **`-O2`** adds inlining of small functions and functions called once, global value numbering, partial redundancy elimination, instruction scheduling, strict-aliasing-based optimization (11.3), devirtualization, and since GCC 12 vectorization with a *very cheap* cost model: a loop is vectorized only when no scalar remainder code is needed, which in practice means a known trip count.
- **`-O3`** adds vectorization with a dynamic cost model (with remainder loops and runtime alias checks), loop unswitching, loop distribution, predictive commoning, function cloning for constant arguments, and more peeling and unrolling. It produces larger code, and is not always faster.
- **`-Os`** optimizes for size; **`-Og`** keeps debugging usable while optimizing a little; **`-Ofast`** is `-O3` plus `-ffast-math` and `-fallow-store-data-races`, which are not standard-conforming.

Two families of flags matter as much as the level. **`-march=`** chooses the instruction set: the default x86-64 baseline (2003, SSE2) lacks POPCNT, AVX2, FMA and BMI2 (3.8, 12.6); `-march=x86-64-v3` targets the AVX2-era baseline; `-march=native` targets the build machine and may produce a binary that dies with `SIGILL` on an older production server. **`-ffast-math`** lets the compiler treat floating-point arithmetic as real arithmetic: reassociate (`-fassociative-math`), use reciprocals, ignore signed zeros, and assume no NaNs or infinities (`-ffinite-math-only`), so `std::isnan(x)` may be folded to `false`. Linking an executable with it on x86 also sets flush-to-zero and denormals-are-zero for the *whole process* at startup.

Distribution compilers are not vanilla GCC either. Ubuntu's g++ defines `_FORTIFY_SOURCE=3` when optimizing, and enables `-fstack-protector-strong`, `-fstack-clash-protection`, `-fcf-protection` (the `endbr64` instructions in 16.3) and position-independent executables by default. `g++ -Q --help=optimizers -O2` prints what is actually enabled.

### Link-time optimization

The compiler optimizes one translation unit at a time, so it cannot inline a function whose body is in another `.cpp` file (5.1). With **`-flto`**, GCC writes its intermediate representation (GIMPLE) into the object files; at link time it runs whole-program analysis, then optimizes the program in partitions (in parallel with `-flto=auto`). Calls across files can then be inlined, unused functions removed, and virtual calls devirtualized when the whole class hierarchy is visible (6.5). The lab's second experiment calls a one-line `notional(px, qty)` defined in another file: `-flto` cut the cost per call from about 0.66 to 0.49 ns, and in a real program the larger gains come from what inlining enables (16.2). The costs: slower and more memory-hungry links, static libraries that need `gcc-ar`, and harder debugging. A useful side effect is that LTO checks the whole program for one-definition-rule violations (`-Wodr`), which the separate-compilation model cannot see (5.1).

### Profile-guided optimization

Static heuristics guess which branches are taken, which calls are hot and which loops are long. **PGO** replaces the guesses with measurements: build with `-fprofile-generate`, run a representative workload (each process writes `.gcda` count files at exit), and rebuild with `-fprofile-use`. GCC then lays out hot paths as fall-through code, moves cold code away, inlines and unrolls where the profile says it pays, and applies *value profile* transformations, such as specializing an indirect call for its most frequent target.

For trading systems PGO has a specific danger: **the training run decides what is optimized for speed.** A profile from a quiet day can mark the burst-handling or error-recovery paths as cold, and GCC by default optimizes never-executed code for *size*. `-fprofile-partial-training` keeps normal optimization for code the training did not reach, and the training workload should replay recorded busy sessions, including rare events. Related tools: **AutoFDO** builds a profile from `perf` samples of production instead of an instrumented binary, and **BOLT** (part of LLVM) rewrites the layout of an already-linked binary from a profile.

## Inlining and Code Layout

### What inlining buys

A call costs a few cycles (push the return address, jump, return), and the CPU predicts both. The real cost of *not* inlining is what the compiler cannot do across the call: propagate constants into the callee, keep values in caller-saved registers, prove that memory is not modified, or vectorize the loop around it. Behind `[[gnu::noinline]]` (lines 12–14, 20), the callee must execute a real `idiv` for an unknown divisor, tens of cycles of latency, plus the call. The 2.7 times difference is almost all lost specialization, not call overhead. (At `-O3` the inlined loop would also be vectorized.)

GCC decides with heuristics based on estimated function size, call frequency and code growth: small functions and functions called once are inlined at `-O2`; `inline` is a linkage keyword, not a command (5.1). Its decisions are visible with `-fopt-info-inline-optimized` and `-fopt-info-inline-missed`, and can be forced with `[[gnu::always_inline]]`, `[[gnu::noinline]]` or `[[gnu::flatten]]` (inline everything called from this function). Forcing should be rare and justified by measurement: every inlined copy grows the code, and a hot path that no longer fits in the instruction caches gets slower everywhere (9.7).

### Code layout

Instruction fetch is a pipeline of its own, so *where* code is placed matters:

- **Hot/cold splitting.** GCC moves blocks it believes cold, such as error handling, branches marked `[[unlikely]]` (12.5) and calls to `[[gnu::cold]]` functions, into separate `.cold` fragments in the `.text.unlikely` section, so the hot path is contiguous and dense. PGO does this from measured data.
- **Fall-through for the common case.** A taken branch, even correctly predicted, can cost a fetch bubble; the likely path should be straight-line code.
- **Register pressure from cold code.** The `record` function in Listing 16.4 shows a fast path that saves and restores six registers on every call only because the rarely executed reallocation path, inlined into the same function, needs them. Problem P16.8 removes this.
- **Alignment.** `-falign-functions`, `-falign-loops` and `-falign-jumps` pad with `nop`s to align targets, which helps instruction fetch and the decoded-instruction cache. The flip side is that unrelated changes that shift code addresses can change a microbenchmark's speed by several percent; Mytkowicz and co-authors' paper "Producing Wrong Data Without Doing Anything Obviously Wrong!" (ASPLOS 2009) showed that even link order and environment-variable size can do it. Benchmark conclusions within a few percent need repeated builds, not just repeated runs.

## Reading x86-64 Assembly

You do not need to write assembly in a QD role, but you must be able to read what the compiler produced: to confirm that a loop vectorized, that a call was inlined, that a branch became a `cmov`, or that a "zero-cost" abstraction is zero-cost. The essentials:

- **Registers:** sixteen 64-bit general-purpose registers, `rax`, `rbx`, `rcx`, `rdx`, `rsi`, `rdi`, `rbp`, `rsp`, `r8`–`r15`; their low halves are `eax`, …, `r8d`. Writing a 32-bit register zeroes the upper 32 bits, which is why `mov edi, edi` zero-extends. Vector registers are `xmm` (128-bit), `ymm` (256) and `zmm` (512).
- **System V calling convention (Linux):** integer and pointer arguments in `rdi`, `rsi`, `rdx`, `rcx`, `r8`, `r9`, floating-point arguments in `xmm0`–`xmm7`, the result in `rax` or `xmm0`. `rbx`, `rbp` and `r12`–`r15` are callee-saved: a function that uses them must save and restore them. The stack is 16-byte aligned at each call, and leaf functions may use 128 bytes below `rsp` (the red zone) without adjusting it.
- **Syntax:** this book prints Intel syntax (`mov dst, src`; `objdump -M intel`, `g++ -S -masm=intel`). AT&T syntax, the GNU default, reverses the operands and adds `%` and `$` sigils.
- **Addressing:** `[base + index*scale + displacement]`, scale 1, 2, 4 or 8. `lea` computes such an address without accessing memory, so compilers use it for arithmetic.

- **`endbr64`** begins every function that can be reached indirectly: a landing pad for Intel's control-flow enforcement, from Ubuntu's default `-fcf-protection`. It executes as a no-op elsewhere. The `nop` variants after each `ret` are padding to align the next function.
- **`qty_at`:** `lea rax,[rsi+rsi*2]` is `3i`, and `[rdi+rax*8+0x8]` is `book + 24i + 8`: the struct is 24 bytes and `qty` sits at offset 8 (6.1). Indexing an array of structs is one address computation.
- **`div10`:** division by a constant becomes a multiplication by a "magic" reciprocal, 0xCCCCCCCD ≈ 2^{35}/10, and a shift by 35 (Problem P16.1): about 4 cycles instead of an `idiv`.
- **`best`:** a `cmov` instead of a branch (12.5). For a ternary between two computed values, GCC usually emits one; for anything with side effects, check.
- **`fee_bps`:** the `switch` became a range check (`cmp edi,0x4; ja` to the default) and a load from a compiler-generated table (`CSWTCH`) addressed relative to `rip` (position-independent code). Dense `switch`es whose cases jump to code become *jump tables* of addresses instead.
- **`sum`:** `movsxd` sign-extends each `int` to 64 bits before adding; the loop runs a pointer up to an end pointer. Not vectorized at `-O2`, as 16.1 predicted.
- **`route`:** a virtual call is two loads and an indirect jump: the vtable pointer from offset 0 of the object, then the function pointer from slot 2 (offset 0x10; slots 0 and 1 hold the two destructor entries a virtual destructor creates in the Itanium C++ ABI, 6.4). Because the call is the last thing `route` does, it is a `jmp`: a tail call.
- **`record`:** `push_back`'s fast path is the six instructions from `mov rax,[rdi+0x8]` (load `end`) to the store and `end` update, but it is wrapped in six pushes and pops because the inlined reallocation path, 74 instructions not shown, needs callee-saved registers.

Tools for this: `objdump -d -C -M intel --no-show-raw-insn`, `g++ -S -masm=intel -fverbose-asm` (annotated with source variable names), Compiler Explorer (godbolt.org) for quick experiments across compilers and flags, `perf annotate` (16.5) to see where samples land, and `disassemble /s` in gdb.

## Benchmarking Correctly

### Decide what you are measuring

A benchmark answers one question, and the design follows from it. **Throughput** ("how many messages per second at full load?") is a total divided by a count. **Latency** ("how long does one message take?") is a *distribution*, measured per event and reported as percentiles. A **microbenchmark** isolates one function and is useful for comparing implementations; it says little about the function's cost inside the full system, where caches, branch predictors and the instruction cache are shared with everything else. Production latency is measured in place, with timestamps at stage boundaries and on the wire (15.5).

### The traps

- **The optimizer deletes or hoists the work.** A result that is never used is dead code, a call with loop-invariant arguments to a function without side effects can be computed once, and a constant input can be folded at compile time. The showdown (16.7) is an example.
- **Unrealistic inputs.** The same input every time trains the branch predictor perfectly and keeps the data in L1; real inputs vary in length, content and address.
- **Cold starts.** The first iterations pay page faults (13.2), lazy symbol binding, instruction-cache misses and predictor training. Warm up, or measure them separately if cold behaviour is what matters.
- **The machine.** Frequency scaling and turbo, other threads on the core or its SMT sibling, interrupts, migrations (13.6). Pin, isolate, and record the configuration with the result.
- **The timer.** Clock reads cost tens of cycles (13.5) and must not be comparable to what is measured.
- **The summary.** A mean hides the tail; a mean of percentiles is meaningless.

### Timing with the TSC

`rdtsc` reads the **time-stamp counter**. On current x86-64 CPUs it is *invariant* (the `constant_tsc` and `nonstop_tsc` flags in `/proc/cpuinfo`): it ticks at a fixed reference rate, regardless of frequency changes and idle states, so it measures *time*, not core clock cycles; with turbo the two differ. It is not serializing, so the CPU may execute it before earlier instructions finish or after later ones start. Listing 16.5 is the small toolkit the showdown uses.

### Percentiles and coordinated omission

Report the **count, p50, p99, p99.9 and maximum**, and say over what period. Percentiles from different machines or intervals cannot be averaged; merge the histograms instead.

A subtler trap is **coordinated omission**, named by Gil Tene. A *closed-loop* load generator sends the next request only after the previous reply. When the system stalls, the generator stalls with it and records one slow sample, while in reality every request that should have been sent during the stall would have waited. An *open-loop* generator sends on a schedule, as a market does, and measures each request from its *intended* send time. Problem P16.5 simulates both against a server that stalls for 10 ms once a second: the closed loop reports a p99 of 20 µs, the open loop 2,020 µs. Market data arrives on the exchange's schedule, not yours, so trading-system latency tests must be open-loop.

## perf

`perf` is the standard Linux profiler. It reads the CPU's **hardware performance counters** (cycles, instructions, branches, cache misses and hundreds of model-specific events) and kernel **software events**, either counting them (`perf stat`) or sampling the program every N events or every T microseconds (`perf record`). Access is controlled by `/proc/sys/kernel/perf_event_paranoid` (2 here: users may profile their own processes, not the kernel) or `CAP_PERFMON`.

### perf stat

Run on the showdown's corrected benchmark, in the build container:

```text

               204      page-faults               #    1.613 K/sec
   <not supported>      cycles
   <not supported>      instructions

   <not supported>      branch-misses
       0.127134000 seconds time elapsed
```

The software counters are real and already useful: no context switches or migrations (the pinning worked), and 204 page faults, all at startup. On a machine with a PMU the four hardware lines carry counts, and `perf stat` adds derived columns: **insn per cycle** (IPC) next to `instructions`, and next to `branch-misses` the percentage of all branches. How to read them:

- **IPC** well above 1 (up to about 4–6 on current cores) means the core is busy retiring work; below about 1 means it waits, usually for memory or after mispredictions (12.1).
- **Branch-miss rate** and **misses per thousand instructions** (MPKI): each miss costs roughly 15–20 cycles (12.5); multiply to see what fraction of cycles they explain (Problem P16.7).
- **Cache events** (`L1-dcache-load-misses`, `LLC-load-misses`) are generic names mapped to model-specific events; their exact meaning varies by CPU, so compare like with like.
- A **percentage in brackets** after a count means the event was *multiplexed*: more events were requested than the CPU has counters, each was counted part of the time and scaled up. Request fewer events for exact counts.
- **Top-down analysis** (`perf stat -M TopdownL1`, or `--topdown`, on Intel) splits issue slots into *retiring*, *bad speculation*, *frontend bound* and *backend bound*, and is the fastest way to know which of 12.1's bottlenecks you have.

`perf stat -r 10` repeats the run and reports the variation of every counter, and `perf diff` compares two recorded profiles, which is how a regression between releases is found.

Sampling attributes time to code. Without hardware counters, the timer-based `cpu-clock` event still works:

The biggest entry is not a parser: it is `clock_gettime` in the vDSO, called in a loop by the 50 ms TSC calibration (Listing 16.5, line 32), a quarter of this short program's run. Profiles show the harness too. `strtod`'s internals (`____strtod_l_internal`, `str_to_mpn`, `round_and_return`) together take three to four times `parse_fixed`'s samples, consistent with the benchmark.

Practical points:

- **Call graphs** need a way to walk the stack. `--call-graph fp` uses frame pointers, which are omitted at `-O1` and above unless you build with `-fno-omit-frame-pointer` (some distributions now build their libraries with frame pointers for this reason); `dwarf` copies a slice of the stack at each sample and unwinds it afterwards (large files, works without frame pointers); `lbr` uses Intel's last-branch-record hardware.
- **Skid:** the sampled instruction pointer can be a few instructions after the one that caused the event; precise modifiers (`cycles:pp`, using Intel PEBS or AMD IBS) reduce it. Keep it in mind when `perf annotate` blames an instruction right after a slow load.
- **Statistics:** a sampled percentage is a binomial estimate, so small shares have large relative error (Problem P16.6).
- **Flame graphs** (Brendan Gregg's scripts: `perf script | stackcollapse-perf.pl | flamegraph.pl`) draw the call-graph samples so that wide boxes are where time goes.

### Beyond sampling

- **`perf c2c`** finds false sharing (14.4). It samples memory loads and stores with their data addresses (PEBS load-latency or AMD IBS, so it needs real hardware) and reports cache lines sorted by *HITM* events, loads that hit a line *modified* in another core's cache. For each hot line it lists the offsets within the line that were accessed, by which code (with source lines) and from which CPUs: two different fields written by different threads in one line is the signature of false sharing.
- **`perf mem`** reports load latencies and where loads were satisfied (L1, LFB, L2, L3, local or remote DRAM).
- **`perf sched`** and **`perf trace`** record scheduler events and system calls with far less overhead than `strace` (13.4).
- **`perf probe`** adds dynamic tracepoints (uprobes) to any function, which is how Section 7.7 suggested checking for allocations on the hot path. In the build container:

```text
$ perf probe -x /lib/x86_64-linux-gnu/libc.so.6 malloc
$ perf stat -e probe_libc:malloc ./bench_right
                 6      probe_libc:malloc
```

Six `malloc` calls in the whole run, and `perf record -e probe_libc:malloc --call-graph dwarf` attributes them all to vectors created outside the timed loops. The 4,096 price strings caused none: each is at most 10 characters and fits in `std::string`'s internal buffer (the small-string optimization, 7.7).

## Sanitizers and gdb

Section 11.6 compared what each sanitizer can detect. This section is about using them, and gdb, day to day.

### Builds and options

A typical setup keeps three build configurations besides release: **ASan + UBSan** (`-fsanitize=address,undefined -O1 -g -fno-omit-frame-pointer`), **TSan** (`-fsanitize=thread -O1 -g`, a separate build because it cannot be combined with ASan), and **debug** (`-O0 -g` or `-Og -g`) for stepping. Run the test suite and replayed market data under the first two in CI. Runtime behaviour is controlled by environment variables: `ASAN_OPTIONS=detect_stack_use_after_return=1` adds use-after-return checking, `halt_on_error` and `abort_on_error` control what happens after a report (and whether a core dump is produced); `UBSAN_OPTIONS=print_stacktrace=1` adds stacks to UBSan's one-line reports (or compile with `-fno-sanitize-recover=all` to make them fatal); TSan accepts suppression files for races in third-party code. The lab's fourth experiment measures what they cost on an allocation-heavy workload: ASan about 3.5–4.3 times, UBSan about 2.2 times, both together about 4.2–4.6 times and TSan about 4 times on this single-threaded program; TSan's own documentation quotes 5–15 times for typical multi-threaded programs, with 5–10 times more memory. That is why they run in CI and staging, never in production.

### When no tool reports anything: gdb

`./buggy corrupt` prints `qty = 0` although the code sets 100 and never assigns `qty` again. ASan reports nothing, because the 9-byte copy into the 8-byte `symbol` stays inside the same object (11.6), and the default `_FORTIFY_SOURCE=3` does not catch it either. A **hardware watchpoint** finds the culprit in seconds. Captured in the build container (built with `-O0 -g`; gdb's echo of the commands and thread messages trimmed):

```text
$ gdb -q ./buggy
(gdb) break buggy.cpp:41
(gdb) run corrupt
Breakpoint 1, main (argc=2, argv=0x7fffffff96f8) at buggy.cpp:41
(gdb) print p
$1 = {symbol = "\000\000\000\000\000\000\000", qty = 100}
(gdb) watch -l p.qty
Hardware watchpoint 2: -location p.qty
(gdb) continue
Hardware watchpoint 2: -location p.qty
Old value = 100
New value = 0
__memcpy_avx512_unaligned_erms () at ../sysdeps/x86_64/multiarch/memmove-vec-...
(gdb) bt
#0  __memcpy_avx512_unaligned_erms () at ...
#1  0x0000555555557810 in main (argc=2, argv=0x7fffffff96f8) at buggy.cpp:42
(gdb) up
(gdb) print p

(gdb) print sizeof(p.symbol)

$4 = 9
```

`watch -l` (watch the *location*, not the expression, so it survives leaving the scope) programs one of the CPU's four debug address registers; the CPU stops the program on the instruction that writes the address, with no slowdown until then. x86-64 has four such registers, each covering up to 8 aligned bytes, so a larger region falls back to *software* watchpoints, which single-step the program and are orders of magnitude slower (Problem P16.11).

The gdb commands worth knowing by heart: `run args`, `break file:line` and `break function`, `condition N expr`, `watch -l`, `rwatch` and `awatch` (reads, any access), `bt`, `frame N`/`up`/`down`, `info locals`, `print expr` and `print/x`, `x/16xb addr` (raw bytes), `finish` (run to return), `catch throw` (stop where an exception is thrown), `thread apply all bt` (the first command for a hung process), `disassemble /s` and `info registers`. Two operational habits: enable **core dumps** for production processes (`ulimit -c unlimited`, or `systemd-coredump` and `coredumpctl`), so a crash can be examined later with `gdb ./prog core`, and keep **debug symbols** for every release (separate `.debug` files), because a core dump without symbols is nearly useless. Optimized code shows `<optimized out>` variables and jumps between lines; `-Og` is the compromise. Where hardware performance counters are available, `rr` records an execution and replays it deterministically under gdb, including *backwards* (`reverse-continue` to the last write of a watched variable), which turns a once-a-day race into a reproducible session.

## The Nanosecond Penalty

"Typical" gives rough ranges for current x86-64 servers; "measured here" comes from this chapter's lab and listings in the build container.

| Effect | Typical | Measured here | Why |
|---|---|---|---|
| `-O0` instead of `-O1`/`-O2` | several times slower | 7× (int sum, 16.1) | every variable lives in memory |
| `-O2` → `-O3` on a vectorizable loop | 2–8× faster | 3.8×; 7.8× with `-march=native` (16.1) | dynamic-cost-model vectorization |
| FP reduction with `-ffast-math` | up to the vector width | 8.5× (16.1) | reassociation allowed |
| missing LTO (call across files) | a few cycles per call, plus lost inlining | 0.66 vs 0.49 ns/call (16.1) | no cross-file inlining |
| lost inlining of a constant argument | 2–10× for small bodies | 2.7× (16.2) | `idiv` instead of multiply-shift |
| PGO on a skewed indirect call | up to 2× on such calls | 2.1 → 1.2 ns/call (16.1) | promoted and inlined call |
| `rdtsc`/`rdtscp` with fences | ≈ 20–40 cycles each | < 20 ns (13.5) | waits for the pipeline to drain |
| sampled-profile share of n samples | ± 1.96 √(p(1−p)/n) | — | binomial sampling error |
| ASan / UBSan / ASan+UBSan | ≈ 2× typical (Clang docs) | 3.5–4.3× / 2.2× / 4.2–4.6× (16.6) | shadow checks, redzones; per-op checks |
| TSan | 5–15× typical, 5–10× memory | ≈ 4× single-threaded (16.6) | happens-before tracking on every access |
| software watchpoint | orders of magnitude | — | single-steps the program |

The two lessons of the table: flags and inlining routinely change hot-loop speed by integer factors, so check what the compiler did before tuning code by hand; and every measurement tool perturbs what it measures, so know by how much.

## Interview Questions

**Q1. What is the difference between `-O2` and `-O3`, and why might `-O3` be slower?**
`-O3` adds aggressive vectorization with runtime checks and remainder loops, loop unswitching and distribution, function cloning and more unrolling; `-O2` vectorizes only when no remainder code is needed. `-O3` code is larger, and vector setup costs more than it saves on short loops, so hot paths with small trip counts or a tight instruction-cache budget can get slower. Measure per hot function; GCC allows per-function attributes, but the usual answer is to choose one level and measure.

**Q2. What are LTO and PGO, and what is the risk of PGO in a trading system?**
LTO keeps the compiler's intermediate representation in the object files and optimizes at link time across files: cross-file inlining, devirtualization, dead-function removal. PGO compiles with profile data from a training run so that layout, inlining, unrolling and indirect-call promotion follow measured behaviour. The risk is an unrepresentative training run: rare-but-critical paths (bursts, recovery, risk rejections) get optimized for size or laid out as cold. Train on recorded busy sessions and consider `-fprofile-partial-training`.

**Q3. How do you benchmark a function that takes about 10 ns?**
Verify correctness first. Use varied realistic inputs; keep results alive (`DoNotOptimize`-style asm); warm up; pin the thread on a quiet core; time batches with a fenced TSC so the timer's 10–20 ns is amortized, and subtract the measured empty-loop overhead; collect many samples and report percentiles; check the assembly to confirm the work is still there; repeat across runs and builds. Then confirm the effect in the real system, because a microbenchmark has the caches and predictors to itself.

**Q4. What exactly does `rdtsc` measure, and what can go wrong?**
An invariant counter at a fixed reference rate: elapsed time in ticks, not core cycles, which differ under turbo. It is not serializing, so without `lfence`/`rdtscp` the measured region can leak in or out. Convert with a calibrated frequency; check that the TSC is invariant and synchronized across cores, and be careful in virtual machines.

**Q5. Why is the mean the wrong number, and what is coordinated omission?**
Latency distributions are skewed and the tail is what costs money; the mean blends a rare 10 ms stall into a misleading small number. Report p50/p99/p99.9/max with counts. Coordinated omission is a load generator waiting for each reply before sending the next request, so a stall produces one slow sample instead of all the requests that would really have queued behind it; use an open-loop generator and measure from intended send times.

**Q6. After a release, a component is 20% slower. How do you use perf to find out why?**
Reproduce with recorded input on a quiet, pinned machine. `perf stat` both builds: if instructions rose, the code does more work (diff the profiles); if IPC fell, look at the top-down breakdown and at branch and cache misses. `perf record` both and `perf diff` the profiles to find which functions changed, then `perf annotate` them, and compare the assembly of the hot functions between builds (inlining or vectorization changes are common causes).

**Q7. Why can't you use ASan and TSan together, and how do they differ from Valgrind?**
Both instrument every memory access at compile time and keep incompatible shadow memory, so each needs its own build. They run at a few times normal speed. Valgrind's memcheck needs no recompilation because it translates the binary dynamically, detects uninitialized reads that GCC's sanitizers cannot, and is much slower.

**Q8. In this assembly, `mov rax, [rdi]; jmp [rax+0x10]` — what is happening?**
A virtual call made as a tail call: load the object's vtable pointer, then jump through the third slot of the vtable. With a virtual destructor, the first two slots hold the destructor entries, so slot 2 is the first declared virtual function after it. It is a `jmp`, not a `call`, because the call is the function's last action.

## Key Takeaways

- **Levels:** `-O2` vectorizes only loops needing no remainder code; `-O3` vectorizes more and grows code; `-ffast-math` permits reassociation and assumes no NaNs; `-march` decides the instruction set. Distribution compilers add hardening flags. Check `-fopt-info` and, above all, the assembly.
- **Whole-program:** LTO inlines across files and devirtualizes; PGO optimizes from a training run, so the training data decides what is fast.
- **Inlining** pays through specialization (constants, registers, vectorization), not saved call instructions; cold code inlined into hot functions costs registers and cache. Mark cold paths, split them out, measure.
- **Assembly:** System V arguments `rdi, rsi, rdx, rcx, r8, r9`; callee-saved `rbx, rbp, r12–r15`; recognize address arithmetic with `lea`, magic-number division, `cmov`, lookup tables, vtable calls and tail calls.
- **Benchmarking:** correct first; realistic varied inputs; keep results alive; warm up; pin; fenced TSC on batches minus measured overhead; percentiles with counts; open-loop load to avoid coordinated omission; repeat across builds.
- **perf:** `stat` for counts (IPC, misses, top-down), `record`/`report`/`annotate` for where, `c2c` for false sharing, `probe` for dynamic tracepoints; mind skid, sampling error and multiplexing. Without a PMU (as in this VM), only software events and timer sampling work.
- **Sanitizers and gdb:** ASan+UBSan and TSan builds in CI (2–15× slower, never in production); read reports as what, freed where, allocated where; hardware watchpoints for silent corruption; core dumps and kept debug symbols for production crashes.
- **Showdown:** a benchmark claimed a ten-million-fold speed-up because the optimizer deleted the loop; the corrected harness measured about 3–5×.
