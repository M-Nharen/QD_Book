# Computer Architecture

Part B treated C++ as a language. Part C is about the machine the language runs on, and it starts at the lowest level a software engineer controls: the CPU core and its memory system. Almost every performance question in a QD interview reduces to one of a few architectural facts: an instruction's result is available only after its *latency*, a core can overlap independent work, memory is fetched in 64-byte lines through a hierarchy whose levels differ in latency by two orders of magnitude, every address must be translated, and every branch must be guessed. This chapter explains each fact from zero, shows the mechanism, and measures it.

The order is: the core (12.1), caches (12.2), coherence between cores (12.3), address translation (12.4), branch prediction (12.5), SIMD (12.6), and a consolidated table of latencies (12.7). The code showdown (12.8) applies all of them to one problem, searching a large sorted table, and gets a 2–5× speed-up without changing the algorithm's complexity. Operating-system topics (page faults, huge pages, scheduling, NUMA) are in Chapter 13; the C++ memory model and lock-free code are in Chapter 14; measurement methodology and `perf` are in Chapter 16.

**About the measurements.** Every listing here was compiled with g++ 13.3 at `-O2` and run in the book's build container: a KVM virtual machine with 2 vCPUs whose CPU reports itself as an Intel Xeon of the Cascade Lake family (2.8 GHz nominal; 32 KiB L1d and 1 MiB L2 per core, 33 MiB shared L3). A virtual machine adds noise and distorts some numbers (Section 12.4 explains why memory latency is inflated), so read the *ratios* and the *shapes* of the curves, not the absolute values. Dependent-chain timings in Listing 12.1 are consistent with the cores running at roughly 3.3 GHz, so in this chapter "about 3 cycles per nanosecond" is a fair conversion for this machine; it is an inference, not a measured clock rate.

## Pipelines, Superscalar and Out-of-Order Execution

### From one instruction at a time to hundreds in flight

The simplest mental model of a CPU executes one instruction completely before starting the next. No CPU built in the last thirty years works that way. A modern x86-64 core is:

- **Pipelined.** Executing an instruction is split into stages (fetch, decode, rename, schedule, execute, retire), and each stage works on a different instruction every cycle, like an assembly line. Recent cores have roughly 14–20 stages from fetch to execution.
- **Superscalar.** Each stage handles several instructions per cycle. Recent Intel and AMD cores can rename and dispatch about 4–6 micro-operations (µops) per cycle and have more execution ports than that (separate ports for integer ALU operations, loads, stores, branches, and vector/floating-point work).
- **Out of order.** Instructions enter a large window (the *reorder buffer*, ROB: 224 entries on Skylake, 512 on Golden Cove, 320 on Zen 4) and execute as soon as their inputs are ready, not in program order. They *retire* (become architecturally visible) in program order, which preserves the illusion of sequential execution.

The front end translates x86 instructions, which have variable length and complex semantics, into simpler fixed-format µops. Most instructions become one µop; a decoded-µop cache avoids re-decoding hot loops. **Register renaming** maps the 16 architectural integer registers onto a physical register file of a few hundred entries, so two instructions that merely reuse the same register name (`rax` for unrelated values) do not have to wait for each other. Only *true* dependencies remain: an instruction that needs a value must wait for the instruction that produces it.

### Latency and throughput

Every instruction has two costs:

- **Latency:** cycles from when its inputs are ready to when its result can be used by a dependent instruction.
- **Throughput** (reciprocal throughput): how often a new independent instance can start, limited by how many execution units can perform it.

| Operation (64-bit unless noted) | Latency (cycles) | Independent ops per cycle | Notes |
|---|---|---|---|
| integer add, sub, and, xor, shift | 1 | 3–4 | several ALU ports |
| integer multiply (`imul`) | 3 | 1 | fully pipelined |
| integer divide (`div`, `idiv`) | about 10–20 (newest cores) to 35–90 (Skylake-family servers) | far below 1 | partly unpipelined; depends on operand values |
| L1 data-cache load | 4–5 | 2–3 | address-generation and load ports |
| FP add, multiply, FMA (scalar or vector) | 3–5 | 2 | |
| FP divide, square root (double) | about 13–20 | well below 1 | |
| conditional move (`cmov`) | 1 | 2+ | a data dependency, not a branch |
| atomic read-modify-write (`lock add`, `xchg`) | about 18–25 uncontended | well below 1 | drains the store buffer (14.3) |

These are typical ranges for recent Intel and AMD cores; exact per-model figures are published in Agner Fog's instruction tables and on uops.info. The rule that follows from the table: **a chain of dependent operations runs at the speed of its latency; independent operations run at the speed of throughput.** The difference is often a factor of 4–10.

### Memory-level parallelism

Out-of-order execution also overlaps *cache misses*. If a loop issues loads whose addresses do not depend on each other, the core can have several misses outstanding at once (Intel cores track on the order of 10–16 outstanding L1 misses per core in *line fill buffers*). The throughput of such a loop is then governed by **Little's law**: lines per second = lines in flight ÷ latency. Pointer chasing (each address comes from the previous load) defeats this completely, which is why linked structures are slow regardless of how few instructions they execute (Listing 12.2, and Problem P12.4).

### Speculation and simultaneous multithreading

To keep hundreds of instructions in flight, the core must guess the outcome of branches long before they execute (12.5) and execute down the guessed path *speculatively*, discarding the work if the guess was wrong. Speculative execution leaves traces in the caches, which is the basis of the Spectre family of attacks; operating-system and compiler mitigations have measurable costs, which is one reason latency-sensitive hosts are tuned carefully (13.8).

**Simultaneous multithreading** (SMT, Intel's Hyper-Threading) runs two hardware threads on one core, sharing its execution units, caches and buffers. It improves total throughput for code that stalls often, but each thread runs slower and less predictably than it would alone. Latency-critical threads in trading systems are typically given a whole physical core, with the sibling hardware thread left idle or disabled (13.6).

## Caches and Cache Lines

### Why caches exist

A core can start several operations per cycle, about every 0.3 ns. A load from DRAM takes on the order of 100 ns: several hundred cycles. Programs nevertheless run fast because memory accesses have **locality**: *temporal* (data used now is likely to be used again soon) and *spatial* (data near recently used data is likely to be used soon). A cache is a small, fast memory that holds recently used data close to the core.

### The 64-byte cache line (diagnostic D8)

Caches do not store bytes; they store **cache lines**, aligned 64-byte blocks of memory, on every current x86-64 processor (some ARM processors, including Apple's M-series, use 128-byte lines). A load of one byte brings the whole 64-byte line containing it into the cache. Every cost in this chapter is counted in lines:

- A struct that straddles a line boundary needs two lines for one access (Problem P12.2).
- Reading the 8 bytes after a line you already touched is almost free; reading 8 bytes 64 bytes away costs a new line.
- Coherence between cores (12.3) is tracked per line, so two variables in one line are, for coherence purposes, one variable (false sharing, 14.4).
- Intel's L2 "spatial prefetcher" tends to fetch lines in 128-byte-aligned pairs, which is why some code pads contended data to 128 bytes rather than 64 (14.4).

### The hierarchy

| Level | Typical size on recent x86-64 servers | Typical load-to-use latency | Shared by |
|---|---|---|---|
| registers | 16 general-purpose, 16–32 vector | 0 (part of the instruction) | one hardware thread |
| L1 data cache | 32–48 KiB, 8–12-way | 4–5 cycles | one core (both SMT threads) |
| L2 cache | 256 KiB – 2 MiB | 12–16 cycles | one core |
| L3 (last-level) cache | about 1.4–4 MiB *per core*, tens to hundreds of MiB per socket | about 30–70 cycles | all cores of a socket or chiplet |
| DRAM | gigabytes | about 70–120 ns local; more for another socket's memory (13.7) | the whole machine |

The build container's CPU reports 32 KiB L1d (8-way), 1 MiB L2 (16-way) and 33 MiB L3.

### How an address finds its line

A cache with *S* sets of *W* ways and 64-byte lines splits an address into three fields:

| Bits | Field | Meaning |
|---|---|---|
| 0–5 | offset | byte within the 64-byte line |
| 6 to 6 + log_{2}S − 1 | set index | which set the line must live in |
| the rest | tag | which of the many lines that map to that set this is |

A 32 KiB, 8-way L1 has 32768 / (64 × 8) = 64 sets, so the set index is bits 6–11. Each set holds at most 8 lines; when a ninth line that maps to the same set is needed, one is evicted (usually an approximation of least-recently-used). This creates **conflict misses**: addresses that differ by a multiple of 4096 bytes map to the *same* L1 set, so walking down a column of a matrix whose rows are 8192 bytes long uses only one set and only 8 lines of the whole cache (Problem P12.9). Padding each row by one line spreads the accesses across all sets.

Note that bits 0–11 are exactly the offset within a 4 KiB page. The L1 can therefore select the set using untranslated address bits while the TLB translates the rest in parallel (12.4); this "virtually indexed, physically tagged" design is why L1 sizes are a multiple of 4 KiB times the associativity (32 KiB = 8 × 4 KiB; 48 KiB = 12 × 4 KiB).

### Writes, prefetchers and the store buffer

- **Write-back, write-allocate.** A store to a line not in the cache first fetches the line (a *read for ownership*, 12.3), then modifies it in the cache; memory is updated only when the dirty line is evicted. Non-temporal stores (`_mm_stream_si128`) bypass this for large buffers that will not be read soon.
- **The store buffer.** Stores do not wait for the cache: they enter a store buffer and drain to L1 in order after they retire. A later load of the same address is satisfied from the buffer (*store-to-load forwarding*, a few cycles). The store buffer is also why x86 allows a later load to pass an earlier store to a different address, the one reordering x86-TSO permits (14.3).
- **Hardware prefetchers** watch the access stream and fetch lines before they are requested: the next line, constant strides from the same instruction, and streams of consecutive lines. They work only when the pattern is predictable from addresses already seen. `__builtin_prefetch(addr)` issues a software prefetch, which helps when *you* know future addresses that the hardware cannot predict (12.8).

Two design rules follow. Keep the hot working set small (structures of arrays rather than arrays of fat structs, 6.7; compact keys; no pointers where indices will do). And make accesses predictable: arrays beat linked lists and trees of separately allocated nodes (`std::list`, `std::map`, 10.2–10.3) not because of instruction counts but because each node visit is a potential cache miss that cannot be prefetched.

## Cache Coherence (MESI)

### The problem

Each core has private L1 and L2 caches. If core A and core B both cache the line holding variable `x`, and A writes `x`, B must not keep reading its stale copy forever. A **cache-coherence protocol** maintains one invariant per line: *at any moment, either one core may write the line, or any number of cores may read it* (single writer, multiple readers), and a read returns the most recent write.

### MESI states

Each cached line is in one of four states:

| State | Meaning | Can read? | Can write? |
|---|---|---|---|
| **M**odified | only copy; dirty (differs from memory) | yes | yes, silently |
| **E**xclusive | only copy; clean | yes | yes, silently (becomes M) |
| **S**hared | other caches may also hold it; clean | yes | no: must first invalidate the others |
| **I**nvalid | not present | no | no |

The key transitions:

- **Read miss.** The core requests the line. If another core holds it in M, that core supplies the data (and writes it back) and both copies become S. If another core holds it in E or S, the new copy is S. If nobody holds it, the new copy is E.
- **Write to a line in S or I.** The core sends a *read-for-ownership* (RFO) or upgrade request; every other copy is invalidated (goes to I); the writer's copy becomes M. The write cannot complete (leave the store buffer) until the invalidations are acknowledged.
- **Write to a line in E or M.** No communication at all. This is why a variable written by only one core is cheap.

Intel uses a variant with a fifth *Forward* state (MESIF) that designates which sharer answers requests; AMD uses MOESI, whose *Owned* state lets a dirty line be shared without writing it back first. The costs below are the same in all of them. Rather than broadcasting every request to every core (*snooping*), large processors keep a directory or *snoop filter* alongside the L3 that records which cores may hold each line, and forward requests only to them.

Divided by two, this is a one-way "core-to-core latency". On bare-metal servers it is typically some tens of nanoseconds between cores of one socket, and more across sockets; a virtual machine adds the uncertainty of where the hypervisor places the vCPUs.

Consequences for design:

- **Single-writer principle.** Arrange data so that each cache line is written by one thread only. Counters are per-thread and summed on read; queues have separate head and tail indices on separate lines (14.5).
- **False sharing** (14.4): two threads writing *different* variables that share a line suffer case (c) without any logical sharing.
- **Readers of a hot line pay for every write.** A line that one thread writes and another polls is transferred on every write (that is the cost of handing a message between threads, and the reason seqlocks (14.7) and SPSC queues are designed around it).
- **Coherence is not ordering.** Coherence guarantees agreement on the history of *each* line. The order in which writes to *different* lines become visible to other cores is a separate question, answered by the hardware memory model and the C++ memory model (14.2, 14.3).

## Virtual-Address Translation and the TLB

### Page tables and the page walk

Every address a program uses is a *virtual* address; the hardware translates it to a *physical* address using page tables maintained by the operating system (13.2 covers the OS side). On x86-64 with 4 KiB pages and 4-level paging, a 48-bit virtual address is split as 9 + 9 + 9 + 9 + 12 bits: four 9-bit indices, one per level of the page-table tree, and a 12-bit offset within the page. Translating an address from scratch, a **page walk**, therefore takes four dependent memory reads (newer processors support 5-level paging for 57-bit addresses, adding a fifth). The walk is done by a hardware page walker, and its reads go through the data caches, so a walk can cost anything from a few cycles (all entries cached) to several DRAM latencies.

### The TLB

To avoid walks, the core caches recent translations in the **translation lookaside buffer** (TLB). On Skylake-family cores, for example, the first-level data TLB holds 64 entries for 4 KiB pages (plus 32 for 2 MiB pages), and a second-level TLB (STLB) holds 1536 entries shared between 4 KiB and 2 MiB pages; other cores have similar structures of different sizes. A first-level hit costs nothing extra; an STLB hit costs several cycles; an STLB miss starts a page walk.

The useful quantity is **TLB reach**: entries × page size. With 4 KiB pages, 64 entries cover only 256 KiB and 1536 entries cover 6 MiB. A random-access working set larger than that misses the TLB on most accesses *in addition to* missing the caches. With **2 MiB huge pages**, the same 1536 entries would cover 3 GiB. How to obtain huge pages (transparent huge pages, `hugetlbfs`, `MAP_HUGETLB`) and the operational trade-offs are in 13.3.

**Context switches and the TLB.** Switching to another process changes the page tables. Process-context identifiers (PCID) let entries of different address spaces coexist in the TLB, but a switch still disturbs TLB and cache contents. This is one of the costs of a context switch quantified in 13.4.

## Branch Prediction

### Why prediction is unavoidable

The front end must fetch the instructions after a branch long before the branch executes: with a pipeline of 15–20 stages and 4–6 µops per cycle, that is tens of instructions per stage of delay, and the out-of-order window holds hundreds. So the core *predicts* every branch at fetch time and executes speculatively down the predicted path. When the branch finally executes and the prediction was wrong, everything after it is discarded and fetching restarts at the correct target. The **misprediction penalty** is about 15–20 cycles on recent cores, plus the useful work that was thrown away.

Predictors are built from several structures: a branch target buffer (where does this branch go?), a direction predictor that correlates each branch's outcome with the recent history of outcomes (modern designs are TAGE-like and can learn long, complex patterns; their exact designs are not published), a return-stack buffer for function returns, and an indirect-branch predictor for `switch` jump tables and virtual calls (6.5). A predictable branch is almost free; an unpredictable one costs about half the misprediction penalty on average if it goes each way half the time.

### Choosing between branches and branchless code

- A branch converts a data dependency into a prediction. If the prediction is good, the core runs ahead, which also lets it issue future loads early (this matters in 12.8). If it is bad, you pay the penalty.
- `cmov` and mask arithmetic remove the penalty but serialize the computation on the condition's inputs. Use them when the condition is unpredictable and cheap to compute.
- **The compiler decides, not the source code.** In Listing 12.5, g++ keeps a branch because two variables are updated; for `if (x >= 128) s += x;` alone it emits `cmov`. The comment in Listing 12.8 (lines 18–20) records the opposite surprise: a branchless-looking ternary compiled *into* a branch. Check the assembly (16.3), and re-check after compiler upgrades.
- `[[likely]]` and `[[unlikely]]` (C++20) and `__builtin_expect` tell the compiler which path is hot so it can lay out the hot path as straight-line, fall-through code and move the cold path away (16.2). They do not program the hardware predictor. Profile-guided optimization (16.1) does the same from measured data.
- On a trading hot path, the branch that matters most is often the rare one: the order that is sent after many messages that were not acted on. A path that executes rarely has cold caches and cold predictor state. Keeping the critical path warm, for example by regularly exercising it with synthetic data that stops short of sending, is a commonly described technique for that reason (17.6 discusses tick-to-trade budgets).

## SIMD Basics

### Vector registers and instruction sets

SIMD (single instruction, multiple data) instructions operate on several values packed into one wide register:

| Extension | Register width | Registers | Lanes for 32-bit values | Status |
|---|---|---|---|---|
| SSE2 | 128-bit `xmm` | 16 | 4 | part of baseline x86-64: always available |
| AVX, AVX2 | 256-bit `ymm` | 16 | 8 | most x86-64 CPUs from the last decade |
| AVX-512 | 512-bit `zmm`, plus 8 mask registers | 32 | 16 | Intel server parts, recent AMD; not on many Intel client CPUs |

On some Intel server generations (Skylake-SP and Cascade Lake), sustained heavy 512-bit (and to a lesser degree 256-bit) work lowers the core's clock frequency for a while, which can make a latency-sensitive thread on the same core slower. That is a reason some low-latency code avoids AVX-512 on the hot path or isolates it on separate cores.

### Three ways to get SIMD code

1. **Auto-vectorization.** The compiler turns loops into vector code when it can prove it is safe and estimates it is profitable. With GCC, `-O3` enables full vectorization; since GCC 12, `-O2` vectorizes only with a "very cheap" cost model, and in practice g++ 13 at `-O2` did not vectorize a simple `int` sum over a run-time-length array, while `-O3` did. Common blockers: possible aliasing between input and output pointers (`__restrict` helps, 11.3), loop-carried dependencies, unknown trip counts with early exits, and floating-point reductions, which change results when reordered and are therefore not vectorized without `-ffast-math` or `-fassociative-math`.
2. **Intrinsics.** Functions such as `_mm_cmplt_epi8` that map one-to-one onto instructions, declared in `<immintrin.h>`. Full control, no portability.
3. **Libraries and language extensions.** GCC vector extensions (`__attribute__((vector_size(32)))`), `std::experimental::simd` (shipped with libstdc++ since GCC 11), or established libraries.

To use instructions beyond the baseline without requiring them everywhere, compile the specific functions for the extension (`[[gnu::target("avx2")]]`, as in Listing 12.6) and choose at run time with `__builtin_cpu_supports`, or build the whole binary with `-march=` matching the production machines (16.1).

| uncontended atomic RMW | 18–25 cycles | ≈ 6–7 ns (12.3) | store-buffer drain |

| minor page fault | ≈ 0.5 µs or more | Chapter 13 | kernel entry, page allocation, zeroing |
| context switch | a few µs including cache effects | Chapter 13 | scheduler, TLB and cache disturbance |
| kernel UDP receive path | a few µs | Chapter 15 | interrupt, protocol stack, copy |

A useful way to use this table in an interview is as a budget. If a component must respond in 1 µs, it can afford perhaps 5–10 DRAM misses and nothing from the bottom four rows; if it must respond in 100 ns, it can afford roughly one. Most low-latency design (Chapter 18) is the art of making the hot path's working set fit in L1 and L2, keeping its accesses predictable, and keeping the kernel out of it.

## Code Showdown: Searching a Large Sorted Table

Looking up a key in a sorted array is everywhere in trading code: mapping a price to its level, a symbol to an instrument record, a timestamp to a position in a recorded data file. Binary search is O(log n) and has tiny constants in the textbook sense. The cost model of this chapter says something else: each of the log_{2} n steps is a *dependent* load with an *unpredictable* branch, so for a large table each step is a cache miss plus a likely misprediction.

**(1) Branchless binary search (lines 21–31).** The loop always runs ⌈log_{2} n⌉ times and replaces the branch with arithmetic on the comparison result (line 27), which g++ compiles to `cmov`. Two details are important:

- The comment on lines 18–20 records a real experiment: written as `(base[half - 1] < x) ? half : 0`, the update was compiled back into a conditional jump, with no speed-up. Writing it as a multiplication produced `cmov`. Always verify in the assembly.
- For arrays that fit in L1 and L2 it is several times faster than `std::lower_bound`, because nothing is mispredicted. For the 64 MiB array it is *slower*. The branchy search, when it predicts correctly (about half the time per step), starts the next level's load before the current comparison has finished: the speculation acts as a prefetch, and some misses overlap. The branchless search cannot issue the next load until the current one returns, because the address depends on it. It has eliminated mispredictions and with them all memory-level parallelism (12.1).

**(2) Eytzinger layout with prefetching (lines 33–62).** The keys are stored in the order of a breadth-first traversal of the implicit binary search tree: the root at index 1, the children of node *k* at 2k and 2k + 1 (the layout used for binary heaps, 3.7). The constructor fills it with an in-order walk (lines 43–48), which visits tree positions in sorted order. The search (lines 49–61) descends with a branchless step, `k = 2k + (b[k] < x)` (line 57). The layout has two advantages:

- **The top of the tree is compact.** Nodes 1–15 (the first four levels) occupy 64 bytes: one line if the array starts on a line boundary, at most two otherwise (`std::vector` guarantees only 16-byte alignment; a 64-byte-aligned allocation is a cheap further improvement). Every search starts with the same few lines, which stay in L1 permanently, whereas in sorted order the first probes of different searches land in different lines.
- **Future addresses are known.** Four levels below node *k*, the 16 possible descendants are nodes 16k … 16k + 15: 16 consecutive 4-byte keys, which form exactly one cache line when the array is 64-byte aligned (two otherwise). Line 56 prefetches that line while the current four levels are still being resolved, so instead of 24 serial misses the search has up to four misses in flight at a time.

Lines 53–56 also apply Chapter 11: near the bottom of the tree 16k exceeds the array size, and *forming* a pointer that far past the end would be UB (11.2) even though prefetching an unmapped address is harmless to the hardware. The address is therefore computed as an integer and converted to a pointer only to pass it to `__builtin_prefetch`. Line 59 converts the final position back to the answer: the search ends below a leaf, and the answer is the last node at which it went left, which is found by shifting off the trailing run of right turns (`countr_zero(~k) + 1` bits). Problem P12.10 traces a small example by hand.

For the smallest table the two branchless versions are within run-to-run noise of each other. From L2-sized tables upwards the Eytzinger search is the fastest: about four times faster than `std::lower_bound` at 256 KiB and about twice as fast at 64 MiB, with the same O(log n) complexity and the same comparisons. Going further, a *B-tree* layout with 16 keys per node (one cache line), searched with one SIMD comparison per node, reduces the number of cache lines touched per lookup from about log_{2} n to about log_{17} n; that is a good extension exercise once Listing 12.8 is understood.

## The Nanosecond Penalty

### Misaligned and split loads

Chapter 11 recommended decoding packets with `memcpy` at arbitrary byte offsets and promised to measure what misalignment costs the hardware.

@code ch12/split_loads.cpp

@output ch12/split_loads.cpp measured in the build container; all loads hit L1

- **Misaligned within one line (offset 3):** no measurable cost. Modern x86-64 cores handle any load that stays inside one 64-byte line at full speed.
- **Split across two lines (offset 60):** the load needs both lines; the core performs two cache accesses and merges the results, which costs extra load-port bandwidth. Measured here as roughly 1.5–2× the time per load in a throughput-bound loop.
- **Split across two pages (offset 4092):** the two halves need two address translations as well as two lines. Measured here as about 3× the aligned case even with both pages in the TLB; on older microarchitectures page splits were much more expensive.

For message decoding, this means: field-level misalignment within a message is free, line splits cost a little, and if a decoder is load-bound it is worth aligning *receive buffers* to 64 bytes so that splits happen only where the wire format forces them.

### Summary of this chapter's penalties

| Penalty | Approximate cost on a modern x86-64 core | How to avoid it |
|---|---|---|
| dependency chain instead of independent work | latency instead of throughput: 3–10× | multiple accumulators, break chains (12.1) |
| integer division in a loop | tens of cycles each | multiply by reciprocal, powers of two (12.1) |
| L1 miss to L2 / L3 / DRAM | ≈ 10 / 40–60 / 200–350 cycles | small hot working set, sequential access (12.2) |
| pointer chasing through a large structure | one full miss per node, no overlap | arrays and indices, prefetch-friendly layouts (12.2, 12.8) |
| writing a line another core is using | tens to hundreds of ns per transfer | single-writer data, padding (12.3, 14.4) |
| TLB miss with page walk | tens of cycles, more in a VM | compact data, huge pages (12.4, 13.3) |
| unpredictable branch | ≈ 15–20 cycles per mispredict | sort or partition data, branchless code (12.5) |
| scalar code on data-parallel work | 4–30× lost throughput | vectorize: compiler or intrinsics (12.6) |
| line- or page-split load | a few cycles extra | align buffers (12.9) |

## Interview Questions

**Q1. What is the cache-line size on x86-64, and why does it matter?**
64 bytes. Caches transfer and track memory in whole lines, so the cost of memory access is counted in lines touched, not bytes; coherence between cores is also per line, which is why two variables written by different threads should not share a line (false sharing, 14.4).

**Q2. Explain latency versus throughput with an example.**
Latency is how long one operation takes before a dependent one can use its result; throughput is how many independent operations can start per cycle. An FP add has about 4 cycles of latency but two can start every cycle, so summing an array with one accumulator runs at 1 add per 4 cycles and with 8 independent accumulators approaches 2 per cycle: an 8× difference for the same arithmetic.

**Q3. Why is iterating over a `std::list` much slower than over a `std::vector` of the same elements, even though both are O(n)?**
Vector elements are contiguous, so each 64-byte line serves several elements and the prefetcher streams them in. List nodes are separately allocated; each `next` pointer must be loaded before the next node's address is known, so the traversal is a chain of dependent, unpredictable loads, each a potential cache miss costing up to about 100 ns, with no overlap.

**Q4. Describe MESI. What happens when two cores repeatedly increment the same atomic counter?**
Lines are Modified, Exclusive, Shared or Invalid; a core may write only a line it holds in M or E, so a write to a shared line first invalidates other copies. With two incrementing cores, every increment requires taking the line in M from the other core, so the line ping-pongs, each increment waits for a cross-core transfer, and throughput collapses compared with per-thread counters on separate lines.

**Q5. What is the TLB, and why do huge pages help?**
The TLB caches virtual-to-physical translations; a miss requires a page walk of up to four dependent memory reads (up to 24 in a VM). Its reach is entries × page size, about 6 MiB for 1536 entries of 4 KiB. With 2 MiB pages the same entries cover gigabytes, so large random-access structures (hash tables, order books, lookup tables) stop paying TLB misses.

**Q6. What is a branch misprediction and what does it cost? How do you avoid it?**
The front end guesses branch outcomes to keep fetching; a wrong guess flushes the speculative work, costing about 15–20 cycles. Avoid unpredictable branches on hot paths by sorting or partitioning data so outcomes are predictable, by computing results with masks or `cmov`, or by restructuring logic (lookup tables); measure, because a well-predicted branch is cheaper than branchless code.

**Q7. Why might branchless binary search be slower than `std::lower_bound` on a huge array?**
Branchless code makes each step's address depend on the previous load, so misses are strictly serialized. The branchy version speculates past the comparison and issues the next load early; even with frequent mispredictions this overlaps some misses. Software prefetching or a layout such as Eytzinger restores the overlap.

**Q8. Why does the compiler not vectorize a floating-point sum at `-O3`?**
Vectorizing changes the order of additions, and FP addition is not associative, so the result could change. The compiler must preserve the source semantics unless allowed otherwise (`-ffast-math`, `-fassociative-math`), or unless you write the reordered sum yourself with intrinsics or multiple accumulators.

**Q9. What are hardware prefetchers, and when do they fail?**
Units that detect access patterns (next line, constant stride, sequential streams) and fetch lines before they are requested. They fail on data-dependent addresses: pointer chasing, hash-table probes, tree searches. Software prefetch helps there if you can compute future addresses early enough.

**Q10. A colleague claims SMT (Hyper-Threading) gives free performance. When is that wrong in a trading system?**
Two hardware threads share one core's execution units, L1/L2 caches and buffers. A latency-critical thread sharing its core with another runs slower and with more jitter, because its caches and ports are contended. Critical threads are therefore usually given a dedicated physical core with the sibling thread idle (13.6).

**Q11. Why is the L1 data cache typically 32 KiB or 48 KiB and not, say, 40 KiB?**
L1 is virtually indexed, physically tagged: the set index must come from address bits that are not translated, i.e. within the 4 KiB page offset. With 64-byte lines that allows 64 sets, so the size is 4 KiB × associativity: 8-way gives 32 KiB, 12-way gives 48 KiB.

**Q12. Estimate the time for 10^{6} random lookups in a 1 GiB hash table with 4 KiB pages.**
Each lookup misses the caches (≈ 100 ns) and, since 1 GiB spans 262,144 pages, also misses the TLB, adding a page walk whose last level is likely another cache miss: roughly 150–250 ns per lookup if done one at a time, so 0.15–0.25 s. Huge pages remove most of the walk cost; issuing lookups in batches with prefetching overlaps the misses (memory-level parallelism) and can cut the total several-fold.

## Key Takeaways

- **The core:** pipelined, 4–6 wide, out of order with hundreds of instructions in flight. Dependent chains run at latency, independent work at throughput; break chains with multiple accumulators. Division is an order of magnitude slower than multiplication.
- **Caches:** 64-byte lines (D8). L1 ≈ 4–5 cycles, L2 ≈ 12–16, L3 ≈ 30–70, DRAM ≈ 70–120 ns. Cost is counted in lines touched and in whether accesses are predictable. Strides that are multiples of 4 KiB cause conflict misses.
- **Prefetching and parallelism:** prefetchers handle sequential and strided access; pointer chasing defeats them and serializes misses. Little's law: bandwidth = lines in flight ÷ latency.
- **Coherence (MESI):** one writer or many readers per line. Writing a line another core holds costs a cross-core transfer; contended atomics and false sharing are the same problem. Design for single-writer data.
- **Translation:** TLB reach = entries × page size (≈ 6 MiB with 4 KiB pages). Page walks add tens of cycles, up to 24 memory references in a VM. Huge pages fix it (13.3).
- **Branches:** mispredictions cost ≈ 15–20 cycles. Predictable branches are nearly free and enable speculation; branchless code trades the penalty for a data dependency. The compiler chooses; read the assembly.
- **SIMD:** SSE2 is always available; AVX2 widely; AVX-512 on servers with frequency caveats. Auto-vectorization needs `-O3` (or the very-cheap model at `-O2`), no aliasing, and permission to reorder FP. Intrinsics with run-time dispatch give control.
- **Showdown lesson:** same algorithm, same comparisons, 2–5× faster by changing memory layout and the dependency structure (branchless + Eytzinger + prefetch).
- **Measure on the target:** virtual machines distort L3 capacity, memory latency and inter-core timing. Ratios transfer; absolute numbers do not.
