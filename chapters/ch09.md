# Compile-Time Programming

A trading system makes thousands of decisions that do not change while it runs: which message types exist and how they are laid out, which risk checks apply and in what order, the width of an integer field, the powers of ten used to scale prices. Compile-time programming moves those decisions out of the hot path and into the compiler. Done well, the generated code contains no branches for decisions already made, no indirect calls whose target is fixed, and no tables computed at startup. Done badly, it produces binaries several times larger than necessary, multi-minute builds, and error messages nobody can read.

Interviewers probe this area for two reasons. First, template and `constexpr` questions separate people who have written generic code from people who have only used it. Second, the costs are subtle: "templates are zero-cost" is true of the arithmetic and false of the instruction cache and the build. This chapter builds the mechanics from zero (Sections 9.1–9.6), measures the costs (Section 9.7), and ends with a code showdown in which a pipeline of pre-trade risk checks is composed at run time and then at compile time (Section 9.8).

The chapter assumes Chapter 5 (the compilation model, Section 5.1) and uses forwarding references from Section 8.3 without re-deriving them.

## Templates and Instantiation

### Intuition: a template is a recipe, not a function

A function template is not a function. It is a recipe the compiler follows to *write* a function when you use it with particular types. `std::max<int>` and `std::max<double>` are two different functions, with different machine code, produced from one recipe. The act of writing out one concrete function or class from a template is called **instantiation**, and the argument list that drives it (`<int>`, `<double>`) determines which instantiation you get.

That single idea explains most template behaviour that surprises beginners:

- **Templates live in headers.** To instantiate `clamp_add<long>`, the compiler needs the full recipe in the translation unit that uses it. A declaration alone is not enough (an exception, explicit instantiation, comes below).
- **Errors appear late.** Code inside a template is only fully checked once it is instantiated, so a mistake can sit unnoticed until someone uses the template with a new type.
- **Every distinct argument list costs code.** Ten instantiations means up to ten copies of the machine code. Section 9.7 measures this.

### What the compiler does

**Deduction.** For a call `clamp_add(1.5, 2.0, 3.0)`, the compiler deduces `T` independently from each argument and requires all deductions to agree. Deduction does not consider conversions: `clamp_add(1, 2.0, 3)` fails because `T` would be both `int` and `double`, even though converting everything to `double` would work. You can always override deduction by naming the arguments explicitly, as in `clamp_add<long>(1, 2, 10)`. (Deduction from forwarding references `T&&` has extra rules; Section 8.3 covers them.)

**Two-phase lookup.** The compiler checks a template twice. At the point of *definition* it parses the template and looks up every name that does not depend on a template parameter; an undeclared non-dependent name is an error even if the template is never used. At the point of *instantiation*, once `T` is known, it looks up the *dependent* names: anything whose meaning depends on `T`. Two consequences show up in every interview about templates:

- A qualified name that depends on `T`, such as `std::vector<T>::size_type`, could be a type or a value (a specialization of `std::vector` could make it a static data member). Inside a function body you must write `typename` to say it is a type. C++20 dropped the requirement in places where only a type can appear, such as a member declaration's type, but not in a function body.
- Members of a *dependent base class* (a base that depends on `T`, like `Base<T>`) are not searched at definition time, because a specialization of `Base` might not have them. Write `this->grow()` or `Base<T>::grow()` to make the name dependent.

**Lazy instantiation of members.** Instantiating a class template instantiates the *declarations* of its member functions, but a member function's *body* is instantiated only if that member is used. `Wrapper<int>` is valid even though `Wrapper<int>::length()` would call `.size()` on an `int`, as long as nobody calls `length()`. The standard library relies on this constantly: `std::vector<T>` has members that need `T` to be copyable, and you can still have a vector of move-only types as long as you do not call them.

**Specialization.** A *full* (explicit) specialization replaces the recipe for one exact argument list. A *partial* specialization of a class template replaces it for a family, such as all pointer types `T*`. Function templates cannot be partially specialized; overloading plays that role, and mixing the two has a well-known trap that Problem P9.1 explores.

**Where the code goes, and why the linker does not complain.** If two translation units both instantiate `clamp_add<double>`, both object files contain its code. That would normally violate the one-definition rule at link time (Section 5.1), so compilers emit each instantiation in its own *COMDAT* section marked as a weak, mergeable definition, and the linker keeps one copy. The duplicates still cost compile time in every translation unit; only the final binary is deduplicated.

## constexpr, consteval and constinit

### Intuition

Some values are knowable before the program runs: 10^{9}, the CRC-32 lookup table, the hash of the string "NewOrder", the offset of a field in a message. Computing them at run time wastes cycles, and computing them in a startup function introduces ordering problems between global objects. C++ lets you mark functions and variables so the compiler evaluates them itself and bakes the results into the binary. The three keywords answer three different questions:

| Keyword | Applies to | Meaning |
|---|---|---|
| `constexpr` (function) | functions | *may* be evaluated at compile time if called with constant arguments in a context that needs a constant; otherwise runs normally at run time |
| `constexpr` (variable) | variables | *must* be initialized at compile time; implies `const` |
| `consteval` | functions | an *immediate function*: every call must be evaluated at compile time; a call with run-time arguments is an error |
| `constinit` | variables with static or thread storage | *must* be initialized at compile time, but the variable is **not** `const` |

### Mechanics: the compiler as an interpreter

When the compiler needs the value of a constant expression, it runs an interpreter over its internal representation of your code. That interpreter is strict in ways the hardware is not:

- **Undefined behaviour is a compile error.** Signed overflow, an out-of-bounds read, or reading an uninitialized variable during constant evaluation is diagnosed, because the standard requires a constant expression to be free of UB. `constexpr int x = 46341 * 46341;` does not compile (the product exceeds `INT_MAX`); the same expression at run time is silent UB (Section 11.2). A cheap way to test a small pure function for UB is to call it in a `static_assert`.
- **There are resource limits.** GCC 13 stops at 512 levels of `constexpr` recursion (`-fconstexpr-depth`), 262,144 iterations of a single loop (`-fconstexpr-loop-limit`), and a cap on total operations (`-fconstexpr-ops-limit`). We checked the first two by triggering them; the error messages name the flag to raise.
- **C++20 widened what is allowed.** `constexpr` functions may contain `try` blocks (a `throw` reached during constant evaluation is an error), call `virtual` functions, use unions with a changing active member, and allocate memory with `new`, provided every allocation is freed before the evaluation ends (*transient allocation*). That is why `std::vector` and `std::string` became usable inside constant evaluation, though a `constexpr std::vector` *variable* that keeps its heap buffer is still not allowed.

The result of a constant evaluation is just data: an immediate operand in an instruction, or bytes in the read-only data section (`.rodata`). There is no run-time trace that a computation ever happened.

### What to use it for

- **Tables:** powers of ten, CRC tables (Problem P9.6), character-class tables for parsers, bit masks. A table generated by code cannot drift out of sync with the code that generated it.
- **Protocol layout checks:** `static_assert(sizeof(AddOrderMsg) == 36)` and `static_assert(offsetof(AddOrderMsg, price) == 20)` turn a wire-format mismatch into a build failure instead of a silent misparse. The feed parser in Section 18.2 depends on them.
- **Compile-time string handling:** message type IDs, perfect hashing of a fixed key set (Problem P9.10).
- **Not for:** values that come from configuration. Risk limits, symbols and network addresses change without a rebuild. Section 9.8 keeps that distinction explicit.

## Type Traits and if constexpr

### Intuition: functions from types to values

A *type trait* is a function that the compiler evaluates on types. `std::is_integral<T>::value` maps a type to `true` or `false`; `std::remove_reference<T>::type` maps a type to another type. They are implemented with nothing more than templates and specialization: a primary template gives the default answer, and specializations give the answer for particular patterns. The `_v` and `_t` suffixes (`std::is_integral_v<T>`, `std::remove_reference_t<T>`) are shorthand variable and alias templates for `::value` and `::type`.

Traits fall into four groups you should be able to name:

| Group | Examples | Typical use |
|---|---|---|
| Primary categories | `is_integral`, `is_floating_point`, `is_pointer`, `is_enum`, `is_class` | choose an implementation by kind of type |
| Properties | `is_trivially_copyable`, `is_nothrow_move_constructible`, `is_standard_layout` | decide whether an optimization is legal |
| Relations | `is_same`, `is_base_of`, `is_convertible` | constrain templates |
| Transformations | `remove_cvref`, `decay`, `make_unsigned`, `conditional` | compute a type from another |

The *property* traits matter most in low-latency code because they gate optimizations. `is_trivially_copyable` is the standard's permission to copy an object with `memcpy`. `is_nothrow_move_constructible` decides whether `std::vector` moves or copies its elements when it grows (Section 10.1). Some traits, such as `is_trivially_copyable`, cannot be written in portable C++ at all: the library implements them with compiler built-ins (`__is_trivially_copyable(T)` in GCC and Clang), because only the compiler knows the answer.

### if constexpr: deleting branches before they are compiled

In an ordinary `if`, both branches must compile for every instantiation, even when the condition is a compile-time constant. `if constexpr (cond)` evaluates `cond` at compile time and, *inside a template*, discards the branch not taken: it is never instantiated, so it may contain code that would be invalid for the current `T`. Outside a template, the discarded branch is still fully checked, so `if constexpr` cannot hide an error in ordinary code.

## SFINAE and Concepts

### Intuition: telling the compiler what a template needs

`clamp_add` in Listing 9.1 works for any `T` that supports `+` and `>`, but nothing in its signature says so. Call it with a type that does not, and the error appears deep inside the body. Worse, because overload resolution looks only at signatures, an unconstrained template is a candidate for *every* call, which makes it impossible to write a second overload for, say, floating-point types. Before C++20, the workaround exploited a rule of template deduction. C++20 added a language feature for the job.

### SFINAE: Substitution Failure Is Not An Error

When the compiler considers a function template for a call, it substitutes the deduced types into the template's *signature* (parameter types, return type, template parameter list). If that substitution produces an invalid type or expression, the template is silently removed from the candidate set; it is not an error. Errors inside the *body* are not covered: the body is only instantiated after the overload is chosen, and a failure there is a hard error.

`std::enable_if_t<cond, int>` exploits this: if `cond` is true it names `int`; if false it names nothing, the substitution fails, and the overload disappears. The *detection idiom* uses the same rule to ask "is this expression valid?": `std::void_t<decltype(expr)>` is `void` if `expr` compiles and a substitution failure otherwise.

### Concepts

A **concept** is a named, compile-time predicate on template arguments. A **requires-expression** lists expressions that must compile, optionally with constraints on their types. A **requires-clause** (`requires Sized<T>`, or the shorthand `template <Sized T>`, or `void f(Sized auto x)`) attaches the predicate to a template. Compared with SFINAE, concepts are:

- **Readable.** The constraint is part of the declaration, in words.
- **Checked at the call site.** A violated constraint is reported where the call is, naming the unsatisfied concept.
- **Ordered.** If two overloads both match, the one whose constraints *subsume* the other's (are logically stronger) wins. SFINAE has no such ordering; with `enable_if` you must make conditions mutually exclusive by hand.
- **Usable on non-template members** of class templates (`requires` after a member function's signature), which SFINAE cannot do without awkward tricks.

### What the error messages look like

Concepts do not automatically make diagnostics short, but they move them to the right place. Sorting a `std::list` with the unconstrained `std::sort` and with the constrained `std::ranges::sort` gives, in GCC 13, diagnostics of similar length (24 and 30 lines). The difference is *where*: the `std::sort` error is reported inside the library implementation (`stl_algo.h`, "no match for `operator-`" on list iterators), while the `std::ranges::sort` error is reported at the call, names the failed requirement `random_access_range`, and ends with the root cause: `std::random_access_iterator_tag` is not a base of `std::bidirectional_iterator_tag`. For your own templates, a well-named concept turns "something deep inside failed" into "your type is not `Price`."

### Choosing between them

Use concepts in new C++20 code. You still need to read SFINAE, because pre-C++20 libraries and much production code use it, and interviewers like to ask how `enable_if` works. Prefer `if constexpr` when you want one function with type-dependent internals (Listing 9.3); prefer concepts when you want separate overloads that callers choose between, because `if constexpr` cannot remove a function from the overload set.

## CRTP

### Intuition: a base class that knows its derived class

The *Curiously Recurring Template Pattern* is a class deriving from a base template instantiated with itself: `class BookBuilder : public FeedHandler<BookBuilder>`. Inside the base, the derived type is a template parameter, so the base can `static_cast<Derived&>(*this)` and call the derived class's members directly. The calls are resolved at compile time and can be inlined, unlike virtual calls, which go through a function pointer chosen at run time.

Section 6.6 compares CRTP with virtual functions, `std::variant` and type erasure as *dispatch mechanisms* and Section 6.5 measures virtual dispatch. This section is about the template mechanics: how the pattern works, how it fails, and the two jobs it does well.

### Why it compiles at all

When the compiler sees `class BookBuilder : public FeedHandler<BookBuilder>`, `BookBuilder` is an *incomplete type*: its members are not known yet. That is fine, because instantiating the class `FeedHandler<BookBuilder>` instantiates only member *declarations*, and declarations such as `Derived& self()` only need the name. The *bodies* of `on_packet` and `self()` are instantiated later, when they are first used, by which time `BookBuilder` is complete. The same rule means a CRTP base cannot use `sizeof(Derived)` or `typename Derived::value_type` in its class body (as a member type or a data member), only inside member function bodies.

### The two jobs CRTP does well

1. **Static interfaces / template method:** a base implements an algorithm (parsing, a state machine, an order-handling loop) and the derived class supplies the steps, with every step inlinable. Feed handlers and strategy frameworks commonly have this shape.
2. **Mixins:** a base adds functionality to whatever derives from it, such as instance counting (Problem P9.8), comparison operators from one primitive, or `std::enable_shared_from_this<T>` in the standard library.

**What CRTP cannot do** is put different derived types in one container or choose the type at run time: `FeedHandler<A>` and `FeedHandler<B>` are unrelated types. When you need a run-time choice among a closed set, use `std::variant` (Section 8.8, Section 6.6); among an open set, use virtual functions.

C++23 adds *explicit object parameters* ("deducing `this`"), which let a member function deduce the type of the object it is called on, so many CRTP bases can be written without the template parameter. GCC supports it from version 14; this book's toolchain (GCC 13) does not, so the listings use classic CRTP.

## Variadic Templates and Fold Expressions

### Intuition

A *parameter pack* is a template parameter that stands for zero or more arguments: `template <class... Ts>` accepts any number of types, and `Ts... xs` declares the corresponding function parameters. You cannot index a pack directly or loop over it at run time. Instead you *expand* it: write a pattern followed by `...`, and the compiler stamps out the pattern once per element. `f(xs)...` becomes `f(x0), f(x1), f(x2)`. A *fold expression* expands a pack with a binary operator: `(xs + ...)` becomes `x0 + (x1 + x2)`.

### The rules worth memorizing

- `sizeof...(Ts)` is the number of elements.
- The four fold forms: unary right `(xs op ...)`, unary left `(... op xs)`, binary right `(xs op ... op init)`, binary left `(init op ... op xs)`. The binary forms supply a value for the empty pack.
- An empty unary fold is valid for exactly three operators: `&&` gives `true`, `||` gives `false`, and the comma operator gives `void()`. For any other operator, an empty unary fold is a compile error.
- `&&` and `||` folds short-circuit, exactly like the written-out expression. The comma fold evaluates left to right, which makes it the idiomatic way to do something once per element in order.
- Before C++17, every such operation needed recursion: a template that handles the first element and calls itself on the rest. Recursion instantiates one template per pack length (N instantiations for an N-element pack) and is still needed when each step changes a type, but most loops over packs are now single fold expressions.

Which is faster depends on the number of types and how predictable the mix is; measure (Section 16.4).

## Costs: Code Bloat and Compile Time

Templates and `constexpr` add no instructions that you would not have written by hand. Their costs are elsewhere.

### Code size and the instruction cache

Every distinct argument list produces its own machine code. The CPU fetches instructions through a small first-level instruction cache (32 KB on many recent x86-64 cores; check your part) and decoded-instruction caches that are smaller still (Section 12.2). On a hot path that touches a few kilobytes of code, it does not matter. A trading process whose hot path calls hundreds of slightly different instantiations (one parser per message type, one logger per call signature, one container per element type) can spend measurable time on instruction-cache misses, and these misses do not show up as "slow code" in any single function; they show up as the whole path being slower than its parts. Section 16.2 covers measuring and controlling code layout.

The experiment below compiled a translation unit containing K different `log(...)` call signatures (combinations of `int`, `unsigned`, `long`, `float`, `double` and `const char*` arguments) with two designs. The "fat" design is a variadic template that formats each argument inline, so each signature gets a full copy of the formatting loop. The "thin" design is Listing 9.7's: each signature only fills a small array and calls one shared non-template function.

Other tools for the same problem:

- **`extern template`** (Section 9.1) stops every translation unit from instantiating a heavy template that one translation unit instantiates explicitly. It saves compile time, not final code size, since the linker already deduplicates.
- **Prefer function parameters to template parameters** when the value does not need to be a compile-time constant. `FixedVec<T, 64>` and `FixedVec<T, 128>` are separate instantiations; a capacity passed to the constructor is not.
- **Let the optimizer merge identical code.** GCC's `-fipa-icf` (on at `-O2`) and the linker's `--icf` (gold, lld) fold functions whose machine code is identical, which often catches instantiations for types with the same representation (`int` and `unsigned`, pointer types). Do not rely on it; it cannot merge code that differs by one instruction.

### Compile time

Compile time is not a run-time cost, but it is a real engineering cost: it limits how fast you can iterate, and interviewers sometimes ask how you would speed up a slow build. Most of the time in a typical C++ build goes into parsing headers, and the standard headers are large:

| Translation unit containing only | Preprocessed lines | Compile time (-O2 -c, best of 3) |
|---|---|---|
| `int main(){}` | 7 | 0.02 s |
| `#include <cstdio>` | 1,052 | 0.03 s |
| `#include <vector>` | 26,261 | 0.17 s |
| `#include <iostream>` | 43,168 | 0.33 s |
| `#include <ranges>` | 44,312 | 0.34 s |
| `#include <format>` | 55,600 | 0.48 s |
| `#include <regex>` | 78,114 | 0.60 s |
| `#include <bits/stdc++.h>` | 164,510 | 2.8 s |

*Measured in the build container with GCC 13.3, `-std=c++20`.* The last row is the reason Section 3.2 says `bits/stdc++.h` is fine for a contest and wrong for a codebase: every translation unit pays about three seconds before compiling a line of your code. The remedies, in rough order of effect:

1. **Include what you use**, and forward-declare in headers where a full definition is not needed.
2. **Precompiled headers** parse a stable set of heavy headers once. GCC compiles `pch.h` to `pch.h.gch` and uses the `.gch` automatically wherever `pch.h` is included first.
3. **Keep heavy templates out of widely included headers**, or instantiate them once with `extern template`.
4. **Watch compile-time computation.** `constexpr` evaluation and deep template recursion both run in the compiler. GCC's `-ftime-report` shows where the time goes. Template recursion is limited to a depth of 900 by default in GCC 13 (`-ftemplate-depth`); hitting it is almost always a sign that a fold expression or a `constexpr` loop would do the job with one instantiation instead of hundreds.
5. **C++20 modules** remove repeated header parsing entirely, but toolchain and build-system support is still uneven, so most trading codebases today rely on the first four.

```asm
.L17:   movzwl  12(%rax), %edx           # o.symbol
        movq    (%rax), %rsi             # o.px
        movzbl  1628(%rsp,%rdx), %r10d   # allowed[o.symbol]
        movl    8(%rax), %edx            # o.qty
        cmpq    %rsi, %r14               # ref - band > px ?
        jg      .L16                     #   yes: rejected, skip the rest
        cmpq    %rsi, %r9                # px <= ref + band ?
        setge   %cl
        cmpl    %edx, %ebp               # qty <= max_qty ?
        setnb   %r11b
        imulq   %rsi, %rdx               # px * qty
        andl    %r11d, %ecx
        andl    %r10d, %ecx
        cmpq    %rdx, %r12               # px * qty <= max_notional ?
        setge   %dl
        movzbl  %dl, %edx
        andq    %rcx, %rdx               # combine the four results
        addq    %rdx, %r15               # sink += ok
.L16:   addq    $16, %rax                # next order (sizeof(Order) == 16)
        cmpq    %rax, %rbx
        jne     .L17
```

Three things are worth noticing. First, every check has been inlined and interleaved with the others; the four loads of the order's fields happen once, at the top. Second, although the source asked for no early exit, GCC chose to keep one branch (the lower price bound, `jg .L16`), because a rejected result makes the rest irrelevant; the `&` in the source states what to compute, and the compiler still decides how. Third, the limits live in registers (`%r14`, `%r9`, `%ebp`, `%r12`) because they are run-time values. In an earlier version of this listing the limits were literals, and GCC went further: it rewrote the band check `px >= 9500 && px <= 10500` as `lea -9500(%rdi), %r8; cmp $1000, %r8; setbe`, one subtraction and one *unsigned* comparison, since a price below the band wraps around to a huge unsigned number. That rewrite needs the compiler to see both the code and the constants. Behind a virtual call it can see neither.

**What changes, and what does not.** Both versions make identical decisions: the reject counts and checksums match. The flexibility you give up is the ability to add a new *kind* of check without recompiling; adding or reordering checks is a code change. In practice risk-check sets change on a release cycle while limits change intraday, so the split (structure at compile time, parameters at run time) matches how these systems are operated. If you do need run-time selection from a fixed menu, a `std::variant` of check types visited in a loop sits between the two designs (Section 6.6).

## The Nanosecond Penalty

### What the showdown measured

In the build container, the virtual list cost about 11–12 ns per order and the compile-time pipeline about 3 ns (short-circuit) or about 2 ns (evaluate all), roughly a 4–7× difference. To separate the cost of the indirect calls from the cost of mispredicted early exits, we re-ran both programs with limits loose enough that no order was rejected, so every branch was predictable: the virtual list still took about 8 ns per order and the static pipeline under 2 ns. Most of the difference is the calls and the optimizations they prevent, not the mispredictions. These are container numbers for four trivial checks; with heavier checks the relative difference shrinks, because the fixed per-call overhead becomes a smaller fraction of the work.

### Approximate costs on modern x86-64

The following ranges are for recent server-class x86-64 cores at typical clock speeds. They are approximate and depend on the microarchitecture; Sections 12.1–12.7 explain the mechanisms.

| Item | Approximate cost | Why |
|---|---|---|
| Calling a template instantiation | same as an equivalent hand-written function | instantiation produces ordinary machine code |
| Using a `constexpr` result | 0 cycles (immediate operand) or one load | the value is in the instruction stream or `.rodata` |
| Load from a `constexpr` table, L1 hit | about 4–5 cycles | L1 data-cache load-to-use latency |
| Same load, served from L2 / L3 | about 12–16 / 40–70+ cycles | the table is cold or too large (Section 12.7) |
| Direct call that is not inlined | a few cycles | call and return, both predicted; argument setup |
| Virtual call, target predicted | a few cycles more than a direct call, plus lost inlining | two dependent loads (vptr, then slot) and an indirect branch |
| Any mispredicted branch, including an indirect call | about 15–20 cycles | the pipeline discards speculative work (Section 12.5) |
| Instruction-cache miss served from L2 | roughly 10–20 cycles of front-end stall, partly hidden | code was evicted by other code; bloat makes this more likely |

The lesson of the table is that the direct costs of dispatch are small numbers of cycles. The large effects come from second-order consequences: a call that cannot be inlined prevents constant propagation, vectorization and the kind of rewrite shown in the price band above, and a branch that cannot be predicted costs more than the work it saves.

### Compile-time costs

The tables in Section 9.7 give the build-side costs: about 0.5 KB of code per signature for a naively written variadic logger, and about three seconds of parsing per translation unit for `bits/stdc++.h`.

## Interview Questions

**Q1. What is the difference between `constexpr`, `consteval` and `constinit`?**
A `constexpr` function *may* run at compile time when called with constant arguments in a context that requires a constant; otherwise it runs at run time. A `constexpr` variable must be initialized at compile time and is `const`. A `consteval` function must *always* be evaluated at compile time; calling it with run-time values is an error. `constinit` applies to variables with static or thread storage duration and guarantees compile-time initialization, which avoids static-initialization-order problems, without making the variable `const`.

**Q2. Why are templates usually defined in headers?**
Instantiation needs the template's definition, not just its declaration, in every translation unit that instantiates it. The linker merges the duplicate instantiations because they are emitted as weak symbols in COMDAT sections. The alternative is explicit instantiation: define the template in one `.cpp`, explicitly instantiate it for the types you need there, and declare those instantiations `extern template` in the header. That works only for a known, closed set of types.

**Q3. What is SFINAE? What replaced it?**
Substitution failure is not an error: if substituting deduced template arguments into a function template's signature produces an invalid type or expression, that template is removed from overload resolution instead of causing an error. `enable_if` and the `void_t` detection idiom exploit it to constrain templates. C++20 concepts replace it with named, readable constraints that are checked at the call site and ordered by subsumption, so the most constrained overload wins without hand-written mutual exclusion. Errors in a function *body* were never covered by SFINAE.

**Q4. What does `if constexpr` give you that `if` does not? Can it replace SFINAE?**
Inside a template, the discarded branch of `if constexpr` is not instantiated, so it may contain code that is invalid for the current type. A plain `if` requires both branches to compile. It cannot replace constraints entirely: it selects behaviour *inside* one function, but cannot remove a function from the overload set, so it cannot make a call fall through to a different overload or make a trait like "is this callable?" report false.

**Q5. Why does code in a class template sometimes need `this->` or `typename`?**
Two-phase lookup. Non-dependent names are looked up when the template is defined; members of a base class that depends on a template parameter are not searched then, because a specialization of the base might not have them, so you write `this->name` to make the lookup dependent. A qualified name that depends on a template parameter, such as `T::value_type`, is assumed to be a value unless you write `typename`; C++20 made `typename` optional in contexts where only a type can appear.

**Q6. Explain CRTP. When would you use it instead of virtual functions, and what are the risks?**
A class derives from a base template instantiated with itself; the base casts `*this` to the derived type and calls its members directly, so calls resolve at compile time and can be inlined, and there is no vptr. Use it when the set of implementations is known at compile time and you never need to hold different implementations in one container: feed handlers, strategy frameworks, mixins. Risks: deriving from the base with the wrong argument (guard with a private constructor and `friend Derived`), misspelled "overrides" silently falling back to the default, and one instantiation per derived type (code size).

**Q7. What happens when a fold expression's pack is empty?**
A binary fold returns its initial value. A unary fold over an empty pack is valid only for `&&` (`true`), `||` (`false`) and the comma operator (`void()`); for any other operator it is ill-formed.

**Q8. Are templates zero-cost?**
At run time, each instantiation is as fast as hand-written code for that type, and usually faster than run-time polymorphism because calls can be inlined. The costs are code size (one copy per argument list, which can pressure the instruction cache on a hot path), compile time, and diagnostics. Techniques to control size: hoist type-independent code into non-template functions or bases, use type erasure at the boundary (as `std::format` does), prefer run-time parameters where a value need not be a compile-time constant, and use `extern template` for compile time.

**Q9. `const bool b = f();` where `f` is `constexpr` and returns `std::is_constant_evaluated()`. What is `b`?**
`true`. A `const` variable of integral type initialized by a constant expression is usable in constant expressions, so its initializer is manifestly constant-evaluated. Only a non-`const` local (or a call in an obviously run-time context) gets `false`. C++23's `if consteval` avoids the confusion.

**Q10. How would you dispatch incoming messages to handlers by type with no run-time overhead beyond the dispatch itself?**
Make the set of message types a compile-time list. Generate the dispatch from it: a `switch` (or a fold over the types comparing the type tag) that calls a handler chosen by overload resolution, or a `constexpr` table of function pointers indexed by the type byte. Handlers are found statically, so they can be inlined into the `switch` arms. Decode payloads with `memcpy`, not pointer casts. Add `static_assert`s on message sizes and offsets so a protocol change breaks the build, not production.

**Q11. Why define named concepts instead of writing `requires` expressions inline?**
Readability and reuse, but also correctness of overload ranking: subsumption only recognises that one constraint implies another when both are built from the same named concepts (or the same occurrence of an expression). Two identical inline expressions are distinct atomic constraints, so overloads that should be ordered become ambiguous.

## Key Takeaways

- **Templates are recipes.** Each distinct argument list is a separate instantiation with its own code; member function bodies are instantiated only when used; definitions go in headers; duplicates are merged by the linker as weak COMDAT symbols. `extern template` saves compile time.
- **Two-phase lookup:** `typename` for dependent types in function bodies, `this->` for members of dependent bases. Function templates cannot be partially specialized; overload them instead, and beware explicit specializations binding to whichever primary template was visible.
- **`constexpr` may, `consteval` must, `constinit` initializes at compile time without `const`.** Constant evaluation diagnoses UB and has limits (512 depth, 262,144 loop iterations in GCC 13). Use it for tables, layout `static_assert`s and string IDs, never for values that come from configuration. `is_constant_evaluated` is true for `const` integral initializers.
- **Traits** are compile-time functions on types; property traits (`is_trivially_copyable`, `is_nothrow_move_constructible`) gate optimizations. `if constexpr` discards untaken branches only inside templates.
- **SFINAE** removes overloads whose *signature* fails substitution; **concepts** do the same job readably, report errors at the call, and rank overloads by subsumption of *named* concepts.
- **CRTP** gives inlinable static dispatch and mixins; guard it with a private constructor and `friend Derived`; it cannot hold mixed types in one container.
- **Packs and folds:** `sizeof...`, four fold forms, empty folds valid only for `&&`, `||` and comma; `index_sequence` turns a tuple into a pack of indices.
- **Costs are code size and build time, not instructions.** Keep templates thin and move type-independent work into non-template code; avoid `bits/stdc++.h` outside contests.
- **Showdown:** composing risk checks at compile time removed the indirect calls and let the compiler fuse the checks; in the container it was about 4–7× faster per order than a vector of virtual checks. Fix the *structure* at compile time, keep the *parameters* at run time.
