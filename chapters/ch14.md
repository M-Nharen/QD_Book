# Concurrency

A trading system is a set of threads that pass data to each other: the feed handler hands quotes to a strategy, the strategy hands orders to a gateway, everyone hands log records to a logger. In a latency-critical path these handoffs often cost more than the work. This chapter makes them correct first and cheap second.

Correctness comes from the C++ memory model, which defines when one thread is guaranteed to see another's writes. Cheapness comes from what lies underneath: cache coherence (12.3), the x86 store buffer, and the scheduler (13.4). The chapter covers threads, mutexes and condition variables (14.1), atomics and the memory model (14.2), x86-TSO (14.3), false sharing (14.4), then the structures that carry most inter-thread traffic in low-latency systems: the SPSC ring (14.5), the bounded MPMC queue (14.6), the seqlock (14.7), and lock-free stacks with their ABA and reclamation problems (14.8). Section 14.9 decides between spinning and blocking; the showdown (14.10) replaces a mutex-and-condition-variable queue with the ring of 14.5 and cuts the median handoff latency more than 20 times.

**About the measurements.** Listings were compiled with g++ 13.3 and run in the build container of Chapter 13: a KVM guest with 2 vCPUs of an Intel Xeon at 2.1 GHz nominal. Two vCPUs suffice for every experiment, but the hypervisor moves and occasionally stops them, so cross-core numbers vary by a factor of two or more between runs (Listing 12.3 measured one-way line transfers of 50–350 ns here, against some tens of nanoseconds on bare metal). The text quotes the printed run and, where it matters, the range across runs. Every concurrent listing was also run under ThreadSanitizer (at `-O1` and `-O2`) and under AddressSanitizer with UBSan, with no reports.

## Threads, Mutexes, Condition Variables

### Threads and mutexes

Section 13.1 covered what a thread is to the kernel. In C++20 prefer `std::jthread`: a `std::thread` neither joined nor detached calls `std::terminate` in its destructor, while a `jthread` joins, and its `request_stop()` sets a flag the thread polls through a `std::stop_token` (and wakes a `std::condition_variable_any` wait given that token). An exception escaping a thread's function also calls `std::terminate`. Low-latency systems create threads once at startup, pin them (13.6), and keep them.

A mutex provides **mutual exclusion** and **ordering**: everything a thread wrote before `unlock()` is visible to the next thread after its `lock()`. In the terms of 14.2, unlock is a release and lock an acquire, so data guarded by a mutex needs no atomics. The RAII guards (8.5):

| Guard | Use it for |
|---|---|
| `std::lock_guard` | the default: lock in the constructor, unlock in the destructor |
| `std::unique_lock` | unlocking early, waiting on a condition variable, `try_lock`, timeouts, moving the lock |
| `std::scoped_lock` | several mutexes at once, without deadlock |
| `std::shared_lock` + `std::shared_mutex` | many readers or one writer; only for long read sections, since a shared lock still writes the mutex's line |

**Deadlock** needs mutual exclusion, hold-and-wait, no preemption and a cycle of waiters (Coffman's conditions). Break the cycle: take locks in one global order, or together with `std::scoped_lock`, which libstdc++ implements by locking one mutex, *trying* the rest, and backing off to retry in another order if a try fails:

```cpp
void transfer(Account& from, Account& to, long amount) {
    std::scoped_lock lk(from.m, to.m);   // concurrent (a, b) and (b, a): no deadlock
    from.balance -= amount;
    to.balance += amount;
}
```

Never call unknown code (callbacks, user virtuals, logging that might lock) while holding a lock.

**How `std::mutex` is built.** libstdc++'s `std::mutex` is a glibc `pthread_mutex_t` built on a futex (13.4): an integer meaning unlocked, locked, or locked with waiters. An uncontended lock is one `lock cmpxchg` and an uncontended unlock one atomic exchange, both in user space; the kernel is entered only to sleep and to wake a sleeper. So an uncontended lock and unlock cost two atomic read-modify-writes, 16 ns in Listing 14.12, and a contended mutex costs microseconds whenever someone sleeps. glibc's mutex is **not fair**: a thread that unlocks and immediately locks again usually beats a woken waiter that has not yet run (*barging*). In Listing 14.12, two threads incrementing a counter under one mutex passed ownership to the other thread on only about one increment in ten. Throughput looks fine; a particular waiter can wait a very long time.

### Condition variables

A condition variable lets a thread sleep until a condition on shared data holds. It is always used with a mutex and a predicate:

- The waiter locks the mutex, checks the predicate, and if it is false calls `wait`, which atomically unlocks and sleeps, then re-locks before returning. Checking under the mutex prevents the **lost wake-up**, in which the notifier changes the state and notifies between the waiter's check and its sleep.
- `wait` may return without a notification (*spurious wake-up*), and another thread may consume the state before the waiter re-locks. Always use `cv.wait(lock, pred)`, which loops; never a bare `if`.
- The notifier changes the state *under the mutex*, then notifies, preferably after unlocking, so the woken thread does not immediately block on the mutex.

## Atomics and the C++ Memory Model

### Why plain variables are not enough

This handoff looks right and is not:

```cpp
int payload = 0;
bool ready = false;                    // BUG: a plain bool used as a flag
// thread 1                            // thread 2
payload = 42;                          while (!ready) { }
ready = true;                          use(payload);
```

The **compiler** may keep `ready` in a register forever (Section 11.2): built at `-O1`, this program loaded `ready` once before the loop, spun on the register, and hung in 15 of 20 runs (it finished only when the thread had already set the flag before the first load) or reorder thread 1's stores, which single-threaded semantics allow. The **hardware** may make the stores visible in another order (not on x86, 14.3, but on ARM). The language declares the program meaningless: it has a **data race**, undefined behaviour (11.2). ThreadSanitizer reports it on the first run (of an `-O0` build): "data race", with the write to `ready` in thread T1, the earlier read in the main thread, and the same again for `payload`. `volatile` does not fix it: it forces each access to happen but gives no ordering relative to other variables. It is for memory-mapped hardware registers.

### What std::atomic provides

`std::atomic<T>` makes accesses indivisible and lets each access state the ordering it needs. For integers, pointers and trivially copyable types of 1, 2, 4 or 8 bytes it is lock-free on x86-64 (`is_always_lock_free`), and each operation is one instruction. Larger types are not: with g++ 13, `std::atomic` of a 16-byte `{pointer, tag}` struct calls `__atomic_compare_exchange_16` in libatomic (link with `-latomic`), and `is_lock_free()` is `false` even with `-mcx16`, although the library uses `cmpxchg16b` underneath when available. Section 14.8 sidesteps this with 32-bit indices in a 64-bit word.

Besides `load`, `store`, `exchange` and `fetch_add` and friends, there is `compare_exchange_weak/strong(expected, desired)`: replace the value if it equals `expected`, otherwise copy the current value into `expected` (the weak form may fail spuriously on LL/SC machines, so use it in loops; on x86 both are `lock cmpxchg`). C++20 adds `wait`/`notify_one` (14.9) and `std::atomic_ref` for ordinary objects. Anything else is a CAS loop:

```cpp
void update_max(std::atomic<std::int64_t>& m, std::int64_t v) {
    std::int64_t cur = m.load(std::memory_order_relaxed);
    while (cur < v && !m.compare_exchange_weak(cur, v, std::memory_order_relaxed)) { }
}   // a failed CAS reloads cur; stop once cur >= v
```

### Happens-before

The model is built on one relation, **happens-before**:

- **Sequenced-before:** within a thread, earlier evaluations are sequenced before later ones.
- **Synchronizes-with:** a **release** operation on atomic M synchronizes with an **acquire** operation on M that reads the value it wrote (or a later value in its *release sequence*). Also: unlocking a mutex synchronizes with the next lock of it; thread start and `join` synchronize with the thread's function.
- **Happens-before** is, roughly, the transitive closure: a chain of sequenced-before and synchronizes-with steps.

If a write happens before a read of the same location (with no other write in between), the read sees that write or a later one. The precise definition promised in 11.2: two accesses to the same memory location **conflict** if at least one writes; a **data race** is two conflicting accesses in different threads, not both atomic, neither happening before the other. A memory location is a scalar, or a maximal run of adjacent non-zero-width bit-fields, so two threads writing different bit-fields of one struct race (P14.2).

Happens-before is not time: a load a microsecond after a store need not see it if nothing orders them. What always holds is that each atomic has one **modification order** all threads agree on (coherence, 12.3), and no thread reads an earlier value after a later one.

### The memory orders

| Order | Applies to | Guarantees | Typical use |
|---|---|---|---|
| `relaxed` | any | atomicity, per-object modification order; nothing about *other* memory | counters, statistics, an index only its owner writes |
| `consume` | loads | intended: ordering through data dependencies only | avoid: compilers implement it as `acquire` |
| `acquire` | loads, RMWs | later accesses in this thread stay after it | reading a flag or index that publishes data |
| `release` | stores, RMWs | earlier accesses in this thread stay before it | publishing data, unlocking |
| `acq_rel` | RMWs | both | reference-count decrement, lock-free push/pop |
| `seq_cst` | any | acquire/release plus a single total order S of all `seq_cst` operations | the default; a store that must precede a later load of *another* variable |

**Release/acquire (diagnostic D10).** A release store pairs with an acquire load **of the same atomic** that reads the stored value. Everything the writer did before the release, to any memory, atomic or not, happens before everything the reader does after the acquire:

```cpp
int payload = 0;
std::atomic<bool> ready{false};
// thread 1
payload = 42;
ready.store(true, std::memory_order_release);
// thread 2
while (!ready.load(std::memory_order_acquire)) { }
use(payload);                                  // guaranteed to see 42
```

The barrier is one-way: release stops earlier accesses moving after it, not later ones moving before it; acquire the reverse. And it is pairwise: thread C learns nothing from A's release unless C acquires something A (directly or transitively) released.

**What release/acquire cannot do** is order a store before a later load of a *different* variable. In the store-buffering pattern each thread writes its own flag, then reads the other's:

```text
thread A: X.store(1); r1 = Y.load();        thread B: Y.store(1); r2 = X.load();
```

With release/acquire, r1 = r2 = 0 is allowed: neither load reads the other's release, so nothing synchronizes. `seq_cst` forbids it, because S must put one store first and the other thread's load after it. Dekker's and Peterson's algorithms and every "announce myself, then look for others" protocol depend on this (P14.5); 14.3 shows the outcome on real hardware.

**Fences.** `std::atomic_thread_fence` orders a thread's surrounding relaxed accesses without naming a variable: a release fence before a relaxed store, paired with an acquire fence after a relaxed load that reads it, synchronizes like a release/acquire pair. The seqlock reader (14.7) needs one, because acquire on a load orders only *later* accesses.

**Release sequences.** Read-modify-writes on M after a release store continue its release sequence, so an acquire that reads any of them synchronizes with the original release. This is why `shared_ptr`-style reference counts decrement with `fetch_sub(1, acq_rel)`: the thread reaching zero acquires everyone's earlier decrements and may delete.

**Choosing.** Start with `seq_cst`; weaken to release/acquire only where you can name the pair that synchronizes; use `relaxed` only when ordering with other data does not matter.

On x86, acquire and release cost no instructions; they only restrain the compiler. `relaxed` still forbids inventing or eliding accesses but not reordering them with other memory, so code that "works with relaxed on x86" can break under the compiler today and on ARM hardware tomorrow.

## x86-TSO

### The model

Intel documents x86 ordering in the Software Developer's Manual (Volume 3A, "Memory Ordering", in the chapter on multiple-processor management); Sewell, Sarkar, Owens, Zappa Nardelli and Myreen formalized it as **x86-TSO** ("x86-TSO: A Rigorous and Usable Programmer's Model for x86 Multiprocessors", *Communications of the ACM*, 2010). The abstract machine:

- Each core has a FIFO **store buffer**. A store enters it at once and drains to the coherent cache later, in order (12.2).
- A load takes the newest matching store from its own buffer if there is one (*store-to-load forwarding*), otherwise reads memory.
- Drained stores are seen by all cores in one order.
- A `lock`-prefixed instruction (and `xchg` with memory) drains the buffer and executes atomically; `mfence` drains it.

So loads are not reordered with loads, stores not with stores, stores not with earlier loads, but **a load may pass an earlier store to a different address**, which is still sitting in the buffer. Cores do execute loads out of order, but if a line loaded early is invalidated before the load retires, they discard the work (a *memory-ordering machine clear*), so load-load reordering is never visible.

Padding costs cache: pad only what is written concurrently. `perf c2c` (16.5) finds false sharing in running code.

## Lock-Free SPSC Ring Buffer

### Progress guarantees

If a thread is suspended at the worst moment: in a **blocking** algorithm others may wait for it forever (a descheduled mutex holder); **obstruction-free** means a thread running alone finishes in bounded steps; **lock-free** means some thread always progresses, though individuals may starve (a CAS loop); **wait-free** means every thread finishes in a bounded number of its own steps. Lock-free does not mean fast; what these structures buy is a hot path that never enters the kernel or waits for a descheduled thread.

### The design

One producer and one consumer share N slots and two counters: `tail` (items ever pushed, written only by the producer) and `head` (items ever popped, written only by the consumer). Item *k* lives in slot k mod N; the ring is empty when head = tail and full when tail − head = N. With 64-bit counters, which never wrap in practice (P14.3), no slot has to be left unused to tell full from empty, and with N a power of two, k mod N is a mask. Each counter has one writer, so there is no read-modify-write anywhere: the protocol is loads and stores with release/acquire, which on x86 are plain `mov`s. The ring is wait-free.

- **Lines 50–53:** `size()` reads `head_` first. Both counters only grow and head ≤ tail always, so the difference cannot go negative and wrap.

**What a first attempt gets wrong.** Default `seq_cst` atomics turn every index store into an `xchg` (about 5 ns each here, 14.11). Adjacent `head` and `tail` falsely share, so every push and pop invalidates the other side's copy. Reading the other index on every operation costs a transfer per message; caching removes it whenever the ring is neither nearly full nor nearly empty (when the consumer keeps up, the ring is nearly empty and caching helps less). And `%` by a non-power-of-two capacity costs a division and breaks with 32-bit counters (P14.3).

**Variations.** *Batching:* drain up to the cached tail, then publish `head_` once; fewer index writes, a little latency for the first item. *Zero-copy:* hand out a pointer to the next slot plus a `commit()`, so the feed handler decodes in place (7.7). *Variable-size messages:* a byte ring with length headers. *Between processes:* put the ring in shared memory (13.1) with offsets, never pointers. What breaks it is a second producer or consumer: the single-writer assumption is the whole design.

## Bounded MPMC Queue

With several producers, a push must claim a slot no other producer will claim, which needs a read-modify-write on a shared index. The hard part is the rest: a consumer must not read a slot that is claimed but not yet written, and a producer must not overwrite a slot that a consumer has claimed but not yet read. Dmitry Vyukov's bounded MPMC queue puts a sequence number in every slot:

| `seq` value | Meaning, for a position *pos* mapping to the slot |
|---|---|
| pos | free, waiting for the producer of pos |
| pos + 1 | full, holding item pos, waiting for its consumer |
| pos + N | free again, for the producer of pos + N (next lap) |

- **Lines 44–46:** write the item, then release-store `pos + 1`; a consumer whose acquire load (line 54) sees it sees the item.

**It is not lock-free in the strict sense.** A producer preempted between its CAS (line 36) and its publish (line 46) leaves a claimed, unpublished slot: consumers reaching it report "empty" even if later slots are full, and after a lap producers report "full". Everyone waits for the sleeping thread. On dedicated cores that never happens; on an oversubscribed machine it does.

When several threads feed one consumer, give each producer its own SPSC ring and let the consumer poll them in turn; cross-producer order, if needed, comes from timestamps. An MPMC queue fits genuinely shared work, such as a pool of identical workers.

## Seqlocks

One thread maintains a small record (top of book, risk limits, the TSC-to-time parameters of 13.5) that many threads read far more often than it changes. A mutex would make every reader *write* the mutex's line. A seqlock gives readers a consistent snapshot without writing anything: the writer makes a sequence counter odd, writes the data, and makes it even again; a reader reads the counter (retrying while it is odd), copies the data, and re-reads the counter, accepting the copy only if the counter did not change. Readers cost the writer nothing but the occasional transfer of lines they read. The price: a continuously writing writer can starve readers, and nothing from an unvalidated copy may be used, not even a pointer or index to follow.

**In C++,** the reader's copy deliberately overlaps the writer's stores. If the data were plain variables that would be a data race, undefined behaviour even though the torn copy is discarded; and the reader's data loads must be ordered *before* its second counter load, which an acquire on that load cannot do. Hans Boehm analysed both in "Can Seqlocks Get Along with Programming Language Memory Models?" (MSPC 2012). Listing 14.6 uses the fence-based scheme from that analysis, with the data in relaxed atomic words.

The Linux kernel's `seqcount_t`, used for the vDSO clock data (13.5), is the same idea under the kernel's own memory model.

## ABA and Memory Reclamation

### The Treiber stack and ABA

The simplest lock-free structure is a stack with one atomic head (R. K. Treiber, IBM, 1986). Push: read head, link the new node to it, CAS head from the old value to the node. Pop: read head and head's `next`, CAS head from head to `next`. It is often used as a lock-free free list of fixed-size objects (7.5).

Pop has a flaw. Between reading head = A (with next = B) and the CAS, other threads may pop A, pop B and push A back. The head is A again, so the CAS succeeds and installs B, which someone else is now using. The CAS compared values and could not tell that this A came from a different point in history: the **ABA problem**. ### Memory reclamation

A second problem hides behind line 40. In a pointer-based stack, popped nodes are deleted. T1 may read head = A, stall, and read `A->next` *after* T2 has popped and freed A: a use-after-free, whatever the CAS decides later. Lock-free structures with dynamic nodes need a scheme that delays freeing until no thread can still be reading:

- **Never free:** nodes come from a pool and return to it, as in Listing 14.7; reading a recycled node is harmless if its fields are atomic and the CAS validates the result. Most trading systems do this.
- **Reference counting:** correct, but every reader writes shared lines.
- **Hazard pointers** (Maged Michael, 2004): a thread publishes the pointer it is about to dereference in a per-thread slot and re-checks that the node is still reachable; nodes are freed only when no slot holds them. Cost: a store and a store→load-ordered re-check per pointer.
- **Epoch-based reclamation and RCU:** readers announce entering and leaving read-side sections; a removed node is freed once every thread has passed a quiescent state. Reads are very cheap; a stalled reader delays all reclamation.

Hazard pointers and RCU have been adopted into the C++26 working draft. The distinction interviewers want: ABA is a CAS succeeding when it should not; reclamation is touching memory that may have been freed. Tags fix the first, not the second.

## Spinning vs Blocking

A thread waiting for another can **block** (sleep in the kernel until woken, 13.4), which frees the CPU but costs a wake-up, or **spin** on a memory location, which reacts within a line transfer but burns a core.

- **Mutex and condition variable (lines 35–47):** about 15 µs one way, a futex wake on the other CPU (13.4 measured 5–13 µs for the mechanism) plus the mutex.
- **C++20 `atomic::wait` (lines 48–56):** about 2–3 µs. In libstdc++ 13 (`<bits/atomic_wait.h>`), `wait` first re-checks the value 16 times, with `pause` between the first 12 checks and `sched_yield` between the last 4, and only then sleeps on a futex; `notify_one` skips the system call when no waiter is registered. In a ping-pong the value often changes during that short spin, but the yields still enter the kernel.
- **Spinning (lines 57–63):** about 100–150 ns, one or two line transfers in this VM, at the cost of both CPUs. A hybrid that spins for a bounded time (say 20 µs) before calling `atomic::wait` behaves like this when the partner answers quickly and like blocking when it does not.

**The `pause` instruction** marks a spin-wait loop. It delays the next instruction (about 12 ns here, 14.11; Intel's optimization manual documents an increase from about 10 cycles before Skylake to up to about 140 on Skylake-derived cores), saves power, yields resources to an SMT sibling (12.1), and avoids the memory-ordering machine clear a tight load loop suffers when the line finally changes. Calibrate spin limits in time, not iterations.

**When to spin:** only on a dedicated core, because a spinner sharing a CPU with the thread it waits for keeps that thread from running (P14.11's solution shows it), so never run more spinners than isolated cores (13.6); and only when the wait is shorter than a wake-up or reaction time is worth a core, as for hot trading threads. Spinlocks belong only where the holder cannot be preempted: a preempted holder makes every waiter spin for a time slice, and under real-time priorities (13.4) a spinner can wait forever for a lower-priority holder (*priority inversion*). Everything off the hot path blocks.

## Interview Questions

**Q1. What does `memory_order_release` on a store pair with, and what does the pair guarantee?**
An acquire load of the same atomic that reads the stored value (or a later value in its release sequence). Everything the writer did before the store, including non-atomic writes, happens before everything the reader does after the load. It does not order the store before later loads of other variables; that needs `seq_cst`.

**Q2. Which reordering does x86 allow?**
Only a load passing an earlier store to another address, because of the store buffer. So acquire and release cost no instructions, while `seq_cst` stores and fences drain the buffer (`xchg`, `lock or`). Code must still follow the C++ model, which compilers and ARM hardware exploit.

**Q3. What is false sharing, and how do you find and fix it?**
Threads writing different variables in one 64-byte line force the line between cores on every write (6 times slower locked increments in Listing 14.3; a mere reader slowed the writer 10 times). Find it with `perf c2c`; fix it with per-writer lines (`alignas(64)`, sometimes 128) and by separating read-mostly from written fields.

**Q4. Design a single-producer single-consumer queue.**
Power-of-two array; 64-bit head and tail on separate lines, each written by one side; full when tail − head = N. The producer writes the slot, then release-stores tail; the consumer acquire-loads tail, reads the slot, release-stores head; each caches the other's index and refreshes it only when the ring looks full or empty. No RMW instructions, wait-free, trivially copyable slots.

**Q5. What is the ABA problem?**
A CAS succeeds because the value matches an earlier read although it changed and changed back, so conclusions drawn from that read (a stale `next`) are wrong. Fix with a version tag incremented on every success, wide enough not to wrap during a stall. Use-after-free of popped nodes is a separate problem, solved by reclamation (pools, hazard pointers, epochs, RCU).

**Q6. A latency-critical thread waits on a condition variable for messages. What is wrong?**
Every message to a sleeping thread costs a cross-CPU futex wake, microseconds (13 µs median in Listing 14.10), with a scheduler-driven tail. Replace it with an SPSC ring and a busy-polling consumer on an isolated core: hundreds of nanoseconds, no system calls, one dedicated core.

## Key Takeaways

- **Correctness:** an unsynchronized conflicting access is a data race (UB), and `volatile` does not help. Release/acquire on one atomic, or unlock/lock, creates happens-before; only `seq_cst` orders a store before a later load of another variable.
- **Costs:** x86 reorders only store→load, so acquire/release are free while `seq_cst` stores, fences and locked RMWs drain the store buffer. A line written by one core and touched by another costs a transfer, including under false sharing.
- **Structures:** the SPSC ring is wait-free with no RMW; MPMC queues bottleneck on contended index lines; seqlocks give readers the latest value without writing; tags stop ABA, and pools or hazard pointers stop use-after-free.
- **Spin or block:** kernel handoffs cost microseconds; spinning costs a dedicated core and reacts in a line transfer. The showdown's ring beat a condvar queue 23× in median latency.
