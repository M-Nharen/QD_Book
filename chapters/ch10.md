# STL Internals

Every C++ interview loop for a trading firm contains some version of "what happens inside `std::vector` when you call `push_back`?" or "why is `std::unordered_map` slow?" The interviewer is not testing whether you memorized the standard. They are testing whether you can predict what the machine does when you use a container: how many allocations, how many cache misses, which pointers become invalid, and what the worst case looks like. Those are exactly the questions you have to answer when you choose a data structure for a hot path.

This chapter opens up the containers you use every day, using GCC's libstdc++ (the standard library on Linux) as the reference implementation: `vector` (Section 10.1), `deque` and `list` (10.2), `map` and `set` (10.3), and `unordered_map` (10.4). Section 10.5 builds a complete open-addressing hash table, the structure most low-latency codebases use instead of `std::unordered_map`, with a differential test. Section 10.6 covers hashes, comparators and allocators, and Section 10.7 turns all of it into rules for choosing containers. The code showdown (Section 10.8) indexes live orders by ID under a feed-like workload, and Section 10.9 measures traversal and lookup costs.

The algorithmic side (complexities, when to use a heap or a map in a contest) is in Chapters 3 and 4; this chapter is about the implementations. Allocators themselves are Chapter 7's subject (Sections 7.2 and 7.5); here we only use them.

## vector

### Intuition: three pointers and a promise

A `std::vector<T>` object is three pointers (24 bytes on x86-64): the start of a heap buffer, the end of the elements in use, and the end of the buffer. In libstdc++ they are called `_M_start`, `_M_finish` and `_M_end_of_storage`; `size()` is `finish − start` and `capacity()` is `end_of_storage − start`. The elements are contiguous, which is the property everything else depends on: iteration walks memory in order, the hardware prefetcher streams it in, and `data()` can be handed to any C API.

The promise is amortized O(1) `push_back`. When `size() == capacity()`, the vector cannot extend its buffer in place, so it must:

1. allocate a larger buffer,
2. move (or copy) every element into it,
3. destroy the old elements and free the old buffer,
4. construct the new element.

Step 2 is O(n). The trick that keeps the *average* cost constant is **geometric growth**: libstdc++ doubles the capacity (1, 2, 4, 8, …), and Microsoft's library multiplies it by 1.5. If capacity grows by a factor g, the reallocations move s + s/g + s/g^{2} + … elements in total, where s < n is the size at the last reallocation, so the total over n `push_back`s is less than n·g/(g − 1): 2n for doubling, 3n for 1.5×. The average cost per `push_back` is therefore a constant number of moves. Growing by a constant amount instead (say +16) would make the total O(n^{2}). A smaller factor wastes less memory but moves elements more often; a well-known argument for 1.5 (made, for example, in the documentation of Facebook's `folly::fbvector`) is that with a factor below the golden ratio, the blocks freed by earlier growth steps can eventually add up to enough space for a new buffer, so a simple allocator can reuse them.

### The noexcept rule

`push_back` gives the *strong exception guarantee*: if it throws, the vector is unchanged. During reallocation that is easy with copies (if a copy throws, discard the new buffer; the old elements are intact) but impossible with moves (if the fifth move throws, the first four source elements have already been gutted). So the vector uses `std::move_if_noexcept`: it moves elements only if the move constructor is `noexcept` (or the type cannot be copied), and copies them otherwise. A class with a user-written move constructor that is not marked `noexcept` gets copied on every reallocation. Listing 10.1 shows it. This is the single most common performance bug in hand-written move constructors (Section 8.6 discusses `noexcept` more generally).

### Invalidation

When the buffer is replaced, every pointer, reference and iterator into the old buffer points to freed memory. Using one is undefined behaviour that often appears to work, because the freed memory still holds the old values until something reuses it. This is diagnostic question D5 from Chapter 1. The complete rules:

| Operation | Invalidates |
|---|---|
| `push_back`, `emplace_back`, `insert`, `resize`, `reserve` that **reallocates** (capacity changes) | all iterators, pointers and references |
| `push_back` / `emplace_back` **without** reallocation | only `end()` |
| `insert` / `emplace` without reallocation | everything at or after the insertion point |
| `erase` | everything at or after the erased element |
| `pop_back` | the last element and `end()` |
| `clear` | all elements (capacity is kept) |
| `swap`, move assignment | nothing is invalidated, but iterators now refer into the *other* vector |

The classic bug is holding a reference across a call that might grow the vector: `auto& first = v[0]; v.push_back(x); use(first);`. AddressSanitizer reports it as a heap-use-after-free (Section 16.6).

## deque and list

### deque: a vector of blocks

`std::deque` supports O(1) insertion at both ends and O(1) random access. libstdc++ implements it as a *map*, a small array of pointers, each pointing to a fixed-size block. Each block holds 512 bytes worth of elements (128 `int`s, 64 `double`s; one element per block if the element is larger than 512 bytes). A deque iterator holds four pointers (current element, block start, block end, and position in the map), which is why `sizeof(std::deque<int>)` is 80 bytes: it stores two such iterators plus the map pointer and size. Other implementations choose very different block sizes; Microsoft's uses blocks of only 16 bytes, which makes its deque behave more like a list of tiny arrays.

Consequences:

- **Element `i`** is found by computing which block and which offset, then two dependent loads (map entry, then element). Slower than a vector, much faster than a list.
- **`push_back` and `push_front` never move existing elements**: they fill the current end block or allocate a new one, occasionally reallocating the small map. So pointers and references to elements *remain valid* after pushing at either end, though iterators are invalidated (the map they point into may have moved). This makes deque useful when you need a growable sequence whose elements must not move.
- **Insertion in the middle** moves elements toward the nearer end and invalidates everything.
- **Traversal** is nearly as fast as a vector's: each block is contiguous, so only block boundaries break the stream (in Section 10.9 both stay under 1 ns per element).

For a FIFO queue of bounded size on the hot path, a preallocated ring buffer beats a deque, because it never allocates; Section 14.5 builds the concurrent version.

### list: one allocation per element

`std::list` is a doubly linked list: every element lives in its own heap node with `prev` and `next` pointers. For an `int`, the node is 8 + 8 + 4 bytes plus 4 bytes of padding, a 24-byte allocation, which glibc rounds up to a 32-byte chunk (Section 7.2): 32 bytes of heap to store 4 bytes of data, before counting the allocator's own bookkeeping.

What a list buys you:

- **Stable iterators and references:** no operation except erasing an element invalidates anything referring to it.
- **O(1) splice:** moving a node or a range between lists, or within a list, relinks pointers without allocating, copying or moving elements. Problem P10.5 uses this for an LRU cache.
- **O(1) insertion and erasure anywhere you already hold an iterator.**

What it costs: one allocation and one deallocation per element, 16 bytes of pointers per element, and traversal by pointer chasing: each step's address is unknown until the previous load completes, so the CPU cannot prefetch or overlap the loads. If the nodes happen to be allocated in order, the allocator places them nearly contiguously and traversal is tolerable; after a long run of inserts and erases the nodes are scattered, and every step can be a cache miss. In Section 10.9 an in-order list cost about 4–5 ns per element and the same list with shuffled nodes about 150 ns, against under 1 ns for a vector.

In low-latency code you rarely see `std::list`, but you see linked lists constantly: the queue of orders at one price level in an order book is typically an *intrusive* doubly linked list, where the `prev`/`next` pointers live inside the preallocated order objects themselves, so linking costs no allocation (Section 18.1).

## map and set

### Intuition: a balanced binary search tree

`std::map<K, V>` keeps its elements sorted by key and supports O(log n) lookup, insertion and erasure, plus ordered iteration and range queries (`lower_bound`, `upper_bound`). Every mainstream implementation uses a **red-black tree**: a binary search tree whose nodes are colored red or black under three rules:

1. the root is black;
2. a red node has no red child;
3. every path from a node down to a missing child passes through the same number of black nodes.

Rules 2 and 3 together mean the longest root-to-leaf path is at most twice the shortest, so the height is at most 2 log_{2}(n + 1). After an insertion or erasure, the tree restores the rules by recoloring and *rotations* (local re-linkings of three nodes): at most two rotations per insertion and three per erasure, plus O(log n) recolorings.

### Mechanics in libstdc++

- **Node layout.** Each node starts with a 32-byte header (`_Rb_tree_node_base`): the color (an `int`, padded to 8 bytes), and `parent`, `left` and `right` pointers. The `std::pair<const K, V>` follows. For `map<int, int>` that is a 40-byte request, 48 bytes on the heap: 12× the 4 bytes of payload.
- **The header node.** The map object contains a sentinel node that serves as `end()`. Its `parent` is the root, and its `left` and `right` point to the leftmost (smallest) and rightmost (largest) nodes, so `begin()`, `rbegin()` and appending at either end do not need to search.
- **Lookup** walks from the root, one comparison and one dependent pointer load per level. For a million elements that is about 20 levels. The top few levels are touched by every lookup and stay in cache; the lower levels are spread across the heap, so a lookup in a large map is a chain of cache misses, each of which must complete before the next address is known. Section 10.9 measured well over a microsecond per lookup in a million-element map in the build container: the worst of all the structures tested.
- **Iterators and references are stable.** Insertion never invalidates anything; erasure invalidates only the erased element. Iteration in order follows parent/child links (amortized O(1) per step), but the nodes are scattered, so it is slower than a list in allocation order (Section 10.9: about 7–9 ns per element).

- **`emplace` may allocate even when the key exists.** In general `emplace` must construct the element before it can see the key, so it builds a node, looks the key up, and destroys the node if the key is present. GCC 13's libstdc++ avoids this for `map::emplace(key, value)`, but in our tests with an allocation counter it still allocated and discarded a node for `map::emplace` with a `std::pair` or piecewise arguments, and for `unordered_map::emplace(key, value)`. `try_emplace(key, args...)` always looks first, constructs only if needed, and never moves from `args` if the key exists. Use it for maps.
- **`operator[]` inserts.** `m[k]` default-constructs a value if `k` is absent, so it cannot be used on a `const` map, and using it "to check" whether a key exists silently adds one. Use `find`, `contains` (C++20) or `at`.
- **The comparator must be a strict weak ordering.** A comparator such as `a <= b` (not irreflexive) breaks the tree's assumptions; the resulting behaviour is undefined and in practice can lose elements or loop forever.

A sorted `std::vector` with `std::lower_bound` (a "flat map") supports the same ordered queries with contiguous storage. It is much faster to iterate and, for small or read-mostly sets, faster to search; but insertion is O(n). C++23 standardizes this as `std::flat_map`, which GCC 13 does not yet provide. For the order book's price levels, Section 18.1 goes further and indexes levels directly by price tick.

## unordered_map

### Intuition: buckets of chains

`std::unordered_map` is a hash table with *separate chaining*. A hash function maps the key to an integer, the integer selects one of `bucket_count()` buckets, and each bucket holds a linked list of the elements that landed there. With a good hash and a load factor (elements per bucket) around 1, the chains are short and lookup is O(1) on average. With a bad hash, or keys chosen by an adversary, all elements can land in one bucket and every operation becomes O(n); Section 3.3 shows how contest problems exploit this and how to defend against it.

### Mechanics in libstdc++

- **One list for the whole table.** All nodes form a single singly linked list. Each bucket stores a pointer not to its first node but to the node *before* it (for the bucket that holds the first node of the list, a sentinel called `_M_before_begin` inside the map object). With the predecessor at hand, inserting at the front of a bucket or erasing a node is a pointer swap. Iterating the whole map just walks the list, which is why `begin()` is O(1) and iteration does not visit empty buckets.
- **Bucket index = hash mod bucket count.** libstdc++ keeps the bucket count prime and computes the index with an integer modulo, a division by a run-time value that costs from about ten cycles on the newest x86-64 cores to several tens on older ones (a power-of-two table uses a one-cycle mask instead; Section 10.5). A prime modulus has one advantage: it uses all bits of the hash, so even the identity hash spreads ordinary keys well.
- **`std::hash` for integers is the identity.** `std::hash<int>{}(42)` is 42 in libstdc++ (line 23). Combined with a prime modulus that works for sequential IDs; combined with a power-of-two mask it would be a disaster (Problem P10.7).
- **Rehashing.** When `size() > max_load_factor() × bucket_count()` (the default maximum load factor is 1.0), the table allocates a new bucket array of the next prime at least twice as large and relinks *every* node into it. That is O(n) work inside a single insert. The output shows the sequence: 13, 29, 59, … 172,933 buckets. In a scratch experiment in the build container, the single worst `emplace` while inserting 2 million integers took about 35–50 ms: one insertion, tens of milliseconds, during which a trading system would be blind. `reserve(n)` sizes the bucket array once, at startup.
- **Rehashing does not move elements.** Nodes are relinked, not copied, so pointers and references to elements stay valid across a rehash; only iterators are invalidated. Some code depends on this, and it is something an open-addressing table cannot offer.
- **Every insert allocates a node; every erase frees one.** The heap allocation is usually the most expensive part of an insert.

### Why the standard container is built this way

`std::unordered_map`'s interface makes separate chaining nearly mandatory. The standard requires references to elements to survive rehashing, requires a *bucket interface* (`bucket(key)`, `bucket_size(n)`, `begin(n)`/`end(n)` to walk one bucket), and allows `max_load_factor` above 1. Open addressing stores elements inside the table array, so it moves them on rehash and has no notion of a bucket holding several elements. The interface was standardized in 2011 from earlier designs; the hash tables that low-latency codebases use today (Section 10.5) trade those guarantees for fewer allocations and fewer cache misses. That trade-off is a common interview question, and "the standard's API forces node-based buckets" is the answer the interviewer is looking for.

## Open-Addressing Hash Tables

### Intuition: one array, walk forward

Open addressing stores the elements in the table array itself. To insert key k, compute its *home slot* from the hash; if that slot is taken, try the next slot, and the next, until an empty one appears. To look up k, start at the home slot and walk forward until you find k or reach an empty slot; the empty slot proves k is absent, because insertion would have put k there or earlier. This is *linear probing*.

Compared with chaining, there are no nodes: no allocation per insert, no pointer per element, and the slots probed after the home slot are adjacent in memory, usually in the same cache line. A lookup in a table that fits in cache is a hash, one or two loads and a compare.

### Design decisions

| Decision | Options | This implementation |
|---|---|---|
| Probe sequence | linear, quadratic, double hashing, Robin Hood (linear with reordering), SIMD group probing | linear: simplest, best cache behaviour |
| Table size | prime (index by `%`) or power of two (index by mask) | power of two, so the index is `hash & (capacity − 1)` |
| Hash quality | trust the user's hash, or mix it | always mix: a mask uses only the low bits |
| Deletion | tombstones (mark "deleted, keep probing") or backward shift | backward shift: no tombstones ever accumulate |
| Metadata | none (test the key), a full/empty bit, or a byte of hash per slot | one control byte per slot: 0 = empty, otherwise 0x80 + 7 hash bits |
| Maximum load factor | 0.5 to 0.875 depending on probing scheme | 0.75 |
| Element stability | none; elements move on rehash and on erase | none (store indices into a stable pool if you need stability) |

**Why the load factor matters so much.** Linear probing suffers from *primary clustering*: occupied slots form runs, and a key hashing anywhere into a run extends it, so long runs grow faster than short ones. Knuth's classical analysis of linear probing with a uniform hash gives the expected number of slots inspected at load factor α as about ½(1 + 1/(1 − α)) for a successful lookup and ½(1 + 1/(1 − α)^{2}) for an unsuccessful one:

| Load factor α | 0.25 | 0.5 | 0.75 | 0.875 | 0.9 |
|---|---|---|---|---|---|
| Successful lookup | 1.17 | 1.5 | 2.5 | 4.5 | 5.5 |
| Unsuccessful lookup or insert | 1.39 | 2.5 | 8.5 | 32.5 | 50.5 |

At 0.75, a miss inspects 8.5 control bytes on average: still within one 64-byte line of metadata, which is why scanning a byte array instead of the slots themselves pays off. At 0.9 linear probing degrades sharply. Problem P10.6 checks these predictions against the implementation below.

**Why not tombstones.** The simple way to delete in open addressing is to mark the slot "deleted": lookups probe past it, inserts may reuse it. But tombstones lengthen every probe that crosses them and never go away on their own, so a table with heavy insert/erase churn (exactly the order-ID workload) slowly fills with tombstones and must be rebuilt periodically, which is an O(n) latency spike at an unpredictable time. With linear probing there is a better option: after removing an element, walk forward through the rest of its cluster and move back any element whose probe path passes through the hole. The table is then exactly as if the erased key had never been inserted.

**Hashing (lines 119–127).** Whatever the user's `Hash` returns is passed through the SplitMix64 finalizer: three xor-shifts and two multiplications, all bits of the output depending on all bits of the input. The low bits pick the home slot (`h & mask_`); the top 7 bits become the tag (line 126). The cost is a few cycles per operation; a table specialized for keys known to be well distributed could skip it.

**Lookup (lines 39–45, 129–136).** `probe` starts at the home slot and walks forward with wrap-around (`& mask_`). It stops at the first empty control byte (key absent; the index returned is where it would be inserted) or at a slot whose tag and key match. The loop always terminates because the load factor is kept below 1, so an empty slot exists.

**Insertion (lines 48–62).** One probe answers both questions: is the key already present, and if not, where would it go. Only if a new element would push the load above 3/4 (line 54) does the table grow. Growth doubles the capacity and moves every element (lines 142–157), after which the old probe position is meaningless, so line 56 finds the empty slot again in the new table (the key is known to be absent, so no comparisons are needed). Line 58 constructs the element with placement new; line 59 marks the slot full only *after* construction succeeds, so an exception from `V`'s constructor leaves the table unchanged.

**Erasure by backward shift (lines 65–84).** After destroying the element in slot i, the loop walks forward through the cluster. For each element at j, it computes the element's home slot and asks whether the hole i lies on that element's probe path, the cyclic interval from home to j. In modular arithmetic, that is "distance from home to j is at least the distance from i to j" (line 74). If so, the element is moved back into the hole, and the hole moves to j. The loop stops at the first empty slot, which ends the cluster. This recomputes the hash of every element it examines; storing a few bits of probe distance per slot avoids that and is one of the refinements of Robin Hood tables (Problem P10.10).

**Rehash (lines 142–157).** Builds a fresh, larger table, moves each element to its new position (no key comparisons: all keys are distinct), destroys the moved-from originals and swaps. The `static_assert` on lines 15–17 requires `noexcept` moves for exactly the reason `std::vector` needs them (Section 10.1): a move that throws halfway through a rehash would leave elements in both tables.

**Memory management (lines 158–174).** Slots are allocated as raw storage with `std::allocator<Slot>::allocate`, which returns correctly aligned uninitialized memory. The control array is allocated first, through a `unique_ptr`, so that if the slot allocation throws, nothing leaks. `destroy_all` skips the loop entirely for trivially destructible types (line 171), which is why clearing or destroying a table of integers costs nothing beyond freeing two blocks.

**The interface (lines 22–113).** `find` returns a pointer (null if absent) rather than an iterator; `try_emplace` returns `{V*, inserted}`; `for_each` replaces iterators. A full STL-style iterator is easy to add, but this shape covers what hot-path code does. Copying is deleted (Problem P10.9 adds it). Note what is *not* promised: any insertion may rehash and move every element, and any erasure may move elements of the same cluster, so **pointers returned by `find` are valid only until the next insert or erase.** If other structures need to hold on to elements, store the elements in a stable pool and keep only pool indices in the hash table; this is the standard design for an order store (Section 18.1).

### Testing it

A hash table has many paths that ordinary tests never reach: wrap-around at the end of the array, erasing from the middle of a long cluster, growth while a cluster wraps, keys whose low hash bits collide. The reliable way to test such a structure is *differential testing*: run a long random sequence of operations against both the new structure and a trusted reference, and compare after every step.

### What production tables add

Mature open-addressing libraries include Abseil's `absl::flat_hash_map` (the "SwissTable" design), Boost's `boost::unordered_flat_map`, `ankerl::unordered_dense` and `tsl::robin_map`. Compared with Listing 10.5 they add:

- **SIMD group probing.** SwissTable keeps control bytes in groups of 16 and compares all 16 against the 7-bit tag with a few SSE2 instructions, producing a bit mask of candidates. Probing then advances a group at a time, which keeps long probe sequences cheap even at a 7/8 load factor.
- **Robin Hood ordering**, which keeps probe lengths uniform (Problem P10.10).
- **Full STL-compatible interfaces**: iterators, heterogeneous lookup (Section 10.6), allocator support, `extract`.
- **Hardening**: per-table hash seeds to resist adversarial keys, and debug checks that catch use of invalidated iterators.

## Custom Hashes, Comparators and Allocators

### What a hash function must do

A hash for a hash table must be **deterministic** and **consistent with equality** (`a == b` implies `hash(a) == hash(b)`), and it should be **cheap** and **spread the bits the table uses**. That last property depends on the table: a prime-modulus table (Section 10.4) uses every bit, so even the identity is fine for well-behaved integer keys; a power-of-two table (Section 10.5) uses only the low bits, so the hash must make every low bit depend on every input bit. Common choices for integers:

- **A finalizer** such as SplitMix64's or MurmurHash3's `fmix64`: xor-shift, multiply, xor-shift, multiply, xor-shift. A few cycles; excellent mixing.
- **Fibonacci hashing**: multiply by 2^{64}/φ ≈ `0x9E3779B97F4A7C15` and take the *top* bits as the index. One multiplication; good enough for many key patterns, but it must use the high bits, because the low bits of a product depend only on the low bits of the key.
- **A seeded hash** for anything an outsider can influence, so that colliding inputs cannot be computed in advance (Section 3.3).

For strings, libstdc++'s `std::hash<std::string>` uses a Murmur-derived byte hash over the whole string. On a hot path, better than any string hash is not hashing strings at all: map each symbol to a small integer ID when it is first seen or at startup, and use the ID everywhere afterwards.

**Composite keys.** If the fields fit in 64 bits, pack them into one integer (Listing 10.7, lines 25–29): the packing is injective, so distinct keys can never collide before the table's own hashing. Otherwise combine the field hashes with a mixing step. Do not XOR two hashes together: `hash(a) ^ hash(b)` gives the same result for `(a, b)` and `(b, a)`, and zero for every `(a, a)`.

### Comparators

Ordered containers need a *strict weak ordering*: irreflexive (`!(a < a)`), transitive, and with incomparability transitive too. `std::less<>` and `std::greater<>` (the `<>` makes them *transparent*, comparing any two types that support `<` or `>`) cover most cases. For the bid side of a book, `std::map<Price, Level, std::greater<>>` makes `begin()` the highest price. Comparators that use floating-point keys with NaN, or `<=`, violate the requirements.

**Heterogeneous lookup.** With `std::map<std::string, V>`, calling `find("XNSE:…")` with a string literal or `std::string_view` first constructs a temporary `std::string`, which allocates for keys longer than the small-string buffer (15 characters in libstdc++). With a transparent comparator (`std::less<>`), `find` accepts the `string_view` directly. C++20 extends this to unordered containers, where *both* the hash and the equality need an `is_transparent` member type (Problem P10.8).

### Allocators

Node-based containers allocate once per element through their allocator. Replacing that allocator is the standard way to keep them off the global heap on a hot path. Chapter 7 covers allocator design (Section 7.5); the two practical options are:

- **A custom allocator type** as a template argument. It changes the container's type (`std::map<K, V, std::less<K>, PoolAllocator<...>>` is a different type from `std::map<K, V>`) and is resolved at compile time.
- **`std::pmr` containers**, which hold a pointer to a `std::pmr::memory_resource` and call it through a virtual function. One container type works with any resource; the cost is an indirect call per allocation (Section 6.5).

## Choosing a Container for the Hot Path

Big-O complexity tells you how cost grows; on modern hardware the constant factors, set by allocations and cache misses, usually decide. Measured in the build container (Section 10.9), a lookup in a million-element `std::map` was more than fifty times slower than in the open-addressing table, though both are "fast" lookups by the textbook.

| Need | First choice | Why | Avoid |
|---|---|---|---|
| A sequence you append to and iterate | `std::vector`, reserved up front | contiguous, prefetchable, no per-element allocation | `std::list` |
| A bounded FIFO | preallocated ring buffer (Section 14.5) | never allocates, contiguous | `std::deque`, `std::list`, `std::queue` over them |
| Look up records by ID | open-addressing table (Section 10.5), reserved; or direct indexing if IDs are dense (Problem P10.11) | no allocation per insert, 1–2 cache lines per lookup | `std::map`; `std::unordered_map` without `reserve` |
| A small set searched often, rarely changed | sorted `std::vector` + `lower_bound`, or a linear scan for tens of elements | contiguous; a linear scan of a few cache lines beats any tree | `std::set` |
| Ordered keys with frequent inserts and erases anywhere, plus range queries | `std::map` with node reuse (`extract`), or a structure specialized for the key range | O(log n), stable iterators, ordered iteration | rebuilding a sorted vector on every update |
| Price levels of an order book | arrays indexed by price tick near the top of book, with a fallback for far prices (Section 18.1) | O(1), contiguous around the best prices | a plain `std::map` as the final design |
| Objects that must not move while others refer to them | a preallocated pool (slab) plus indices or intrusive links | stable addresses, no allocation | containers whose elements move (vector growth, open addressing) |

General rules:

1. **Default to `std::vector`.** Choose something else only when you can say what property you need that a vector lacks.
2. **Size everything at startup.** `reserve`, fixed capacities, pools. A container that grows on the hot path will eventually grow at the worst moment. Section 7.7 shows how to fail loudly if it does.
3. **Know your invalidation rules** before storing a pointer or iterator anywhere.
4. **Prefer integer keys.** Intern strings into IDs; pack composite keys.
5. **Measure with your real sizes and access pattern.** A structure that fits in L1 behaves completely differently from one that does not (Section 10.9).

Ordered iteration over order IDs is not something a feed handler needs, so it pays for a feature it does not use.
- **`std::unordered_map` is several times faster than the tree**, but still allocates on every add and frees on every cancel (0.4 allocations per operation is exactly the 40% of events that are adds). Its lookups chase two dependent pointers: the bucket array entry, then the node (and for erase, the predecessor).
- **`FlatHashMap` performs zero allocations and is the fastest.** With 10,000 live orders everything fits in the caches and the two hash tables are close (in our runs the flat table was ahead by anywhere from a few per cent to about 2×). With a million live orders the flat table is clearly faster: its table (2^{21} slots of 32 bytes plus 2 MB of control bytes) is still far larger than the caches, so most operations still miss in cache once or twice; the gain over `unordered_map` comes from fewer dependent misses and no allocator calls.

The *mean* understates the difference that matters most for trading. Every `unordered_map` add calls `malloc`, whose cost has a long tail (a fast thread-local path most of the time, occasionally a slower path that takes locks, consolidates free chunks or asks the kernel for memory; Section 7.2). A table that never allocates after startup has no such tail. And had either hash table not been reserved, one insertion would have rehashed the entire table: in a scratch experiment in the build container, the single worst insertion while growing either table to 2 million entries took 35–50 ms. Section 16.4 shows how to measure latency distributions properly; for the hot path, the absence of allocation and of rehashing matters more than a few nanoseconds of mean.

**A better answer may not be a hash table at all.** If the exchange assigns IDs that are dense and increasing, an array indexed by `id − base`, with the base advanced as old orders die, needs no hashing and no probing. Problem P10.11 works through that design and its failure modes.

- **list with shuffled nodes, about 150 ns:** the same values and the same code, but every step jumps to a random place in 32 MB of nodes. - **set, about 7–9 ns:** in-order tree traversal follows parent and child pointers through nodes allocated in key order here; in a long-lived tree the nodes would be scattered and traversal would approach the shuffled-list number.

**Lookup of random keys that are present:**

- **With 1,000 keys** (everything fits in L1 or L2), the sorted vector and the map take about 50–55 ns: about 10 levels of binary search, each a compare-and-branch the predictor cannot guess, so roughly half of them mispredict at around 15–20 cycles each. The hash tables avoid the unpredictable branches: about 12 ns for `std::unordered_map` (hash, modulo, two dependent loads) and about 7 ns for `FlatHashMap` (mix, mask, one or two loads).
- **With 2^{20} keys**, the differences explode: roughly 320–360 ns for binary search over an 8 MB sorted array, 1.4–1.5 µs for `std::map`, 50–60 ns for `std::unordered_map`, and roughly 15–25 ns for `FlatHashMap`.

The last number needs care. A random access into a 34 MB table should cost a full DRAM access, roughly 70–100 ns or more. `FlatHashMap` shows about 20 ns because this benchmark measures *throughput*: the lookups are independent, each probe address is computed from the key alone, and the out-of-order core keeps several cache misses in flight at once (*memory-level parallelism*). `std::unordered_map` gets less of that benefit because each lookup is a chain of two dependent misses; `std::map` and binary search get almost none, because each of their roughly 20 loads depends on the previous one. On the trading hot path, one message usually needs one lookup and then work that depends on its result, so you pay closer to the full *latency* of each miss. Batch throughput benchmarks like this one rank structures correctly but understate single-event latency; Section 16.4 shows how to measure the latter.

These ranges are typical for recent server-class x86-64 cores; they vary with the microarchitecture, clock speed and memory system (Section 12.7 explains the hierarchy).

| Event | Approximate cost | Why |
|---|---|---|
| Load hitting L1 | about 4–5 cycles | first-level cache latency |
| Load served from L2 / L3 | about 12–16 / 40–70+ cycles | larger, farther caches |
| Load served from DRAM | roughly 70–100+ ns | row access plus the trip through the memory controller; more on a remote NUMA node (Section 13.7) |
| TLB miss with a page walk | from a few cycles to hundreds | depends on whether the page-table entries are cached; huge pages reduce misses (Section 13.3) |
| Mispredicted branch | about 15–20 cycles | speculative work is discarded (Section 12.5) |
| Integer modulo by a run-time prime | about 10 to several tens of cycles | hardware division; a power-of-two mask costs 1 cycle |
| `malloc` + `free`, glibc fast path | tens of nanoseconds | thread-cache lookup and bookkeeping; much more on a slow path (Section 7.2) |
| Vector reallocation of n elements | O(n) moves plus an allocation | at n = 10^{6} 8-byte elements, about 8 MB copied: on the order of a millisecond |
| Hash table rehash at a million entries | milliseconds to tens of milliseconds | every element is moved or relinked; measured 35–50 ms at about 1.5 million entries in the build container |

The pattern behind every row: the expensive events are *misses*, *mispredictions* and *calls into the allocator*. A container choice is mostly a choice of how many of each you will take per operation.

## Interview Questions

**Q1. What happens when you `push_back` into a full `std::vector`?**
It allocates a larger buffer (twice the capacity in libstdc++, 1.5× in MSVC), moves the existing elements into it if their move constructor is `noexcept` (copies them otherwise), destroys the old elements, frees the old buffer, and constructs the new element. Every iterator, pointer and reference to an element is invalidated. The cost is O(n) for that call but amortized O(1) per `push_back` because growth is geometric; total moves over n pushes are below n·g/(g − 1), i.e. 2n for doubling.

**Q2. Why should move constructors be `noexcept`?**
Because containers that offer the strong exception guarantee, `std::vector` above all, use `std::move_if_noexcept` when relocating elements: a move that might throw cannot be undone halfway through a reallocation, so they copy instead. A missing `noexcept` silently turns every reallocation into a full copy (Listing 10.1).

**Q3. How does `std::map` guarantee O(log n)? What does a node look like?**
It is a red-black tree: the root is black, red nodes have black children, and every root-to-leaf path has the same number of black nodes, which bounds the height by 2 log_{2}(n + 1). Insertion and erasure restore the invariants with recoloring and at most two (insert) or three (erase) rotations. In libstdc++ each node has a color, parent, left and right pointers (32 bytes) followed by the key/value pair, and is separately heap-allocated.

**Q4. Why is `std::unordered_map` slower than a well-written hash table? Why can't the standard library just use open addressing?**
It allocates a node per element, so inserts call `malloc`, erases call `free`, and every lookup chases pointers (bucket entry, then node) that are usually in different cache lines. libstdc++ also indexes with a modulo by a prime, which is a division. The standard's interface forces this design: references must remain valid across rehashing, and the bucket interface (`bucket`, `bucket_size`, local iterators) assumes buckets that hold several elements. Open addressing moves elements within the array and has no such buckets.

**Q5. Which iterators does an `unordered_map` rehash invalidate?**
All iterators, but not pointers or references to elements: nodes are relinked into the new bucket array, not moved. Contrast an open-addressing table, where a rehash moves every element and invalidates everything.

**Q6. How do you delete from a linear-probing hash table?**
You cannot simply empty the slot, because that would break the probe chain of any key that was inserted past it. Either mark it with a tombstone (lookups skip it, inserts may reuse it; tombstones accumulate and force periodic rebuilds), or use backward-shift deletion: walk forward through the cluster and move back each element whose probe path crosses the hole, until an empty slot ends the cluster. Backward shift leaves no residue; it is specific to linear probing.

**Q7. What makes a good hash function for a power-of-two table?**
It must make the low bits of the result depend on all bits of the key, because the index is `hash & (capacity − 1)`. Identity hashing fails for keys sharing low bits (multiples of 4096 all land on a few slots). Use a mixing finalizer (SplitMix64, `fmix64`) or Fibonacci hashing using the high bits, and a random seed if keys can be chosen by an adversary.

**Q8. When would you use `std::list`? `std::deque`?**
`std::list`: when you need O(1) splicing, or stable iterators with insertion and removal in the middle, and the element count is small or allocation is not on a hot path; LRU caches are the classic case. In low-latency code, intrusive lists over preallocated objects replace it. `std::deque`: when you need efficient push/pop at both ends of an unbounded sequence and want existing elements to stay in place when you push at the ends; for a bounded queue a ring buffer is better.

**Q9. Design a container mapping order ID to order for a feed handler.**
Start from requirements: lookups on every cancel/modify/execute, insert per add, erase per removal, no allocation or latency spikes after startup, pointers to orders held by the order book's per-level queues. Store orders in a preallocated pool with stable addresses; index them with an open-addressing table from ID to pool index, reserved for the maximum expected live count with headroom, using a mixing hash; erase by backward shift. If the exchange's IDs are dense and increasing, consider a direct-indexed ring keyed by `id − base`. State what happens on overflow (fail loudly, never rehash silently) and how you would test it (differential test against `std::unordered_map`, sanitizers).

**Q10. What is the difference between `insert`, `emplace`, `try_emplace` and `operator[]` on a map?**
`insert(value)` inserts a fully constructed pair if the key is absent. `emplace(args...)` constructs the pair from `args`; because the key may only be known after construction, it can allocate and discard a node when the key already exists (libstdc++ does so for most argument forms). `try_emplace(key, args...)` looks the key up first and constructs the value only if the key is absent, never moving from `args` otherwise. `operator[](key)` inserts a default-constructed value if absent and returns a reference; it cannot be used on a `const` map.

**Q11. Is `std::vector<bool>` a container of `bool`?**
No. It is a space-optimized specialization storing one bit per element. `operator[]` returns a proxy object, you cannot take a `bool*` or `bool&` to an element, `auto x = v[i]` gives you a proxy rather than a copy of the value, and different elements share bytes, so concurrent writes to different elements race. Use `std::vector<char>`, `std::vector<std::uint8_t>`, or `std::bitset` / a dedicated bitset type depending on what you need.

**Q12. Why is a binary search over a sorted array sometimes slower than a hash lookup even when the array fits in cache?**
Each step's branch depends on a comparison with data the predictor cannot guess, so about half the steps mispredict (around 15–20 cycles each), and each step's load address depends on the previous comparison. A hash lookup computes its address directly from the key, with one predictable branch. Branchless binary search variants (computing the next index with a conditional move) remove the mispredictions but not the dependent loads.

## Key Takeaways

- **vector:** three pointers; geometric growth (×2 in libstdc++, ×1.5 in MSVC) gives amortized O(1) `push_back`; reallocation invalidates everything and copies instead of moving unless the move constructor is `noexcept`; `reserve` at startup; `clear` keeps capacity; `vector<bool>` is a bitset with proxies.
- **deque:** a map of 512-byte blocks in libstdc++; pushes at either end keep references valid but invalidate iterators. **list:** one allocation per node, 32 bytes of heap for an `int`; stable iterators and O(1) splice; traversal is pointer chasing (about 150 ns per element measured when nodes are scattered).
- **map/set:** red-black trees, height ≤ 2 log_{2}(n + 1), 32-byte node header; stable iterators; use `try_emplace`, `emplace_hint` for sorted input, `extract` to reuse nodes, transparent comparators; lookups in large maps are chains of cache misses.
- **unordered_map:** separate chaining with one singly linked list and per-bucket predecessor pointers; prime bucket counts and modulo; identity hash for integers; max load factor 1.0; rehash is O(n) inside one insert but keeps references valid; one allocation per insert. Its interface forces this design.
- **Open addressing (Listing 10.5):** power-of-two slots, mixed hash, one control byte with 7 hash bits per slot, linear probing at load ≤ 3/4, backward-shift deletion with no tombstones, placement new and `noexcept` moves. Pointers are valid only until the next insert or erase. Test differentially against a reference, under sanitizers.
- **Hashes:** consistent with equality; low bits must be good for masked tables; mix and seed; intern strings; pack composite keys; never XOR two hashes.
- **Choosing:** default to `vector`; preallocate everything; open addressing or direct indexing for ID lookup; ordered containers only when you need order; measure with real sizes.
- **Showdown:** for an order-ID index, `std::map` was slowest by a wide margin (roughly 5–15× the flat table), `unordered_map` allocated on every add, and the flat table was fastest with zero allocations. Rehash spikes of tens of milliseconds are avoided only by reserving.
