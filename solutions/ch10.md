## Chapter 10: STL Internals

### *P10.1

**Doubling (libstdc++):** capacities 1, 2, 4, …, 1024: **11 allocations**, final capacity **1024**. Each reallocation moves the current elements: 1 + 2 + 4 + … + 512 = **1023 moves**.

**1.5× rule:** capacities 1, 2, 3, 4, 6, 9, 13, 19, 28, 42, 63, 94, 141, 211, 316, 474, 711, 1066: **18 allocations**, final capacity **1066**, and the moves are the sum of the capacities reached before each reallocation, **2137**.

Both are within the n·g/(g − 1) bound of Section 10.1 (2000 and 3000). The 1.5× vector wastes less memory at the end (1066 against 1024 slots here, but in the worst case 50% overshoot against 100%) and pays with more allocations and about twice the moves. *Verified*: the libstdc++ numbers by counting moves of a real `std::vector`, the 1.5× numbers by simulating the rule.

### *P10.2

(a) Only the past-the-end iterator `end()`; every element stays in place. (b) **All iterators** are invalidated, but **pointers and references to elements remain valid**: the elements do not move, but the block map that iterators point into may be reallocated. (c) Everything: iterators, pointers and references. (d) Only iterators, pointers and references to the erased element. (e) Nothing. (f) **All iterators**, but **not** pointers or references: nodes are relinked into the new bucket array, never moved. (g) Without a rehash, nothing moves: the new element is constructed in an empty slot, so existing pointers stay valid. With a rehash, every element moves and every pointer is invalid. Since a caller cannot easily tell which case occurred, treat every insertion as invalidating unless the table was reserved for the maximum size. (h) The erased element, and also *any other element in the same cluster*, because backward-shift deletion moves them back. Treat every erase as invalidating all pointers obtained from `find`.

### *P10.3

- **`std::list<int>`:** node = `next` (8) + `prev` (8) + `int` (4) + padding (4) = 24 bytes requested; 24 + 8 = 32 → **32 bytes per element**.
- **`std::map<int, int>`:** node header (color padded to 8, parent, left, right) = 32, plus `pair<const int, int>` = 8, so 40 requested; 40 + 8 = 48 → **48 bytes per element**.
- **`std::unordered_map<int, int>`:** node = `next` (8) + pair (8) = 16 (no cached hash for `int`); 16 + 8 = 24, rounded to the 32-byte minimum → **32 bytes per node**, plus the bucket array: 8 bytes per bucket, with at least as many buckets as elements (10,273 buckets for 10,000 elements gives about 8.2 more bytes per element, about 40 in total).
- **`std::deque<int>`:** 512/4 = 128 elements per block, so ⌈10,000/128⌉ = **79 blocks**, plus one allocation for the block map.

*Verified* against the output of Listing 10.2 (32.0, 48.0, 40.2 bytes per element; 80 live blocks for the deque).

### *P10.4

(a) **Does not compile.** `v[0]` returns a `std::vector<bool>::reference` proxy by value; you cannot take the address of that temporary, and there is no `bool` object in the vector to point to. GCC: "taking address of rvalue". With `std::vector<char>` it compiles and points into the buffer.

(b) `auto x = v[0]` deduces the proxy type, not `bool`. The proxy refers to bit 0 of the vector, so after `v[0] = true`, **`x` reads `true`**. With `std::vector<char>`, `auto` would copy the value and `x` would stay 0. Generic code that does `auto x = c[i]` therefore behaves differently for `vector<bool>`. *Verified* by running it.

(c) **A data race (undefined behaviour).** The standard guarantees that distinct objects are distinct memory locations that different threads may write concurrently; bits 0 and 1 of a `vector<bool>` live in the same word, and each write is a read-modify-write of that word, so one thread's update can be lost. With `std::vector<char>` the two elements are separate bytes and the program is correct (though the two bytes share a cache line, so performance suffers from false sharing, Section 14.4).

### *P10.5

```cpp
class LRU {
public:
    explicit LRU(std::size_t cap) : cap_(cap) {}
    int get(int k) {
        auto it = pos_.find(k);
        if (it == pos_.end()) return -1;
        order_.splice(order_.begin(), order_, it->second);   // move to front, O(1)
        return it->second->second;
    }
    void put(int k, int v) {
        if (auto it = pos_.find(k); it != pos_.end()) {
            it->second->second = v;
            order_.splice(order_.begin(), order_, it->second);
            return;
        }
        if (order_.size() == cap_) {                          // evict least recent
            pos_.erase(order_.back().first);
            order_.pop_back();
        }
        order_.emplace_front(k, v);
        pos_[k] = order_.begin();
    }
private:
    std::size_t cap_;
    std::list<std::pair<int, int>> order_;                    // front = most recent
    std::unordered_map<int, std::list<std::pair<int, int>>::iterator> pos_;
};
```

The list keeps recency order; the map finds a key's list node in O(1). `splice` moves a node to the front without allocating and without invalidating the iterator stored in the map, which is exactly the list property this design depends on. The results are **1, −1, −1, 3, 4**: `put(3,3)` evicts key 2 (least recently used, since `get(1)` refreshed key 1), and `put(4,4)` evicts key 1. *Verified.*

**Hot-path version:** with a fixed capacity C, allocate C nodes once in an array; link them with `prev`/`next` *indices* (intrusive list), keep a free list for unused nodes, and replace `std::unordered_map` with an open-addressing table (Section 10.5) mapping key to node index, reserved for C entries. Eviction reuses the tail node in place. No operation allocates, and the whole structure occupies a few contiguous arrays.

### *P10.7

Without mixing, slot = key & 65,535 = (i × 4096) mod 65,536 = (i mod 16) × 4096, so only **16 distinct home slots** are used, 4096 apart. Each receives 625 keys, which form a contiguous run of 625 slots starting at the home slot (the runs never meet, since 625 < 4096). The k-th key into a run is found after k probes, so the average successful lookup inspects (1 + 2 + … + 625)/625 = 626/2 = **313 slots**. An unsuccessful lookup whose home slot falls inside a run must walk to the end of the run.

With the mixing finalizer, the same keys behave like random keys at load 10,000/65,536 ≈ 0.153, for which Knuth predicts ½(1 + 1/0.847) ≈ 1.090; the table measured **1.092**. *Verified.* This is why Listing 10.5 never trusts the user's hash with a power-of-two mask.

### *P10.8

```cpp
struct StringHash {
    using is_transparent = void;                      // enables heterogeneous lookup
    std::size_t operator()(std::string_view s) const noexcept {
        return std::hash<std::string_view>{}(s);
    }
};
std::unordered_map<std::string, int, StringHash, std::equal_to<>> m;
m.find(std::string_view{"XNSE:RELIANCE-FUTURES-2026-12"});   // no std::string built
```

C++20 enables the heterogeneous overloads of `find`, `count`, `contains` and `equal_range` only when **both** the hash and the key-equality type declare `is_transparent`; `std::equal_to<>` does. The hash must give the same value for a `std::string` and a `std::string_view` with the same characters, which `std::hash<std::string_view>` does, since a `std::string` converts to a `string_view` before hashing. ### *P10.9

```cpp
FlatHashMap(const FlatHashMap& o) : hash_(o.hash_), eq_(o.eq_) {
    if (o.cap_ == 0) return;
    allocate(o.cap_);                     // same capacity, same hash: same layout
    try {
        for (std::size_t i = 0; i < cap_; ++i) {
            if (o.ctrl_[i] == kEmpty) continue;
            ::new (static_cast<void*>(&slots_[i])) Slot(o.slots_[i]);
            ctrl_[i] = o.ctrl_[i];        // mark full only after construction
            ++size_;
        }
    } catch (...) {
        destroy_all();                    // the destructor will not run
        deallocate();
        throw;
    }
}
FlatHashMap& operator=(const FlatHashMap& o) {
    if (this != &o) {
        FlatHashMap tmp(o);               // may throw: *this untouched
        swap(tmp);                        // noexcept
    }
    return *this;
}
```

Because the copy has the same capacity and the same hash function, every element can go into the same slot index as in the source, and the control bytes can be copied as they are: no rehashing and no probing. If a copy constructor throws partway, the constructor's own destructor will not run (the object was never fully constructed), so the `catch` destroys what was built (only slots already marked full) and frees the arrays before rethrowing. Copy assignment uses *copy-and-swap*: all the work that can throw happens on a temporary, and the `noexcept` swap commits it, which gives the strong guarantee.

**New requirements:** `K` and `V` must be copy-constructible (the move requirements remain for rehash and erase), and `Hash` and `Eq` must be copy-constructible. Copying is O(capacity), not O(size), because it scans every control byte. *Checked* in a scratch build under ASan/UBSan, including a value type whose copy constructor throws on the 1000th copy: the assignment threw and the destination kept its original single element.

### *P10.10

| Scheme | Mean displacement | Standard deviation | Maximum |
|---|---|---|---|
| Linear probing | 1.463 | 4.01 | 109 |
| Robin Hood | 1.463 | 1.77 | 14 |

*Verified* (49,152 random keys, 65,536 slots).

**Why the means are identical.** Whichever key wins a contested slot, the set of occupied slots after all insertions is the same: a new key always ends in the first empty slot at or after its home, and Robin Hood only changes *which* key sits where within a cluster. The total displacement is the sum over occupied slots of their positions minus the sum of the keys' home slots (modulo wrap-around), and both sums are fixed. So Robin Hood cannot reduce the average; it redistributes displacement from keys that are far from home to keys that are close, which cuts the variance and the maximum dramatically. A lookup's worst case (109 slots inspected against 14) is what improves.

**Faster unsuccessful lookups.** In a Robin Hood table, as you walk a cluster the displacements of the stored keys never fall below the distance you have walked, until you pass the point where your key would have been placed. So a lookup can stop as soon as it reaches a slot whose resident's displacement is smaller than its own current probe distance: the key cannot be further on. Unsuccessful lookups then cost about as much as successful ones, instead of the 8.5 inspections of plain linear probing at α = 0.75. Storing each slot's displacement in its metadata byte avoids recomputing hashes, both for this test and for backward-shift deletion.

### *P10.11

Use a **direct-indexed ring** of W = 2^{22} entries: entry `id & (W − 1)` holds the order (or its pool index) together with the full ID. Lookup is one mask, one load and a comparison of the stored ID with the requested one; insertion writes the entry; deletion marks it empty. No hashing, no probing, no collisions while the window assumption holds, because two live IDs less than W apart always map to different entries.

**Orders older than the window:** an add for ID x reuses the entry of ID x − W. If that entry is still occupied, the assumption is violated: an order more than W IDs old is still live. Detect it on every insert by checking the occupied flag (and the stored ID), and handle it explicitly: move the old order to a small overflow hash table and raise an alert, rather than silently overwriting it. Lookups check the stored ID, so a stale or reused entry can never return the wrong order; on a mismatch, consult the overflow table.

**Memory:** 2^{22} × 32 bytes = 134,217,728 bytes = **128 MiB**. Only the region near the newest IDs is hot; the rest is touched rarely. Back it with huge pages to avoid TLB misses on a 128 MiB array (Section 13.3), and pre-fault it at startup (Section 7.4). If each entry stores only the 8-byte ID and a 4-byte pool index (16 bytes with padding), it needs 64 MiB.

### *P10.12

**Faster:** finding a level by exact price (add or cancel at a known price) becomes an O(1) average hash lookup instead of an O(log n) tree walk.

**Broken or slower:** the order book's central queries are *ordered*: the best bid is the maximum price, the best ask the minimum, and when the best level empties you need the next best. A hash table has no order, so each of these becomes a scan of all levels, or you must maintain the best price separately and rescan when it disappears. Depth snapshots (the top N levels in price order) need a sort. Each new level is still a heap allocation, and a rehash during a burst of new levels is a latency spike. Iteration order also becomes non-deterministic, which hurts replay testing.

**Proposal:** exploit the fact that prices are integers in ticks and activity concentrates near the touch: an array of levels indexed by `(price − base)` in ticks, covering a window around the current best prices, with the best bid and ask tracked as indices (a bitmap of non-empty levels finds the next best quickly), and a fallback ordered structure for the rare far-away prices; recentre the window when the market moves. Levels and orders come from preallocated pools. Section 18.1 develops this design and its alternatives.
