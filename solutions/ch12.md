## Chapter 12: Computer Architecture

### *P12.1

With 64-byte lines the offset is bits 0–5; with 32768 / (64 × 8) = 64 sets the set index is bits 6–11. The low 12 bits of 0x7ffd3a2c1e58 are 0xe58 = 3672. **Offset** = 3672 mod 64 = **24** (0x18). **Set index** = ⌊3672 / 64⌋ mod 64 = 57 mod 64 = **57**. The set index uses only bits 6–11, which lie inside the 12-bit offset of a 4 KiB page, so it is **the same in the virtual and the physical address**: the L1 can select the set before translation finishes (virtually indexed, physically tagged). *Verified.*

### *P12.2

Struct *i* occupies bytes 40i … 40i + 39. The pattern repeats every 8 structs (320 bytes = 5 lines); within each period, structs 1, 3, 4 and 6 (counting from 0) cross a boundary, so **500 of the 1000** straddle. *Verified* by enumeration (and independently in Python).

Fixes: (1) `alignas(64)` or padding each struct to 64 bytes: no struct straddles, but memory use and the number of lines for a full scan grow by 60%, which hurts sequential scans; (2) shrinking the struct to 32 bytes (reorder fields, narrower types, move cold fields elsewhere): two per line, never straddling, and a full scan touches fewer lines. Which to choose depends on whether the hot operation is random access to one struct (alignment wins) or scanning (density wins). Splitting hot and cold fields (6.7) often does both.

### *P12.3

Reach = entries × page size: **64 × 4 KiB = 256 KiB**; **1536 × 4 KiB = 6 MiB**; **32 × 2 MiB = 64 MiB**. *Verified.* (If the STLB also holds 2 MiB entries, as on Skylake-family cores, its reach for 2 MiB pages is 3 GiB.)

### *P12.4

By Little's law, bandwidth = (bytes in flight) / latency = 12 × 64 B / 90 ns = 768 / 90 ≈ **8.53 GB/s** per core for random accesses (sequential streams can do better, because the L2 prefetcher has its own tracking resources). To sustain 20 GB/s at 90 ns: 20 B/ns × 90 ns / 64 B ≈ **28.1, so 29 lines in flight**, more than one core can track; this is why a single thread cannot saturate a socket's memory bandwidth with random accesses. *Verified.*

### *P12.5

To keep both FMA units busy every cycle while each FMA takes 4 cycles to produce its result, 2 × 4 = **8 independent accumulators** (8 ymm registers) must be in flight. Peak = 2 FMAs/cycle × 4 doubles × 2 flops (multiply + add) = **16 flops per cycle**. One accumulator completes one FMA every 4 cycles: 4 × 2 / 4 = 2 flops per cycle, **1/8 of peak**.

A practical caveat that interviewers like: a dot product reads two doubles per FMA lane, so peak FMA rate needs four 256-bit loads per cycle, while most cores sustain two (some three). The loop is therefore load-bound at about half the FMA peak, 8 flops per cycle, and 4 accumulators already suffice. Peak FMA throughput is only reachable in kernels that reuse loaded data, such as blocked matrix multiplication.

### *P12.6

Replace the conditional negation by a mask, exactly as in Listing 12.5:

```cpp
const long long m = -static_cast<long long>(p[1] != 'B');   // 0 for buy, all ones for sell
total += (v ^ m) - m;                                        // v if m == 0, else -v
```

`(v ^ m) - m` is the two's-complement identity −v = ~v + 1 applied conditionally: with m = 0 it is v; with m = −1 it is ~v + 1. The checksum is unchanged (−1,609,972,405 per pass, i.e. 1/50 of the checksum printed by Listings 11.4 and 11.5, which run 50 passes). In the build container the time per message fell from about 6 ns to about 3 ns (the verification program prints both; values vary by run).

The speed-up (about 2×) is smaller than in Listing 12.5 because the remaining cost is not the branch: each message is 22 bytes, the 22 MiB buffer does not fit in the effective cache of the VM, and streaming it from memory sets a floor of a few nanoseconds per message. Section 11.7's loop also does more work per element (two loads, a multiply). With the branch gone, the loop is bound by memory bandwidth, and the next optimizations would be about data size (12.2), not control flow.

### *P12.7

| Step | A | B | Notes |
|---|---|---|---|
| A reads | E | I | no other copy, so Exclusive |
| B reads | S | S | A's clean E copy downgrades |
| A writes | M | I | **invalidation 1** sent to B |
| B reads | S | S | A supplies the dirty data and writes it back |
| B writes | I | M | **invalidation 2** sent to A |
| A reads | S | S | B supplies the data and writes it back |

**Two invalidations.** Under MOESI (AMD) the fourth and sixth steps would leave the supplier in O (Owned) without a write-back to memory; under MESIF (Intel) one of the sharers would be in F. *Verified* with a two-core MESI model.

### *P12.8

Set = (address / 16) mod 4. Addresses 0, 64, 128, 192 are blocks 0, 4, 8, 12, all in set 0; 16 and 80 are blocks 1 and 5, in set 1.

| Access | Block, set | Result | Set contents after (most recent first) |
|---|---|---|---|
| 0 | 0, 0 | miss | 0 |
| 64 | 4, 0 | miss | 4, 0 |
| 0 | 0, 0 | **hit** | 0, 4 |
| 128 | 8, 0 | miss (evicts 4) | 8, 0 |
| 64 | 4, 0 | miss (evicts 0) | 4, 8 |
| 16 | 1, 1 | miss | 1 |
| 80 | 5, 1 | miss | 5, 1 |
| 16 | 1, 1 | **hit** | 1, 5 |
| 0 | 0, 0 | miss (evicts 8) | 0, 4 |
| 192 | 12, 0 | miss (evicts 4) | 12, 0 |

**2 hits, 8 misses.** Four blocks compete for the two ways of set 0 while sets 2 and 3 are never used: conflict misses. *Verified* with the LRU cache simulator.

### *P12.9

Element (r, c) is at byte r × 8192 + 8c. For c < 8 all of a row's eight elements are in one line, and the set index is bits 6–11 of the address. 8192 = 2^{13}, so r × 8192 contributes nothing to bits 6–11: **every row's line maps to set 0**. Walking column 0 touches 256 lines in one 8-way set, so each access evicts a line needed later; column 1 finds none of them. Every access misses: **2048 misses out of 2048 accesses**.

With rows padded to 1032 doubles (8256 = 8192 + 64 bytes), row *r* starts *r* lines further along in the set space, so the 256 lines spread evenly over the 64 sets, 4 per set, which fits in 8 ways. Column 0 misses 256 times; columns 1–7 hit in the lines already loaded: **256 misses, 8× fewer**. *Verified* with the cache simulator.

The general rule: power-of-two strides of 4 KiB or more are pathological for set-associative caches. Pad leading dimensions, or traverse in the storage order (here, sum rows of an 8-column block instead of columns).

### *P12.10

In-order filling of the implicit tree of 15 nodes gives

b[1..15] = 80, 40, 120, 20, 60, 100, 140, 10, 30, 50, 70, 90, 110, 130, 150.

Search for 65: k = 1 (80 < 65? no → k = 2), k = 2 (40 < 65? yes → k = 5), k = 5 (60 < 65? yes → k = 11), k = 11 (70 < 65? no → k = 22 > 15, stop). **Visited 1, 2, 5, 11.** Final k = 22 = 10110₂. ~k ends in a single 1 bit (…01001₂), so countr_zero(~k) = 0 and k >>= 1 gives **k = 11**, and the answer is **b[11] = 70**, the smallest key ≥ 65. (The correction removes the trailing right turns plus the final left turn; the node where the search last went left holds the answer.) *Verified.*

### *P12.11

2 GiB with 4 KiB pages is 524,288 pages, far beyond any TLB, so nearly every lookup is both a TLB miss and a cache miss:

- **Page walk.** The upper levels of the page tables are few and stay cached (the page-directory level for 2 GiB is 1024 entries, 8 KiB). The last level holds 524,288 8-byte entries, 4 MiB, competing with everything else for cache; assume it hits L3 sometimes and misses to DRAM often: roughly **20–100 ns**.
- **The record itself:** a DRAM access, roughly **80–120 ns** on bare metal.
- Total with 4 KiB pages: roughly **100–220 ns** per lookup, done serially.

With 2 MiB pages the table is 1024 pages, which fits in a 1536-entry STLB: no walk, so roughly **80–120 ns**, the DRAM access alone. (In a VM, add the nested-walk cost to the 4 KiB case.)

Data-structure changes that reduce it further: (1) **separate hot from cold**: keep only the fields the check needs (limits, current exposure) in a dense array indexed by a small integer instrument or account id, so the hot set is megabytes, not gigabytes, and largely cache-resident; (2) **batch and prefetch**: when several orders are checked together, compute all addresses first and prefetch them, so the misses overlap (memory-level parallelism, P12.4) instead of being paid one after another; (3) replace hashing of sparse keys with **direct indexing** assigned at startup, which removes probe sequences entirely.

### *P12.12

```cpp
std::size_t find_byte_sse2(const std::uint8_t* a, std::size_t n, std::uint8_t t) {
    const __m128i tv = _mm_set1_epi8(char(t));
    std::size_t i = 0;
    for (; i + 16 <= n; i += 16) {
        const __m128i x = _mm_loadu_si128(reinterpret_cast<const __m128i*>(a + i));
        const unsigned mask = unsigned(_mm_movemask_epi8(_mm_cmpeq_epi8(x, tv)));
        if (mask) return i + std::size_t(std::countr_zero(mask));
    }
    for (; i < n; ++i)
        if (a[i] == t) return i;
    return n;
}
```

`_mm_cmpeq_epi8` produces 0xFF in each matching lane. `_mm_movemask_epi8` gathers the top bit of each of the 16 bytes into a 16-bit integer, bit *j* for lane *j*, so the first match is the lowest set bit, found with `std::countr_zero` (a `tzcnt` or `bsf` instruction). The tail is handled with a scalar loop so the function never reads past the end of the buffer. (`memchr` implementations instead round the pointer down to an aligned 16-byte block, which cannot cross a page boundary and therefore cannot fault, and mask off the bytes outside the range; with `_mm_loadu_si128` on a C++ object that over-read would be out-of-bounds access, 11.2.)

In a FIX parser, messages are sequences of `tag=value` fields separated by the SOH byte (0x01), so finding the next SOH and the next `=` is the innermost loop; vectorized delimiter search processes 16 bytes per step instead of one. *Verified* against `std::find` on 2000 random arrays of random lengths (0–199 bytes, so that matches occur in the vector part, in the tail, and not at all).
