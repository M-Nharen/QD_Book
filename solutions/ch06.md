| Struct | Layout (offset: member) | sizeof | alignof |
|---|---|---|---|
| (a) `A` | 0: c, 1–7 padding, 8: d, 16: s, 18–23 tail padding | **24** | **8** |

### *P6.2

As declared: `valid` 0, seven padding bytes, `bid` 8, `bid_qty` 16, `venue` 20–22, one padding byte, `ask` 24, `ask_qty` 32, `flags` 36–37, two bytes of tail padding: **40 bytes**. Sorted by decreasing alignment:

```cpp
struct Quote {
    std::int64_t bid, ask;             // 0, 8
    std::int32_t bid_qty, ask_qty;     // 16, 20
    std::uint16_t flags;               // 24
    char venue[3];                     // 26..28
    bool valid;                        // 29
};                                     // 30 bytes of data, 2 of tail padding
```

**32 bytes.** That is the minimum: there are 30 bytes of data and the size must be a multiple of 8. It also divides 64, so no element of an array straddles a cache line. *Verified.*

### *P6.3

**1, 8, 4, 8.** `X` is 1 byte so that distinct `X` objects have distinct addresses. In `Y`, the member `x` takes a byte and `i` must start at offset 4. In `Z`, the empty base occupies no space (EBO). In `W`, the empty base subobject and the member `x` are both of type `X`, so they must have *different* addresses: the base takes offset 0, `x` goes to offset 1, `i` to offset 4, and the size is 8. EBO cannot apply when the first member has the same type as the empty base. *Verified.*

### *P6.4

`A` is a vptr (0–7) and `a` (8–11), size 16. `B` is a vptr and `b`, size 16, alignment 8. In `C`, `A` is the primary base at offset 0. `B` must be 8-aligned, so it cannot start in `A`'s tail padding at 12; it goes to **offset 16**. `c` follows at **offset 32**, and the size rounds up to **40**. *Verified.*

`static_cast<B*>(&obj)` is `&obj + 16`, while `reinterpret_cast<B*>(&obj)` is `&obj` itself, pointing at the `A` subobject: **16 bytes apart**. A virtual call through the reinterpreted pointer would use `A`'s vtable slots as if they were `B`'s.

### *P6.5

The Itanium ABI lets a derived class place members in the tail padding of a base class *unless the base is a POD* (in the ABI's C++03 sense). `P` has a virtual destructor, so it is not a POD: its data ends at offset 12, `y` goes into the tail padding at **offset 12**, and `Q` stays **16** bytes. `P2` is a POD, so all **16** of its bytes belong to it and `y` must start at offset 16: `Q2` is **24** bytes. *Verified.*

The reason for the rule: code is allowed to copy a POD with `memcpy(dst, src, sizeof(P2))`. If `y` lived in `P2`'s tail padding, copying a `P2` into the base part of a `Q2` that way would overwrite `y`. A non-POD class cannot be copied like that, so its padding can be reused.

### *P6.6

```text
Base
Derived
Derived
Base
```

Construction runs `Base()` first, while the object's vptr points to `Base`'s vtable, so `hello()` prints "Base". Then `Derived()` sets the vptr to `Derived`'s table, and its `hello()` prints "Derived". Destruction runs in reverse: `~Derived()` prints "Derived", then `~Base()` resets the vptr to `Base`'s table before its body runs and prints "Base". A virtual call made during construction or destruction never reaches a more-derived class, whose part of the object does not exist yet, or no longer exists. *Verified.*

### *P6.7

| Type | sizeof | Why |
|---|---|---|
| `std::variant<char, std::int16_t>` | **4** | 2 bytes of storage plus a 1-byte index, rounded up to the alignment of 2 |
| `std::variant<std::int64_t, double, char>` | **16** | 8 bytes of storage plus the index, rounded up to 8 |
| `std::optional<double>` | **16** | the value plus a `bool` "engaged" flag, rounded up to 8 |
| `std::optional<std::int32_t>` | **8** | 4 + 1, rounded up to 4 |
| `std::variant<std::string, int>` | **40** | `std::string` is 32 bytes in libstdc++, plus the index, rounded up to 8 |
| `std::unique_ptr<int, void (*)(int*)>` | **16** | the pointer plus the stored function pointer; a stateless deleter would cost nothing |

In every case the discriminator costs a whole alignment unit, which is why a vector of `std::optional<double>` takes twice the memory of a vector of `double`. Where a value can never legitimately occur (for example, a price of zero or a NaN), a sentinel value avoids the extra bytes, at the price of discipline. *Verified.*

### *P6.8

```cpp
#pragma pack(push, 1)
struct TradeMsg {
    char type;                  // offset 0
    std::uint64_t ts_ns;        // offset 1
    char symbol[8];             // offset 9
    std::uint32_t price;        // offset 17
    std::uint32_t qty;          // offset 21
};
#pragma pack(pop)
static_assert(sizeof(TradeMsg) == 25);
static_assert(offsetof(TradeMsg, ts_ns) == 1 && offsetof(TradeMsg, symbol) == 9);
static_assert(offsetof(TradeMsg, price) == 17 && offsetof(TradeMsg, qty) == 21);
static_assert(std::is_trivially_copyable_v<TradeMsg>);
```

*Verified:* size 25, price at offset 17.

`const std::uint32_t* p = &msg.price;` creates a `std::uint32_t*` holding a misaligned address, but the type promises 4-byte alignment. Dereferencing it is undefined behaviour, and the compiler may generate code (for example, vector loads or instructions that require alignment) that breaks. With `__attribute__((packed))` GCC warns (`-Waddress-of-packed-member`); with `#pragma pack` GCC 13 did not, in the build container. Accessing `msg.price` *by name* is fine, because then the compiler knows the member is packed.

`reinterpret_cast<const TradeMsg*>(packet + header_len)` pretends a `TradeMsg` object lives in the receive buffer. No such object was ever created there, so reading through the pointer is not guaranteed by the language (the strict-aliasing and object-lifetime rules of Section 11.3). It "works" with today's compilers in many cases, which is exactly why it is dangerous. The defined way costs nothing at -O2:

```cpp
std::uint32_t price;
std::memcpy(&price, packet + header_len + offsetof(TradeMsg, price), sizeof price);
// then convert byte order if the specification says big-endian
```

Alternatively, `memcpy` all 25 bytes into a local `TradeMsg` and read its members by name.

### *P6.9

AoS: every order's 64-byte line must be fetched: 10^{7} × 64 = **640 MB**, so **64 ms** at 10 GB/s. SoA: 10^{7} × (8 + 4 + 1) = **130 MB**, so **13 ms**. *Verified* (arithmetic). Listing 6.7 measured the same shape on 4 million orders in the build container.

The estimate is **optimistic** if the loop is not purely bandwidth-bound: data-dependent branches that mispredict (the first version of Listing 6.7 ran at about 7 ns per order in every layout for exactly that reason), a single thread that cannot sustain the machine's peak bandwidth, page-table misses on a large array without huge pages (Section 13.3), or other cores competing for memory. It is **pessimistic** if part of the data is already in cache: 130 MB does not fit in caches, but a smaller book's columns would, and then the SoA scan runs at cache speed, not DRAM speed.

### *P6.11

`sizeof(Stats)` is **16**: both counters share one 64-byte cache line. Each increment by one thread takes the line in exclusive state, invalidating the other core's copy, so the line bounces between the two cores on nearly every update, even though the threads never touch the same variable. This is false sharing, and it can make the counters many times slower than with each in its own line. Fix it with `alignas(64)` on each member (or per-thread structs, each aligned to 64): the size becomes **128**. *Verified.* Section 14.4 measures the effect.

The design:

- **Storage:** an aligned byte buffer of `Cap` bytes (line 28) holds the callable, constructed with placement new (Section 7.3). The `static_assert`s on lines 36–38 reject, at compile time, callables that are too large, over-aligned, or whose move constructor could throw (a throwing move would make the container's own move impossible to declare `noexcept`).
- **The "vtable":** `ops_for<F>` (lines 19–26) is one `constexpr` table of four function pointers per stored type F: invoke, copy-construct, move-construct and destroy, each a captureless lambda converted to a function pointer. The object stores a pointer to its type's table (line 29), exactly as a polymorphic object stores a vptr. A call is one load of `ops_`, one load of `invoke` and an indirect call, the same machine-level cost as a virtual call, with the same lack of inlining.
- **Empty state:** a null `ops_` means "empty"; `reset` destroys the callable and nulls it. A moved-from object is left empty (line 46), which is why the output reports the moved-from function as empty.
- **Size:** 32 bytes of buffer plus an 8-byte pointer is 40, rounded up to a multiple of the buffer's 16-byte alignment: **48 bytes**.

Compared with `std::function`: never allocates, so it is safe on a hot path that must not allocate (Section 7.7), at the cost of a fixed capacity chosen at compile time. Several open-source libraries provide variants of this type; the closest standard relative is C++23's `std::move_only_function`, which is move-only and may still allocate.

### *P6.13

A strong answer argues from the costs measured in this chapter.

- **Use a `switch` on the type byte that decodes and applies in one pass.** For each known type, `memcpy` the fixed-size body into a local struct and call that type's handler, defined inline so the compiler can see it. No event objects are created, nothing is allocated, nothing is copied twice, and the bodies are inlined. With about 40 dense case values, GCC typically emits a jump table: one bounds check and one indirect jump per message. Check the generated code rather than assuming.
- **Unknown or rare types.** The `default` case uses the message length from the header to skip the message, and increments a counter that monitoring watches; an unknown type is a normal event (a new protocol version), not an exception. Put rare handlers (administrative messages, rarely used types) in separate functions marked `[[unlikely]]` or `__attribute__((cold))` so their code does not dilute the hot path in the instruction cache.
- **Branch prediction.** The jump is unpredictable to the extent that the message mix is random, and no dispatch mechanism removes that: the measurements in Section 6.6 showed variants, switches and tables mispredicting alike. What you can control is the cost around it: keep the handlers short and the hot types' code compact, so a mispredicted jump lands in code that is already in the instruction cache.
- **The alternatives.** A 256-entry table of function pointers has the same jump but cannot inline the handlers; it is reasonable when handlers are registered at run time. A virtual hierarchy adds either an allocation per message or placement-new into a buffer, plus an extra dependent load, for no benefit with a closed set of types. A `std::variant` buffer (Listing 6.9) is the right design when events must be stored or passed to another thread, for example through an SPSC queue (Section 14.5), but it adds a pass and a 32-byte copy when they need not be.
- **Code size.** Forty handlers inlined into one function can make a large function. Watch the hot path's instruction footprint (Section 9.7, Section 16.2), and keep only the frequent types inline.
- **Measurement.** Replay a captured feed through the decoder; record per-message latency with timestamps and report percentiles, not averages (Section 16.4); and use hardware counters for branch mispredictions and instruction-cache misses (Section 16.5) to see *why* one design wins.
