## Chapter 13: Operating Systems and Linux

### *P13.1

The child has **one thread**: the copy of thread B, the one that called `fork`. Its memory is a copy of the parent's, including the logging library's mutex in the locked state, but thread A does not exist in the child, so nobody will ever unlock it. The child's first attempt to log blocks forever (a deadlock with no other party). glibc avoids this for its own internal locks (it takes the `malloc` arena locks around `fork`, for instance), but it cannot know about an application library's mutex.

Ways to avoid it: (1) in the child, call only async-signal-safe functions and `exec` immediately (or use `posix_spawn`, which does exactly that); (2) fork any helper processes at startup, before creating threads, or delegate all spawning to a small single-threaded launcher process; (3) `pthread_atfork` handlers that acquire the library's locks before the fork and release them in both parent and child. Option 3 is fragile (every library must cooperate, and the parent's hot threads are blocked during the fork), so (1) and (2) are preferred.

### *P13.2

Only **(c)** and **(g)** enter the kernel.

- (a) `CLOCK_REALTIME`, (b) `CLOCK_MONOTONIC_RAW`, (d) `gettimeofday` and (e) `time` are served by the vDSO with a TSC clocksource. (Which clocks the vDSO supports depends on the kernel version; `CLOCK_MONOTONIC_RAW` and `CLOCK_BOOTTIME` were added later than the others, so check on older kernels.)
- (c) `CLOCK_PROCESS_CPUTIME_ID` must sum the CPU time of all threads of the process, which only the kernel knows: a system call.
- (f) `sched_getcpu` reads the CPU number from the thread's rseq area (glibc 2.35 and later).
- (g) `getpid` is a system call; glibc stopped caching the PID in version 2.25.
- (h) `malloc(32)` is served from the thread cache or an existing heap chunk; it enters the kernel only when the heap must grow (`brk`) or for large requests (`mmap`), 7.2.
- (i) `std::this_thread::get_id()` returns `pthread_self()`, which reads the thread pointer (the `fs` base, 13.1).

*Verified* by running each call 1000 times under `strace -c` in the build container (Linux 6.18, glibc 2.39): only `clock_gettime` with the process CPU clock and `getpid` appeared, 1000 times each.

### *P13.3

**4 KiB pages:** 1 GiB / 4 KiB = **262,144** minor faults (one per page; the write faults directly, with no zero-page step because the first access is a write) and **262,144** page-table entries. Each last-level table page holds 512 entries, so 512 table pages are needed: **2 MiB** of page tables, about 0.2% of the data. (Plus one entry in each of the higher levels per table page below it, which is negligible.)

**2 MiB pages:** 1 GiB / 2 MiB = **512** faults and 512 entries at the PMD (second-lowest) level: exactly one table page, **4 KiB**. No last-level tables at all.

**1 GiB pages:** **one** fault and one entry at the PUD level, inside one 4 KiB table page. (The fault itself zeroes 1 GiB, which takes tens of milliseconds: do it at startup.) *Verified.*

### *P13.4

Two million voluntary switches in 10 s is 200,000 per second: the thread **blocks** about every 5 µs. A thread that busy-polls never blocks, so it is not busy-polling. Voluntary switches are counted when a task stops being runnable: waiting on a futex (a `std::mutex` that is contended, a `std::condition_variable`, a blocking queue), sleeping (`usleep`, `nanosleep`, `std::this_thread::sleep_for`, even with tiny durations, as a "back-off"), or a blocking `recv`/`epoll_wait`. Look for those in the poll loop and its back-off path; `strace -f -c -p <tid>` in a test environment or `perf trace` shows which system call it is.

The opposite numbers, 40 voluntary and 2,000,000 involuntary, would mean the thread does spin but is **preempted** 200,000 times a second: something else is runnable on its CPU and keeps being woken there (wakeup preemption), for example another busy thread or a high-rate interrupt-driven kernel thread sharing the core. The fix is then isolation (13.6), not a code change.

### *P13.5

A tick delays a message if it fires while the message is being handled, that is, within the 5 µs after arrival. With the tick phase uniform over the period *T*, the probability is 5 µs / *T* (ignoring the 3 µs duration of the tick itself, which only adds a second-order term).

(a) *T* = 4 ms: 5/4000 = **0.125%** of messages are delayed by 3 µs. The 99th percentile is unaffected; the **99.9th percentile is affected** (0.125% > 0.1%), so p99.9 rises from 5 µs to about 8 µs.

(b) *T* = 1 ms: **0.5%** of messages; the 99.5th percentile and above are affected, so p99.9 is 8 µs and p99 still 5 µs.

(c) One residual tick per second: 5 µs / 1 s = **0.0005%**, five messages in a million; only percentiles beyond p99.999 see it.

*Verified* by simulation with 2 × 10^{7} uniformly random phases per case. Real hosts also have interrupts and other kernel work, which this model ignores; the point is the method: interruption rate × handling time = fraction affected.

### *P13.6

(a) The parent writes 10^{7} updates to 1,048,576 pages of 4 KiB, uniformly at random. A page is copied on its first write after the fork, so the number of copy-on-write faults is the expected number of distinct pages touched:

N (1 − (1 − 1/N)^{U}) ≈ N (1 − e^{−U/N}) with N = 1,048,576 and U = 10^{7}: U/N ≈ 9.54 and e^{−9.54} ≈ 7 × 10^{−5}.

So about **1,048,500 faults**: essentially every page is copied, and the snapshot needs **almost 4 GiB of extra memory**, doubling the footprint. About 10.5% of all updates take a fault; at the ≈ 2.4 µs measured in Listing 13.2, that is about **2.5 s of fault handling** spread over the 10 s, a quarter of the parent's time.

(b) With 2 MiB pages there are only 2048 pages. All of them are copied (again ≈ 4 GiB extra), and quickly: by the coupon-collector argument (2.4) the expected number of updates until every page has been written is 2048 × H_{2048} ≈ 16,800, about **17 ms** at 10^{6} updates per second.

(c) With 4 KiB pages, the worst-case update pays one 4 KiB copy fault, microseconds, and it happens to one update in ten. With 2 MiB pages, almost all updates are unaffected, but about 2048 updates in the first ~17 ms each pay a fault that copies **2 MiB**, which takes hundreds of microseconds (compare the 2 MiB zero-fill faults of Listing 13.3). Huge pages convert many small stalls into a burst of very large ones right after each fork. The real fix is not to fork the latency-critical process: snapshot from a replica, or have the hot process stream changes to a separate persistence process. *Verified.*

### *P13.7

Use the container measurements of Listing 13.4 and say so: a wake-up of a sleeping thread on another CPU took about **11 µs** in the printed run (5–13 µs across runs; bare metal is typically a few µs, more from deep C-states), and a same-CPU handoff, a reasonable proxy for the CPU work of one sleep-and-wake cycle, about **1.1–1.6 µs**.

- **Latency added:** roughly one cross-CPU wake-up per message, ≈ 10 µs here. But at 200,000 messages per second the messages arrive every 5 µs on average, *faster than the wake-up completes*. The strategy thread will often still be awake, processing a backlog, when the next message arrives, so most messages wait in the queue instead: the latency is now set by queueing behind a slow consumer, and it varies with the burstiness of the feed.
- **CPU:** at 1.1–1.6 µs of kernel work per handoff, 200,000 handoffs cost **0.22–0.32 of a core** per second, before any useful work, plus the producer's `FUTEX_WAKE` system calls.

**Replacement:** a single-producer single-consumer ring buffer (14.5) with the consumer busy-polling on its own isolated core. A handoff then costs one or two cache-line transfers between cores, on the order of 100 ns (12.3), with no system calls and no scheduler involvement. The price is a whole core that spins at 100% even when the market is quiet, and the need to isolate it (13.6). *Arithmetic verified.*

### *P13.8

The parser and formatter are in the verification program below (lines 14–57). The parser splits on commas, accepts either a number or `lo-hi` per item, rejects empty items, non-digits (`std::from_chars` must consume the whole item), negative numbers and reversed ranges, then sorts and removes duplicates. The empty string is accepted as the empty set, because that is what `/sys/devices/system/cpu/isolated` contains on a host with no isolated CPUs. The formatter sorts, removes duplicates and emits maximal runs of consecutive numbers as `lo-hi`, which is the shortest representation. *Tested* on fixed cases, eight malformed inputs, and 20,000 random subsets of 0–63 in both directions.

### *P13.9

Waiting time per second is lookups × latency, because the lookups are dependent and cannot overlap:

- now (remote): 2 × 10^{6} × 150 ns = **0.30 s per second**, 30% of a core;
- after the fix (local): 2 × 10^{6} × 90 ns = **0.18 s per second**, 18% of a core.

The fix saves 0.12 s per second, and each lookup is 60 ns faster, which matters more than the throughput if the lookup is on the critical path. *Verified.*

**At startup:** pin the pricing thread to its socket-0 core first and let *it* allocate and initialize the table, so first touch places the pages on node 0; or bind the table's memory explicitly with `mbind` to node 0 (or run the whole process under `numactl --membind=0` if everything belongs on node 0). **For a running process:** migrate the pages with `move_pages` (for a range of the process's own memory) or `migrate_pages`/`migratepages` (for all of a process's pages between nodes), outside trading hours, since migration takes page faults and TLB shootdowns. Do not rely on automatic NUMA balancing to do it; it is the unpredictable version of the same thing.

### *P13.10

(a) **Classic RT throttling.** The polling thread never blocks, so it uses up the real-time budget of CPU 3: 950 ms out of every 1000 ms period. For the remaining **50 ms of each second** the kernel stops running real-time tasks on that CPU, and the logging thread (and any per-CPU kernel threads) runs. The polling thread sees a gap of up to **50 ms once per second** and loses **5%** of its time. (Older kernels could let a CPU borrow unused real-time budget from other CPUs, which delays or avoids the throttling; current kernels disable that sharing by default.)

(b) **Fair server (Linux 6.12 and later).** Normal tasks that are runnable but starved by real-time tasks get a reserved deadline budget, by default 50 ms per second. The effect for this scenario is similar: when the logging thread has work, the polling thread can be stopped for up to about **50 ms per second (5%)**. When no normal task is runnable on CPU 3, the polling thread keeps the CPU. The interaction with the legacy throttling settings differs between kernel versions, so verify on the target kernel with the jitter tool of Listing 13.6.

(c) Writing **−1** disables the protection. The polling thread then never yields CPU 3: the logging thread starves forever if its affinity allows only CPU 3 (and its queue fills, which may block the producers that log), and per-CPU kernel work on CPU 3 never runs. Kernel threads such as the per-CPU workqueue workers and `ksoftirqd` are normal-priority tasks, so the symptoms are RCU stall warnings, hung-task warnings, and other CPUs blocking when they wait for work queued to CPU 3 (for example a `synchronize_rcu` or a workqueue flush). It can take the whole machine down.

(d) **Isolate CPU 3** (13.6) so that nothing else is runnable there: move the logging thread to a housekeeping CPU, remove CPU 3 from the scheduler's domains with `isolcpus` or a cpuset, and move kernel work off it (`nohz_full`, `rcu_nocbs`, interrupt affinity). With nothing else runnable, the polling thread can stay at normal priority; there is nothing to preempt and nothing to starve. *Budget arithmetic verified.*

### *P13.11

Problems, in order of appearance:

1. **`mlockall(MCL_FUTURE)` before the `mmap`.** With `MCL_FUTURE`, the `mmap` populates and locks the whole mapping immediately, with 4 KiB pages, before `madvise(MADV_HUGEPAGE)` runs; the `madvise` comes too late (at best `khugepaged` collapses the pages later, in the background, during trading). Map, `madvise`, touch, *then* `mlockall`.
2. **No alignment.** THP can only use 2 MiB-aligned 2 MiB blocks; an unaligned mapping gets 4 KiB pages at its ends. Over-allocate and align as in Listing 13.3, or use hugetlbfs pages with `MAP_HUGETLB` reserved at boot (and check for failure).
3. **No error checks.** `mmap` returns `MAP_FAILED`, not `nullptr`; `madvise` and `mlockall` can fail (`RLIMIT_MEMLOCK`). A trading process should refuse to start rather than run untuned.
4. **Pre-faulting from the main thread places the book on the main thread's node** (first touch, 13.7), which is unknown.
5. **The hot threads are on the wrong node.** The NIC is on node 1, but the feed thread is pinned to CPU 2 on node 0, so every packet crosses the socket link. Pin the feed and strategy threads to node-1 cores, and touch the book from a thread pinned to node 1 (or `mbind` it there).
6. **Threads pin themselves after they start.** Each thread first runs wherever the scheduler puts it, and its stack and TLS may be touched there. Set the affinity before the thread runs (`pthread_attr_setaffinity_np` with `pthread_create`), or at least pin first thing and pre-fault the stack afterwards (7.4).
7. **Signals.** `SIGTERM` is not blocked in the hot threads, so its handler may run on the feed or strategy thread at any moment; and a `std::signal` handler may only do async-signal-safe things (set a `volatile std::sig_atomic_t` or lock-free atomic flag). Block all asynchronous signals in `main` with `pthread_sigmask` *before* creating threads (they inherit the mask), and handle them in a dedicated thread with `sigwait`.
8. **No warm-up.** The first clock read, first use of every code path and the first touch of each thread's stack fault or miss on the first market-data message. Warm up and then check, with fault and context-switch counters, that the hot loop takes none.

A corrected outline: block signals; pin the main thread to a node-1 housekeeping core; map an aligned region (or hugetlbfs); `madvise`; touch it from the node-1 thread; `mlockall`; create the feed and strategy threads with node-1 affinity set at creation; pre-fault their stacks and warm their paths; start a signal-handling thread; verify the counters; only then start trading.
