## Chapter 9: Compile-Time Programming

### *P9.1

Namespace `a`: `f(1)` → **"f(int)"** (a non-template exact match beats a template with the same conversion sequence). `f(&i)` → **"f(T*)"** (both templates match; `f(T*)` is more specialized by partial ordering). `f(&c)` → **"specialization"**. `f(1.5)` → **"f(T)"**.

Namespace `b`: `f(&c)` → **"f(T*)"**.

The difference: an explicit specialization is *not* an overload. It specializes whichever primary template it matches *at the point where it is declared*, and overload resolution then chooses among primary templates only. In `a`, both primaries are visible when `template <> f(char*)` is declared, and it matches `f(T*)` with `T = char` more specifically, so it specializes `f(T*)`; resolution picks `f(T*)` and uses its specialization. In `b`, only `f(T)` exists when the specialization is declared, so it specializes `f(T)` with `T = char*`; resolution later picks the more specialized primary `f(T*)`, and the specialization of `f(T)` is never used. The practical rule: do not specialize function templates; overload them. *Verified* (verification program below).

### *P9.3

```cpp
template <class T, class... Ts>
inline constexpr bool is_one_of_v = (std::is_same_v<T, Ts> || ...);
template <class T, class... Ts>
inline constexpr bool all_same_v = (std::is_same_v<T, Ts> && ...);
```

With an empty `Ts`, the `||` fold gives **false** (T is not one of nothing) and the `&&` fold gives **true** (a single type is "all the same"), by the empty-fold rules of Section 9.6. Both answers are the mathematically sensible ones, which is why those two operators were given identity values. *Verified* by `static_assert`.

### *P9.4

```cpp
template <class T, template <class...> class Tmpl>
struct is_specialization_of : std::false_type {};
template <template <class...> class Tmpl, class... Args>
struct is_specialization_of<Tmpl<Args...>, Tmpl> : std::true_type {};
```

The partial specialization matches when `T` can be deduced as `Tmpl<Args...>` for the *same* `Tmpl` passed as the second argument. `std::vector<int>` is really `std::vector<int, std::allocator<int>>`; the pack `Args...` absorbs both arguments.

It does not work for `std::array<int, 4>` because `std::array`'s second parameter is a value (`std::size_t N`), not a type, so `std::array` cannot bind to a template template parameter declared as `template <class...> class`. A pack of types cannot mix with non-type parameters. You need a separate trait for each shape, e.g. `template <class T, std::size_t N> struct is_std_array<std::array<T, N>>`. *Verified* by `static_assert` for vector, list and tuple.

### *P9.5

(a) `g(1)` → **2**: both overloads are satisfied, and `std::integral<T> && Small<T>` subsumes `std::integral<T>` because it is the conjunction of the same named concept with another constraint. `g(1L)` → **1**: `long` is 8 bytes, so `Small` fails and only the first overload is viable. `g(short{1})` → **2**. *Verified.*

(b) `h(1)` is **ambiguous** and does not compile. Atomic constraints are identical only if they come from *the same appearance* of an expression in the source. The two occurrences of `std::is_integral_v<T>` are different atomic constraints, so the compiler cannot prove that the second overload's constraint implies the first's; neither is more constrained, and both are viable. GCC 13: "call of overloaded 'h(int)' is ambiguous". The fix is to name the shared part as a concept (or use `std::integral`), so both overloads refer to the same concept. *Verified* by compiling.

### *P9.6

```cpp
constexpr auto kCrcTable = [] {
    std::array<std::uint32_t, 256> t{};
    for (std::uint32_t i = 0; i < 256; ++i) {
        std::uint32_t c = i;
        for (int k = 0; k < 8; ++k) c = (c & 1) ? 0xEDB88320u ^ (c >> 1) : c >> 1;
        t[i] = c;
    }
    return t;
}();
constexpr std::uint32_t crc32(std::string_view s) {
    std::uint32_t c = 0xFFFFFFFFu;
    for (char ch : s) c = kCrcTable[(c ^ static_cast<unsigned char>(ch)) & 0xFF] ^ (c >> 8);
    return c ^ 0xFFFFFFFFu;
}
static_assert(crc32("123456789") == 0xCBF43926u);
```

Each table entry is the CRC of one byte, computed bit by bit; the run-time loop then processes a byte per table lookup. The initial value and final XOR of `0xFFFFFFFF` are part of the standard CRC-32 definition, and `0xCBF43926` is its published check value for the ASCII string "123456789". The table costs 1 KB of `.rodata` and no startup time. (On x86-64 with SSE4.2 there is a `crc32` instruction, but it implements the Castagnoli polynomial CRC-32C, not this one.) *Verified* by `static_assert` and at run time.

### *P9.7

```cpp
template <class Tuple, std::size_t... I>
constexpr auto reverse_impl(Tuple&& t, std::index_sequence<I...>) {
    constexpr std::size_t N = sizeof...(I);
    return std::make_tuple(std::get<N - 1 - I>(std::forward<Tuple>(t))...);
}
template <class... Ts>
constexpr auto tuple_reverse(const std::tuple<Ts...>& t) {
    return reverse_impl(t, std::index_sequence_for<Ts...>{});
}
```

The pattern `std::get<N - 1 - I>(t)` is expanded once per index, producing the elements from last to first. For the empty tuple, `I...` is empty, `N` is 0, the expansion produces no arguments, and `std::make_tuple()` returns `std::tuple<>`; `N - 1` is never evaluated because nothing is expanded. (Note: `std::make_tuple` decays its arguments, so a tuple of references comes back as a tuple of values; use `std::tuple<std::tuple_element_t<N-1-I, ...>...>` to preserve the exact types.) *Verified* by `static_assert`.

### *P9.8

```cpp
template <class Derived>
class InstanceCounter {
public:
    static long live() { return live_; }
private:
    InstanceCounter() { ++live_; }
    InstanceCounter(const InstanceCounter&) { ++live_; }
    ~InstanceCounter() { --live_; }
    friend Derived;
    static inline long live_ = 0;
};
struct Widget : InstanceCounter<Widget> {};
```

Each instantiation `InstanceCounter<Widget>`, `InstanceCounter<Gadget>` has its own static member, which is why the counts are independent: the CRTP parameter's only job here is to make the base a *different type* per derived class. The copy constructor must be user-provided, or copies would not be counted. The destructor is not virtual, which is correct: nobody should delete a `Widget` through an `InstanceCounter<Widget>*` (and the private destructor prevents it from outside the class). The private constructor plus `friend Derived` rejects `struct Oops : InstanceCounter<Widget> {}` at the point an `Oops` is constructed. `live_` is a plain `long`; if objects are created on several threads it must be `std::atomic<long>` (Section 14.2). *Verified*: with two widgets, one copy and one gadget alive, the program prints 3 and 1, then 2 and 1 after the copy dies, then 0.

### *P9.9

(a) **31**: `Fib<0>` through `Fib<30>`, two of them the explicit specializations and 29 implicit instantiations. A class template specialization is instantiated once per translation unit and then reused, so the compiler effectively memoizes the recursion: `Fib<28>` is requested by both `Fib<30>` and `Fib<29>` but created once.

(b) Let C(n) be the number of calls. C(0) = C(1) = 1 and C(n) = 1 + C(n − 1) + C(n − 2), which gives C(n) = 2F(n + 1) − 1 where F is the Fibonacci sequence. F(31) = 1,346,269, so C(30) = **2,692,537** calls. *Verified* by counting at run time.

(c) Because of (a): template instantiation is cached, so the template computes each value once, 31 instantiations in total. For the `constexpr` function, the language says nothing about caching; GCC does cache the results of some `constexpr` calls during constant evaluation, but that is an implementation detail. If you write recursion at compile time, write it with memoization or as a loop, as you would at run time; the `constexpr` interpreter is far slower per operation than compiled code.

### *P9.10

**a = 377** for m = 8, and **a = 1** for m = 16. With a = 377 the slots are NewOrder 1, Cancel 0, Replace 7, Trade 5, Heartbeat 3, Logon 6, Logout 4, Reject 2: a *minimal perfect hash* for this key set. The search is a `consteval` function that tries odd multipliers in order and tests each candidate with a 64-bit occupancy mask:

```cpp
consteval std::uint32_t find_multiplier(int lg) {
    for (std::uint32_t a = 1; a < 100'000; a += 2) {
        std::uint64_t used = 0;
        bool ok = true;
        for (auto k : kKeys) {
            const std::uint32_t slot = (fnv1a(k) * a) >> (32 - lg);
            if ((used >> slot) & 1) { ok = false; break; }
            used |= std::uint64_t{1} << slot;
        }
        if (ok) return a;
    }
    return 0;
}
```

Why it is reasonable to expect a solution quickly: for a random function, the probability that 8 keys land in 8 distinct slots of 8 is 8!/8^{8} ≈ 0.0024, so on the order of 400 trials are expected; the search found one at the 189th odd multiplier. For 16 slots the probability is 16!/(8! × 16^{8}) ≈ 0.12, and the very first multiplier works. The search runs in the compiler, well inside GCC's loop limit; at run time, looking up a message name is one hash, one multiply, one shift, one table load and one string compare to reject names not in the set. *Verified.*

### *P9.11

```cpp
using Fn = void (*)(const unsigned char*);
template <class... Msgs>
constexpr std::array<Fn, 256> make_table() {
    std::array<Fn, 256> t{};
    t.fill(&unknown);
    ((t[static_cast<unsigned char>(Msgs::kType)] = &handle<Msgs>), ...);
    return t;
}
constexpr auto kTable = make_table<Add, Cancel, Trade>();
// dispatch: kTable[type](body);
```

Each `handle<M>` decodes its payload (with `memcpy`) and calls the user's handler for `M`. The table is built by the compiler and occupies 2 KB of `.rodata` (256 eight-byte pointers). Work per message: one load from the table (L1 or L2 resident if dispatch is frequent) and one indirect call, independent of the number of types. The fold-of-compares version of Listing 9.6 does up to k compares for k types but makes direct, inlinable calls. For a handful of types with a skewed mix (most messages being adds and cancels, as in many feeds), the compare chain with the common types first is typically as fast or faster; as k grows, or when the mix is unpredictable, the table wins because its cost does not grow and it has one indirect branch instead of a chain of conditional ones. A `switch` on the type byte lets the compiler pick between a compare chain and a jump table itself, and keeps the handlers inlinable, which is why hand-written `switch` dispatch remains common in feed handlers (Section 18.2). Measure with the real message mix. *Verified*: the program dispatches "AXTTZA" and counts 2 adds, 1 cancel and 2 trades, with 'Z' going to the default handler.
