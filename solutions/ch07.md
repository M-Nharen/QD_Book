## Chapter 7: Memory Management

### *P7.1

A chunk for *n* bytes is max(32, round up (n + 8) to a multiple of 16), and the usable size is the chunk size minus 8 (the following chunk's "previous size" field is usable while this chunk is in use):

| n | n + 8 rounded up to 16 | chunk | usable |
|---|---|---|---|
| 0 | 16 | 32 (minimum) | **24** |
| 24 | 32 | 32 | **24** |
| 25 | 48 | 48 | **40** |
| 56 | 64 | 64 | **56** |
| 57 | 80 | 80 | **72** |
| 1000 | 1008 | 1008 | **1000** |

General formula: usable(n) = max(32, (n + 23) & ~15) − 8. *Verified* with `malloc_usable_size` (the check is skipped under AddressSanitizer, whose allocator reports the requested size instead).

### *P7.3

1 GiB / 4 KiB = 2^{30} / 2^{12} = **262,144 faults**. With 2 MiB pages: 2^{30} / 2^{21} = **512 faults**. At 1.5 µs per fault, the 4 KiB case takes 262,144 × 1.5 µs ≈ **0.39 s** of fault handling. Huge pages cut the number of faults by 512×, but each huge-page fault zeroes 2 MiB, so the time falls by much less (Listing 7.4 shows this). *Verified.*

### *P7.4

(a) The cookie is max(sizeof(size_t), alignof(T)) = max(8, 8) = 8 bytes. Request: 5 × 24 + 8 = **128 bytes**, through `operator new[](std::size_t)`.

(b) The cookie is max(8, 32) = 32 bytes, so that the array that follows it stays 32-byte aligned. Request: 5 × 32 + 32 = **192 bytes**. Because alignof(T) = 32 exceeds `__STDCPP_DEFAULT_NEW_ALIGNMENT__` (16), the call is **`operator new[](std::size_t, std::align_val_t)`** with alignment 32. *Verified* with replaced allocation functions that record the requested size.

### *P7.5

| Request (size, align) | Cursor before | Aligned offset | Cursor after |
|---|---|---|---|
| (1, 1) | 0 | **0** | 1 |
| (8, 8) | 1 | **8** | 16 |
| (2, 2) | 16 | **16** | 18 |
| (64, 64) | 18 | **64** | 128 |
| (4, 4) | 128 | **128** | 132 |
| (16, 16) | 132 | **144** | 160 |

**160 bytes used** for 95 bytes of data: 65 bytes of padding. Allocating in decreasing order of alignment (64, 16, 8, 4, 2, 1) places every object at an offset that is already aligned, using exactly **95 bytes**, which saves all 65 bytes of padding. It is the same rule as ordering struct members (Section 6.1). *Verified.*

### *P7.6

`std::make_shared` puts each 1 MiB `Snapshot` inside the same allocation as its control block. When the last subscriber's `shared_ptr` goes away, the snapshot's destructor runs, but the allocation cannot be freed while any `weak_ptr` still refers to the control block, and the cache holds one `weak_ptr` per snapshot it has ever stored. So every snapshot's 1 MiB stays allocated for as long as its cache entry exists. If entries are keyed by something that keeps changing (sequence number, timestamp), the cache never removes them, and memory grows without bound.

Fixes (any two):

1. **Separate the object from the control block:** create snapshots with `std::shared_ptr<Snapshot>(new Snapshot(...))`. Then the 1 MiB is freed when the last `shared_ptr` dies; only the small control block lives on with the `weak_ptr`.
2. **Remove expired entries:** on each lookup or periodically, erase entries whose `weak_ptr::expired()` is true. This fixes the unbounded growth of the cache itself, which is a bug even with fix 1.
3. **Redesign for the hot path:** keep a fixed number of pre-allocated snapshot buffers in a ring, published with a sequence number (a seqlock, Section 14.7), so readers copy what they need and nothing is allocated or reference-counted per update.

### *P7.7

Allocations, in execution order (exact counts depend on string lengths):

1. `symbol + ":"` creates a temporary string, and appending `std::to_string(qty)` creates the key. Any string over 15 characters allocates. The key is also hashed, character by character, on every call.
2. `book[key]` allocates a node (and copies the key into it) whenever the key is new, and may rehash, allocating a new bucket array.
3. `v.push_back(Order{})` allocates whenever the vector is full. Worse, the vector grows by one element per message forever: a memory leak by design.
4. `std::make_shared<Order>(v.back())`: one allocation, plus copying 64 bytes.
5. On the error path: `"bad price " + std::to_string(px)` allocates (19+ characters), `std::invalid_argument` copies the message into its own reference-counted string (another allocation), and `throw` allocates the exception object with `malloc`, then unwinds (microseconds; Section 8.6).
6. `cb` is a `std::function` taken *by value*: if the caller passes an existing `std::function`, it is copied, which allocates when its target is stored on the heap.

Other avoidable costs: `cb(p)` copies the `shared_ptr` into the parameter (two atomic count updates in a multi-threaded process); calling through `std::function` is an indirect call that cannot be inlined; `double` prices invite rounding problems (Section 5.7); string keys where an integer instrument ID would do.

A hot-path version takes an integer instrument ID and an integer price, looks up a pre-sized open-addressing table (Section 10.5) or an array indexed by ID, writes the order into a pool slot, reports invalid input with a return code, and invokes a callback passed as a template parameter (or a non-owning function reference, Section 8.7) with an `Order&`.

### *P7.8

**What happens.** The feed thread is attached to one arena (A) and the strategy thread usually to another (B). Each `new` in the feed thread first looks in the feed thread's tcache. Each `delete` in the strategy thread puts the chunk into the *strategy* thread's tcache until that size's list holds 7 entries; after that, each `free` must lock arena A (the chunk's owner) and return the chunk to A's bins. The strategy thread never allocates messages, so its tcache entries are never used. The feed thread's tcache is never refilled by frees, so after its first few allocations every `new` goes to arena A under the lock, competing with the strategy thread's frees for the same lock. In addition, every chunk's header and contents migrate between the two cores' caches: the producer writes it, the consumer reads it, the consumer's `free` writes free-list pointers into it, and the producer's next `malloc` reads them back (Section 12.3). The result is extra latency on both threads and occasional long stalls when one thread holds the lock or the allocator consolidates.

**Fixes.**

1. **Pre-allocated ring of message slots.** Replace pointer passing with a single-producer single-consumer ring buffer whose slots hold the message itself (Section 14.5). The producer decodes directly into the next free slot; the consumer reads in place and advances the read index. No allocation at all, and the memory is reused in a fixed, cache-friendly pattern.
2. **Return-to-owner pool.** Keep a pool owned by the feed thread. The consumer, instead of calling `delete`, sends the slot back through a second SPSC queue; the producer drains that queue and pushes the slots onto its own free list. Only the owning thread ever touches the free list.

A different general-purpose allocator with better cross-thread handling would reduce the cost but not remove it.

### *P7.9

`std::vector` and `std::map` instantiate the allocator for different types: the vector allocates `int`, but the map allocates internal tree nodes, so it *rebinds* `ArenaAllocator<std::pair<const int, long>>` to `ArenaAllocator<Node>`. The converting constructor template is what makes that rebinding possible: `allocator_traits` builds the node allocator from the one you passed. `operator==` must return true exactly when memory allocated through one allocator can be deallocated through the other, which for this design means "same arena". Containers rely on it in move assignment and `swap`. Everything else (`pointer`, `size_type`, `rebind`, `construct`, `destroy`) has correct defaults in `std::allocator_traits` since C++11, so a C++20 allocator needs only `value_type`, `allocate`, `deallocate`, the converting constructor and equality.

### *P7.11

**Change the code.**

- Inventory the hot path: every function reachable from the market-data callback to order send.
- Replace allocations there with pre-sized structures: pools for orders, arenas for per-message scratch, reserved vectors, open-addressing tables sized for the worst case, integer IDs instead of strings, `string_view`/`span` parameters, template or function-reference callbacks, error codes instead of exceptions, binary logging into a pre-allocated ring (Section 18.5).
- At startup: allocate everything, write every page (or `mlockall(MCL_CURRENT | MCL_FUTURE)`), pre-fault thread stacks, set `M_TRIM_THRESHOLD`/`M_MMAP_THRESHOLD` so the allocator does not return memory, then run a warm-up that executes each hot-path branch once.

**Unit tests.** Link a replacement global `operator new` (all forms, including `nothrow` and aligned) with a thread-local "hot" depth, as in Listing 7.8; wrap each hot-path entry point in the guard; abort with a stack trace on any allocation. Include error paths and rare branches (book empty, price at limit, reject) in the tests, because that is where allocations hide.

**Integration and staging.** Replay recorded market data through the full process with an `LD_PRELOAD` interposer for `malloc`/`calloc`/`realloc`/`free`/aligned variants that checks the same thread-local flag, and separately with a uprobe on `malloc` (`perf probe` or `bpftrace`) counting calls by stack from the trading threads. Track page faults per thread (`perf stat -e minor-faults`, or `getrusage` with `RUSAGE_THREAD`) during the replay: they should be zero after warm-up.

**Production.** Export counters: allocator statistics (`mallinfo2()` or the allocator's own), minor-fault counts per trading thread, and latency percentiles. An allocation regression shows up as counters growing with message count; alert on any change after warm-up.

**What the detection misses.** An `operator new` hook misses `malloc` from C code and the exception runtime; a `malloc` interposer misses allocations made with direct `mmap`/`brk` calls and anything inside the kernel (socket buffers, page tables). Neither catches page faults on memory allocated *before* the hot path but touched for the first time during it, nor stalls that are not allocations (system calls, locks, cache misses), so keep the page-fault and latency monitoring as well. Tests also only cover the paths they exercise, which is why replaying real data matters.
