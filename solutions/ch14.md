## Chapter 14: Concurrency

### *P14.1

(a) **Yes.** With everything `relaxed`, nothing synchronizes, so seeing `flag == 1` implies nothing about `data`.

(b) **No.** The release store of `flag` and the acquire load that reads 1 synchronize, so `data.store(42)`, sequenced before the release, happens before `data.load`, which must return 42 (relaxed operations are ordered by the surrounding release/acquire pair).

(c) **Yes.** The acquire is on the wrong load. Acquire on `data` would only synchronize with a release store *to `data`*, and there is none; the relaxed load of `flag` synchronizes with nothing.

(d) **No.** A `seq_cst` store is also a release and a `seq_cst` load also an acquire, so this is case (b) with extra guarantees.

(e) In hardware, no: x86-TSO never reorders two stores, or two loads, so if the instructions are emitted in program order, r = 0 is impossible. But the program is still wrong. Relaxed operations impose no ordering on other memory, so the compiler is *allowed* to emit the two stores, or the two loads, in the other order; current g++ is conservative and in practice does not reorder atomic operations with each other, so you would very probably not observe r = 0 on x86 today. On AArch64, where relaxed accesses compile to plain `str`/`ldr`, the hardware itself produces r = 0. "It works on x86" is not a correctness argument.

### *P14.2

(a) **No race:** different objects.

(b) **Race.** The control block's reference count is atomic, but the `shared_ptr` object `p` itself (two pointers) is written by one thread and read by the other without synchronization. Use `std::atomic<std::shared_ptr<Config>>` (C++20; not lock-free in libstdc++), a mutex, or publish through a seqlock-protected index into pre-built configs.

(c) **No race:** each `int` element is its own memory location. Neighbouring elements written by different threads can false-share (14.4), which is a performance problem only.

(d) **Race.** `std::vector<bool>` packs elements into bits of shared words, so writing one element is a read-modify-write of a word that holds others (solution to P10.4 shows it losing updates).

(e) **Race.** Adjacent non-zero-width bit-fields form one memory location (14.2); writing `a` is a read-modify-write of the byte that also holds `b`. Separate them with a zero-width bit-field (`unsigned : 0;`) or make them separate members.

(f) **No race.** Initialization of a function-local static is thread-safe since C++11: one thread runs `build()`, the others wait on the guard (5.3). (Later unsynchronized *writes* to `t` would race.)

### *P14.3

(a) 2^{64} / 10^{9} s ≈ **584.5 years**: 64-bit counters never wrap in practice, which is why the ring of Listing 14.4 needs no wrap handling at all.

(b) 2^{32} / 10^{8} s ≈ **42.95 s**. The wrap is **harmless** with a power-of-two capacity: 1024 divides 2^{32}, so `counter & 1023` continues 1021, 1022, 1023, 0, 1, … across the wrap exactly as if the counter had not wrapped, and `tail - head` in 32-bit unsigned arithmetic is the true difference modulo 2^{32}, which is correct whenever the true occupancy is below 2^{32}.

(c) 2^{32} mod 1000 = **296**. Just before the wrap the counter 2^{32} − 1 maps to slot 295; after it, counter 0 maps to slot 0 instead of 296. The producer skips slots 296–999 and starts overwriting slot 0, which may still hold unconsumed items, and the consumer, which wraps at a different moment, reads slots the producer never wrote. *Verified* by the program at the end of this section. Either use power-of-two capacities, or 64-bit counters, or reduce the counters modulo the capacity explicitly (and then handle full/empty with an extra slot or flag).

### *P14.4

Five bugs:

1. **Data race:** the producer writes `job` and `ready` without holding `m` while the consumer reads them under `m`. Undefined behaviour.
2. **Lost wake-up:** because the producer does not hold the mutex, it can set `ready` and notify between the consumer's check of `!ready` and its call to `wait`. The notification finds no waiter and the consumer sleeps forever.
3. **`if` instead of a loop:** after a spurious wake-up the consumer runs `job` with `ready` still false.
4. **Work under the lock:** `run(job)` holds `m` for 50 µs, blocking the producer for that long.
5. **No back-pressure:** a second `producer` call can overwrite `job` before the consumer has taken the first.

A correct version (one slot; for more, use the queue of Listing 14.1):

```cpp
std::mutex m;
std::condition_variable has_job, has_space;
bool ready = false;                                   // guarded by m
Job job;                                              // guarded by m
void producer(Job j) {
    {
        std::unique_lock lk(m);
        has_space.wait(lk, [] { return !ready; });    // back-pressure
        job = std::move(j);
        ready = true;
    }
    has_job.notify_one();
}
void consumer() {
    Job mine;
    {
        std::unique_lock lk(m);
        has_job.wait(lk, [] { return ready; });       // predicate: loops
        mine = std::move(job);
        ready = false;
    }
    has_space.notify_one();
    run(mine);                                        // outside the lock
}
```

### *P14.5

With release stores and acquire loads, the lock **fails**: in the printed run of the program below, 128 of 4,000,000 increments were lost, so both threads were inside the critical section at the same time. With `seq_cst` stores and loads, none were lost.

The failure is the store-buffering pattern of Section 14.3. Thread 0's stores to `flag[0]` and `victim` enter its store buffer; its next load reads `flag[1]` from cache, where thread 1's store is still invisible because it is sitting in *thread 1's* store buffer. Both threads read the other's flag as false and both enter. Release/acquire cannot prevent this: no load reads a value written by the other thread's release, so nothing synchronizes, and in the C++ model the outcome is allowed.

The minimal fix is to order each thread's stores before its loads: make the stores `seq_cst` (on x86 the store to `victim` becomes `xchg`, which drains the store buffer), or keep the stores as they are and put `std::atomic_thread_fence(std::memory_order_seq_cst)` between the stores and the loop. The loads may then stay `acquire`. Peterson's lock is a classic exam question; in production, use a real mutex or spinlock, which needs only one RMW.

### *P14.6

The program below is the solution.

- **`lock`** first tries `exchange(true, acquire)`. If that fails, it waits with **plain loads** (`relaxed`), which keep the line in Shared state in the waiter's cache, so waiting generates no traffic until the holder's unlock invalidates it. Each round of waiting runs a growing number of `pause` instructions (bounded at 64) so that several waiters do not all retry the moment the lock is released.
- **Memory orders.** The successful `exchange` is `acquire`, so nothing in the critical section moves before it; `unlock` is a `release` store, so nothing moves after it. The pair gives the next owner everything the previous owner wrote. The waiting loads can be `relaxed` because they only decide when to retry; the ordering comes from the acquire exchange that follows.
- **`try_lock`** reads first and attempts the exchange only if the lock looks free, so polling a held lock does not take the line exclusively.

- **Naive exchange loop, about 90 ns:** every waiting iteration is a locked RMW that takes the line exclusively, so the waiter steals the line from the holder over and over, and the holder's unlock and next lock both wait for it.
- **TTAS with backoff, about 19 ns:** the waiter reads a shared copy and backs off, so the holder usually keeps the line and re-acquires the lock without a transfer. Part of this speed is *unfairness*, like the mutex barging of Section 14.1: long runs of acquisitions by one thread. For a fair lock, use a ticket lock (one `fetch_add` to take a ticket, then wait for `now_serving` to reach it), at the cost of a line transfer per handoff.
- **`std::mutex`, about 50 ns:** under contention the waiter sleeps in the kernel, and each wake-up costs microseconds; throughput stays reasonable only because handoffs are rare.

### *P14.7

(a) The strategy runs continuously from the first arrival, completing one message every 250 ns. The last arrival is at 49,999 × 100 ns = 4,999,900 ns; by then the strategy has finished 19,999 messages and popped the 20,000th, so **30,000** messages are in the ring (the event simulation in the verification program counts 30,001, including the one being processed). The smallest power of two that holds them is **32,768** (2^{15}); with 32-byte messages that is 1 MiB of slots.

(b) Processing is back to back from time 0, so the last message finishes at 50,000 × 250 ns = **12.5 ms**. *Verified* by the simulation.

(c) It arrived at 4.9999 ms and finished at 12.5 ms, a latency of about **7.5 ms**, against 250 ns for a message that finds the ring empty. A ring absorbs bursts without loss, but every queued message adds the consumer's service time to the latency of those behind it. When only the latest state matters (a quote for one instrument), conflating to the latest value (a seqlock per instrument) bounds the staleness instead of growing a queue.

### *P14.8

(a) A first attempt retries if its 30 ns window overlaps a 20 ns write window. With writes starting every 1000 ns, the read start times that overlap a write starting at w form the interval (w − 30, w + 20), 50 ns long, so P(retry) = 50/1000 = **0.05**. With independent attempts, the number of attempts is geometric, with mean 1/(1 − 0.05) = **≈ 1.053**. *Verified* by Monte Carlo (10^{7} trials, fixed seed) in the verification program.

(b) The counter stays odd, so every reader spins (Listing 14.6, lines 43–47) until the writer runs again, which may be a full scheduler time slice, milliseconds. Readers that cannot afford that should bound their spin and fall back to the last good copy, and the writer should run on a dedicated core so that it is not preempted.

(c) Both writers can read the same even value s and both store s + 1. Suppose writer A finishes first and stores s + 2 while writer B is still writing data. A reader now sees the even value s + 2, starts copying, and reads some of B's words; then B stores s + 2 again, so the reader's second load also returns s + 2. The counter did not change between the reader's loads, so it accepts a record mixing A's and B's data. Serialize writers with a mutex or spinlock around `store`, or make the odd transition a CAS from an even value so that a second writer must wait.

### *P14.9

(a) Every successful push needs the `enq_` line in Modified state on the pushing core (the CAS), and a successful CAS from a different core than the previous one requires a line transfer. One line can therefore support at most about 1 / 60 ns = **16.7 million** successful CAS operations per second, **however many producers** there are. (The slot lines add more transfers, so the real figure is lower.) *Verified arithmetic* in the verification program.

(b) It rises. While one producer's CAS succeeds, every other producer that read the same `enq_` value fails, reloads and retries, and each retry also needs the line, competing with the next successful CAS. Total throughput stays flat or *falls* as producers are added; even on two CPUs, the test below measured the cost per message rising as producers and consumers were added.

(c) One SPSC ring per producer (Listing 14.4), with the consumer polling the four rings in turn: no line is written by more than one thread, so total throughput grows with the number of producers until the consumer saturates. It gives up a single global FIFO order (if needed, merge by sequence number or timestamp), costs one ring of memory per producer, and makes the consumer's empty poll cost grow with the number of rings.

### *P14.10

(a) T1 reads head = (A, tag t) and A's `next` = B, then stalls. T2 and T3 perform successful pushes and pops, each incrementing the tag, until A is back on top. If exactly 65,536k successful operations (any positive integer k) have happened since T1's read, the tag is back to t. T1's CAS then succeeds and installs B, which T2 or T3 may be using, as in Listing 14.7's untagged case.

(b) 2^{16} / (25 × 10^{6} s^{−1}) = **2.62 ms**. A thread preempted for a 4 ms time slice spans more than a full wrap, so the tag can be back at its old value. A collision also needs A to be on top at that exact moment, so it is rare, but at 25 million operations per second over months, rare events happen; a 16-bit tag is **not safe** unless threads cannot be preempted.

(c) 2^{20} nodes need 20 index bits, leaving **44 tag bits**: 2^{44} / (25 × 10^{6}) s ≈ 703,687 s ≈ **8.1 days** per wrap. A thread would have to stall for days between two instructions, so this is safe in practice. *Verified* in the verification program.

### *P14.11

The program below gives each slot its own seqlock-style counter: the writer stores 2n + 1 into slot n mod N while writing message n and 2n + 2 when done (lines 39–42), so a counter value identifies both the message number and whether it is complete. A reader that wants message n:

- sees a counter below 2n + 2: not yet written, try again (line 50);
- sees exactly 2n + 2: copies the words, then re-checks the counter after an acquire fence (lines 53–55). Unchanged means a consistent copy of message n;
- sees a counter above 2n + 2, or a changed counter after the copy: the writer has lapped it. The reader counts the messages it skipped and resynchronizes half a lap behind the newest message, which is still in the ring, rather than at the newest, where it would immediately be overrun again.

The writer never reads anything the readers write, so it never waits, and any number of readers add no load to it beyond reading its lines.

Reader 0, on its own CPU, receives most messages but is still overrun at times: copying four atomic words, fencing and re-checking per message is slower than the writer's tight publish loop, and the writer does not wait. Reader 1 shares the writer's CPU and gets only the scheduler's time slices in which to read; it yields when it finds nothing new, otherwise it would spin away the time slice the writer needs to produce the message it is waiting for. In a real system, each consumer would be on its own core, and a consumer that is overrun raises an alarm and recovers from a snapshot (17.4).

### *P14.12

Load: 8 × 200,000 = 1.6 million records per second, 102 MB/s.

**(a) Mutex-protected vector, swapped by the logger.** Hot path: a contended mutex shared by nine threads (tens of ns uncontended, microseconds whenever a thread sleeps) plus `push_back`, which allocates whenever the vector grows. During a 100 ms disk stall the vector keeps growing (allocation and page faults on the hot path) or, if capped, the strategies must block or drop. Ordering: the logger sorts each swapped batch by timestamp; records stamped just before a swap but appended just after it can still be out of order across batches, so a short reorder window is needed.

**(b) One MPMC queue.** Hot path: a CAS on a line written by eight producers, so each push costs a contended line transfer, tens to hundreds of ns, and throughput is capped by that line (P14.9); a producer preempted mid-push stalls the logger. A disk stall fills the queue, and producers must drop or block. Ordering: queue order is enqueue order, not timestamp order (a thread can be delayed between stamping and pushing), so the logger still needs a reorder window.

**(c) Eight SPSC rings (recommended).** Hot path: a slot write and a release store, no RMW and no contention, tens of ns or less. Size each ring for the stall: 200,000 records/s × 0.1 s = 20,000 records, so **32,768 slots** of 64 bytes = **2 MiB per ring, 16 MiB in total**, pre-faulted at startup (7.4). If a ring is nevertheless full, the strategy drops the record and increments a counter, never blocks. Ordering: the logger performs an 8-way merge by timestamp with a small heap. It may emit a record with timestamp T only when every ring either has a pending record with timestamp ≥ T or is empty and its producer's published "low-water" timestamp (a per-ring atomic updated by the producer) is ≥ T, so a slow producer cannot inject an earlier record later.
