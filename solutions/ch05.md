## Chapter 5: C++ Foundations Bridge

### *P5.1

Both operands are promoted to `int` before the addition, so `c` is an **`int` with value 260**. Assigning 260 to a `std::uint8_t` keeps it modulo 256, so **`d` is 4**. Neither `-Wall` nor `-Wextra` warns, because an implicit narrowing conversion in an assignment is legal C++. Only `-Wconversion` (not part of either set) reports it. Braces would have caught it: `std::uint8_t d{a + b};` does not compile, because `a + b` is an `int` that is not a constant expression. *Verified.*

### *P5.2

When `v` is empty, `v.size() - 1` wraps to 2^{64} − 1, so the first access is far out of bounds. And for *any* `v`, `i >= 0` is always true for an unsigned `i`: after `i = 0`, `--i` wraps to 2^{64} − 1 and the loop continues out of bounds instead of stopping. `-Wextra` warns about the second bug ("comparison of unsigned expression in '>= 0' is always true", `-Wtype-limits`). Correct versions:

```cpp
for (std::size_t i = v.size(); i-- > 0; ) use(v[i]);                 // test, then decrement
for (std::ptrdiff_t i = std::ssize(v) - 1; i >= 0; --i) use(v[i]);   // C++20 signed size
for (auto it = v.rbegin(); it != v.rend(); ++it) use(*it);            // reverse iterators
for (int x : v | std::views::reverse) use(x);                         // C++20 ranges
```

### *P5.3

`~S() = default;` is still a *user-declared* destructor. `S` therefore has a default constructor, the destructor, a copy constructor and a copy assignment operator (the last two generated, though that generation is deprecated), and **no move constructor or move assignment**: they are not declared at all. `std::is_nothrow_move_constructible_v<S>` is **false**, because constructing an `S` from an rvalue selects the copy constructor, which copies a `std::string` and may throw. Consequences: `std::move(s)` copies, and `std::vector<S>` copies every element when it reallocates, one heap allocation per element whose string exceeds the small-string buffer. Remove the destructor, or default all five special members. *Verified* with type traits.

### *P5.4

**−3, −1, −3, 1, −4.** Division truncates toward zero and the remainder takes the sign of the dividend, so that (a / b) × b + a % b = a holds: (−3)(2) + (−1) = −7 and (−3)(−2) + 1 = 7. The arithmetic right shift rounds toward negative infinity, so −7 >> 1 = −4 ≠ −7 / 2. *Verified.*

### *P5.5

(a) Declares a **function** `t` taking no arguments and returning `Timer`. (b) Declares a **function** `w` returning `Widget`, whose parameter has type "function returning `Gadget`", which adjusts to a pointer to such a function. (c) `v(10, 0)` is **ten zeros**; `v{10, 0}` is **two elements, 10 and 0**, because braces prefer the `initializer_list` constructor. (d) `s(3, 'x')` is **"xxx"**; `s{3, 'x'}` is **the two characters `'\x03'` and `'x'`** (the integer constant 3 converts to `char` without narrowing because it fits). Fixes for (a) and (b): `Timer t{};` (or `Timer t;`) and `Widget w{Gadget{}};`. *Verified* for (c) and (d).

### *P5.6

Each of `risk.o` and `router.o` contains a definition of `g_max_qty` (symbol type D) and of `clamp_qty(int)` (type T). Compilation succeeds; **linking fails** with "multiple definition of `g_max_qty`" and "multiple definition of `clamp_qty(int)`".

- **Function:** mark it `inline` in the header, or declare it in the header and define it in one `.cpp`.
- **Variable:** if it is a run-time setting, write `extern int g_max_qty;` in the header and `int g_max_qty = 1000;` in exactly one `.cpp`, or `inline int g_max_qty = 1000;` in the header (C++17). If it is truly a constant, `inline constexpr int kMaxQty = 1000;`.
- **Why `static` is wrong for the variable:** it gives each TU its *own* `g_max_qty`. The program links, but if start-up code in `risk.cpp` sets the limit to 500 from the configuration, `router.cpp` still sees 1000. A risk limit that is silently different in two places is a serious bug, and nothing reports it. `static` on the function merely duplicates its code.

### *P5.7

(a) **Dangles.** `s` is destroyed when the function returns; the view points into its freed heap buffer, or into its small-string buffer in a dead stack frame. GCC 13 gives no warning for this one.

(b) **Dangles.** `std::max` returns a reference to its larger argument, here the temporary `"zzz"`, which is destroyed at the end of the full expression. Lifetime extension applies only to a temporary bound *directly* to the reference, never through a function's return value.

(c) **Safe.** The range-for binds `auto&& __range = make_order().symbol;`. Member access on a temporary is one of the cases where binding a reference extends the lifetime of the whole temporary `Order`.

(d) **Dangles in C++20.** The `Order` temporary dies at the end of the range expression, because the reference is bound to the result of a function call, not to the temporary. AddressSanitizer reports `stack-use-after-scope` (checked in the build container). C++23 extends the lifetimes of all temporaries in a range-for initializer. In C++20, write `for (auto o = make_order(); char c : o.get_symbol())`.

(e) **Dangles.** With `size() == capacity()`, `push_back` reallocates, moves the elements into a new buffer and frees the old one; `first` refers to freed memory (Section 10.1).

### *P5.8

(a) The double next to 1.0 is 1 + 2^{−52} (that gap is `DBL_EPSILON`). Any x for which 1 + x lies past the midpoint 1 + 2^{−53} rounds up. At exactly x = 2^{−53} the sum is a tie and rounds to even, which is 1.0. So the answer is **the smallest double greater than 2^{−53}, namely 2^{−53} + 2^{−105} ≈ 1.1102230246251568 × 10^{−16}** (the doubles near 2^{−53} are 2^{−105} apart). About half of `DBL_EPSILON` already suffices.

(b) A `float` has 24 significant bits, so every integer up to **2^{24} = 16,777,216** is exact, and 16,777,217 is not. For `double`, **2^{53} = 9,007,199,254,740,992**. *Verified.*

### *P5.9

Truncation gives the wrong tick count for **6,457 of the 20,000 prices** (about 32%). *Verified* by enumeration.

Why: the parsed price is the double nearest k × 0.05, the divisor is the double nearest 0.05 (slightly *above* 0.05, at 0.05000000000000000277…), and the division rounds once more. The computed quotient lands within a few units in the last place of the integer k, sometimes just above and sometimes just below. Truncation turns every "just below" into k − 1.

Why `std::llround` is correct: the relative error of the quotient is a few times 2^{−53}, so for k ≤ 20,000 the absolute error is below about 10^{−11}, far from the 0.5 needed to round to the wrong integer.

Detecting a price that is not on the grid: compute k = llround(px / tick) and check |px − k × tick| ≤ ε with ε well above the floating-point error (say 10^{−9} × max(1, |px|)) and well below half a tick. The better fix is upstream: obtain the decimal text and parse it directly into integers, where the check is an exact remainder test (Listing 5.7, lines 61–71).

### *P5.10

```cpp
std::int64_t floor_avg(std::int64_t a, std::int64_t b) { return (a & b) + ((a ^ b) >> 1); }
```

Proof: binary addition gives a + b = (a ^ b) + 2(a & b), since `^` is the sum without carries and `&` marks the positions that generate a carry. Hence (a + b) / 2 = (a & b) + (a ^ b) / 2, and taking the floor affects only the second term. Floor division by 2 is exactly the arithmetic shift `>> 1`, defined for negative values since C++20. No intermediate overflows: `a & b` and `(a ^ b) >> 1` are each representable, and their sum is ⌊(a + b) / 2⌋, which lies between a and b. *Verified* exhaustively for small values and against 128-bit arithmetic for a million random 64-bit pairs.

`std::midpoint(a, b)` (C++20, `<numeric>`) is also overflow-free for integers, but when a + b is odd it rounds **toward `a`**, so `std::midpoint(a, b)` and `std::midpoint(b, a)` can differ by one. For a mid-price in ticks, decide explicitly which rounding you want; there is no universally right answer.

### *P5.11

Two bugs. **Self-assignment** (`x = x`): `delete[] data_` frees the buffer that `o.data_` also points to, and `memcpy` then reads freed memory, a use-after-free. **Exception safety:** if `new` throws `std::bad_alloc`, `data_` still holds the deleted pointer, so the destructor later deletes it again (a double free), and `size_` is already wrong.

Fix 1 is copy-and-swap, as in Listing 5.4, lines 26–29. Fix 2 allocates and copies before releasing anything:

```cpp
Buffer& operator=(const Buffer& o) {
    char* p = o.size_ ? new char[o.size_] : nullptr;   // may throw: *this untouched
    if (o.size_) std::memcpy(p, o.data_, o.size_);     // correct even if &o == this
    delete[] data_;
    data_ = p;
    size_ = o.size_;
    return *this;
}
```

Fix 2 can be extended to reuse the existing buffer when `size_ == o.size_`, avoiding the allocation, which copy-and-swap cannot do. That is the trade-off `std::vector` makes.

### *P5.12

`total` is −2. In `total / v.size()`, `v.size()` is a `std::size_t`, so `total` is converted to `std::size_t` (2^{64} − 2) and divided by 2, giving 2^{63} − 1 = 9,223,372,036,854,775,807; converting that to `double` rounds to **2^{63} ≈ 9.22 × 10^{18}**. *Verified.* The problems in the last line: the signed-to-unsigned conversion; integer division (even with matching signedness, {1, 2} would average to 1); division by zero for an empty vector; and, on the line before, `int` accumulation that can overflow, which is undefined behaviour. Fix:

```cpp
if (v.empty()) return std::nullopt;                      // or whatever "no data" means
std::int64_t total = 0;
for (int x : v) total += x;
double avg = static_cast<double>(total) / static_cast<double>(v.size());
```

`-Wsign-conversion` would have flagged the original; `-Wall -Wextra` do not.

### *P5.13

Every iteration makes **2** allocations, whatever the class: one for the 17- to 22-character string built on line 54 (beyond the 15-character small-string buffer) and one for `levels` on line 55. With doubling from capacity 1, the vector allocates buffers of capacity 1, 2, 4, …, 2^{18} = 262,144 ≥ 200,000: **19** buffers.

- **QuoteZero and QuoteFive:** `push_back(std::move(q))` and every reallocation move elements, allocating nothing. Total: 2N + 19 = 400,000 + 19 = **400,019**.
- **QuoteDtor:** `push_back` copies the element (**2N** more allocations), and each reallocation copies all existing elements: when the full buffers of capacity 1, 2, …, 2^{17} are replaced, 1 + 2 + … + 2^{17} = 2^{18} − 1 = 262,143 elements are copied, each with 2 allocations. Total: 400,019 + 400,000 + 524,286 = **1,324,305**.

With `book.reserve(N)` there is one buffer and no reallocation: **400,001** for QuoteZero and QuoteFive, and **800,001** for QuoteDtor (the copies in `push_back` remain). *Verified* by recomputing the formula in the verification program and against the listing's own output.

### *P5.14

**Why it fails.** The initializers of `reg` in `limit.cpp`, `market.cpp` and `ioc.cpp` and the constructor of `g_registry` in `registry.cpp` run in an unspecified order across TUs. In practice the order follows the link order, which differs between the debug and release builds (or changes under LTO). If `limit.cpp` initializes first, `add` runs on a `Registry` whose storage has been zero-initialized but whose constructor has not run: an unconstructed `std::unordered_map`. That may crash, or, worse, appear to work and then be wiped when the real constructor runs later, silently losing the registered order types.

**Fix that keeps self-registration:**

```cpp
Registry& registry() {                 // registry.cpp; declared in registry.h
    static Registry* r = new Registry; // constructed on first use, thread-safe
    return *r;                         // intentionally never destroyed
}
// limit.cpp
static bool reg = registry().add("LIMIT", &make_limit);
```

The first `add` call constructs the registry, whichever TU gets there first. The guard check costs about a cycle per call, and calls happen only at start-up and at lookup time (cache the reference if lookups are hot).

**At exit:** if the registry were a plain `static Registry r;`, it would be destroyed in reverse order of construction, and any other static object whose destructor still uses it (a logger that prints order types, say) would touch a destroyed object. Allocating it with `new` and never deleting it means no destructor runs; the operating system reclaims the memory at process exit.

**With `constinit`:** if `Registry` had a `constexpr` constructor and no dynamic allocation (for example a fixed-capacity array of name and factory pairs), then `constinit Registry g_registry;` would be constant-initialized, which happens before any dynamic initialization. Every registration would then see a valid object, and with a trivial destructor there is no exit problem either. `std::unordered_map` cannot be used this way in C++20.

**One more trap worth mentioning in an interview:** if `limit.o` is placed in a static library and nothing references a symbol in it, the linker does not pull it into the executable, and its registration never runs. Linking with `--whole-archive`, or referencing the objects explicitly, avoids that.
