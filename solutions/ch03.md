## Chapter 3: DSA I: Foundations for Online Tests

Line numbers refer to the verification program at the end of this section, which contains every solution as a function and checks it against a brute force on thousands of random inputs.

### *P3.1

(a) n ≤ 12: exponential is intended. 12! ≈ 4.8×10^{8} permutations is borderline, so prefer an O(2^{n}·n^{2}) bitmask DP (about 6×10^{5} steps; Section 4.5); plain permutation search works only if each check is O(1) or pruned heavily. (b) n ≤ 40, subset sum: meet in the middle, O(2^{n/2}·n) (Problem P3.13); 2^{40} ≈ 10^{12} is far too many. (c) n ≤ 400: O(n^{3}) ≈ 6.4×10^{7}: interval DP or Floyd–Warshall (Section 4.3). (d) n ≤ 5000: O(n^{2}) = 2.5×10^{7}: quadratic DP such as LCS (Section 4.5). (e) n ≤ 10^{6}: O(n) or O(n log n) with a small constant (sorting, prefix sums, two pointers), and fast input, because synchronized `cin` alone would take about a third of a second per million integers on the build machine (Section 3.11). (f) A single n ≤ 10^{18}: O(log n) (binary search on the answer, fast exponentiation, matrix exponentiation, digit DP) or a closed form; even O(√n) = 10^{9} is too slow. (g) **No.** The sum can reach 2×10^{5} × 10^{9} = 2×10^{14}, far above the `int` limit of about 2.147×10^{9}. Use `long long`.

### *P3.2

Set d_{l} += v and d_{r+1} −= v for each update (lines 25–30): d = [3, −1, 2, 0, −2, 6, −5, 0] at positions 1–8 (the entry at position 9 is never read). Prefix sums give the final array **[3, 2, 4, 4, 1, 7, 2, 2]**. *Verified* against direct updates on random cases.

### *P3.3

Prefix sums are P = 0, 1, 3, 6, 3, 4, 6, 5, 8. A subarray (i, j] has sum 3 exactly when P_{j} − P_{i} = 3. Sweep j and add the number of earlier prefixes equal to P_{j} − 3 (lines 32–41): contributions 0, 1, 1, 1, 1, 2, 0, 1, so the answer is **7**. The map is seeded with {0 : 1} for the empty prefix, which counts subarrays starting at index 0.

A sliding window fails because, with negative numbers, the window sum is not monotone in the window's length: shrinking from the left can increase the sum (removing the −3), so there is no rule for which pointer to move.

### *P3.4

Feasibility is monotone in s: eating faster never takes more hours. The hours needed at speed s are Σ ⌈p/s⌉, computed as `(p + s - 1) / s` in integers. Binary search for the first feasible s between 0 (infeasible) and the largest pile (always feasible, one hour per pile) (lines 43–52). For h = 6: s = 23 needs 2 + 1 + 1 + 1 + 1 = 6 hours, and s = 22 needs 2 + 1 + 2 + 1 + 1 = 7, so **s = 23**. For h = 5 there are 5 piles, so every pile must be finished in one hour: **s = 30**. *Verified* against a linear scan over s.

### *P3.5

For each bit position, count how many elements have that bit set (lines 54–62). The values that appear three times contribute a multiple of 3 to each count, so count mod 3 is exactly the bit of the unique element. Build the result in an unsigned integer and convert it to `int32_t` at the end; in C++20 that conversion is defined as two's complement, so negative answers come out right. Time O(32n), space O(1). The test array gives **−4**. (A faster version keeps two bitmasks `ones` and `twos` that implement a counter modulo 3 for all 32 bits in parallel; it is the same idea with bitwise operations.)

### *P3.6

Window template "longest valid" (lines 64–73): extend r, update a count array and the number of distinct characters; while there are more than k distinct characters, advance l. Each character enters and leaves once: O(n) with a 256-entry count array (no hashing needed for bytes). Answers: "eceba" → **3** ("ece"); "aaabbccdddd" → **6** ("ccdddd"). *Verified.*

### *P3.7

Binary search on the answer (lines 75–88). For a candidate maximum part sum `cap`, the greedy "keep adding to the current part until the next element would exceed `cap`" uses the fewest parts possible, and the number of parts needed decreases as `cap` grows, so feasibility (parts ≤ m) is monotone. lo starts at max(a) − 1 (infeasible, some element would not fit), hi at the total sum (one part). O(n log S). For [7, 2, 5, 10, 8] and m = 2 the answer is **18**: [7, 2, 5 | 10, 8]. *Verified* against an O(n^{2}m) DP on random inputs.

### *P3.8

Each subarray's minimum is attributed to one index i. Let L_{i} be the number of choices of the left end (extend left while elements are *greater than or equal to* a_{i}; stop at the previous strictly smaller element) and R_{i} the number of choices of the right end (extend right while elements are *strictly greater* than a_{i}; stop at the next smaller-or-equal element). Then a_{i} is the designated minimum of exactly L_{i} × R_{i} subarrays, and the answer is Σ a_{i} L_{i} R_{i}. Two monotonic-stack passes compute L and R in O(n) (lines 90–108).

The asymmetry (strict on one side, non-strict on the other) is what prevents double counting. In [2, 2], the subarray [2, 2] has two equal minima; with the rule above it is attributed only to the right one: the right 2 may extend left over an equal value (line 94 pops `>=`, so only a strictly smaller element stops it), while the left 2 may not extend right over it (line 100 pops only `>`, so an equal element stops it). Using "greater or equal" on both sides would count [2, 2] twice; using "strictly greater" on both sides would not count it at all.

Answers: [3, 1, 2, 4] → **17** (contributions 3·1·1 + 1·2·3 + 2·1·2 + 4·1·1 = 3 + 6 + 4 + 4); [11, 81, 94, 43, 3] → **444**. *Verified* against the O(n^{2}) definition with values in 1..4, where ties are frequent.

### *P3.9

A max-heap `low` holds the smaller half, a min-heap `high` the larger half (lines 110–121). Insert into `low` if the value is at most `low.top()`, else into `high`; then rebalance so that `low` has the same number of elements as `high` or one more. The median is `low.top()` when the count is odd and the average of the two tops when it is even. Each step is O(log n). (The code returns twice the median to stay in integers.) For 5, 15, 1, 3, 8, 7, 9, 10 the medians are **5, 10, 5, 4, 5, 6, 7, 7.5**. *Verified* against sorting each prefix.

### *P3.10

Always join the two shortest ropes (lines 123–133): 2 + 3 = 5 (cost 5), 4 + 5 = 9 (cost 9), 6 + 9 = 15 (cost 15), total **29**.

Proof. Any sequence of joins forms a binary tree whose leaves are the original ropes, and the total cost is Σ (length × depth), because a rope's length is paid once for every join above it. In an optimal tree, the two shortest ropes can be assumed to be siblings at the maximum depth: if a longer rope were deeper, swapping it with a shorter one would not increase the cost. So an optimal solution starts by joining the two shortest; after the join, the problem is the same with one fewer rope, and induction finishes the proof. This is exactly the argument for Huffman coding. *Verified* against exhaustive search over all join orders for up to 5 ropes.

### *P3.11

Sort by right end; shoot an arrow at the right end of the first balloon not yet burst, and skip every balloon that contains that position (lines 135–142). For the example, sorted by right end: [1, 6], [2, 8], [7, 12], [10, 16]. Arrow at 6 bursts the first two; arrow at 12 bursts the last two: **2 arrows**.

Proof (exchange). Let b be the balloon with the smallest right end r. Some arrow must hit b, at a position x ≤ r. Moving that arrow to r keeps b burst and also bursts every balloon that x burst: any balloon containing x has left end ≤ x ≤ r and right end ≥ r (because r is the smallest right end), so it contains r. So some optimal solution shoots at r; remove everything it bursts and repeat. The number of arrows also equals the maximum number of pairwise disjoint balloons (each arrow's balloon b is disjoint from the next arrow's), which is the interval-scheduling result of Section 3.9. Note the comparison `l > last` (closed intervals: touching balloons share a point). *Verified* against brute force over subsets of right ends.

### *P3.12

With prefix sums P, we need the minimum j − i over pairs i < j with P_{j} − P_{i} ≥ K. Keep a deque of candidate start indices i with *increasing* P values (lines 144–159):

- **Front (lines 151–154):** while P_{j} − P_{front} ≥ K, record j − front and pop the front. A later j' > j would only give a longer subarray with that start, so the front is never needed again.
- **Back (line 155):** pop indices whose P is ≥ P_{j}. For any future end, starting at j is better than starting at such an index: it is later (shorter subarray) and has a smaller or equal prefix (larger or equal sum).

Each index is pushed and popped at most once: O(n). Answers: [2, −1, 2], K = 3 → **3**; [84, −37, 32, 40, 95], K = 167 → **3** ([32, 40, 95]); the code returns −1 when no subarray qualifies. *Verified* against the O(n^{2}) scan with mixed-sign values.

### *P3.13

Meet in the middle (lines 161–179). Split the array into halves of sizes ⌊n/2⌋ and ⌈n/2⌉. List all 2^{20} subset sums of each half (each list built by doubling, without recursion). Sort one list; for each sum x in the other, count the elements equal to T − x with `equal_range`. Time O(2^{n/2}·n), about 2×10^{7} comparisons for n = 40, and 2 × 2^{20} `long long`s = 16 MiB of memory, against 2^{40} ≈ 1.1×10^{12} subsets for brute force.

For {1, …, 40} and T = 410 the count is **5,830,034,720**. Because the elements are small, the same number can be computed independently with the subset-sum counting DP (ways[s] += ways[s − x] over s descending), which the program does as a cross-check; it also compares the meet-in-the-middle function with brute-force enumeration on random sets of up to 14 elements. (410 is half of the total 820, so this is also the number of ways to split {1, …, 40} into two halves of equal sum, counted with order.)

### *P3.14

Number the heap's nodes 1..n (array index + 1). The children of node i are 2i and 2i + 1, and the last level is filled from the left, so node i has a descendant at depth h below it exactly when its leftmost such descendant, i·2^{h}, exists, i.e. when i·2^{h} ≤ n. Hence height(i) = max{h : i·2^{h} ≤ n}, and

Σ_{i} height(i) = Σ_{h≥1} #{i : i·2^{h} ≤ n} = Σ_{h≥1} ⌊n/2^{h}⌋.

Now write n in binary. A set bit of weight 2^{k} contributes 2^{k−1} + 2^{k−2} + … + 1 = 2^{k} − 1 to Σ_{h≥1} ⌊n/2^{h}⌋ (shifting right by h moves it to weight 2^{k−h} while k − h ≥ 0). Summing over the set bits gives Σ (2^{k} − 1) = n − popcount(n), which proves the identity. (The same sum is the exponent of 2 in n!, by Legendre's formula.)

Each sift-down in bottom-up heapify moves its element down one level per swap, so it performs at most height(i) swaps. The total number of swaps is therefore **at most n − popcount(n) < n**, and the number of comparisons at most twice that: O(n). Listing 3.6 shows descending input reaching the bound exactly for n = 2^{20} − 1. *Verified* by computing heights directly for every n ≤ 20,000 (lines 181–190).
