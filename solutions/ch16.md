## Chapter 16: Compilers and Profiling

### *P16.1

0xCCCCCCCD = 3,435,973,837 = ⌈2^{35}/10⌉, which exceeds 2^{35}/10 by e = 0.2. So (x × 0xCCCCCCCD) / 2^{35} = x/10 + x e / 2^{35}, and for x < 2^{32} the error term is below 2^{32} × 0.2 / 2^{35} = 0.025. The fractional part of x/10 is at most 0.9, so adding less than 0.025 never reaches the next integer, and the floor is exactly ⌊x/10⌋. The product needs at most 64 bits, so one `imul` and one `shr` suffice: a few cycles of latency, against an integer division that is several times slower and not pipelined as well. *Verified* for all 2^{32} inputs.

For 7, no 32-bit multiplier has a small enough error, so the magic number needs 33 bits. g++ 13 emits `imul` by 613,566,757 (0x24924925, the low 32 bits of the 33-bit constant), keeps the high half q, then computes (q + ((x − q) >> 1)) >> 2, an add-and-shift fix-up that supplies the missing bit without overflowing.

### *P16.2

(1,550 − 92) / 32 = 45.6 ticks per call; at 2.1 ticks per nanosecond, **21.7 ns**. *Verified.* A pair of fenced TSC reads costs tens of cycles (here the empty batch's 92 ticks include the loop), comparable to the 46 ticks being measured, and it disturbs the pipeline around the call; timing each call separately would mostly measure the timer. ### *P16.3

(a) GCC's vectorizer cost model: *very cheap* at `-O2` (no remainder code allowed), *dynamic* at `-O3`. (b) Floating-point addition is not associative; vectorizing reorders it, which `-ffast-math` (`-fassociative-math`) permits. (c) `-march=native` (or another `-march` above the production CPU's) emitted instructions the old CPU lacks. (d) `-ffast-math` includes `-ffinite-math-only`, which lets the compiler assume there are no NaNs and fold `isnan` to false. (e) Separate compilation: without `-flto` the compiler cannot see the body. (f) `-fcf-protection`, enabled by default in Ubuntu's GCC: `endbr64` marks valid targets of indirect branches for Intel CET.

### *P16.6

n = 300,000 samples, p = 600/300,000 = 0.2%, standard error √(p(1 − p)/n) ≈ 0.0082%, so the share is **0.200% ± 0.016%** (95%): about **0.06 s** of CPU in the 30 s. *Verified.* At a million calls per second, 0.2% of a CPU is about **2 ns per call**. Optimizing F cannot improve throughput by more than 0.2%, but if F is on the latency-critical path, 2 ns per event might still matter, and only a latency measurement (16.4) can say. More samples are needed to compare two versions of F (a difference of 0.02 percentage points is within the error here) or to resolve which instructions inside F are hot (each line gets a small share of the 600 samples).

### *P16.7

IPC = 2.1 / 4.2 = **0.50**; branch-miss rate 42 / 400 = **10.5%**; branch MPKI = 42 × 10^{6} / 2.1 × 10^{6} = **20**; LLC MPKI = **14.3**. *Verified.* Mispredictions at 15 cycles explain 42 × 10^{6} × 15 = 6.3 × 10^{8} cycles, **15%** of the total. LLC misses at 200 cycles would explain 6 × 10^{9} cycles, **143%** of all cycles, which is impossible: the misses must overlap (memory-level parallelism, 12.1), so you cannot add up miss counts times latency. The picture is a memory-bound program (low IPC, high LLC MPKI) that also mispredicts often; the top-down breakdown would confirm the split between backend (memory) stalls and bad speculation. The next steps are data layout and access patterns (6.7, 12.2) before branch tuning.

### *P16.8

The fast path of `std::vector::push_back` compares `end` with `capacity end`, stores and increments; it needs no callee-saved registers. g++ 13 inlined the reallocation path into the same function, and that path does need them, so the shared prologue saves six registers on every call. The fix is to keep the slow path in a separate function that is never inlined and is marked cold, so the caller's register needs are only the fast path's. The program checks its own machine code: `record_log` contains no `push` at all, and GCC additionally split the call to `grow` into a `.cold` fragment.

### *P16.9

- `system_clock` can jump (NTP adjustments, manual changes); use `steady_clock` or the TSC (16.4).
- `(t1 - t0).count()` is in the clock's tick unit, which the standard does not fix as nanoseconds; use `duration_cast<nanoseconds>`. Integer division also truncates.
- 1,000 iterations is too few, with no warm-up: the first adds pay allocations, page faults and cold caches, and dominate the total.
- One fixed order added repeatedly is unrealistic: every add hits the same price level (one branch path, one cache line), and the book's state changes as it grows, so the benchmark measures neither an empty book nor a realistic one. Replay a recorded mix of adds, modifies and cancels against a book pre-populated to a realistic depth.
- A mean over a loop hides the distribution: time individual operations or small batches and report percentiles.
- No pinning, no repetition across runs, no check that the result is used and correct.

### *P16.10

- **uaf:** ASan reports a heap-use-after-free (the 22-character string lives on the heap; a string of 15 characters or fewer would sit in the small-string buffer and ASan would report a stack-use-after-scope instead, 11.4). g++ 13 gives no warning; UBSan and TSan see nothing.
- **overflow:** UBSan only (`signed-integer-overflow`); the product is not a constant expression, so no compile-time diagnostic. A `constexpr` test with edge values (11.6) would catch the function's design flaw.
- **race:** TSan only, and only because the two loops actually overlapped in the run. The result looked correct.
- **corrupt:** no sanitizer. The 9-byte write stays inside the `Position` object, so ASan's redzones (which surround objects, not fields) are untouched, and `_FORTIFY_SOURCE` checks `memcpy` against the size of the whole object. Only a watchpoint (or a reviewer) finds it.

Making it impossible: (1) give the field a type that owns the rule, for example a `Symbol` class holding `std::array<char, 8>` whose constructor takes a `std::string_view`, rejects (or truncates) anything longer than 8 characters, and space-pads the rest, as fixed-width exchange fields usually are, so no terminator is ever stored; (2) where the length is a compile-time constant, use a `consteval` constructor or `static_assert(sizeof(src) <= sizeof(dst))`, so a bad literal fails the build; and in any case copy `std::min(len, sizeof field)` bytes, never `len + 1`.

### *P16.11

x86-64 has four debug address registers (DR0–DR3), each watching 1, 2, 4 or 8 naturally aligned bytes, so at most **32 bytes** can be watched in hardware at once: four of the five 8-byte words of the struct. `watch -l` on the whole 40-byte struct cannot be implemented in hardware, so gdb falls back to a **software watchpoint**: it single-steps the program and compares the value after every instruction, thousands of times slower, which is useless for a bug that appears after minutes. Efficient approaches: watch the corrupted field (or the 32 bytes most likely affected) first, and the remaining word in a second run; find *which* field is corrupted first with a cheap check, then watch only it; or place the object alone on a page, `mprotect` the page read-only after initialization, and catch the `SIGSEGV` at the faulting write (moving legitimate writes through a function that unprotects temporarily). With hardware counters available, `rr` records the run once and `reverse-continue` with a watchpoint goes straight back to the last write.

### *P16.12

- **Training data:** replay several recorded sessions, including the busiest days and special events (opening and closing auctions, halts, volatility interruptions), through the production binary built with `-fprofile-generate`, plus fault-injection runs that exercise gap recovery, reconnection and risk rejections. Merge the profiles (`gcov-tool merge`), weighting busy sessions appropriately.
- **Rare-but-critical paths:** build with `-fprofile-partial-training`, so code the training never reached is optimized normally rather than for size; mark known cold paths explicitly (`[[gnu::cold]]`, `[[unlikely]]`) so their layout does not depend on the training.
- **Keeping it current:** regenerate the profile in CI for every weekly build from the latest recordings; treat `-Wmissing-profile` and `-Wcoverage-mismatch` (source changed since the profile) as errors, so a stale profile cannot be used silently.
- **Checking it:** run the full regression suite on the PGO build (PGO changes code generation, so it can expose latent UB, 11.5); compare open-loop replay latency percentiles of the PGO and non-PGO builds on sessions *not* used for training; inspect the hot path's assembly for unexpected changes; deploy as a canary and compare live latency before switching over.
