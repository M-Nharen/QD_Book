## Chapter 11: Undefined Behaviour and the Optimizer

### *P11.1

| | Statement | Verdict |

### *P11.2

`a - b` overflows upwards when `b < 0` and `a > INT_MAX + b`, and downwards when `b > 0` and `a < INT_MIN + b`. Each bound is computed without overflow because `b` has the sign that moves the constant towards zero:

```cpp
constexpr bool sub_would_overflow(int a, int b) {
    return (b < 0 && a > INT_MAX + b) || (b > 0 && a < INT_MIN + b);
}
```

Note that `b == INT_MIN` is handled by the first clause (`INT_MAX + INT_MIN = −1`, so any `a ≥ 0` overflows: for example 0 − `INT_MIN` = 2^{31}). *Verified* against `long long` arithmetic on all 81 pairs of edge values.

### *P11.3

**−0.0 → 0x8000000000000000** (only the sign bit set), **1.0 → 0x3ff0000000000000** (exponent 1023, mantissa 0), **−2.5 → 0xc004000000000000** (−1.25 × 2^{1}: sign 1, exponent 1024 = 0x400, mantissa 0.25 → top mantissa bits 01, giving 0xc004…). Function: `std::uint64_t bits(double d) { return std::bit_cast<std::uint64_t>(d); }`. *Verified.*

### *P11.4

Little-endian: the first byte is least significant, so the value is 0x00002710 = **10000**. Big-endian: 0x10270000 = **270991360**.

```cpp
std::uint32_t load_be32(const unsigned char* p) {
    return (std::uint32_t(p[0]) << 24) | (std::uint32_t(p[1]) << 16) |
           (std::uint32_t(p[2]) << 8) | std::uint32_t(p[3]);
}
```

Each byte is converted to `uint32_t` before shifting; shifting the promoted `int` value `p[0] << 24` would be defined in C++20 but produces a negative `int` for bytes ≥ 0x80, which is easy to mishandle. g++ and Clang recognize this pattern and emit a single `mov` plus `bswap` (or `movbe`). *Verified.*

### *P11.5

Three bugs.

1. `venue_of` returns a `string_view` into the temporary `std::string` returned by `substr`, destroyed at the end of the return statement. Fix: return `std::string`, or build the view from `sym` itself: `std::string_view(sym).substr(sym.find('.') + 1)` (valid as long as the caller's string lives).
2. `make_logger` captures `prefix` by reference; the lambda is called after `make_logger` has returned and `prefix` is destroyed. Fix: capture by value, `[prefix] { ... }` (or `[prefix = std::move(prefix)]`).
3. `on_fill` holds `Order& o` across `push_back`, which may reallocate. Fix: work with the index (`orders[f.index].qty -= f.qty;` after the push), or do the subtraction before the push, or reserve capacity in advance and document it. (There is also a subtle point about `orders.push_back(make_replacement(o))`: the argument is fully evaluated before `push_back` runs, so that line itself is fine.)

### *P11.6

```cpp
constexpr unsigned unsigned_abs(int x) { return x < 0 ? 0u - unsigned(x) : unsigned(x); }
constexpr unsigned abs_diff(int a, int b) {
    return a > b ? unsigned(a) - unsigned(b) : unsigned(b) - unsigned(a);
}
```

All arithmetic is unsigned, so it wraps by definition, and the results fit because |x| ≤ 2^{31} and |a − b| ≤ 2^{32} − 1. **`unsigned_abs(INT_MIN)` = 2147483648** and **`abs_diff(INT_MIN, INT_MAX)` = 4294967295**. `std::abs(INT_MIN)` must return an `int`, and +2^{31} is not representable, so it is UB (in practice it returns `INT_MIN`). C++20 also provides `std::midpoint` for the related averaging problem. *Verified.*

### *P11.7

(a) **Allowed**: the unsigned counterpart of the dynamic type. (b) **Allowed**: `std::byte` may examine any object's bytes. (c) **Not allowed**: writing a `float` object through an `int` lvalue. (d) **Not allowed** (portably): the buffer holds `unsigned char` objects (or, at best, implicitly created objects whose type nobody chose), and there is the separate alignment question; use `memcpy`. (e) **Allowed**: the cast chain goes through a different pointer type, but the access itself is through `int`, which is the dynamic type of the object. Aliasing is about the type of the access versus the type of the object, not about the history of the pointer.

### *P11.8

g++ 13.3 at `-O2` compiles `find_index` to three comparisons (against `table[0]`, `table[1]`, `table[2]`) and then **returns 3 without reading `table[3]`**, so `find_index(99)` returns 3. Reasoning: if no earlier element matched, either `table[3] == v` (return 3) or the loop proceeds to read `table[4]`, which is UB; the compiler may therefore assume `table[3] == v` and return 3. The `return -1` is unreachable as far as the compiler is concerned. Fix the loop bound to `i < 4` (better: iterate over `std::size(table)` or use `std::ranges::find`). *Checked* against the generated assembly.

### *P11.9

With `int h`, the multiplication overflows after a handful of characters (a 10-character string reaches values around 10^{15}), which is UB; the optimizer may, for example, assume `h` stays non-negative and remove a later `% buckets` sign adjustment. With `std::uint32_t h = 0; for (unsigned char c : s) h = h * 31u + c;`, wrapping is defined. Iterating over `unsigned char` also avoids sign-extending bytes ≥ 0x80 differently on platforms where `char` is signed.

Hash of "AAPL": ((65 × 31 + 65) × 31 + 80) × 31 + 76 = **2001436** (no wrap occurs). Hash of "ESZ6 C5000": the exact integer is 1,897,648,925,297,992, far beyond 2^{31}; reduced modulo 2^{32} it is **3524906312**. *Verified* in C++ and independently in Python.

### *P11.10

```cpp
bool mul_overflows(std::int64_t a, std::int64_t b) {
    if (a == 0 || b == 0) return false;
    if (a > 0) {
        if (b > 0) return a > INT64_MAX / b;
        return b < INT64_MIN / a;                 // a > 0, b < 0
    }
    if (b > 0) return a < INT64_MIN / b;          // a < 0, b > 0
    return a < INT64_MAX / b;                     // both negative
}
```

Proof sketch. Let q = M/b be the real quotient for the relevant bound M, and let C++ integer division truncate towards zero.

- a, b > 0: the product overflows iff a > M/b. Here the truncated quotient is ⌊M/b⌋, and for integer a, a > M/b ⇔ a > ⌊M/b⌋.
- a > 0, b < 0: overflow iff ab < INT64_MIN ⇔ b < INT64_MIN/a. The real quotient is negative, truncation gives ⌈INT64_MIN/a⌉, and for integer b, b < x ⇔ b < ⌈x⌉. The case a < 0, b > 0 is symmetric.
- a, b < 0: the product is positive; overflow iff ab > INT64_MAX ⇔ a < INT64_MAX/b (dividing by negative b flips the inequality). The real quotient is negative, truncation gives its ceiling, and the same integer argument applies.

No division overflows: the only overflowing division is INT64_MIN / −1, and INT64_MIN is never divided by a negative number here. *Verified* against `__builtin_mul_overflow` on all pairs of 13 edge values (including ±3037000499/500, around √(2^{63})) and two million pseudo-random pairs with random magnitudes.

### *P11.11

Because `ready` is a plain `bool` written by another thread without synchronization, any concurrent write is a data race and therefore UB. The compiler may assume no other thread modifies `ready`, so within the loop its value is invariant and can be read once. A loop whose condition never changes and whose body has no side effects either exits immediately or runs forever; C++'s forward-progress rule lets the compiler assume it terminates, so it deletes the loop and just returns `payload`. With `-fno-finite-loops` the loop is kept, but the load is still hoisted: the code becomes "if `ready` was false at the first check, spin forever".

`volatile bool ready` forces a fresh load on each iteration, so the loop would eventually see the store on x86. But `volatile` creates no happens-before relation: the read of `payload` may still be reordered by the compiler (or, on weakly ordered CPUs, by the hardware) relative to the read of `ready`, and the access is still a data race in the C++ model. Correct code:

```cpp
std::atomic<bool> ready{false};
int payload = 0;
void publish(int v) { payload = v; ready.store(true, std::memory_order_release); }
int wait_for_payload() {
    while (!ready.load(std::memory_order_acquire)) { /* optionally _mm_pause() */ }
    return payload;      // guaranteed to see v
}
```

Section 14.2 explains the release/acquire pairing; 14.9 discusses spinning versus blocking.

### *P11.12

1. **Misalignment.** `AddOrderWire` with natural layout has alignment 8. `buf + 2` is at best 2 mod 8 (a vector's storage is 16-byte aligned by `operator new` on x86-64 Linux), so `m` is a misaligned pointer, and the member access is UB. UBSan reports it as: `runtime error: member access within misaligned address 0x… for type 'const struct AddOrderWire', which requires 8 byte alignment` (confirmed with g++ 13.3, `-fsanitize=undefined`).
2. **Aliasing/lifetime.** No `AddOrderWire` object was created in the buffer; the bytes are `unsigned char`. No sanitizer reports this.
3. **Layout mismatch.** With natural alignment the struct has padding (`order_id` at offset 8, not 2), so the struct no longer mirrors the wire format at all, and `sizeof` is 32, not 24. A `static_assert` on `sizeof` and `offsetof` would catch this; the packed version in Listing 11.4 avoided it with an extension.

Why a developer test may pass: x86-64 loads tolerate misalignment, and with no other code in the function the compiler emits ordinary scalar loads, so the program prints the expected numbers. The same code may fault on other architectures, or on x86 if the compiler vectorizes the loop with alignment-assuming instructions, and a later compiler is free to use the aliasing assumption. Decoding with `memcpy` as in Listing 11.5 avoids all three problems.
